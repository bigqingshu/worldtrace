# Input Execution Lab（输入执行实验）

## 当前目标

`experiments.input_execution_lab` 是独立的输入方案编排与前台受控回放实验。它验证：

```text
选择普通本地窗口
→ 手工添加或录制输入
→ 查看和编辑共享主时钟的多轨原子时间线
→ 原子保存方案
→ 读取 WorldTrace 与候选目标的 Windows 进程完整性级别
→ 当前进程低于目标或无法确认时保持零输入并提示重新启动
→ 启动 WindowLifetimeGuard（窗口生命周期守卫）
→ 冻结 HWND、PID 和进程创建时间，不读取最小化客户区
→ 等待同一窗口恢复并成为精确前台
→ 两次读取一致的正尺寸客户区并稳定 200 ms
→ 再次确认最终目标的进程完整性级别
→ 确认调用线程仍处于原生物理像素坐标空间
→ 创建发送会话和全局紧急停止监听
→ 200 ms 前台稳定确认
→ 进入倒计时前复核进程完整性级别
→ 原生提示层完成绘制确认
→ GUI 心跳不超过 250 ms 的固定 3 秒安全倒计时
→ 提示层隐藏确认
→ 开始发送前最后复核进程完整性级别
→ 使用 Win32 SendInput 尝试发送
→ 失焦、停止或异常时释放持有输入
```

该实验不属于 2D 界面识别器，不由 OCR、图标候选或状态候选自动触发，也不把
发送报告写成确认的游戏状态。现有
`experiments.input_capture_lab`（输入捕获实验）继续保持纯被动观测边界。

## 输入、输出与契约

输入：

- 用户显式选择的可见顶层窗口；
- 选择和执行前重新确认的 `HWND + PID + process_started_at`；
- 当前 WorldTrace 进程和目标进程令牌中的 integrity RID
  （完整性级别 RID）；
- 由进程范围 `SetWinEventHook` 观察到的目标顶层窗口销毁事件；
- 用户通过结构化表单添加的动作；
- `input_capture_lab` 在同一会话、同一目标和同一 `focus_epoch`
  （焦点代次）中观察到的完整键盘、按钮和滚轮事件；
- 用户显式加载的本地版本化方案。

输出：

- 实验私有 `InputPlan`（输入方案）；
- `InputTrack`（输入轨道）及其启用、锁定和整体起始偏移；
- `runtime_data/input_execution_lab/plans/*.json` 中的原子方案文件；
- 进程内 `ExecutionStatus`（执行状态）和
  `ExecutionReport`（执行报告）；
- GUI 中有界的原始录制详情、结构化录制诊断和发送流水。
- GUI 内易失的 `ProcessIntegritySnapshot`（进程完整性快照）。

这些输出不进入 Trace Core 公共契约、`StateSnapshot`、关系图或确认状态。
即使发送报告为 `SUCCEEDED`，也只表示方案发送链路完成，不能证明目标程序消费了
输入，更不能证明游戏达到预期状态。

结构化录制诊断和原始录制详情默认只存在于当前 GUI 进程内，不会自动落盘、上传
或转换成输入方案。只有用户显式执行“保存／另存为”时，经过校验的
`InputPlan` 才写入方案目录；诊断记录本身没有导出或自动保存路径。

## GUI 能力

### 目标窗口

- 刷新并下拉选择普通可见顶层窗口；
- 排除当前 GUI 进程；
- 显示标题、PID 和 HWND；
- 显示 WorldTrace 与当前候选目标的 `MEDIUM / HIGH / SYSTEM` 等完整性级别、
  原始 RID 和门禁结论；
- 当前进程 RID 低于目标 RID 时禁用“开始”按钮，并明确提示关闭本实验、以管理员
  身份重新启动后重新选择目标；查询失败或结果异常同样按失败关闭原则阻止；
- 下拉框始终表示“当前候选”，不会继续显示成上一次冻结目标；
- 开始执行时先安装只读窗口生命周期守卫，再冻结 HWND、PID、标题和进程创建
  时间；标题已经变化时要求刷新列表并重新确认；
- 守卫观察到目标顶层窗口销毁后会永久失效，即使 Windows 随后复用相同数值
  HWND，也不会恢复本次执行；
- 等待目标恢复并成为精确前台后，才读取和冻结本次客户区；
- 等待恢复期间不创建执行会话、不启动全局紧急停止监听，也没有输入发送能力；
  此时只有不具备输入能力的窗口销毁监听线程；
- 客户区必须连续 `200 ms` 保持两次读取一致的正尺寸，才能形成最终绑定；
- GUI 轮询间隔超过 `250 ms` 时重新开始客户区稳定计时，不把两个相隔很久的端点
  当作连续稳定；
- 开始录制仍使用现有即时客户区绑定；目标最小化时会明确失败，不复用旧尺寸；
- 运行中不按标题自动重连。

候选变化后，旧发送报告若保留会明确标为“上次执行”；新候选等待、失败或超时不会
与旧目标的 `SUCCEEDED` 并列成当前结果。通用窗口枚举仍只接纳正尺寸客户区，因此
已经最小化后再点击“刷新窗口”可能暂时不显示该窗口；应先恢复一次并刷新选择，
随后点击开始再切回目标。

### 方案管理

- 新建方案；
- 下拉加载已保存方案；
- 保存和另存为；
- 显式确认后删除方案；
- 新建、录制替换和关闭前保护含动作的未保存草稿；
- 严格 `schema_version`；当前写出版本为 `4`，版本 `1`、`2` 和 `3` 只在读取时
  严格迁移到一个默认主轨道，不自动覆写原文件；版本 `1` 仍不允许相机相对移动，
  版本 `1`／`2` 也不允许伪装成版本 `3` 新增的直接按钮事件；
- 同目录临时文件、`fsync` 和 `os.replace` 原子替换；
- 拒绝重复 JSON 键、NaN/Infinity、BOM、非法 UTF-8、未知字段、
  不安全文件名和超大文件。

方案不会保存可自动复用的 HWND。每次运行仍需用户重新选择目标窗口。

### 多轨时间线（第一版）

`InputTrack`（输入轨道）是方案中持久化的编排单位，不是独立执行线程。每个轨道
可以设置名称、是否启用、是否锁定和 `start_offset_ms`（整体起始偏移）。锁定只
阻止编辑、删除和移入／移出动作，不会改变已经保存动作的执行语义；禁用轨道则
保留在方案中，但不会进入本次执行日程。

方案仍以一个扁平、稳定排序的 `InputPlan.events` 作为权威事件集合，每个事件通过
`track_id` 归属轨道。执行前由 `CompiledInputSchedule`（编译输入日程）只应用一次
轨道整体偏移，再按“有效时间 + 原始编写顺序”归并。随后所有轨道共用一个
`monotonic clock`（单调主时钟）执行；不会为每条轨道创建一个睡眠线程，也不会
依赖线程调度碰巧实现同步。

第一版 GUI 提供：

- 新增和删除轨道；
- 启用／禁用、锁定／解锁、重命名和整体偏移；
- 选择轨道后只编辑该轨道的动作；
- 把选中的单个动作或完整按下／释放配对原子地移到另一轨道；
- 为同一轨道内互相重叠的逻辑动作派生只读“泳道”编号，帮助查看重叠；泳道不是
  第二套持久化时间线，也不影响执行顺序。

并发不表示放弃资源冲突校验：

- `WAIT`（等待）只阻塞所属轨道，其他轨道仍可到期执行；
- 相机相对移动可以与其他轨道的键盘或直接按钮动作交错；
- 会移动系统指针的动作与定位点击、滚轮或另一段鼠标移动发生资源重叠时拒绝；
- 两个轨道在重叠区间持有同一个物理键或鼠标按钮时硬拒绝；
- 同一到期时刻按原方案编写顺序稳定执行。

手动录制仍只生成一个默认持久轨道。录制中出现的重叠只用于派生泳道展示，不会
根据一次样本自动猜测新的语义轨道。第一版也不支持运行中单轨暂停／静音、轨道
循环、条件分支或独立时钟漂移修正。

执行器会先把移动动作展开为采样槽，再与普通事件归并。报告分别记录编写事件数、
展开／已处理调度槽数、静态或动态零位移抑制数、原生调用尝试／接纳数，以及调度
漂移的 p50、p95 和最大值。相邻同刻动作当前仍逐次经过完整安全门禁并调用后端；
第一版不把它们合并成一次 `SendInput` 批量调用，以免部分接纳时无法可靠维护按键
和按钮持有账本。

### 手工动作

结构化添加和替换选中动作／配对：

- 按键按住；
- 锁定指针点击（仅按钮，3D 实验）；
- 定位式 UI 点击（移动并严格验证）；
- 客户区归一化绝对移动；
- 相对指针移动（客户区约束，会转换为绝对坐标）；
- `CAMERA_MOVE_RELATIVE`（相机相对移动，直接 Win32 相对输入）；
- 双向滚轮；
- 显式等待。

按键按住会编译成独立的 `KEY_DOWN / KEY_UP` 原子事件，因此可以表达：

```text
0 ms     KEY_DOWN W
1000 ms  KEY_DOWN SPACE
1100 ms  KEY_UP SPACE
2000 ms  KEY_UP W
```

鼠标移动保存位移或目标位置、`duration_ms`、`update_rate_hz` 和插值方式。
新建动作的 GUI 更新率范围为 `1–240 Hz`，`240 Hz` 同时是当前绝对硬上限。方案自己的
`safety_limits.max_mouse_update_rate_hz` 可以进一步收紧该范围，不会在追加动作时
自动放宽。
旧 `MOUSE_MOVE_RELATIVE`（相对指针移动）在方案中保存 `delta`，执行时仍从每个
采样点的实际光标位置计算下一客户区内绝对目标点，经窗口、客户区几何和实际到达
位置复核后，使用绝对移动发送。版本 `1` 方案读取后保留这一语义，不会静默改成
相机输入。

新 `CAMERA_MOVE_RELATIVE` 专门用于锁定或隐藏光标的 3D 视角实验。它把计划总
`delta` 按持续时间、更新率和插值拆成累计取整后的非零分片，每片直接调用
`SendInput`，只设置 `MOUSEEVENTF_MOVE`，不设置 `MOUSEEVENTF_ABSOLUTE` 或
`MOUSEEVENTF_MOVE_NOCOALESCE`。执行时不读取、移动到或验证系统光标位置，也不
要求采样点命中客户区；但每片发送前仍严格复核冻结窗口、PID／进程实例、精确前台、
`focus_epoch`、客户区几何、窗口生命周期守卫、紧急停止监听和调度时限。
实现仅依据微软公开的
[`SendInput`](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-sendinput)
与
[`MOUSEINPUT`](https://learn.microsoft.com/windows/win32/api/winuser/ns-winuser-mouseinput)
契约独立编写，没有复制远控项目源码。

相对移动的平均名义速度以 `relative units/s`
（相对输入单位／秒）显示，由位移和持续时间派生，不承诺等于屏幕像素速度，也不
作为第二套权威字段保存。`平滑起停（Smoothstep）` 继续使用兼容 wire value
`EASE_IN_OUT`，其理论中段峰值约为平均名义速度的 `1.5` 倍；GUI 会同时显示两者，
避免把平均值误认为整段绝对上限。Windows 指针速度、加速阈值、拆分频率、游戏
灵敏度和游戏自身的输入消费方式都可能改变实际转角，因此相同总 `delta` 在不同
配置下不保证得到相同画面结果。

鼠标点击现在明确分为两种互不兼容的投递语义：

- `POSITIONED_UI_CLICK`（定位式 UI 点击）继续保存为
  `MOUSE_BUTTON_DOWN + MOUSE_BUTTON_UP`。每个事件都带客户区归一化位置；
  执行时先发送绝对移动，再读取并严格验证实际光标位置和命中窗口，适合普通
  2D 界面；
- `LOCKED_POINTER_CLICK`（锁定指针点击）保存为
  `MOUSE_BUTTON_DOWN_DIRECT + MOUSE_BUTTON_UP_DIRECT`。事件只带鼠标按钮，
  执行时不移动、读取或验证系统光标，也不做点位命中检查，适合已经由目标程序
  捕获、隐藏或回中的 3D 指针上下文。

“锁定指针点击”是实验场景名称，不表示 WorldTrace 会主动建立、确认或维持指针
锁定。它仍要求同一冻结窗口、PID／进程实例、精确前台、`focus_epoch`、稳定客户区、
完整性门禁、窗口生命周期守卫和紧急停止监听全部通过。直接按钮与定位式按钮必须
在各自模式内成对，不能用一种模式的按下配另一种模式的释放。

两种点击都会保存为“按下 + 释放”两个原子事件。因此在一段相机移动后追加点击，
至少需要三个方案事件；点击从 `4000 ms` 开始并按住 `300 ms` 时，方案总时长为
`4300 ms`。若已有方案把
`max_event_count` 或 `max_total_duration_ms` 收紧到更小值，GUI 会用中文列出命中的
私有预算，不会静默扩张导入或用户收紧过的安全边界。

`SendInput` 返回完整插入数时，只能说明 Windows 输入流接纳了本实验提交的记录；
它不证明目标窗口、游戏或 Raw Input 路径消费了这些记录。GUI 固定显示警告，发送
报告仍只属于 delivery（投递）证据，游戏视角响应保持 `UNKNOWN`，直到有独立的
人工或视觉后验。

选中按键或鼠标按钮的一行时，GUI 会把完整按下／释放配对载入上方结构化编辑器，
可一次修改按键、按钮、开始偏移和按住时长。两种点击在加载、替换和删除时保持
各自事件族，不会互相转换。按下和释放位置不同的定位式拖拽配对不会被结构化
编辑器误改成点击，只能逐行修改位置或删除后重建。表格非法编辑会显示失败原因，
不会静默保留半套修改。

### 手动录制

第一版复用 `input_capture_lab`：

- 键盘按下和释放；
- 鼠标按钮按下和释放；
- 鼠标滚轮；
- 按下持续时间；
- 客户区归一化坐标；
- 单调时间和焦点代次。

启动录制后，目标窗口需先稳定前台 `200 ms`，再完成固定 `3 秒`倒计时。
从已激活状态失焦会结束本次录制，不会跨焦点代次恢复旧时间线。
单次录制最多保留 `500` 个事件。GUI 在正常轮询期间检测激活录制是否达到
`60 秒`，达到后会请求提前停止；这项 active 计时是 GUI 策略，不是捕获线程的
独立硬截止。无论 GUI 是否继续轮询，捕获会话从启动起另有 `65 秒` 总会话硬截止，
其中包含等待前台、录制倒计时和激活录制时间；达到后由独立后台计时器停止捕获
会话，避免 GUI 卡顿时无限延长会话。

这里与独立 `Input Capture Lab`（输入捕获实验）的连续观测语义不同：独立实验
失焦后可以保持会话暂停，并在目标重新稳定成为精确前台时开启新的
`focus_epoch`（焦点代次）；本 GUI 的方案录制只要已经激活过，首次失去精确前台
就结束，不会在同一份方案采样中续录。这是录制安全策略，不能作为游戏或反作弊
行为的结论。

原始录制事件保持只读，只有通过以下校验才生成新方案草稿：

- 事件序号连续且无队列缺口；
- 同一捕获会话、目标和焦点代次；
- 按下和释放完整配对；
- 持续时间一致；
- 键盘事件具有 VK 或扫描码；
- 鼠标按钮受支持。

当前不会从 `pynput` 绝对光标回调伪造鼠标移动轨迹。手动录制观察到的按钮事件
继续编译为带客户区位置的定位式 UI 点击，不会根据目标类型自动猜测或升级成
锁定指针点击。普通 UI 指针移动、锁定光标和 Raw Input 游戏视角仍需后续分别
实验；当前方案中的鼠标移动只用于上述客户区指针式绝对采样路径。

独立 [Pointer Context Lab（指针上下文实验）](../pointer_context_lab/README.zh-CN.md)
会以只读方式输出 `POSITIONED_UI_CANDIDATE`、`LOCKED_RELATIVE_CANDIDATE`、
`HYBRID_OR_TRANSITION` 或 `UNKNOWN`。这些结果只能辅助人工选择点击语义，不会
自动修改本实验的录制草稿或 `InputPlan`。

### 录制诊断标签页

“原始录制事件”和“录制诊断”是两个独立的只读标签页。前者只显示被门禁接纳的
事件；后者显示实验私有 `InputCaptureDiagnosticsSnapshot`（输入捕获诊断快照）
的结构化 JSON 行以及一次 `coordinate_context`（坐标上下文）记录。各行通过
`kind` 区分 `capture_diagnostics`、`coordinate_context`、
`diagnostics_error` 和 `diagnostics_recovered`，并携带或关联 `session_id`，帮助
区分：

- 当前前台关系是精确目标 `EXACT_TARGET`、同进程其他窗口
  `SAME_PROCESS_OTHER_WINDOW`、其他进程 `OTHER_PROCESS`、无前台
  `NO_FOREGROUND`，还是无法确认的 `UNKNOWN`；
- 目标句柄、PID、进程实例、最小化状态和客户区是否仍健康；
- 键盘和鼠标监听器是否各自存活、收到多少回调、最后回调时间、失败数量和停止
  状态；
- 最近鼠标点命中了哪个根窗口、是否位于目标客户区以及具体拒绝原因；
- 哪个按键／按钮的 press（按下）在何时、因何种失焦或停止条件中断。

诊断快照修订号只在语义变化时递增，GUI 不会按 `50 ms` 轮询频率重复追加完全
相同的记录。若按下事件已被接纳、释放前发生失焦，原 `KEY_DOWN` 或
`MOUSE_BUTTON_DOWN` 会保留，中断按压以独立诊断证据显示；不会伪造
`KEY_UP`／`MOUSE_BUTTON_UP`。方案编译仍会拒绝这种未配对时间线，并在报告中指出
最近的设备、按键／按钮、事件 ID、组 ID 和中断原因。

这些诊断只解释 WorldTrace 在用户态观察到的窗口、回调和门禁状态。没有回调、
同进程其他窗口、失焦或未配对 press 都不能单独证明目标使用了反作弊，也不能
证明输入被拦截；反作弊兼容性仍为 `UNKNOWN`。

## 执行状态机

GUI 在创建执行会话前有一段只读等待：

```text
候选窗口
→ 安装 WindowLifetimeGuard（窗口生命周期守卫）
→ 冻结 TargetWindowIdentity（目标窗口身份）
→ WAITING_FOREGROUND / WAITING_CLIENT
→ READY（生成 TargetWindowBinding，目标窗口绑定）
→ 创建执行会话
```

等待预算为 `30 秒`，由 GUI 使用单调时间在每次轮询时判定。若 GUI 自身暂时卡顿，
卡顿期间仍不存在发送会话或全局紧急停止监听；恢复轮询后会立即按已经过去的
单调时间判定是否超时。窗口句柄失效、PID 改变、进程创建时间改变或无法复核时，
本次等待永久
失败；窗口销毁监听一旦触发也永久失败，不按标题、进程名或 PID 寻找替代窗口。
用户可在等待期间点击
“取消等待（尚未发送）”；此时全局 `Ctrl+Shift+F12` 监听尚未启动，因为发送资源
根本不存在。只读窗口生命周期守卫会在取消、超时、失败或执行终态时清理。

最终绑定形成后才进入原有执行状态机：

```text
IDLE
→ WAITING_FOREGROUND
→ COUNTDOWN
→ RUNNING
→ SUCCEEDED / BLOCKED / CANCELLED / CANCELLED_PARTIAL / FAILED
```

- `WAITING_FOREGROUND`：等待精确目标窗口稳定前台 `200 ms`；
- `WAITING_FOREGROUND` 最长 `30 秒`，超时后本次会话失效，不会在很久以后突然执行；
- `COUNTDOWN`：GUI 先等待原生提示层完成一次绘制确认，再开始完整固定
  `3 秒`，不可由方案缩短；
- `BLOCKED`：尚未发送输入前，安全门禁阻止本次运行；
- `CANCELLED_PARTIAL`：已经发送部分输入后发生失焦或停止；
- `SUCCEEDED`：发送计划完成，但游戏效果仍为未知。

### Windows 进程完整性级别门禁

`process_integrity`（进程完整性诊断）只使用公开的 Windows 用户态令牌接口：

- `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`；
- `OpenProcessToken(TOKEN_QUERY)`；
- `GetTokenInformation(TokenIntegrityLevel)`；
- 读取完整性 SID 的最后一个 sub-authority RID。

比较使用原始 RID，不只比较显示名称，因此 `MEDIUM_PLUS` 等中间值不会被错误压平。
WorldTrace 当前 RID 大于等于目标 RID 时允许继续；当前 RID 更低、当前令牌查询
失败、目标令牌查询失败、PID 不匹配或返回值非法时全部阻止。门禁不会请求
`SeDebugPrivilege`，不会枚举目标命令行，不会修改令牌，也不会自动提权。

GUI 在四个位置检查：

1. 选择候选和点击“开始”时，发送资源尚未创建；
2. 同一 HWND、PID、进程实例恢复并形成最终绑定后，创建执行会话前；
3. 执行线程通过前台稳定门禁、进入安全倒计时前；
4. 完成倒计时、开始发送输入前。

第 3、4 次检查只发生在状态阶段边界，不会在兼容旧方案的 `240 Hz` 绝对硬上限下
对每个鼠标分片反复打开令牌句柄。同一进程的完整性级别本身不会在运行中改变；原有 PID、进程创建
时间、窗口生命周期和焦点门禁继续负责阻止目标进程实例替换。任一次完整性复核
失败均以 `BLOCKED` 或 GUI 启动前阻止结束，`sent_atomic_count` 保持为 `0`。

这项门禁只验证 UIPI（用户界面特权隔离）相关的必要前提。门禁通过不代表目标会
消费 `SendInput`，门禁阻止也不能单独证明存在反作弊。

倒计时提示层使用不激活、鼠标穿透的独立原生窗口。`isVisible()` 等逻辑状态不足
以开始倒计时，必须由实际绘制回调完成 paint 确认。绘制确认后的完整三秒内，
执行线程要求 GUI 心跳间隔不超过 `250 ms`；倒计时结束时，GUI 还必须先隐藏提示层，
再在 `250 ms` 内确认隐藏。绘制确认、持续心跳或执行前隐藏确认任一缺失，均保持
零输入并阻止本次执行。首次绘制确认仍有 `5 秒`总等待上限。

### DPI、客户区与提示层坐标

客户区绑定来自 Win32 调用线程当时的坐标空间；正式执行前的 DPI 门禁必须确认
它是原生物理像素。Qt 顶层窗口的位置和大小则使用 device-independent pixels
（设备无关像素，DIP）。提示层不能直接把原生物理像素区域当作 DIP。
`WindowsNativeClientRegionConverter`（Windows 原生客户区转换器）会：

1. 找到完整包含客户区的 Win32 显示器及其原生物理像素原点；
2. 选择同名 `QScreen`，或仅在物理尺寸映射唯一时使用候选回退；
3. 以各自显示器原点为锚，按该屏幕的 device pixel ratio
   （设备像素比，DPR）把客户区严格转换为 Qt 全局 DIP；
4. 仅在客户区完整位于单一显示器、DPR 有效、物理尺寸一致且屏幕映射唯一时显示。

客户区跨屏、屏幕匹配歧义、DPR 非法或几何不一致时，转换按失败关闭原则报错，
提示层隐藏，执行保持零输入；不会退回把原生物理坐标直接交给 Qt。

项目入口在创建 `QApplication` 前请求 Per-Monitor V2 DPI awareness
（每显示器 V2 DPI 感知）。在当前 4K、Windows 缩放 `200%`、目标窗口 DPI
`192` 的本机只读观测中，Per-Monitor V2 调用方读取游戏客户区为
`1920×1080`；DPI-unaware（DPI 不感知）调用方会被 Windows 等比虚拟化为
`960×540`。后者是调用方坐标空间，不是游戏实际渲染分辨率。录制开始时，
“录制诊断”会写入一条易失 `coordinate_context`，明确记录调用线程所观察到的
客户区、调用线程 DPI 感知级别、目标 DPI、缩放比例和坐标空间；只有坐标空间已
确认为 `NATIVE_PHYSICAL_PIXELS` 时，记录才另外填写
`client_region_native_px`。被动录制的探测失败只记为 `UNKNOWN`，不会静默猜测，
也不会因此停止被动观察。

正式执行采用更严格的零发送门禁：最终目标绑定完成后、创建发送会话前，再次探测
同一 HWND。诊断 HWND 不一致、探测报错、坐标空间为 `UNKNOWN` 或不属于
`NATIVE_PHYSICAL_PIXELS` 时，本次执行直接阻止，不创建 `SendInput` 会话和紧急
停止监听。这个门禁验证的是 WorldTrace 自身的坐标前提，不表示目标程序接受输入。

## 固定安全边界

- 第一版只提供前台 Win32 `SendInput`；
- 不提供 `PostMessage`、后台输入或隐式后端回退；
- 不自动调用 `SetForegroundWindow` 抢回焦点；
- 不调用 `ShowWindow` 强制恢复最小化窗口；恢复和切回目标必须由用户完成；
- 不使用枚举时旧客户区、`1×1` 占位或可空宽高冒充最终绑定；
- 当前 WorldTrace 进程完整性 RID 低于目标、或任一 RID 无法确认时，禁止创建
  输入会话和进入倒计时；
- 最终绑定后、进入倒计时前和开始发送前均再次执行完整性级别门禁；
- 最终绑定后、创建输入资源前必须通过同 HWND 的原生物理像素 DPI 坐标门禁；
- 等待恢复期间只保存身份并监听目标窗口销毁，不创建 `SendInput` 后端会话或
  全局紧急停止监听；
- `WindowLifetimeGuard` 使用目标进程范围的 `WINEVENT_OUTOFCONTEXT`
  （进程外 WinEvent）监听，不向目标进程注入代码；安装失败按失败关闭原则阻止；
- 执行倒计时提示层必须重新读取当前客户区，且必须与最终冻结客户区完全一致，
  禁止回退到候选快照位置；
- 每个原子输入和每个鼠标插值采样前都重新校验同一 `focus_epoch`；
- 定位式鼠标按钮和滚轮发送前读取实际光标，要求它仍位于本次计划位置和目标窗口；
- 锁定指针按钮不读光标，但每次按钮发送前仍执行其余窗口、前台、客户区、
  `focus_epoch` 和停止门禁；
- 最终绑定后客户区的位置或尺寸发生任何变化都会中止，不按新几何静默重映射；
- 相对位移规划解析出的每个绝对采样点都必须仍命中目标客户区；
- 相机相对移动不做光标命中或到达校验，但每个分片仍要求目标窗口保持精确前台、
  窗口实例与冻结客户区不变；
- 倒计时失焦时发送数必须为零；
- 运行中失焦后不再发送剩余方案；
- 调度迟到超过 `250 ms` 时不突发补发过期事件；
- 移动展开后的全方案调度槽最多 `50,000` 个，防止少量编写动作在高更新率下
  膨胀成不可控的发送日程；
- 维护键盘和鼠标按钮持有账本；
- 正常结束、失焦、停止和异常均执行同一幂等释放；
- 松键／松按钮失败时保持输入租约锁定，GUI 只允许“重试释放残留输入”，
  释放成功前不能开始下一方案或安全关闭；
- 当前进程同一时刻只有一个输入执行租约；
- 同一个 GUI 实例内录制和回放互斥；
- 执行开始前等待全局紧急停止监听真正就绪，并把监听健康状态注册为执行安全门禁；
- 等待前台、倒计时、运行调度及每次原子输入发送门禁都会同时复核紧急停止监听
  和窗口生命周期守卫；任一不可用或健康检查异常时按失败关闭原则停止执行；
- 全局紧急停止固定为 `Ctrl+Shift+F12`，只在执行期间启用；
- 方案校验拒绝包含完整 `Ctrl+Shift+F12` 组合的时间线；
- 单个输入方案第一版最多 `500` 个事件、总时长最多 `60 秒`；
- 单键/按钮按住和单段鼠标移动最多 `5 秒`；
- 方案文件只能进一步收紧这些上限，不能把第一版硬上限调大；
- 第一版不支持循环、条件、脚本表达式和无限重试。

不自动提权，不注入目标进程，不读游戏内存，不安装驱动，不绕过反作弊。首轮只应
使用记事本、画图或自建测试窗口；不要在在线竞技游戏、敏感输入窗口或条款禁止
输入钩子/自动输入的软件上测试。

第一版尚未使用低级钩子的 injected flag 区分“用户临时输入”和“本实验发送输入”。
执行期间除紧急停止组合键外不要同时操作键鼠；后续再单独验证检测人工干预后自动
中止的机制。

当前输入租约只覆盖同一 Python 进程，不能阻止另一个 WorldTrace 进程或其他自动化
工具同时发送输入；独立的 `input_capture_lab` 也尚未共享该租约。因此第一版验收
只允许启动一个本 GUI 实例，并关闭其他键鼠自动化或录制工具。

录制期间 `Ctrl+Shift+F12` 不是“停止录制”热键；若用户把完整组合录进时间线，
后续方案校验会拒绝它。停止录制应返回本 GUI 点击“停止录制”。

## 建议的首次人工验证

1. 打开记事本或自建测试窗口；
2. 在 GUI 中选择该窗口；
3. 新建方案并添加 `W` 或普通字母按住 `100 ms`；
4. 校验并保存方案；
5. 点击“开始”，手动切换到目标窗口；
6. 观察原生提示层完成显示、完整倒计时并在输入前消失，确认仅产生一次预期字符；
7. 再测试倒计时中切走，确认没有字符；
8. 测试按住事件运行中切走或按 `Ctrl+Shift+F12`，确认停止并释放；
9. 返回 GUI 查看发送数量、取消原因和清理结果；
10. 不把目标窗口的可见结果写成自动确认状态。

完成上述桌面安全门禁验证后，再单独验证 3D 视角相对移动：

1. 显式选择 `3D 视角相对移动（实验）`，不要使用旧相对指针移动；
2. 首次使用 `dX=180, dY=0, duration=3000 ms, update_rate=60 Hz,
   interpolation=LINEAR`，它会尝试约 `60` 个每秒、持续 `3` 秒的右向命令；
3. 只在安全、静止、允许输入实验的场景中启动，切到目标并等待完整倒计时；
4. 投递验收记录 `sent_atomic_count`、焦点／窗口门禁和停止原因；
5. 视觉验收另行人工观察或录像比较方向是否一致；即使画面转动，仍只记录为
   “当前版本、当前设置下观察到响应”；
6. 若过慢，可按 `180 → 360 → 900` 逐级增加 `dX`，每次保留更新率、游戏灵敏度、
   Windows 鼠标设置和游戏窗口模式，不把输入量换算成角度；
7. 若投递完成但画面不动，记录为 `delivery=SUCCEEDED,
   target_response=NOT_OBSERVED`，不解释成反作弊结论。

自动测试使用 fake backend、fake native sender、fake WinEvent native interface
（伪 WinEvent 原生接口）或离屏 Qt，不向真实窗口发送键鼠，也不安装真实 WinEvent
Hook。
真实 `SendInput`、原生提示层的绘制／不夺焦／隐藏确认、多显示器与 DPI、游戏
Raw Input、反作弊兼容性和目标程序响应仍需用户在明确选择的安全测试窗口中人工
安全验收；自动测试通过不能替代这些验证。

当前只读 DPI 诊断已经能区分本机《原神》《无限暖暖》窗口在 PMv2 与不感知调用方
中的坐标虚拟化现象；这不等于已经验证窗口化、无边框全屏或独占全屏提示层，
也不等于验证了游戏内录制、鼠标视角或点击响应。全屏原生提示层是否可见、进程
范围 WinEvent 监听是否兼容和反作弊兼容性仍为 `UNKNOWN`（未知）。

2026-07-30 的本机定向 A/B 只形成一条环境限定证据：对同一《原神》窗口进程，
`WorldTrace MEDIUM → 目标 HIGH` 时，Windows 虽接纳了相对鼠标记录，但前后画面
未观察到视角偏移；经用户确认的 UAC 提权辅助进程以
`WorldTrace HIGH → 目标 HIGH` 发送相同类型的相对输入后，前后截图观察到椰子树、
岩石和远景整体按预期方向移动。它说明完整性级别不匹配是该次环境中的实质条件，
不等于所有游戏都需要提权，也不能据此判定、绕过或排除反作弊。本实验不提供或
声称绕过反作弊；任何后续人工验证都应先确认符合目标软件的官方条款。
