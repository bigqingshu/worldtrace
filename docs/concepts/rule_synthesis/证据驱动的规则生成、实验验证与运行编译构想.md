## 1. 核心目标

界迹不应把每个游戏状态、按钮作用、物品变化和操作关系都手写成固定函数。系统需要能够根据以下信息自行形成逻辑：

- 当前和历史游戏状态；
- 用户真实键鼠操作；
- 图标、文本、布局、数值和画面变化；
- 操作前后连续时间窗；
- 相同操作在不同上下文中的差异；
- 系统主动进行的低风险实验；
- 成功、失败、未知和反例记录。

但“自行生成逻辑”不应等同于让LLM随时生成Python并立即执行。更稳妥的核心形式是：

> 系统生成带类型、证据、适用范围和版本的声明式规则数据，由固定且受限的规则引擎解释或编译执行。

## 2. 不是完全消除函数

系统仍然需要稳定函数实现基础事实和基础运算，否则没有可靠的执行地基。

应该固定的是：

```text
截图和帧时间线
键鼠输入和窗口归属
图标、文本、区域和数值观测
布尔、比较、算术、空间和时间算子
规则类型检查
证据保存与离线回放
安全停止、资源预算和权限边界
```

应该动态生成的是：

```text
哪些现象共同定义一个状态
某个操作可能引起哪些变化
哪些前置条件决定规则是否适用
证据需要保持多久
数值之间使用什么公式或查表关系
遇到什么反例时拆分上下文
某类失败采用哪条已验证恢复路径
```

最终原则是：

```text
基础算子固定
+ 算子组合动态生成
+ 规则版本可验证、可回退
```

## 3. 关系作为数据而不是代码分支

传统写法可能是：

```text
if 当前是主界面 and 用户按下B:
    等待背包页面
```

界迹中的权威定义应更接近：

```text
TransitionRule
├── rule_id
├── version
├── scope
├── source_state_query
├── applicability_guards
├── action_spec
├── acceptance_predicates
├── progress_predicates
├── success_predicates
├── failure_predicates
├── temporal_constraints
├── evidence_refs
├── counterexample_refs
├── validation_summary
└── lifecycle_status
```

关系规则可以完全不知道“背包”这个语义名称，只记录：

```text
state_cluster_12
+ press_key(B)
-> token_421变为SELECTED
-> layout_08出现
-> token_137消失
-> state_cluster_37
```

用户或LLM以后可以给`state_cluster_37`添加“背包界面”名称，但名称不参与确定性执行。

## 4. 五层总体结构

```text
事实层 Fact Layer
-> 帧、输入、视觉标记、OCR、数值和事件

假设层 Hypothesis Layer
-> 相关关系、状态候选、公式候选和适用范围候选

实验层 Experiment Layer
-> 离线回放、影子评估和受控干预

规则层 Rule Layer
-> 已验证的声明式StateRule、TransitionRule等

编译执行层 Compilation and Runtime Layer
-> 类型检查、版本固定、执行和结果解释
```

每一层只消费下层的结构化输出，不能绕过证据直接把解释写成运行规则。

## 5. 事实层

事实层只记录可复现观测，不负责提前解释含义。

```text
FactRecord
├── fact_id
├── fact_type
├── frame_id或window_id
├── action_id
├── window_instance_id
├── focus_epoch
├── observed_value
├── confidence
├── freshness
├── producer_id与版本
└── evidence_ids
```

可能的事实包括：

```text
KEY_PRESSED(B)
TOKEN_VARIANT_CHANGED(token_421, NORMAL, SELECTED)
REGION_APPEARED(layout_08)
OCR_VALUE_CHANGED(region_12, 34, 35)
MOUSE_DELTA_APPLIED(dx=4)
SLIDER_POSITION_CHANGED(delta=0.021)
WINDOW_FOCUS_CHANGED
FRAME_CAPTURE_FAILED
```

事实记录应尽量不可变。后续识别器升级时，可以基于相同原始证据产生新版本事实，但不能静默覆盖旧结果。

## 6. 假设层

被重复观察到的模式先形成假设，而不是直接成为有效关系。

```text
RuleHypothesis
├── hypothesis_id
├── rule_type_candidate
├── input_fact_patterns
├── proposed_expression
├── proposed_scope
├── support_evidence_refs
├── counterexample_refs
├── unresolved_variables
├── induction_method
├── confidence_components
└── hypothesis_status
```

建议状态：

```text
OBSERVED_ASSOCIATION
TRANSITION_HYPOTHESIS
CAUSALITY_SUPPORTED
CONTRADICTED
SUPERSEDED
```

被动观察只能优先产生`OBSERVED_ASSOCIATION`。只有经过重复干预、上下文控制或可靠自然实验后，才能提高因果等级。

## 7. 统一规则外壳

不同规则拥有各自字段，但可以共享一个公共外壳：

```text
RuleSpec
├── rule_id
├── rule_type
├── version
├── content_hash
├── scope
├── input_schema
├── output_schema
├── expression_or_model_ref
├── applicability_guards
├── evidence_requirements
├── validation_artifact_refs
├── quality_metrics
├── created_by
├── created_at
└── lifecycle_status
```

`created_by`可以是：

```text
USER_AUTHORED
DETERMINISTIC_INDUCER
STATISTICAL_LEARNER
LLM_PROPOSED
IMPORTED
```

来源不同不会自动决定规则是否可靠，所有规则都必须进入相同验证流程。

## 8. 规则必须分类

不建议设计一个万能规则格式。至少区分以下规则族。

### 8.1 `StateRule`

描述哪些事实共同支持某个状态：

```text
StateRule
├── state_definition_id
├── evidence_expression
├── minimum_freshness
├── stability_requirement
├── ambiguity_policy
└── output_confidence_model
```

### 8.2 `TransitionRule`

描述某个上下文中的操作、变化和目标状态：

```text
TransitionRule
├── source_state_query
├── action_spec
├── acceptance_predicates
├── progress_predicates
├── success_predicates
├── failure_predicates
└── expected_timing
```

### 8.3 `DerivedValueRule`

从观测推导数值：

```text
屏幕滑块位置
-> 归一化音量值

小地图箭头角度
-> 镜头相对方向
```

### 8.4 `CalibrationRule`

描述输入量和实际响应之间的关系：

```text
鼠标位移
-> 视角旋转角度

滚轮格数
-> 地图缩放等级
```

### 8.5 `TemporalRule`

描述刷新、持续、超时、可用窗口和失效条件。

### 8.6 `ReconciliationRule`

描述多个快照和事件如何对账，例如库存数量变化、物品转移和缺失候选。

### 8.7 `RecoveryPolicy`

描述在特定故障归因下，可以尝试哪些恢复能力、尝试顺序、预算和停止条件。

恢复策略可以逐步学习，但输入焦点验证、全局停止和危险动作授权等安全约束不能由学习规则取消。

## 9. 表达式图而不是任意代码

生成的计算逻辑建议使用有类型的`ExpressionGraph`：

```text
输入事实
-> 归一化
-> 比较或变换
-> 时间与空间组合
-> 聚合
-> 输出TRUE / FALSE / UNKNOWN或数值结果
```

表达式节点只能引用白名单算子。

### 9.1 布尔算子

```text
all_of
any_of
not
xor
at_least_n
```

### 9.2 比较与数值算子

```text
equal
greater_than
less_than
within_range
add
subtract
multiply
divide_safe
clamp
normalize
lookup
piecewise
```

### 9.3 时间算子

```text
before
after
within
stable_for
changed_within
count_in_window
sequence
```

### 9.4 空间算子

```text
inside
near
overlap_ratio
relative_position
same_region
```

### 9.5 证据算子

```text
token_present
token_variant_is
region_changed
layout_matches
ocr_matches
value_changed
capture_is_fresh
focus_epoch_matches
```

表达式图本身保持DAG，禁止无界循环和隐藏副作用。游戏状态图和空间拓扑仍然可以存在受控循环，两者不能混淆。

## 10. 三值逻辑

规则判断不能只有`TRUE`和`FALSE`。游戏截图、OCR和窗口状态经常存在无法确认的情况。

```text
TRUE
FALSE
UNKNOWN
```

例如：

```text
没有检测到图标
+ 当前截图健康
+ 目标区域完整可见
+ 检测器适用于当前UI版本
-> TOKEN_ABSENT = TRUE
```

如果区域被遮挡或截图失败，则应该是`UNKNOWN`而不是`FALSE`。

逻辑算子必须定义三值传播规则，危险操作遇到关键`UNKNOWN`时默认不执行。

## 11. 状态规则自动生成

系统可以从稳定画面片段中寻找共同现象：

```text
多次停留在候选状态S
-> 提取稳定图标、布局、文本和区域特征
-> 去除动画、角色和随机提示
-> 对比相邻状态寻找区分特征
-> 生成StateRule候选
```

生成状态规则时不仅需要正样本，还需要相似负样本。只在一个页面出现过的图标，可能同时存在于其他页面，不能因为缺少反例就直接成为唯一状态条件。

更稳妥的输出：

```text
all_of(
  token_variant_is(token_421, SELECTED),
  layout_matches(layout_08),
  not(token_present(token_137)),
  stable_for(350ms)
)
```

具体阈值和稳定时间来自样本与验证，不需要人工写进业务函数。

## 12. 转换规则自动生成

用户输入为发现因果关系提供天然时间锚点：

```text
输入前时间窗
-> action_id
-> 输入后时间窗
```

系统可以统计：

- 哪些现象在操作前稳定存在；
- 哪些现象在操作后高频出现；
- 变化通常需要多久；
- 哪些上下文下没有变化；
- 是否存在其他同时发生的输入；
- 相同操作是否产生多个结果分支。

候选转换：

```text
scope = game_profile + state_cluster_12 + control_context_3
action = press_key(B)
acceptance = region_changed(main_hud)
success = state_rule_37 == TRUE
timeout = learned_distribution
```

系统不能因为一次成功就发布关系，也不能把输入后的所有变化都归因给该输入。

## 13. 计算和校准逻辑自动生成

连续控件适合通过低风险实验拟合规则。

### 13.1 滑块示例

```text
当前滑块值
+ 鼠标位移
+ UI缩放
+ 拖动方向
-> 新滑块值
```

系统执行多个小幅可逆操作后，可以生成：

```text
CalibrationRule
├── inputs
│   ├── current_value
│   ├── mouse_delta
│   ├── direction
│   └── ui_scale
├── model_type = PIECEWISE_LINEAR
├── parameters
├── valid_range
├── prediction_error
├── context_scope
└── calibration_evidence_refs
```

### 13.2 可选拟合方式

```text
线性回归
分段线性模型
单调样条
有限查表
决策树
符号回归
简单状态空间模型
```

第一版优先使用可解释、可限制范围和容易回退的模型。黑盒模型必须通过`ModelSpec`声明输入、输出、版本和适用范围，不能假装成普通表达式节点。

## 14. 被动观察与主动实验

### 14.1 被动观察

记录用户正常游玩，成本和风险最低，可以发现：

- 高频状态组合；
- 操作前后相关变化；
- 常见时间延迟；
- 候选控制响应；
- 可能的上下文变量。

但被动观察容易受到同时操作、剧情触发、服务器事件和用户意图影响，只能优先产生相关假设。

### 14.2 主动实验

系统在用户授权和安全边界内改变一个变量，观察结果是否可重复：

```text
保持状态和上下文稳定
-> 执行一个最小操作
-> 观察变化
-> 恢复初始状态
-> 重复或改变一个变量
```

主动实验可以增强因果证据，但不能默认任何游戏操作都适合试验。

## 15. 实验计划数据

```text
ExperimentPlan
├── experiment_id
├── question
├── hypotheses
├── controlled_variables
├── intervention_steps
├── expected_observations
├── risk_class
├── resource_cost_limit
├── max_attempts
├── timeout
├── rollback_capability_ref
├── stop_conditions
├── user_approval_requirement
└── evidence_collection_spec
```

风险等级可以初步分为：

```text
SAFE_REVERSIBLE
LOW_COST_REVERSIBLE
RESOURCE_CONSUMING
POTENTIALLY_IRREVERSIBLE
FORBIDDEN_AUTONOMOUS
```

出售物品、消耗稀有资源、改变账号设置、进入不可逆剧情和涉及付费的操作，不能由系统自行试验。

## 16. 规则生成流水线

```text
FrameStream与InputStream
-> EventSegmenter 事件切分器
-> FactBuilder 事实生成器
-> PatternMiner 模式发现器
-> RuleInducer 规则归纳器
-> HypothesisStore 假设存储
-> ExperimentPlanner 实验规划器
-> RuleValidator 规则验证器
-> RuleCompiler 规则编译器
-> RuleRegistry 规则注册表
-> RuleEvaluator 规则求值器
```

### 16.1 `EventSegmenter`

根据用户输入、界面突变、加载、稳定区间和时间间隔切分候选步骤。

### 16.2 `PatternMiner`

寻找重复出现、顺序稳定或与输入高度相关的事实模式。

### 16.3 `RuleInducer`

把模式转换成带类型的候选表达式、公式和适用范围。

### 16.4 `RuleValidator`

使用正样本、负样本、反例、离线回放和影子运行评估规则。

### 16.5 `RuleCompiler`

检查类型、算子权限、依赖版本、资源上限和副作用边界，生成固定版本的可执行产物。

## 17. 归纳方法不只依赖LLM

系统内部可以组合：

```text
变化点检测
频繁序列发现
关联规则学习
决策树和规则列表
贝叶斯更新
聚类和上下文分裂
符号回归
有限状态模型归纳
```

LLM适合：

- 根据结构化证据提出候选解释；
- 为机器状态和规则命名；
- 建议还缺少哪些实验；
- 从说明文本提取候选条件；
- 向用户解释规则冲突。

LLM输出仍然只是候选，必须经过同一验证流程。

## 18. 规则验证层级

### 18.1 结构验证

检查：

- 输入和输出类型；
- 是否使用允许算子；
- 是否存在无界循环；
- 引用的检测器和能力是否存在；
- 时间窗口和资源预算是否有效；
- 是否包含禁止副作用。

### 18.2 离线回放

在历史证据上重复运行规则，验证：

- 正样本召回；
- 相似负样本误判；
- 反例解释能力；
- 不同帧率和延迟下的稳定性；
- 依赖检测器版本变化的影响。

### 18.3 影子运行

在线计算规则结论但不执行动作，与用户真实操作和后续结果对照。

### 18.4 受控运行

只允许低风险、可恢复动作，并严格绑定窗口、焦点代次和停止条件。

## 19. 发布生命周期

规则继续使用统一生命周期：

```text
DRAFT
-> CANDIDATE
-> SHADOW
-> ACTIVE
-> DEGRADED
-> RETIRED
```

### 19.1 `ACTIVE`规则不可原地修改

运行中的规则版本必须不可变。新证据只能产生：

```text
旧ACTIVE版本
+ 新候选修改
-> 新CANDIDATE版本
```

新版本经过验证后再原子切换。已有`ExecutablePlan`继续固定旧版本，除非计划明确允许重新编译。

### 19.2 回退

每个发布动作保存：

```text
previous_active_version
activation_reason
validation_artifacts
rollback_conditions
```

新版本异常时可以恢复旧版本，而不是临时修改表达式。

## 20. 适用范围优先于全局规则

游戏行为高度依赖上下文：

```text
游戏版本
界面状态
角色和能力
控制模式
任务或活动阶段
分辨率与UI缩放
输入配置
窗口和账号实例
```

每条规则都需要`scope`和`applicability_guards`。证据不足时，先生成狭窄规则：

```text
角色A + 普通状态 + 主HUD + B
-> 打开某状态
```

只有在多个上下文中验证一致后，才能合并为更一般的规则。不能先假设跨角色、跨地区或跨游戏通用。

## 21. 反例和上下文分裂

发现反例时，系统依次判断：

```text
截图或检测是否健康
输入是否送达正确窗口
前置状态是否真的成立
游戏是否存在瞬态故障
是否遗漏上下文变量
关系本身是否错误
```

如果规则在载具状态下失效，可以生成上下文分裂：

```text
普通状态 + B
-> rule_version_A

载具状态 + B
-> rule_version_B或UNKNOWN
```

反例不能直接删除原关系，也不能不经归因就降低所有上下文中的可靠性。

## 22. 竞争假设

系统可能同时存在多个解释：

```text
按B导致页面变化
任务阶段变化导致页面变化
两者共同满足时才变化
```

`HypothesisStore`应允许：

- 保留多个候选；
- 记录各自支持和反例；
- 标记彼此竞争、包含或依赖；
- 生成能够区分它们的实验；
- 无法消歧时继续返回多个候选。

不能仅按最高分候选覆盖其余假设。

## 23. 规则结果必须可解释

```text
RuleEvaluationResult
├── rule_id与version
├── outcome
├── output_value
├── matched_predicates
├── failed_predicates
├── unknown_predicates
├── consumed_fact_ids
├── evidence_ids
├── evaluation_time
└── reason_code
```

`outcome`至少包含：

```text
MATCHED
NOT_MATCHED
UNKNOWN
ERROR
```

用户和调试工具应能回答：

```text
为什么认为当前是这个状态
为什么判断操作成功
哪项证据缺失
使用的是哪个规则版本
```

## 24. 编译和运行安全

`RuleCompiler`必须禁止：

- Python `eval`、`exec`或任意脚本注入；
- 未注册的函数或系统命令；
- 无界循环和无限递归；
- 表达式内部直接执行键鼠输入；
- 未声明的文件、网络或模型访问；
- 绕过`FocusLease`和资源互斥；
- 修改活动规则自身。

纯计算表达式和有副作用动作必须分开：

```text
RuleEvaluator
-> 只计算状态、条件和数值

ExecutablePlan
-> 经过编译后调用允许的CapabilitySpec
```

即使后续为了性能生成机器代码或缓存函数，权威来源仍然是版本化`RuleSpec`，生成产物可以随时删除并重新编译。

## 25. 与状态和关系网的连接

`StateDefinition`和`TransitionDefinition`不应被理解为永远由人手工填写的固定结构。更合理的是：

```text
StateDefinition
-> 稳定逻辑身份

StateDefinitionVersion
-> 引用某个StateRule版本

TransitionDefinition
-> 稳定关系身份

TransitionDefinitionVersion
-> 引用某个TransitionRule版本
```

运行计划固定具体版本：

```text
ExecutablePlan
-> state_rule_version
-> transition_rule_version
-> capability_version
-> detector_version
-> calibration_version
```

这样系统可以持续学习新规则，但已经开始执行的计划不会在中途被悄悄改变。

## 26. 与图标系统的连接

图标模块产生：

```text
VisualTokenObservation
VisualTokenEvent
VisualEvidencePredicate候选
```

规则归纳器可以发现：

```text
某组图标和布局反复共同出现
-> StateRule候选

某个输入后图标稳定改变
-> TransitionRule候选
```

图标无需语义名称，也能参与规则生成和验证。

## 27. 与物品系统的连接

物品领域中的以下逻辑适合由规则生成系统承载：

```text
说明文本
-> AttributeClaim和AcquisitionClaim候选

库存快照差异
-> InventoryEvent候选

完整扫描中持续缺失
+ 时间规则或用户操作
-> 消失归因候选
```

例如：

```text
all_of(
  previous_presence_confirmed,
  current_scan_coverage_complete,
  item_not_observed,
  no_active_filter,
  capture_is_fresh
)
-> MISSING_UNCONFIRMED
```

只有继续匹配消耗、转移、过期或转换证据后，才能产生具体删除原因。

## 28. 与连续控制器的连接

连续控制器不应把所有鼠标量、持续时间和阈值写成游戏专用常量。

```text
实验样本
-> CalibrationRule
-> ContinuousController读取固定版本
-> 每步执行后重新观测
-> 偏差超过范围时触发重新校准候选
```

控制器的安全停止、最大输入量和窗口归属是固定边界；输入响应公式和适用范围可以动态生成。

## 29. 与LLM的边界

LLM可以：

- 为机器状态、规则和图标建议名称；
- 从结构化事实提出候选关系；
- 解释反例和上下文差异；
- 建议低风险实验；
- 把用户目标转换为规则查询；
- 解释`RuleEvaluationResult`。

LLM不能：

- 直接把候选发布为`ACTIVE`；
- 生成任意代码并立即执行；
- 绕过规则类型和安全检查；
- 在没有输入送达证据时判定操作成功；
- 在没有可区分实验时宣布因果关系成立；
- 原地修改正在执行的规则版本。

LLM只读取固定`revision`的`ReadModel`，并通过受限提交接口返回`Proposal`、`Question`或`Explanation`。`ProposalService`负责校验和保存候选，这不代表LLM拥有数据库写权限。候选通过规则验证与发布流程后，才由程序服务创建新的`RuleHypothesis`或`RuleSpec`版本：

```text
ReadModel(revision=N)
-> LLM Proposal
-> ProposalStore
-> RuleValidator与发布策略
-> 正式Command
-> RuleRegistry新版本
```

完整权限与记忆边界见[程序事实记忆、AI智能体记忆与写入治理](../../architecture/程序事实记忆、AI智能体记忆与写入治理.md)。

## 30. 置信度分离

规则不能只有一个综合置信度。至少应区分：

```text
observation_confidence
pattern_support
causal_support
predictive_accuracy
context_coverage
calibration_error
detector_reliability
input_delivery_confidence
counterexample_rate
evidence_freshness
```

规则质量只使用适合的样本更新。截图故障、输入错投、游戏Bug和前置状态错误不能作为关系本身的反例。

## 31. 建议的持久化边界

```text
EvidenceStore
-> 原始帧、输入、观测和实验现场

FactStore
-> 版本化结构事实

HypothesisStore
-> 候选关系、竞争假设和反例

RuleRegistry
-> 不可变规则版本和发布指针

CompilationCache
-> 可删除、可重建的执行产物
```

规则文件可以使用JSON、数据库记录或其他结构化格式，但必须经过Schema验证。不能把Python源码作为唯一规则存储形式。

## 32. 第一阶段不立即实现完整规则学习

当前`Trace Core`顺序仍然有效：

```text
CaptureService
InputRecorder
WindowRegistry
Timeline
FrameRingBuffer
EvidenceStore
ReplayTool
```

如果事实时间线不可靠，后续模式发现和因果实验只会生成错误关系。规则系统的首个实现应从离线回放中的手工规则解释器开始，再逐步加入自动归纳。

## 33. 分阶段验证

### 阶段一：规则Schema和解释器

人工编写少量`StateRule`和`TransitionRule`数据，证明同一规则可以在离线回放中稳定求值，不把关系写进Python业务分支。

### 阶段二：三值逻辑和证据解释

注入截图缺失、遮挡和旧帧，验证规则返回`UNKNOWN`并列出缺失证据。

### 阶段三：被动模式发现

记录用户多次打开和关闭同一个菜单，自动生成候选状态和转换关系，不立即执行。

### 阶段四：影子验证

在线评估候选规则，与用户真实操作结果对照，收集正样本、负样本和时间分布。

### 阶段五：安全连续控件

在可逆滑块上进行微小移动，拟合一条分段线性`CalibrationRule`并验证误差范围。

### 阶段六：上下文分裂

选择一个在两种游戏状态下结果不同的操作，验证规则能够拆分适用范围而不是平均成一个错误关系。

### 阶段七：低风险受控实验

系统提出实验计划，用户批准后执行有限次数，并保留完整恢复和停止记录。

### 阶段八：规则发布和回退

把候选版本从`SHADOW`提升为`ACTIVE`，再故意注入反例触发`DEGRADED`和回退。

## 34. 第一版验收标准

- 游戏专用状态关系不需要写成Python条件分支；
- 规则由结构化数据表示并通过Schema和类型检查；
- 每个规则结论都能列出使用的事实和证据；
- 缺少关键证据时返回`UNKNOWN`；
- 被动相关关系不会直接冒充因果关系；
- 主动实验具有风险等级、预算、停止和恢复条件；
- 相同操作在不同上下文中可以生成不同规则版本；
- `ACTIVE`规则不会被运行时原地修改；
- 可执行计划固定所使用的全部规则和检测器版本；
- 规则编译不允许任意代码、无界循环和隐藏副作用；
- 截图、输入或游戏故障不会直接污染关系可靠性；
- 生成的计算公式可以离线重放、解释误差并安全回退。

## 35. 当前结论

界迹应把“关系网驱动执行”进一步收束为“证据驱动规则合成”：

```text
用户操作和游戏现象
-> 可复现事实
-> 关系与计算假设
-> 离线和受控实验
-> 版本化声明式规则
-> 确定性编译与执行
```

系统真正自行生成的是状态判定条件、关系边条件、数值公式、上下文范围和恢复候选；系统不能自行取消的是输入安全、证据追溯、版本固定、风险预算和用户授权。

这样既避免把每个游戏关系固化成手写函数，也避免让不可审计的动态代码直接控制游戏。
