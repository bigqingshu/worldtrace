# 游戏视觉反馈的分层判定与操作有效性确认

## 一、核心问题

操作后的“画面稳定”不能直接等同于“操作完成”。

游戏画面通常由多个视觉层叠加组成，这些层可能分别运动、暂停、出现或消失。例如：

- 大世界持续运动，但屏幕中心出现重要资源获取提示。
- 全屏展示获得物品时，大世界可能暂停。
- UI 页面切换结束后，主体界面已经稳定，但装饰动画仍在播放。
- 资源领取成功后，右侧数量变化，但背景场景仍在运动。

因此，更合理的判断方式是：

> 不判断整张画面是否稳定，而是判断与当前操作相关的视觉区域和状态是否进入预期状态。

---

## 二、画面分层

### 1. 大世界层

包括：

- 角色
- 场景
- NPC
- 天气
- 草木、水面
- 镜头运动
- 粒子特效

这部分即使用户没有操作，也可能一直运动，因此不能把“大世界持续变化”直接视为操作失败。

### 2. 固定 HUD 层

包括：

- 小地图
- 血条
- 技能图标
- 任务追踪
- 交互提示
- 道具快捷栏

这一层通常位置固定，适合判断：

- 是否回到可操作状态
- 某个按钮是否激活
- 某个提示是否出现或消失
- 某项资源数量是否变化

### 3. UI 交互层

包括：

- 背包
- 地图
- 菜单
- 副本界面
- 确认窗口
- 商店
- 任务列表

这类界面通常大面积覆盖大世界。动画结束后，主要 UI 区域会趋于稳定，适合通过页面模板和局部稳定时间判断。

### 4. 临时反馈层

包括：

- 全屏展示获得物品
- 屏幕中心出现重要资源图标
- 右侧出现普通拾取提示
- 奖励列表弹出
- 升级或成就动画
- 短暂获得提示

这一层可能覆盖 UI 或大世界，但不一定改变主流程状态。

---

## 三、不能只使用全屏稳定值

例如拾取重要物品后：

```text
大世界：仍在运动
屏幕中心：出现物品图标和文字
右侧资源数量：发生变化
```

如果只分析全屏差异，系统会认为画面一直不稳定。

更合理的判断是：

```text
中心反馈区域出现目标特征
→ 资源反馈保持一段时间
→ 图标开始消失
→ HUD 恢复正常
→ 判定拾取成功
```

反过来，全屏奖励展示可能是：

```text
大世界：完全时停
全屏奖励动画：持续变化
最终奖励页面稳定
```

此时大世界虽然稳定，但不能认为操作已经完成，因为奖励动画还没有结束。

因此需要判断：

```text
哪一层在变化
哪一层应该变化
哪一层稳定才代表完成
```

## 四、建立区域运动图

系统可以把画面划分为粗略区域：

```text
左上：小地图
右上：任务、货币或状态
左下：聊天或提示
右下：技能和操作提示
中心：角色、目标、重要反馈
全屏：弹窗、奖励和页面覆盖层
```

连续帧之间分别计算各区域变化程度，例如：

```text
中心区域变化：高
四周 HUD 变化：低
大世界背景变化：中
```

最终可以得到类似状态：

```json
{
  "大世界运动": true,
  "UI主体稳定": true,
  "中心反馈动画": true,
  "交互提示存在": false
}
```

第一版不一定需要语义分割，固定区域、帧差和模板识别就能够实现。

---

## 五、操作完成使用多证据确认

例如“点击领取”操作，不应只判断动画是否停止，而可以组合以下证据：

```text
领取按钮消失
+
奖励图标出现
+
资源数量变化
+
奖励动画最终稳定
```

可以给不同证据设置权重：

```text
按钮消失：0.3
奖励图标出现：0.3
资源数量变化：0.4
```

达到一定总分后，确认操作成功。

这样比单独依赖动画稳定更可靠。

## 六、反馈类型

### 1. 页面切换反馈

例如打开背包：

```text
旧页面特征消失
→ 页面切换动画
→ 背包页面特征出现
→ UI 区域连续稳定若干帧
```

完成条件重点是目标页面出现。

### 2. 状态修改反馈

例如切换装备：

```text
点击装备
→ 选中框变化
→ 属性值变化
→ 按钮变成“已装备”
```

完成条件重点是局部状态变化。

### 3. 数量反馈

例如领取资源：

```text
点击领取
→ 中心或右侧出现资源图标
→ 数量增加
```

即使大世界仍在运动，也可以确认成功。

### 4. 动画型反馈

例如抽奖、升级、剧情奖励：

```text
动画开始
→ 持续动态变化
→ 最终结果页稳定
→ 出现确认或关闭按钮
```

稳定时间有价值，但必须结合结果页特征。

### 5. 无明显视觉反馈

例如按键切换某种隐藏状态，可能只有角色动作略微变化。

此类操作可以结合：

- 多帧动作检测
- HUD 图标变化
- 再次操作验证
- 后续节点是否可执行

---

## 七、全屏物品展示

全屏物品展示可能具有以下特征：

- 背景变暗或模糊
- 屏幕中央出现大型物品图标
- 大世界暂停
- HUD 部分隐藏
- 出现“点击继续”或确认按键

可以将其识别为临时页面或覆盖层：

```text
临时状态：全屏奖励展示
```

处理方式：

```text
检测到全屏奖励覆盖层
→ 暂停主流程
→ 等待动画进入稳定
→ 检测继续提示
→ 执行继续
→ 等待覆盖层消失
→ 恢复主流程
```

---

## 八、中心重要资源提示

中心重要资源提示出现时，大世界可能继续运动。

可以将中心区域设置为短期事件监听：

```text
中心图标出现
→ 截取图标和文字
→ 记录资源获取事件
→ 不阻塞主流程或只短暂等待
```

如果该提示会遮挡准星或交互提示，可以等待其消失；如果不影响操作，则继续执行。

---

## 九、阻塞反馈与非阻塞反馈

### 1. 阻塞反馈

不处理就无法继续，例如：

- 全屏奖励展示
- 确认弹窗
- 剧情结果页面
- 加载界面
- 升级界面
- 错误提示

处理方式：

```text
暂停当前执行节点
→ 完成反馈处理
→ 再恢复
```

### 2. 非阻塞反馈

不会妨碍主流程，例如：

- 右侧获得物品提示
- 中心短暂资源图标
- 成就进度
- 任务进度更新
- 小型经验增加提示

处理方式：

```text
旁路记录
→ 不暂停主流程
```

临时反馈节点可以带属性：

```json
{
  "类型": "资源获取提示",
  "阻塞性": false,
  "持续时间": "约2秒",
  "检测区域": "屏幕中心",
  "对主流程影响": "无",
  "记录内容": ["物品名称", "数量"]
}
```

## 十、动画稳定时间作为辅助属性

稳定时间仍然很有价值，但不应作为唯一依据。

每个节点可以配置：

```text
最短等待时间
最大等待时间
目标区域
稳定持续时间
允许持续运动区域
必须出现的特征
必须消失的特征
```

例如打开背包：

```json
{
  "操作": "打开背包",
  "最短等待": 0.3,
  "最大等待": 5.0,
  "稳定检测区域": "UI主体",
  "允许运动区域": ["背景角色", "装饰特效"],
  "必须出现": "背包页面特征",
  "稳定持续时间": 0.4
}
```

例如拾取重要资源：

```json
{
  "操作": "拾取资源",
  "最大等待": 3.0,
  "反馈检测区域": ["屏幕中心", "右侧资源提示"],
  "允许大世界运动": true,
  "完成证据": [
    "资源图标出现",
    "物品名称出现",
    "交互提示消失"
  ]
}
```

## 十一、视觉状态采用组合形式

不要只分类为：

```text
游戏内
UI界面
```

可以允许多个状态同时存在，例如：

```text
基础状态：大世界
覆盖状态：重要物品获取提示
运动状态：大世界持续运动
输入状态：暂时允许移动
流程状态：拾取节点待确认
```

或者：

```text
基础状态：大世界
覆盖状态：全屏奖励展示
运动状态：大世界暂停
输入状态：只允许确认
流程状态：主流程暂停
```

可以理解为：

```text
最终视觉状态
=
基础页面
+
覆盖层
+
动画状态
+
交互权限
```

这种组合状态比单一状态机更适合现代游戏界面。

---

## 十二、独立反馈判定器

可以将反馈判断单独做成一层：

```text
操作执行器
    ↓
反馈判定器
    ├─ 页面特征
    ├─ 区域稳定性
    ├─ 局部动画
    ├─ 资源变化
    ├─ 临时覆盖层
    └─ 后续可操作性
    ↓
成功 / 失败 / 等待 / 被覆盖 / 结果不确定
```

反馈判定器不应只返回布尔值，最好返回结构化状态：

```json
{
  "状态": "被临时反馈覆盖",
  "基础页面": "大世界",
  "覆盖层": "重要资源获取",
  "是否阻塞": false,
  "操作是否可能成功": true,
  "建议": "继续主流程并旁路记录资源"
}
```

## 十三、核心结论

操作后的反馈不是单一画面变化，而是一组分层、局部、可能并行发生的视觉事件。

因此，反馈判断应从：

```text
等待整张画面稳定
```

升级为：

```text
识别基础页面
→ 判断覆盖层
→ 分析相关区域变化
→ 收集多项成功证据
→ 判断反馈是否阻塞
→ 决定继续、等待、处理覆盖层或重新验证
```

这样能够同时处理：

- UI 页面切换
- 大世界持续动画
- 全屏物品展示
- 中心资源提示
- 数量变化
- 非阻塞反馈
- 临时中断覆盖层

## 十四、当前架构复核与边界修正

> 本节是对前述开放构想的后续架构复核。原始案例继续保留，用于追溯想法来源；本节按照当前架构共识修正视觉观测、执行验证和运行调度之间的边界。
>
> 当前状态：`HYPOTHESIS`
>
> 综合分析见：[关系网规划优化与视觉反馈闭环分析](关系网规划优化与视觉反馈闭环分析.md)

### 1. 画面分层是观察模型，不是物理图层

大世界、HUD、UI和临时反馈已经被游戏合成为同一张截图。前文的分层方式适合帮助提出观察问题，但不能假定系统总能从像素中无歧义地分离这些层。

更适合实验的正交观察轴是：

```text
基础页面候选
+ 覆盖层候选及遮挡顺序
+ 区域运动观测
+ 持续时间和动画阶段
+ 对当前能力的影响候选
```

固定ROI（感兴趣区域）可以作为单游戏、固定分辨率下的实验基线，但ROI、模板和阈值必须绑定游戏版本、窗口客户区、DPI、分辨率、UI缩放、语言和布局Profile（布局配置档），不能提前视为通用规则。

### 2. 观测、操作评估和最终结果必须分开

“看到了什么”“当前操作是否完成”“下一步现在能否执行”和“调度器应该做什么”属于不同职责。推荐链路为：

```text
视觉观测
-> 页面候选、覆盖层、区域运动和VisualTokenEvent（图标变化事件）

操作反馈评估
-> 输入可能被接受、执行中、后置条件满足、存在矛盾或证据不足

StepAttempt（步骤尝试）协调
-> 结合输入投递、窗口身份、截止时间和验证规则

ExecutionOutcome（执行结果）
+ reason_code
+ FailureAttribution（失败归因）
+ SampleDisposition（样本处置）
```

视觉观察器只发布事实候选和证据，不直接发送按键，也不独立宣布最终失败归因。

公共`ExecutionOutcome`只允许：

```text
SUCCEEDED / FAILED / UNKNOWN / CANCELLED / BLOCKED
```

前文中的“等待”表示仍在收集证据，是过程状态；“被覆盖”是画面事实或`reason_code`；“结果不确定”对应`UNKNOWN`。它们不能组成另一套顶层结果枚举。

### 3. 多证据确认不能只做加权求和

按钮消失、图标出现和数量变化可能高度相关，也可能分别由遮挡、切页或并发奖励造成。简单相加会让多个弱证据掩盖必要后置条件的缺失。

后置条件规则应至少区分：

```text
有效性门禁
-> 帧新鲜、窗口正确、目标ROI可见、检测器适用

必需证据
-> 缺少时不得宣布成功

支持证据
-> 提高判断强度，但不能替代必需证据

反证
-> 与目标后置状态冲突

缺失、遮挡和超时
-> 根据输入是否可能已经生效返回UNKNOWN或相应终态
```

负证据只有在观测范围完整、截图健康、目标区域可见且规则适用时才成立。系统应保存各项原始分数和证据引用，不能只保存一个综合置信度。

### 4. 阻塞性取决于当前能力

同一个中心提示可能不影响读取背包，却会遮挡瞄准区域；同一个全屏奖励可能是领取动作的预期结果，也可能中断另一个操作。因此“阻塞”不是反馈类型的永久属性。

影响判断需要同时考虑：

- 覆盖区域和遮挡程度；
- 当前能力依赖的视觉区域；
- 当前能力占用的输入资源；
- 当前后置条件是否已经满足；
- 当前能力的中断与恢复策略版本。

还必须分开记录：

```text
本次操作是否已经成功
与
当前画面是否已经允许执行下一步
```

例如拾取已经成功，但提示仍遮挡准星时，原步骤可以是`SUCCEEDED`，后续依赖准星的能力仍暂时不可执行。

### 5. 中断、恢复和单次反馈不得覆盖运行事实

稳定的覆盖层类型可以形成定义，但某次提示出现只是一条运行观测或`VisualTokenEvent`，不应为每次临时反馈创建永久关系网节点。

发生真正中断时：

```text
原StepAttempt按已有证据结束
-> 可选RecoveryRun（独立恢复过程）或中断处理能力
-> 恢复后创建新的StepAttempt
```

恢复成功只表示重新获得可控状态，不能把原尝试改写为成功。视觉模块可以提供基础页面候选、覆盖层和运动观测；输入权限、暂停主流程、旁路还是恢复属于运行调度和策略判断。

### 6. 当前阶段的数据边界

当前`Trace Core`（轨迹核心）阶段不接入OCR、YOLO、CLIP、SAM或LLM。本文提到的物品名称、数量语义和复杂页面识别暂时不能成为第一阶段验收条件。

`Trace Core`首期只需可靠保存项目阶段路线已经规定的原始事实：

- 连续帧及唯一`frame_id`、时间戳和像素元数据；
- 原始按下、释放和鼠标事件，以及唯一`action_id`；
- 输入所作用的窗口身份；
- 输入前后帧、丢帧、旧帧和截图失败信息；
- 最近数秒错误现场和可重复离线回放的数据。

后续视觉反馈实验可以从这些原始事实派生或在第二阶段控制闭环中关联：

- 响应期、稳定期等细分时间窗；
- ROI派生图及其原始帧引用；
- 焦点代次和控制配置代次；
- `StepAttempt`、`ExecutionOutcome`和验证规则修订。

未来所有识别器必须消费统一帧流，不能各自临时截图。上述派生数据不是`Trace Core`首期完成标准。若文中的JSON示例以后提升为结构化配置或公共契约，配置键需要改为英文。

### 7. 当前最小实验

第一项实验只验证一个问题：

> 在大世界或装饰动画持续运动时，局部必需证据是否比全屏稳定更可靠地确认一个安全菜单已经打开？

固定一个游戏、窗口模式、分辨率和UI缩放，录制：

- 20次正常打开和返回；
- 10次无操作或无效输入对照；
- 若干旧帧、缺帧、遮挡和错误窗口样本。

离线比较：

```text
规则A：全屏达到稳定阈值

规则B：目标页面必需证据成立
     + 帧和窗口有效
     + 局部稳定只作辅助
```

预先冻结验收条件：

- 正常样本至少19/20在截止时间内确认后置条件；
- 无操作对照不得误判为`SUCCEEDED`；
- 旧帧、错误窗口和不可判定遮挡返回`UNKNOWN`或无效样本；
- 同一记录重复回放产生一致结果；
- 每项判断都能回溯到原始帧和规则修订。
