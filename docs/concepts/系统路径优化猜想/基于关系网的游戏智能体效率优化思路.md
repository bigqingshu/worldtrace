# 基于关系网的游戏智能体效率优化思路

## 一、核心方向

在形成 UI 关系网、物品关系网和操作关系网之后，系统不应只追求“能够完成目标”，还可以通过计算时间、资源、风险和成功率，选择更高效的执行方式。

整体思路是：

> 先确定能够完成目标的主流程，再利用物品、快捷操作、实时提示和历史统计，对主流程进行局部优化。

系统最终可以从“固定脚本执行器”逐渐发展为“具备局部最优决策能力的游戏助手”。

## 二、关系应分为三层

### 1. 主流程关系

主流程决定目标是否能够完成，例如：

```text
主界面
→ 打开地图
→ 传送至目标区域
→ 找到副本
→ 完成挑战
→ 领取奖励
```

这些关系构成任务骨架，不能被随意破坏。

### 2. 效率修饰关系

效率修饰关系不会改变最终目标，只改变执行成本。

例如：

```text
前往目标位置
  ├─ 步行：180秒
  ├─ 坐骑：90秒
  └─ 传送道具：20秒，消耗1个道具
```

又例如：

```text
完成战斗
  ├─ 正常战斗：120秒
  ├─ 使用增益道具：80秒
  └─ 使用扫荡券：5秒
```

这些关系适合附着在主流程节点或边上，而不是扩展为大量独立主流程。

### 3. 实时反应关系

实时反应关系用于处理不影响主任务结构、但能够提高效率的即时操作，例如：

- 出现“按 F 跳过”
- 出现“一键领取”
- 出现“再次挑战”
- 出现奖励弹窗
- 出现批量选择
- 加载完成
- 出现长按提示
- 意外进入其他界面

这类操作不需要重新调用大模型规划，应由低延迟反应层直接处理。

## 三、关系网可以减少计划时间

### 1. UI 路径直接计算

UI 页面之间可以建立固定跳转关系：

```text
主界面 → 菜单
菜单 → 背包
菜单 → 活动
活动 → 副本
地图 → 主界面
```

当系统知道当前页面和目标页面后，可以通过 BFS、Dijkstra 或 A* 直接计算路径，不需要让大模型重新推理。

例如：

```text
当前页面：地图
目标页面：背包

计算结果：
地图 → 主界面 → 菜单 → 背包
```

### 2. 缓存常用计划

常见目标可以保存为计划模板，例如：

- 完成每日任务
- 领取体力
- 进入材料副本
- 清理背包
- 领取活动奖励

再次执行时，只检查当前状态、资源数量和异常情况，不需要重新生成完整计划。

### 3. 只加载相关子图

当用户提出某个具体目标时，只需要查询与目标相关的关系，例如：

```text
目标材料
→ 获取来源
→ 对应副本
→ UI 入口
→ 体力消耗
→ 可使用道具
→ 可用加速方式
```

不需要把整个游戏关系网全部交给大模型。

## 四、建立统一执行成本

每个操作节点或关系边可以保存以下成本：

- 预计耗时
- 物品消耗
- 货币消耗
- 体力消耗
- 失败概率
- 识别难度
- 人工介入概率
- 大模型调用成本
- 可恢复性

可以通过综合评分选择方案：

```text
综合成本
=
时间权重 × 预计时间
+
资源权重 × 资源消耗
+
风险权重 × 失败概率
+
操作权重 × 操作次数
```

用户可以设置不同偏好：

- 优先节省时间
- 优先节省体力
- 不使用稀有物品
- 保留至少一定数量的扫荡券
- 活动结束前允许大量消耗
- 优先选择高成功率方案

## 五、物品关系网

物品关系网不应只保存物品名称和分类，还可以保存：

- 当前数量
- 来源
- 用途
- 稀有度
- 是否可补充
- 获取成本
- 默认保留数量
- 过期时间
- 作用目标
- 作用效果
- 使用条件
- 替代物品
- 冲突物品
- 使用后的收益变化

例如：

```text
双倍奖励券
  ├─ 作用于：材料副本
  ├─ 效果：奖励数量 ×2
  ├─ 消耗：每次1张
  ├─ 来源：周任务
  ├─ 默认保留：5张
  └─ 推荐使用：高体力收益副本
```

系统可以根据目标数量、当前库存、体力和道具数量进行普通计算，而不需要大模型进行数学推理。

## 六、建立独立实时反应层

实时反应层可以运行多个轻量观察器：

- 跳过提示观察器
- 奖励领取观察器
- 对话继续观察器
- 确认弹窗观察器
- 加载完成观察器
- 异常页面观察器
- 一键操作观察器

例如：

```text
检测到 F 跳过提示
→ 判断当前是否允许跳过
→ 判断短按或长按
→ 执行按键
→ 验证提示是否消失
→ 返回原流程
```

反应层只对当前流程进行修饰，不改变主计划。

## 七、长按与短按识别

### 1. 通过模板区分

保存不同提示模板：

- F
- 按 F
- 长按 F
- 按住 F
- 带进度圆环的 F

### 2. 通过 OCR 识别

识别提示文字，例如：

- 按 F 跳过
- 长按 F 跳过
- 按住 F
- 长按确认

### 3. 通过动态反馈判断

如果无法提前确定，可以让操作本身形成闭环：

```text
按下 F
→ 等待短时间
→ 提示立即消失：释放 F
→ 出现进度条：继续按住
→ 提示消失或进度完成：释放 F
```

### 4. 设置安全条件

不能只看到 F 就执行，因为 F 可能代表：

- 跳过
- 拾取
- 对话
- 确认
- 退出
- 交互

因此操作必须结合：

- 当前页面
- 当前任务
- 当前目标
- 提示位置
- 提示图标
- 附近文字

## 八、副属性附着在主流程关系上

例如主关系：

```text
剧情开始 → 剧情结束
```

附加属性：

```text
基础耗时：45秒
可跳过：是
跳过按键：F
按键方式：长按
跳过后耗时：2秒
跳过风险：低
禁止跳过条件：首次重要剧情
```

又例如：

```text
当前位置 → 目标位置
```

附加属性：

```text
步行：120秒
坐骑：60秒
传送：10秒，消耗传送道具1个
滑翔：45秒，需要高处起点
```

这样主流程保持简单，但规划器仍然可以比较不同执行方式。

## 九、机会型优化

执行过程中，系统可以识别一些原计划之外的低成本机会：

- 路过可领取奖励
- 附近存在任务物品
- 体力即将溢出
- 附近有同类采集点
- 限时增益即将结束
- 当前正好可以批量合成
- 当前页面存在顺手可完成的小任务

可以计算：

```text
额外收益 / 偏离成本
```

收益足够高时，临时插入小任务，完成后回到主计划。

需要限制：

- 最大偏离时间
- 最大插入次数
- 是否影响主目标
- 是否消耗关键资源
- 是否可能形成循环

## 十、动作等价关系

同一个目标状态可能存在多种操作方式，例如：

```text
关闭窗口
  ├─ 按 ESC
  ├─ 点击右上角 X
  └─ 点击空白区域
```

系统可以比较：

- 执行速度
- 识别难度
- 误操作风险
- 当前可用性
- 历史成功率

长期运行后可以记录实际成功率，并优先选择更稳定的方式。

## 十一、经验成本自学习

初期成本由人工估算：

```text
打开背包：2秒
传送：10秒
战斗：90秒
```

运行多次后改为真实统计：

```text
打开背包：
平均耗时：1.4秒
95%耗时：2.1秒以内
失败率：0.3%

进入副本：
平均耗时：7.8秒
波动范围：3～18秒
失败率：1.2%
```

还可以根据环境区分：

- 后台编译时
- 网络延迟较高时
- 游戏帧率较低时
- 磁盘繁忙时
- 不同分辨率下

系统最终选择的不是理论最短路径，而是当前环境下实际最优方案。

## 十二、推荐整体结构

```text
目标规划层
负责理解用户目标和生成任务骨架
        ↓
关系计算层
负责 UI 路径、物品需求、成本和方案比较
        ↓
执行节点层
负责确定性的截图、识别、输入和验证
        ↓
实时反应层
负责跳过、弹窗、领取、长按和异常处理
```

大模型主要负责：

- 理解模糊目标
- 选择总体策略
- 处理未知情况
- 必要时重新规划
- 解释推荐方案

普通程序主要负责：

- UI 最短路径
- 数量和成本计算
- 道具使用判断
- 快捷提示检测
- 长短按控制
- 节点执行
- 状态验证
- 成功率统计

## 十三、初期最值得加入的属性

第一版不必一次做得过于复杂，可以先给操作节点加入三个属性：

```text
预计耗时
历史成功率
是否存在快捷操作
```

后续再逐步扩展：

- 道具消耗
- 资源保留策略
- 机会型任务插入
- 动态成本统计
- 当前环境修正
- 多目标联合规划

最终关系网可以从：

```text
状态 A → 操作 → 状态 B
```

扩展为：

```text
状态 A
→ 存在多种操作可到达状态 B
→ 每种操作具有时间、资源、风险和前置条件
→ 执行过程中可以插入即时优化
```

这样形成的不只是操作记录，而是一个由游戏状态、能力、物品、资源和成本共同组成的决策网络。

## 十四、当前架构复核与边界修正

> 本节是对前述开放构想的后续架构复核。原始案例继续保留，用于追溯想法来源；本节按照当前架构共识修正模块边界，不把构想直接提升为正式契约。
>
> 当前状态：`HYPOTHESIS`
>
> 综合分析见：[关系网规划优化与视觉反馈闭环分析](关系网规划优化与视觉反馈闭环分析.md)

### 1. 推荐定位

本文适合作为规划优化视图，回答：

```text
在已经知道目标、可达关系和可用能力后，
怎样从多个可行方案中选择更合适的执行方案。
```

它不负责：

- 直接识别当前页面；
- 直接发送键鼠输入；
- 保存权威库存数量；
- 根据一次运行立即修改活动规则；
- 把地点图、状态图、能力调用图和运行记录合成一张万能关系网。

前文中的概念应按当前架构映射为：

| 原始概念 | 当前推荐归属 | 边界说明 |
| --- | --- | --- |
| 主流程关系 | `AbstractPlan`（抽象计划）、`StateDefinition`（状态定义）和`TransitionDefinition`（状态转换定义） | 表达目标骨架和状态可达性，不保存某次运行结果 |
| 效率修饰关系 | 多个`CapabilitySpec`（能力规格）及其条件统计 | 同一状态转换可以引用不同执行能力 |
| 实时反应关系 | 进度证据、备选能力、中断候选或恢复候选 | 不能统一视为一种图边 |
| 物品关系网 | `ItemCatalog`（物品知识目录）、`InventoryLedger`（库存实例账本）和`MaterialPlan`（材料计划） | 稳定知识、动态事实和未来计划分别保存 |
| 经验成本 | 从`RunStore`（运行记录存储）派生的只读统计视图 | 不能覆盖原始运行证据或直接改写活动能力 |

### 2. “实时反应关系”需要继续拆分

前文列出的实时现象实际包含不同语义：

```text
加载完成
-> 当前步骤的进度或后置条件证据

跳过、一键领取、再次挑战
-> 备选能力或有界机会候选

奖励弹窗、全屏展示
-> 目标操作的预期结果，或当前能力的中断候选

意外进入其他界面
-> 重新定位、重新规划或恢复候选
```

它们不能仅因“出现得很快”就由同一个低延迟层直接点击。观察逻辑只发布结构化证据或候选事件；是否暂停、旁路、恢复或执行新能力，由运行调度结合当前计划、输入所有权和用户授权决定。

### 3. 成本模型先处理硬约束

时间、普通资源、稀有物品、失败概率和不可逆后果没有天然统一单位。前文的综合成本可以保留为候选排序思路，但不能覆盖硬约束。

推荐顺序为：

```text
用户授权与安全门禁
-> 最低库存、不可逆操作等硬约束
-> 风险预算和恢复能力检查
-> 生成可行方案
-> 按时间、普通资源、条件可靠性和恢复代价排序
-> 固定具体版本并编译`ExecutablePlan`（可执行计划）
```

例如“不使用付费货币”或“至少保留一个稀有道具”必须直接淘汰不合规方案，不能因为节省时间而被其他权重抵消。

边成本也不应只保存一个常数。后续候选统计至少需要区分：

- 能力和规则修订版本；
- 前置状态和游戏Profile（游戏配置档）；
- 分辨率、帧率、网络等上下文；
- P50、P95、样本量和数据时间范围；
- 有效失败后的恢复代价；
- 统计所引用的原始运行证据。

### 4. 历史成功率必须经过归因和样本处置

一次`StepAttempt`（步骤尝试）的结果不能直接累计到“能力成功率”。完整链路应为：

```text
StepAttempt
-> ExecutionOutcome（执行结果）
-> FailureAttribution（失败归因）
-> SampleDisposition（样本处置）
-> 条件化耗时和可靠性统计
```

其中：

- `UNKNOWN`、`CANCELLED`和`BLOCKED`不能简单计为能力失败；
- 截图失败、旧帧、错误窗口和输入错投不能污染能力可靠性；
- 游戏故障、感知失败和执行器失败需要分别归因；
- 恢复成功不能把原失败尝试改写为成功；
- 小样本的偶然高成功率不能直接压过已有稳定能力。

“经验成本自学习”因此应理解为生成候选统计和候选规则版本，而不是在线原地修改活动关系：

```text
真实运行记录
-> 证据验证和样本隔离
-> 候选统计或规则修订
-> CANDIDATE
-> SHADOW
-> ACTIVE
```

已经生成的可执行计划必须固定所用图、能力、规则、检测器和校准版本。

### 5. 动作等价和机会任务需要更强条件

两个动作到达同一可见页面，不足以证明它们等价。动作等价还需要比较：

- 前置条件；
- 必需后置条件；
- 可见与隐藏副作用；
- 资源消耗；
- 可取消性和恢复方式；
- 对后续能力可用性的影响。

机会任务也不能只比较“额外收益/偏离成本”。每个机会候选至少需要：

- 进入条件和收益证据；
- 最大偏离时间与资源预算；
- 有效期、截止时间和幂等标识；
- 回归主计划的位置；
- 插入次数和循环上限；
- 用户授权与不可逆风险检查。

当前数量属于库存实例账本，不应保存在物品定义关系中。规划器只能读取带版本的库存和资源计划视图，不能维护第二份库存事实。

### 6. 计划缓存必须有失效条件

常用计划缓存可以减少重复计算，但缓存键不能只有起点和终点。至少还应考虑：

- 状态图、转换和能力修订；
- 规则、检测器和游戏Profile修订；
- 用户策略和风险预算；
- 库存基线与关键资源条件；
- 当前状态和上下文守卫。

任一关键版本或硬约束变化后，旧缓存只能作为候选参考，不能直接执行。

### 7. 当前最小实验

在`Trace Core`（轨迹核心）完成可靠记录和离线回放前，本文不进入完整规划器实现。可以先验证以下有界假设：

1. 在4至6个安全UI状态的小图上，确定性图搜索能够稳定生成可达路径。
2. 在留出运行样本上，条件化P95耗时是否比固定等待常量更能降低完成时间。
3. 对`ESC`、关闭按钮和点击空白区分别验证完整后置状态，判断它们是否真是等价能力。
4. 构造包含最低库存约束的反例，验证任何成本权重都不能选择违规路径。
5. 离线插入一个机会任务，验证偏离预算、幂等、防循环和返回主计划节点。

这里的“第一版属性”应理解为第一轮路径优化实验，而不是当前项目第一阶段。当前第一阶段仍只建设连续截图、键鼠记录、窗口身份、统一时间线、帧缓冲、证据保存和离线回放。
