## 1. 总体判断

两篇构想方向成立，而且彼此互补，但不应实现成一个同时规划、观察、判定和输入的“万能关系网”。

第一篇负责回答：

```text
有哪些可行路径和能力，
在当前约束下应该选择哪一种。
```

第二篇负责回答：

```text
一次输入之后实际出现了什么证据，
目标后置条件是否已经成立。
```

第二篇是第一篇的数据基础。如果视觉反馈和失败归因不可靠，历史耗时与成功率就会被错误样本污染，规划器只会越来越确信错误经验。

这组构想真正形成的是一个证据驱动的优化闭环：

```text
选择计划
-> 执行受控能力
-> 收集动作相关证据
-> 验证后置条件
-> 记录结果与失败归因
-> 处置统计样本
-> 生成候选成本和可靠性版本
-> 后续计划使用经过验证的统计
```

## 3. 推荐闭环

```text
用户目标
-> AbstractPlan（抽象计划），只描述目标骨架
-> 查询StateDefinition（状态定义）和TransitionDefinition（状态转换定义）
-> 为每次转换选择可用CapabilitySpec（能力规格）
-> 应用用户授权、资源、安全和不可逆操作等硬约束
-> 比较条件化耗时、可靠性、风险后果和恢复代价
-> 生成并固定ExecutablePlan（可执行计划）
-> runtime（运行调度）创建StepAttempt（步骤尝试）
-> 从统一连续帧中取得输入前后时间窗
-> 收集页面、覆盖层、局部变化和时序证据
-> 验证必需后置条件
-> ExecutionOutcome（执行结果）
-> FailureAttribution（失败归因）
-> SampleDisposition（样本处置）
-> RunStore（运行记录存储）派生条件化统计
-> 候选统计经离线与SHADOW验证后供后续计划使用
```

这条链路中，任何执行器只能证明“输入尝试已经提交”；只有新鲜、来源正确且满足规则的后置证据才能证明转换成功。

## 4. 必须分开的逻辑边界

### 4.1 定义层和运行层

```text
StateDefinition / TransitionDefinition / CapabilitySpec
-> 描述可以做什么和怎样尝试

PlanRun（计划运行） / CapabilityRun（能力运行）
/ StepAttempt / RecoveryRun（独立恢复过程）
-> 保存某次真实运行发生了什么
```

运行成功不能自动证明关系永久正确，运行失败也不能自动降低关系置信度。地点图、状态图、能力调用图和运行记录不得混入同一张图。

### 4.2 物品知识、库存和未来计划

```text
ItemCatalog（物品知识目录）
-> 相对稳定的种类、用途和来源知识

InventoryLedger（库存实例账本）
-> 当前数量、批次和库存变化事件

MaterialPlan（材料计划）
-> 未来需求、预留和可消耗额度
```

路径优化只能读取这些带版本的视图，不能维护第二份物品或库存事实。

### 4.3 视觉事实、能力判断和调度决策

```text
视觉事实
-> 看到了什么、哪里变化、是否被遮挡

能力验证
-> 当前能力的必需后置条件是否满足

运行调度
-> 是否等待、暂停、恢复、重新规划或执行另一能力
```

视觉观察器不能直接发送输入，也不能因为看到了弹窗就自行修改主计划。

### 4.4 活动规则和候选经验

真实运行数据只能追加原始事实。新的阈值、成本、关系和可靠性先形成候选版本，经离线和影子验证后才能发布；`ACTIVE`规则不可原地修改，已生成的可执行计划固定使用具体修订。

## 5. 关键修正结论

### 5.1 不能建立万能关系网

“主流程、物品、实时反应、动作替代和经验成本”是方便讨论的关系视角，不代表它们必须存入同一种图结构。统一查询不等于统一所有权。

### 5.2 硬约束不能被综合成本抵消

最低库存、付费货币、不可逆操作和用户授权必须先做可行性过滤。只有通过门禁的方案，才可以按时间、普通资源、可靠性和恢复代价排序。

### 5.3 历史成功率不是原始计数

能力可靠性必须绑定能力修订、前置状态、游戏Profile（游戏配置档）、环境上下文、样本量和时间范围。截图失败、错误窗口、输入错投和游戏故障不能混入能力失败分母。

### 5.4 动作等价需要比较副作用

到达同一可见页面只是必要条件之一。不同动作还可能改变焦点、选中项、历史栈、资源、动画阶段和后续可恢复性。

### 5.5 阻塞性是相对当前能力的判断

同一个覆盖层对不同能力可能产生不同影响。操作已经成功和下一步已经可执行也不是同一个时刻，必须分别判断。

### 5.6 多证据不能只做分数相加

后置条件需要区分有效性门禁、必需证据、支持证据、反证、遮挡、缺失和超时。若输入可能已经生效但证据不足，应保留`UNKNOWN`，不能用几个弱证据凑出成功。

### 5.7 过程状态不能扩展公共终态

公共`ExecutionOutcome`保持：

```text
SUCCEEDED / FAILED / UNKNOWN / CANCELLED / BLOCKED
```

等待是评估过程，被覆盖是视觉事实或`reason_code`，恢复过程使用独立`RecoveryRun`（独立恢复过程）。

## 6. 可证伪假设

| 假设编号 | 假设 | 支持证据 | 主要反证 |
| --- | --- | --- | --- |
| `HYP-PATH-001` | 操作相关ROI（感兴趣区域）的必需证据比全屏稳定更可靠地确认安全菜单打开 | 正常样本检出率更高，且无操作对照不增加误报 | 局部规则没有改善，或在遮挡和动画下产生更多伪成功 |
| `HYP-PATH-002` | 条件化P95耗时比固定等待更适合路径与等待策略 | 留出运行中总耗时下降，超时和误判不增加 | 统计不稳定，或环境切换后表现低于固定策略 |
| `HYP-PATH-003` | 同一后置条件的多个能力可以通过证据和运行统计稳定比较 | 能区分耗时、可靠性、副作用和适用上下文 | 所谓等价动作产生不同隐藏状态，无法共用目标契约 |
| `HYP-PATH-004` | 覆盖层影响可以根据当前能力依赖的ROI和输入资源判断 | 同一覆盖层对两个不同能力产生符合预期的不同影响 | 仅凭现有画面无法区分影响，或判断依赖不可观测内部状态 |
| `HYP-PATH-005` | 条件化可靠性比全局历史成功率更能预测下一次执行 | 正常和低帧率等上下文的留出校准更准确 | 样本不足或上下文切分导致估计更差 |

这些假设均未经过实验，不能写成系统已具备的能力。

## 7. 最小实验顺序

### 7.1 局部后置条件实验

固定一个游戏、窗口模式、分辨率和UI缩放，选择可逆菜单：

```text
基础HUD
-> 按键
-> 目标菜单
-> 返回基础HUD
```

采集20次正常打开、10次无操作或无效输入对照，并加入旧帧、缺帧、遮挡和错误窗口样本。离线比较全屏稳定与局部必需证据。

### 7.2 动作等价实验

分别使用`ESC`、关闭按钮和点击空白区域关闭同一安全页面，记录完整前后状态、耗时、失败、焦点和副作用，验证它们是否可以作为同一转换的多个能力。

### 7.3 小型UI图搜索实验

建立4至6个安全UI状态和两条可达路径，先验证BFS，再用留出数据中的P95耗时验证Dijkstra是否真的降低完成时间。BFS只适用于等权边，Dijkstra只适用于非负可加成本。

### 7.4 覆盖层影响实验

对同一段覆盖层记录配置两个虚拟能力：一个依赖被遮挡ROI，另一个不依赖。验证同一覆盖层能否产生不同影响判断。

### 7.5 条件可靠性实验

在正常帧率和低帧率上下文重复同一安全能力，使用留出样本比较条件化统计与全局成功率。样本必须先经过失败归因和样本处置。

### 7.6 机会任务实验

只在离线小图中注入一个可选任务，验证偏离预算、截止时间、幂等、防循环、资源门禁和返回主计划节点。此实验暂不操作真实稀有资源。

## 8. 对Trace Core的原始数据要求

以上实验不要求当前接入OCR、YOLO、CLIP、SAM或LLM。`Trace Core`（轨迹核心）首期按照项目阶段路线保存：

- 连续帧、唯一`frame_id`和统一单调时间；
- 每个输入的唯一`action_id`及键鼠原始事件；
- 输入所作用的窗口身份；
- 输入前帧、输入后帧、丢帧、旧帧和截图失败信息；
- 最近数秒错误现场；
- 能够重复离线回放的原始记录。

后续实验从这些事实派生或在第二阶段控制闭环中增加关联：

- 响应期、稳定期等细分时间窗；
- ROI派生图和对应原始帧引用；
- 焦点代次、输入租约和控制配置代次；
- `StepAttempt`、`ExecutionOutcome`及验证规则修订；
- 面向规则复现实验的完整版本清单。

在具备上述原始记录后，可以离线使用手工ROI、帧差、模板或人工标注构造实验基线。它们不是`Trace Core`首期验收项，也不代表未来正式视觉实现已经确定。

## 9. 当前不进入实现的内容

以下内容继续保留为开放构想，但不应进入当前第一阶段源码：

- 完整物品关系网和自动资源消耗策略；
- 实时自动领取、机会任务和复杂中断仲裁；
- 依赖OCR的物品名称和数量理解；
- 在线自动修改活动规则或路径权重；
- 跨游戏通用ROI、视觉层分离和成本模型；
- LLM直接决定输入成功、故障归因或底层操作。
