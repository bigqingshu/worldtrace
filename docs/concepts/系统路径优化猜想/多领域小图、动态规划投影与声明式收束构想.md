## 1. 核心问题

随着项目加入以下内容：

- 游戏内界面状态；
- 可配置功能和游戏设置；
- 物品、库存和多种获取方式；
- 与主游戏低耦合的独立小游戏；
- 外部账号登录和会话维护；
- 弹窗、掉线、输入错投和错误重试；
- 运行统计、失败归因和经验成本；

如果把它们都扩展到一张永久关系网中，关系网会同时承担定义、事实、库存、执行、恢复和历史记录。节点数量并不是唯一问题，更严重的是不同语义开始使用同一种节点和边，导致：

- 当前事实和永久定义互相污染；
- 同一登录、恢复或设置流程被复制到多个任务；
- 小游戏内部状态泄漏到主游戏规划；
- 当前库存和历史样本变成规划节点；
- 每个错误都产生一批重试边和循环；
- 图的任何局部修改都可能影响无关领域；
- 计划无法说明实际固定了哪些规则和能力版本。

因此，本构想不继续寻找一张更复杂的万能关系网，而是改变“主关系网”的定位。

## 2. 核心结论

> 统一的不是一张图，而是`CapabilitySpec`（能力规格）提供的能力契约。

> 主关系网不是永久事实数据库，而是根据当前状态、目标和约束临时生成的规划投影。

> 关系可以存在于目录、账本、规则和索引中，不代表所有关系都必须成为状态图的边。

推荐总体结构：

```text
永久保存：
分域状态和转换定义
+ 能力规格和局部图模块
+ 物品知识、获取规则和库存账本
+ 声明式规则和恢复策略
+ 运行记录和原始证据

按目标临时生成：
StateSnapshot（状态快照）
+ 用户目标
+ 当前账号、库存和策略
-> GraphRegistry（图注册表）查询相关能力
-> 生成当前目标的高层能力投影
-> PlanCompiler（计划编译器）固定准确修订
-> ExecutablePlan（可执行计划）
```

临时规划投影可以在计划结束后丢弃，但已生成的可执行计划及其版本清单、运行记录和非敏感证据必须保留。二维码、设备码、验证码、恢复码、令牌和其他认证秘密受单独的凭据不留存策略约束，不能因为“保留全部证据”而进入普通证据存储。

## 3. 永久资产和临时视图必须分开

### 3.1 永久定义

适合长期保存和版本化：

```text
StateDefinition（状态定义）
TransitionDefinition（状态转换定义）
CapabilitySpec
GraphModule（图模块）
RuleSpec（声明式规则规格）
RecoveryPolicy（故障恢复策略）
AcquisitionRule（物品获取规则）
```

这些对象描述“在什么上下文中可能做什么”，不是某次运行已经发生的事实。

### 3.2 权威事实和账本

适合由程序存储维护：

```text
ItemCatalog（物品知识目录）
InventoryLedger（库存实例账本）
账号、角色和区服作用域
当前会话事实
当前功能和设置投影
```

定义可以引用这些事实，但不能维护第二份互相竞争的副本。

### 3.3 运行记录和证据

某次真实执行继续使用：

```text
PlanRun（计划运行）
-> CapabilityRun（能力运行）
-> StepAttempt（步骤尝试）
-> 可选GraphCallRun（图调用运行）
-> 可选RecoveryRun（独立恢复过程）
```

运行记录不能被重新解释成永久图节点。恢复成功也不能覆盖原始失败或不确定尝试。

### 3.4 临时规划投影

临时投影只回答当前问题：

```text
当前状态下有哪些已发布能力可用
+ 哪些能力效果接近当前目标
+ 哪些资源、账号和时间条件满足
+ 哪些安全、授权和风险门禁允许
```

调整音量时，地图、战斗、物品和小游戏模块不进入高层搜索；获取活动代币时，也不需要加载全部设置和大世界导航关系。

## 4. 不同问题使用不同结构

| 领域 | 推荐结构 | 不应进入该结构的内容 |
| --- | --- | --- |
| 游戏界面可达性 | 因子化状态、状态图和页面转换 | 库存数量、账号凭据和运行历史 |
| 高层任务分解 | 复合能力和局部`GraphModule` | 原始截图和长期统计 |
| 可配置功能 | 功能清单、参数范围、依赖、冲突和能力引用 | 藏在开关后的任意脚本 |
| 游戏设置 | 参数化设置能力和当前值事实 | 为每个数值复制状态节点 |
| 物品知识和来源 | `ItemCatalog`和`AcquisitionRule` | 当前库存实例和小游戏内部状态 |
| 当前库存 | `InventoryLedger`追加事件和当前投影 | 页面路线和获取操作步骤 |
| 独立小游戏 | 封闭局部状态机或`GraphModule` | 主游戏全部页面和物品账本写权限 |
| 外部登录 | 独立认证流程、会话事实和受信适配器 | 密码、令牌、验证码和任意网络调用 |
| 错误恢复 | `RecoveryPolicy`和有限恢复能力 | 复制到每条转换上的重试循环 |
| 真实执行 | 运行记录和证据包 | 修改永久定义和活动规则 |

这是一套混合结构，不要求所有问题都使用图。

## 5. 因子化状态避免组合爆炸

不要为完整快照建立组合节点：

```text
背包页
+ 已登录
+ 活动开启
+ 音量60%
+ 账号A
+ 奖励弹窗出现
```

应保存独立、带命名空间的事实轴。以下仅为说明性示例，不是已经确定的配置Schema（模式）：

```yaml
account:
  session: AUTHENTICATED
  profile_ref: account.test_a

game:
  mode: GAMEPLAY

ui:
  page: INVENTORY
  overlays: []

settings:
  master_volume: 0.60

activity:
  rhythm_game_phase: IDLE

health:
  capture: HEALTHY
```

每个能力只读取自己声明的事实，并声明预期影响：

```text
打开背包
-> 关心game.mode、ui.page和ui.overlays
-> 不关心master_volume和小游戏阶段

设置音量
-> 关心ui.page和settings.master_volume
-> 不关心库存数量和活动奖励
```

无法观察的事实返回`UNKNOWN`，不能默认当成`FALSE`。否则某个模块缺少证据时，会被错误解释为条件不成立。

能力声明的`postconditions`和预期影响不是事实写权限。能力只能提交受控动作和提供证据引用；`StateSnapshot`、事实存储和各领域账本必须由其权威服务根据新观测、对账或正式命令更新。

## 6. 能力契约是唯一通用连接点

原子操作、复合UI流程、小游戏和登录流程都可以向外提供同一种能力外壳。候选字段可以包括：

```text
CapabilitySpec
├── capability_id
├── revision_id
├── parameters
├── preconditions
├── postconditions
├── preserved_facts
├── required_resources
├── authorization_policy
├── risk_level
├── idempotency
├── timeout_policy
├── verifier_ref
├── recovery_policy_ref
└── implementation_ref
```

调用者只需要知道：

- 需要什么参数和前置事实；
- 预期改变哪些事实；
- 哪些事实应保持不变；
- 会占用什么资源；
- 是否有不可逆副作用；
- 怎样验证结果；
- 可能返回哪些公共执行结果。

调用者不应知道被调用模块内部包含多少页面、按钮、等待、局部循环和恢复步骤。

`implementation_ref`只能是受信安装清单中预注册实现的不可执行ID。声明数据不能用它注册新实现，也不能填写Python模块、类路径、脚本、命令、文件路径或URL。编译器遇到未知、未安装、未授权或版本不匹配的实现引用必须拒绝编译。

复合能力只通过`graph_id + graph_revision`引用`GraphModule`，不能把子图复制进每个调用者。模块具有明确入口、出口、上下文、预算、超时和返回事实；模块内部变化不能要求所有主图调用点同步修改。

## 7. 各领域的具体落位

### 7.1 游戏内界面状态

UI状态图只保存稳定页面身份和可达转换：

```text
GAMEPLAY
-> BASE_MENU
-> INVENTORY / MAP / SETTINGS / ACTIVITY_HUB
```

覆盖层、焦点模式、加载状态和窗口健康作为正交事实，不与每个页面做笛卡尔积。

```text
ui.page = INVENTORY
ui.overlays = [REWARD_TOAST]
input.mode = CURSOR_UI
application.lifecycle = RUNNING
```

某次奖励提示只是一条运行观测，不创建永久页面节点。

### 7.2 可配置功能和游戏设置

需要区分两类“配置”。

WorldTrace自身的可选功能声明只描述：

- 是否暴露给当前游戏和账号；
- 参数类型、范围和默认值；
- 依赖、冲突和风险级别；
- 引用哪个已发布能力；
- 启用后需要哪些证据和授权。

功能开关不能藏入一段任意工作流，也不能引用Python类路径。

游戏内设置则使用参数化能力，而不是为每个值创建节点：

```text
set_setting(setting_id, target_value)
```

例如音量0至100应是一个有范围的连续或离散值，不是101个页面状态。适配信息负责说明控件位置、数值映射和验证方式。

### 7.3 物品和多种获取方式

`ItemCatalog`保存相对稳定的物品知识，`InventoryLedger`保存当前数量和库存变化事件，`AcquisitionRule`连接物品、来源、条件、成本和能力引用：

```text
AcquisitionRule
├── item_type_ref
├── source_type
├── prerequisite_facts
├── temporal_constraints
├── expected_quantity_or_range
├── cost_or_resource_requirements
├── provider_capability_ref
├── provenance
└── validation_status
```

同一个物品可以存在：

```text
地图采集
商店兑换
任务奖励
邮件领取
副本掉落
独立小游戏奖励
```

规划器查询可用来源并选择能力，但不能直接修改库存数量。奖励提示只能产生获取证据或库存事件候选，不能单独证明物品已经结算到正确账号。只有账号和角色作用域匹配的库存差量、完整对账或用户确认通过确定性校验后，库存服务才能追加正式库存事件。

### 7.4 低耦合独立小游戏

独立小游戏最适合成为封闭的“物品来源提供者”。它只向外提供：

```text
检查可用性
估计产出和成本
执行一次受控获取
返回奖励证据
返回约定锚点
```

主系统只增加一条获取规则，不展开小游戏内部流程。以下同样是说明性伪配置：

```yaml
source_id: activity.rhythm_game
item_type_ref: item.event_token
expected_quantity: 5
prerequisites:
  - account.session == AUTHENTICATED
  - activity.rhythm_game.available == true
provider_capability_ref: minigame.rhythm.acquire_reward
return_state_ref: ui.activity_hub
```

小游戏内部可以独立闭环：

```text
READY
-> STARTED
-> PLAYING
-> RESULT
-> CLAIMED
-> READY
```

它可以拥有自己的局部状态、临时货币、失败判断和有限恢复，但不能：

- 直接写入主库存账本；
- 跳转到主计划任意节点；
- 读取无关模块内部状态；
- 把恢复成功伪装成奖励获取成功；
- 将内部每一步暴露为主关系网节点。

若小游戏需要新的高频视觉反馈、物理控制或专用算法，可以由领域控制器或适配器实现，但主系统看到的能力契约保持不变。

### 7.5 外部账号登录

外部登录属于桌面、应用生命周期和认证领域，不属于游戏UI主图。主计划只应调用类似：

```text
ensure_authenticated(account_ref)
```

认证模块内部负责：

```text
检查现有会话
-> 必要时发起登录
-> 等待扫码、网页授权或用户确认
-> 验证账号和区服身份
-> 返回已认证会话事实
```

账号别名、平台、区服和角色可以成为作用域事实；密码、令牌、二维码、设备码、验证码和恢复码不能进入关系图、普通配置、持久化截图证据或日志。声明数据只能保存安全凭据别名或引用，真实秘密由受信凭据存储管理。

认证流程必须具有不可绕过的敏感采集边界：

- 在打开扫码、验证码、设备码或恢复码界面前，先切换到禁止持久化或经过验证的脱敏采集策略；
- 认证窗口或敏感ROI不得进入普通帧存储、缩略图、崩溃证据包、离线回放、模型输入、远程预览或调试导出；
- 进入和退出敏感阶段时清理相关帧环形缓冲和派生缓存；
- 只保存提供者ID、账号别名、阶段、时间、结果和原因码等脱敏审计事件；
- 意外出现无法可靠隔离的敏感页面时，立即停止持久化和下游分发，隔离并清除已捕获的敏感派生物；
- 无法在采集前建立可靠隔离时，该登录流程只能交给用户完成，不能进入自动录制或模型分析。

这里的二维码本身也按短期凭据处理，不能因为它表现为图像而进入普通视觉证据链。

遇到多因素认证（MFA）、验证码、扫码确认或权限授权时，应返回：

```text
BLOCKED
+ reason_code: USER_INTERACTION_REQUIRED
```

系统不能通过高频重试绕过用户操作、访问限制或平台安全措施。测试账号和正式账号的库存、计划、批准、运行记录及统计必须隔离。

### 7.6 错误重试和恢复

错误重试不能表示成复制到每条转换上的普通回边。推荐链路为：

```text
StepAttempt
-> ExecutionOutcome（执行结果）
-> reason_code
-> FailureAttribution（失败归因）
-> SampleDisposition（样本处置）
-> 选择适用RecoveryPolicy
-> 独立RecoveryRun
-> 重新观察真实状态
-> 创建新的StepAttempt、重新规划或停止
```

`RecoveryPolicy`用声明数据描述：

- 适用的结果、原因码和上下文；
- 可调用的已注册恢复能力；
- 最大次数、总时限和退避；
- 进展条件、停止条件和升级条件；
- 是否要求操作幂等；
- 结果不确定时是否允许重新输入；
- 风险和用户授权门禁。

说明性策略示例：

```yaml
match:
  outcome: UNKNOWN
  reason_code: CAPTURE_FAILED
  side_effect_state: POSSIBLE

actions:
  - capability_ref: system.reobserve

constraints:
  max_attempts: 1
  replay_original_input: false
```

不同故障必须区别处理：

```text
输入尚未发送
-> 可以在预算内创建新尝试

输入可能已经生效但后置证据丢失
-> 先重新观察，禁止盲目重放输入

窗口或输入归属变化
-> 恢复输入归属，再创建新尝试

网络瞬态失败
-> 在服务器限制和退避预算内处理

购买、删除、消耗、领取或账号切换结果UNKNOWN
-> 先对账或请求用户判断，不自动重试
```

恢复完成只表示系统重新获得可控状态，不能把原`StepAttempt`改成`SUCCEEDED`。

## 8. 尽量不写游戏专用逻辑

本构想中的“尽量不写代码逻辑”应定义为：

> 新增已知模式的页面、物品、获取方式、局部流程和恢复策略时，不新增游戏专用Python分支。

它不表示系统完全没有固定程序，也不表示所有算法都应写进YAML。

### 8.1 三类受限声明

#### 纯计算谓词

使用`ExpressionGraph`（有类型的计算表达式图）组合事实和证据：

```text
输入事实和证据
-> 白名单归一化、比较、布尔、时间和聚合算子
-> TRUE / FALSE / UNKNOWN或数值结果
```

谓词没有副作用，不能发送输入、修改账本或调用网络。

#### 有界工作流

`GraphModule`只允许有限控制结构：

```text
sequence
call_registered_capability
select_or_branch
wait_until(timeout)
repeat(max_count)
return
```

动作只能引用已注册`CapabilitySpec`。每个等待、循环和模块调用都必须有超时、次数或总成本边界。

#### 策略声明

策略负责：

- 适用条件；
- 用户授权和危险动作门禁；
- 资源预算和保留量；
- 候选能力排序；
- 重试预算、退避、升级和停止；
- 需要用户接管的位置。

策略只能收紧安全限制，不能取消输入归属、全局停止、危险动作授权和硬预算。

### 8.2 YAML和JSON不是语义模型

YAML或JSON只作为人和工具编辑声明的格式。加载后必须经过Schema和语义校验，编译为有类型、版本固定的内部结构。

编译检查至少包括：

- 字段类型、单位和作用域；
- 引用是否存在且版本兼容；
- `implementation_ref`是否来自受信安装清单中的白名单ID；
- 定义依赖是否形成允许的DAG；
- 是否存在无界循环或递归；
- 是否声明所有超时和动作预算；
- 资源占用和能力调用是否冲突；
- 副作用、幂等性和验证要求是否一致；
- `UNKNOWN`时是否存在安全停止路径；
- 危险动作是否需要用户授权；
- 最大可能输入次数和最大运行时间是否可计算。

### 8.3 固定小内核和窄适配器

固定程序负责：

```text
截图、键鼠、窗口、时间线和存储
类型与Schema校验
白名单基础算子
规则求值和确定性编译
资源租约、安全停止和授权
Registry查询、运行调度和证据记录
```

声明数据负责：

```text
页面和状态规则
状态之间的能力引用
参数范围和适用条件
物品获取方式
局部有界工作流
恢复策略和预算
游戏、版本和布局差异
```

以下情况仍然需要窄代码边界：

- 新截图、视觉、设备或窗口事实提取器；
- 新键鼠、平台、OAuth、网络协议和第三方SDK；
- 凭据、加密和账号安全；
- 高频闭环、连续控制和性能敏感算法；
- 具有事务性或不可逆副作用的原子动作；
- 现有白名单算子无法明确、可测试地表达的新算法。

这时应增加一个输入输出明确的基础算子、原子能力、连续控制器或适配器，而不是让适配器接管全局编排。

### 8.4 硬禁止项和声明式停止线

以下内容属于无条件拒绝项，不能通过拆分配置或增加`GraphModule`绕过：

- 任意变量赋值；
- `while`或无界循环；
- 用户自定义函数和递归；
- `eval`、`exec`、脚本片段、动态导入、类路径和系统命令；
- Jinja或其他能够执行逻辑的模板；
- 任意文件、URL或网络访问；
- 由声明数据注册实现、插件、算子或外部协议；
- 绕过受信安装清单解析`implementation_ref`；
- 在谓词和规则求值中直接产生键鼠、账本、文件或网络副作用；
- `before`、`after`等隐藏执行钩子。

如果确实需要新的协议、算法或基础算子，必须在声明系统之外实现为窄的受信代码，经过安装注册、类型校验、安全审查和版本发布后，声明才能引用其白名单ID。

以下现象属于复杂度停止信号，说明当前声明应拆成更小模块或重新审查抽象：

- 大量字符串拼接生成动态标识符；
- 多层继承、深度覆盖和隐式优先级；
- 十几层难以解释的`all_of`和`any_of`嵌套。

出现复杂度停止信号时，应拆成更小的`GraphModule`，或者承认系统缺少一个可复用基础算子并将其放入实验。硬禁止项则必须直接拒绝，不能继续扩展成另一种更难调试的通用编程语言。

纯声明式表达一个行为需要同时满足：

1. 所需事实已经存在并具有来源；
2. 所有副作用都由已注册能力承担；
3. 流程存在明确次数、时间和资源上限；
4. 结果具有可执行的验证规则。

任一条件不满足，该行为就不能仅靠声明安全落地。

## 9. 版本、加载和发布

所有定义使用稳定语义ID和不可变修订：

```text
capability_id + capability_revision
graph_id + graph_revision
rule_id + rule_revision
policy_id + policy_revision
profile_id + profile_revision
```

推荐加载过程：

```text
启动
-> 只加载Registry元数据和索引

规划
-> 根据StateSnapshot、目标、账号作用域和风险预算
-> 生成相关能力的临时投影

编译
-> 加载选中能力及其传递依赖
-> 校验引用、资源、循环、超时和授权
-> 固定全部准确修订

执行
-> 只使用已固定版本
-> 不因Registry发布新版本而中途切换
```

历史修订只在回放和审计时按需加载。`CANDIDATE`和`SHADOW`内容不进入普通自动规划；`ACTIVE`规则不可原地修改。缓存键必须包含完整版本锁指纹，任何规则、能力或Profile（配置档）变化后不能误用旧编译产物。

## 10. 完整调用示例

假设用户目标是：

```text
每日获得5个活动代币
```

系统可以执行：

```text
读取当前账号和角色作用域
-> InventoryLedger计算活动代币缺口
-> ItemCatalog和AcquisitionRule返回可用来源
   ├── 地图采集
   ├── 商店兑换
   └── 节奏小游戏
-> 应用活动时间、库存预留、资源和用户授权硬门禁
-> 选择小游戏提供的获取能力
-> 确保外部账号会话有效
-> 打开活动入口
-> 调用minigame.rhythm.acquire_reward(quantity=5)
-> 小游戏内部完成自身闭环
-> 奖励提示生成获取证据和库存事件候选
-> 验证账号作用域和库存实际差量
-> 对账通过后由库存服务追加正式库存事件
-> 返回约定UI锚点
```

主计划只看到少量高层能力：

```text
ensure_authenticated
open_activity_hub
acquire_reward
verify_inventory_delta
return_to_anchor
```

它看不到小游戏的开始、游玩和结算节点，也不读取认证模块内部会话缓存。物品系统只知道小游戏是一个候选来源，不直接调用小游戏内部节点。错误恢复由当前失败归因选择，不能由获取规则自行重复输入。

这个例子体现了低耦合关系：

```text
物品系统
-> 知道该能力可能产生什么物品

小游戏模块
-> 知道怎样尝试获得奖励

库存服务和账本
-> 在账号绑定的差量或对账通过后追加实际变化

认证模块
-> 确认当前会话属于哪个账号

恢复策略
-> 决定失败后能否安全再次尝试
```

## 11. 最小文档模型

当前不应立即设计覆盖所有游戏的完整DSL。可以先建立一个纯文档玩具模型：

```text
4个UI状态
+ 1个参数化设置项
+ 1种物品
+ 2种获取来源
   └── 其中1种来自独立小游戏
+ 1个模拟外部登录流程
+ 3类故障
   ├── 截图失败
   ├── 会话过期
   └── 输入可能生效但验证缺失
```

先验证以下问题：

- 是否能只通过稳定ID引用组合完整目标；
- 主规划投影是否不暴露小游戏内部节点；
- 当前库存是否只存在于账本；
- 密码和令牌是否完全不进入声明和证据；
- 二维码、设备码和验证码是否不会进入环形缓冲持久化、崩溃包、模型输入和调试导出；
- 奖励提示是否只能生成候选，不能绕过账号绑定和库存对账直接写账；
- 所有实现引用是否只能解析受信安装清单中的白名单ID；
- 每个循环、等待和重试是否具有静态上限；
- 购买、领取等非幂等操作出现`UNKNOWN`时是否停止盲重试；
- 编译前能否解释最大输入次数、资源风险和所有停止路径；
- 修改小游戏内部图时，主物品获取规则是否无需同步改写。

这个玩具模型通过后，再根据真实录制数据决定最小字段和基础算子。不要先预建一个覆盖所有未来情况的巨大Schema。

## 12. 与当前阶段的关系

当前第一阶段仍是`Trace Core`（轨迹核心）：

```text
连续截图
+ 键鼠记录
+ 窗口身份
+ 统一单调时间线
+ 帧缓冲
+ 证据保存
+ 离线回放
```

本构想不要求第一阶段实现`GraphRegistry`、规则编译器、规划器、登录模块、小游戏执行器或恢复引擎。`Trace Core`只需为未来实验保留可靠原始事实，但认证秘密和其他敏感内容必须服从更高优先级的不留存与脱敏策略，不能进入普通原始证据集。

后续应按以下顺序逐步验证：

```text
Trace Core可靠记录
-> 离线手工状态和规则
-> 一个安全UI往返
-> 一个参数化设置能力
-> 一种物品的两种获取来源
-> 一个封闭小游戏模块
-> 模拟登录和恢复策略
-> 当前目标的动态规划投影
```

每一步都先在录制数据、模拟环境或测试账号中验证，不把未经验证的声明直接提升为`ACTIVE`。

## 13. 当前结论

关系网膨胀不能靠删除细节解决，因为这些细节仍然需要被保存和验证。正确做法是将细节放回各自的结构和所有权边界：

```text
界面可达性
-> 小型状态图

操作方法
-> CapabilitySpec和GraphModule

物品知识与来源
-> ItemCatalog和AcquisitionRule

当前库存
-> InventoryLedger

外部登录
-> 独立认证流程和受信适配器

错误重试
-> RecoveryPolicy和独立RecoveryRun

某次真实发生的事情
-> 运行记录和证据

当前目标需要看到的关系
-> 按目标临时生成的规划投影
```

最终目标不是消灭代码，而是让代码规模随基础能力种类增长，而不是随游戏页面、物品数量、获取方式和错误案例数量增长。

> 主图是一张按需生成的路线图，不是保存整个世界全部事实的仓库；系统统一的是能力契约、证据语义和安全边界，而不是一种万能数据结构。
