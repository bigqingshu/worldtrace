## 1. 核心目标

材料规划首先解决的不是复杂优化，而是把以下问题可靠地连接起来：

```text
用户想获得什么
当前已经拥有什么
还缺少多少
可以通过哪些方式获得
每种方式消耗什么
需要多少轮、多少现实时间或游戏时间
哪些材料必须保留
用户是否已经确认允许消耗
游戏内实际是否发生了消耗或获得
```

大多数基础材料计划只需要：

```text
加法
减法
乘法
除法
向上取整
简单时间排程
```

第一版不需要先建立复杂求解器。真正重要的是数量来源、取整规则、计划版本、审核结果和实际执行证据都能够追溯。

## 2. 计划和真实事件必须分开

最重要的原则是：

> 计划中预计消耗某种材料，不代表库存账本已经发生消耗。

建议区分：

```text
PlannedConsumption
-> 计划准备消耗什么

ExecutionIntent
-> 用户已经允许系统尝试执行什么

StepAttempt
-> 系统实际尝试了哪个操作

InventoryEvent
-> 游戏画面和库存证据确认发生了什么
```

只有满足以下过程后，才能写入真实消耗事件：

```text
用户确认计划
-> 用户主动启动执行
-> 执行前重新检查
-> 游戏内完成兑换、合成或消耗
-> 后置证据确认数量变化
-> 生成InventoryEvent
```

计划取消、暂停或执行失败时，不能凭计划内容修改实际库存。

## 3. 总体数据流

```text
ItemCatalog物品知识
+ InventoryLedger当前库存
+ AcquisitionRule获取规则
+ TemporalRule时间规则
+ 用户目标与限制
-> ResourcePlanner资源规划器
-> MaterialPlan材料计划
-> DeterministicValidator确定性校验
-> AIReviewReport人工智能审核报告
-> UserApproval用户批准
-> ExecutableMaterialPlan可执行材料计划
-> StepAttempt与运行证据
-> InventoryEvent实际库存事件
-> 重新对账和更新计划
```

AI审核位于计划生成和用户确认之间，不直接修改库存，也不能替代用户对消耗行为的授权。

## 4. `MaterialGoal`

用户目标需要比“我要100个材料”更完整：

```text
MaterialGoal
├── goal_id
├── target_items
├── target_quantities
├── deadline
├── preferred_acquisition_methods
├── excluded_acquisition_methods
├── maximum_gameplay_time
├── maximum_real_world_wait
├── maximum_currency_cost
├── protected_items
├── allow_random_yield
├── risk_preference
└── user_notes
```

用户可以只填写物品和数量，其余字段使用明确默认值。系统不能把缺失限制默认为“允许无限消耗”。

计划必须固定所使用的库存快照、兑换规则、获取规则、刷新规则和公式版本。否则同一个计划在不同时间重新计算时可能悄悄改变含义。

## 6. 材料需求图

目标物品可能依赖多层合成、兑换或制作：

```text
目标装备
-> 需要高级材料A
-> 高级材料A需要3个中级材料B
-> 中级材料B需要3个基础材料C
```

建议生成`MaterialRequirementGraph`：

```text
MaterialRequirementGraph
├── goal_nodes
├── item_nodes
├── conversion_edges
├── required_quantities
├── owned_offsets
├── reserved_offsets
├── protected_minimums
└── unresolved_requirements
```

需求图是计划计算结构，不等同于游戏状态图，也不应把每次实际消耗写回定义边。

## 7. 基础数量计算

### 7.1 缺口

```text
usable_owned
= confirmed_inventory
- reservations_for_other_plans
- protected_minimum

shortage
= max(0, target_quantity - usable_owned - confirmed_incoming)
```

`confirmed_incoming`只包含已经确认会获得的数量。尚未执行的随机掉落不能当作确定库存。

### 7.2 批次和取整

```text
batches
= ceil(shortage / output_per_batch)

required_input
= batches × input_per_batch

actual_output
= batches × output_per_batch
```

向上取整必须显式保存，因为很多兑换和合成不能执行半批。

### 7.3 多层展开

```text
required_base_material
= parent_batches × child_input_per_parent
```

每层都需要先进行批次取整，不能只在最终结果上统一取整。

### 7.4 数值类型

数量优先使用整数。货币、小数比例和时间使用`Decimal`、定点数或有理数。避免普通二进制浮点误差影响兑换批次和边界判断。

## 9. OCR数值只能作为观测

商店价格、库存数量、剩余兑换次数和生产时间可以由OCR读取，但OCR结果不能直接成为永久规则。

```text
ObservedNumericValue
├── raw_text
├── parsed_value
├── unit
├── frame_id
├── roi_ref
├── ocr_confidence
├── parser_version
├── temporal_context
└── evidence_ids
```

执行资源消耗前应检查：

- 多帧结果是否一致；
- 数值是否为非负整数或允许的小数；
- 是否落在已知合理范围；
- 数量、价格和按钮状态是否来自同一界面版本；
- 当前界面是否存在遮挡、动画或焦点异常；
- OCR结果是否与库存差分相互印证。

用户可以手动覆盖OCR结果，但必须记录`USER_OVERRIDE`来源，不能静默替换原始观测。

## 10. 库存基线

每个计划绑定一个`InventoryBaseline`：

```text
InventoryBaseline
├── inventory_snapshot_ref
├── account_profile_id
├── character_or_save_scope
├── captured_at
├── scan_coverage
├── quantity_confidences
└── unresolved_items
```

库存扫描不完整时，系统可以生成草案，但不能把未知数量当作零。计划应明确显示哪些需求仍依赖用户确认或重新扫描。

## 11. 资源预留和最低保留量

多个计划不能同时承诺使用同一批材料。

```text
Reservation
├── reservation_id
├── plan_id与version
├── item_type_id或instance_ref
├── reserved_quantity
├── priority
├── expires_at
└── status
```

可支配数量：

```text
available_quantity
= confirmed_quantity
- active_reservations
- protected_minimum
```

`protected_minimum`由用户设置，例如始终保留10个稀有材料。AI可以提醒保护值过低，但不能自行取消。

预留不是实际消耗。计划取消、版本失效或过期后必须释放预留。

## 12. 计划状态必须拆轴

计划生命周期、审核状态和用户批准不能压成一个状态字段。

```text
PlanLifecycle
-> DRAFT / READY / EXECUTING / PAUSED / COMPLETED / CANCELLED

ReviewStatus
-> NOT_REVIEWED / PASSED / WARNINGS / BLOCKED / STALE

ApprovalStatus
-> NOT_APPROVED / USER_APPROVED / REVOKED
```

计划处于`READY`不代表用户已经批准；AI审核为`PASSED`也不代表可以执行。

## 13. 用户修改计划

用户可以直接修改：

- 目标数量；
- 允许消耗的材料；
- 最低保留量；
- 截止时间；
- 允许的获取方式；
- 是否接受随机产出；
- 最大游玩时间或货币成本；
- 各步骤优先级。

任何影响数量、时间或消耗的修改都必须：

```text
创建新的plan_version
-> 重新计算完整需求图
-> 重新检查库存和预留
-> 旧ReviewStatus变为STALE
-> 旧ApprovalStatus变为REVOKED
-> 重新生成变更摘要
-> 重新审核和确认
```

不能在用户已经批准后悄悄修改同一个版本。

## 14. 确定性校验

`DeterministicValidator`负责可以明确计算的内容：

- 加减乘除和批次取整；
- 需求图是否存在循环；
- 数量是否为负数或超出范围；
- 库存和预留是否重复占用；
- 商店兑换上限是否足够；
- 时间窗口是否数学上可满足；
- 使用的规则版本是否存在；
- 必要前置材料是否完整；
- 最大预算是否被突破；
- 计划是否引用了失效库存快照。

确定性校验结果包含可复算明细，AI不能替代这一步。

## 15. AI审核

AI适合发现结构计算不容易表达的问题：

- 是否漏掉说明文本中的隐含前置条件；
- 是否误用稀有、活动限定或不可再生材料；
- 是否存在更省时间或更省材料的路径；
- 是否把预期掉落当成保证掉落；
- 是否引用了过时攻略或旧版本价格；
- 截止时间是否虽然可算，但实际操作负担不合理；
- 用户修改是否偏离原目标；
- 是否存在不可逆操作或测试账号要求；
- 哪些假设需要用户再次确认。

建议输出：

```text
AIReviewReport
├── plan_id与version
├── reviewer_model_id
├── reviewed_rule_versions
├── findings
├── unresolved_questions
├── recommended_changes
├── source_refs
└── created_at
```

每个`ReviewFinding`包含：

```text
severity
category
message
affected_step_refs
evidence_or_source_refs
suggested_fix
```

AI审核可以提出`WARNINGS`或建议阻止，但最终用户批准与确定性安全门禁保持独立。

## 16. 用户批准和执行授权

用户确认的是一个不可变计划版本及其最大资源边界：

```text
UserApproval
├── plan_id与version
├── approved_account_profile_id
├── approved_consumption_limits
├── approved_currency_limit
├── approved_risk_class
├── expires_at
└── approval_evidence
```

批准计划不等于立即运行。系统还需要用户主动点击执行或发出明确执行命令。

如果执行需要超出批准上限，必须停止并请求新的计划版本和批准。

## 17. 执行前检查

每次开始执行前进行`ExecutionPreflight`：

```text
当前窗口和游戏实例正确
当前账号、区服和角色匹配
当前库存没有超出允许偏差
商店价格和兑换上限没有变化
时间窗口仍然有效
相关按钮和功能可用
输入焦点和截图健康
用户批准没有过期或撤销
```

不满足时产生`PLAN_DRIFT`或其他明确原因，并暂停执行。

## 18. 计划漂移

计划生成后可能发生：

- 用户手动消耗或获得材料；
- 商店价格或剩余次数改变；
- 活动结束或刷新；
- 物品规则被新版本替换；
- OCR重新识别出不同库存；
- 其他计划占用了资源；
- 用户切换账号、角色或区服。

```text
PlanDrift
├── drift_type
├── expected_value
├── observed_value
├── affected_steps
├── severity
├── evidence_ids
└── recommended_action
```

轻微且位于批准容差内的变化可以重新计算；会改变消耗种类、数量上限或风险等级的变化必须重新审核和批准。

## 19. 实际执行和库存事件

每次兑换、制作和采集仍然是独立`StepAttempt`：

```text
执行前数量
-> 操作
-> 输入接受证据
-> 界面结果证据
-> 执行后数量
-> 对账
-> InventoryEvent
```

可能结果：

```text
SUCCEEDED
FAILED
UNKNOWN
CANCELLED
BLOCKED
```

如果按钮动画发生但库存数量无法确认，只能记录输入可能被接受和结果`UNKNOWN`，不能直接扣减账本。

## 20. 时间和来源排程

材料来源可统一描述为`SourceSchedule`：

```text
SourceSchedule
├── source_id
├── obtainable_items
├── yield_per_cycle_or_distribution
├── capacity
├── duration
├── respawn_rule
├── clock_domain
├── availability_window
├── required_capabilities
├── route_or_operation_time
├── resource_cost
└── evidence_ids
```

计划器根据来源时间、容量和用户限制估算完成时间。

## 21. 家园种植

家园种植通常是简单且适合第一批验证的排程问题：

```text
HomePlantingRule
├── plot_type
├── plot_capacity
├── seed_cost
├── growth_duration
├── yield_per_plot
├── harvest_window
├── acceleration_options
├── replant_requirement
└── clock_domain
```

基础计算：

```text
required_plots
= ceil(shortage / yield_per_plot)

cycles
= ceil(required_plots / available_plot_capacity)

earliest_completion
= start_time + cycles × growth_duration
```

如果不同批次可以并行，应按地块容量建立时间槽，而不是简单把全部时长相加。

## 22. 大世界采集点

```text
GatheringSource
├── item_type_id
├── map_space_id
├── place_anchor_or_area_refs
├── expected_quantity_range
├── respawn_rule
├── server_region
├── route_ref
├── route_duration_estimate
├── collection_capability_ref
└── last_confirmed_collection_at
```

基础估算：

```text
guaranteed_or_conservative_yield_per_round
expected_yield_per_round
route_duration
next_available_time
```

如果刷新规则不确定，计划需要给出范围而不是虚构精确时间。

## 23. 商店、副本和体力资源

商店来源受以下条件限制：

```text
价格
库存上限
每日、每周或活动重置
前置任务
货币余额
```

副本和体力来源还需要：

```text
每次消耗
每次产出范围
每日恢复量
上限溢出
开放日期
挑战时间
失败或额外掉落概率
```

这些仍然可以先使用简单规则和时间表，不需要立刻引入通用优化器。

## 24. 不确定产出

掉落、采集和额外奖励可能是随机的。计划应分别提供：

```text
guaranteed_quantity
expected_quantity
conservative_quantity
optimistic_quantity
confidence_interval或经验范围
```

完成时间也应表达为：

```text
earliest_completion
expected_completion
conservative_completion
```

用户可以选择偏好：

```text
GUARANTEED_ONLY
CONSERVATIVE
EXPECTED_VALUE
RISK_ACCEPTING
```

AI不能把平均掉落数量表述为保证产出。

## 25. 规划算法分级

### 25.1 第一版

```text
需求展开
简单优先级
加减乘除
批次取整
按刷新时间排序
```

### 25.2 中期

当同一材料存在多种来源时，可以按以下目标选择：

```text
最少现实等待
最少游戏操作时间
最少稀有资源消耗
最少路线距离
最高确定性
```

### 25.3 后期

当目标、来源、容量和时间窗口很多时，再考虑约束求解、线性规划或整数规划。规划器输出仍然必须回到可解释的`MaterialPlan`，不能只返回黑盒最优值。

## 26. 风险策略

```text
RiskPolicy
├── allowed_action_classes
├── protected_item_rules
├── maximum_single_transaction
├── maximum_plan_consumption
├── irreversible_action_policy
├── paid_currency_policy
├── account_environment_policy
└── user_confirmation_policy
```

至少禁止系统未经额外确认执行：

- 出售或分解稀有物品；
- 消耗付费货币；
- 使用不可再生活动材料；
- 修改会影响账号安全的设置；
- 执行不可逆剧情选择；
- 超过用户批准的材料或货币上限。

## 27. 测试账号

后期高风险规则优先在测试账号验证：

```text
AccountProfile
├── account_profile_id
├── game_profile_id
├── server_region
├── environment_type
├── inventory_scope
├── allowed_risk_classes
└── identity_evidence_spec
```

`environment_type`至少区分：

```text
TEST_ACCOUNT
PRODUCTION_ACCOUNT
UNKNOWN
```

执行前必须从当前窗口和游戏画面重新确认账号或角色身份。测试账号和正式账号的库存、计划、批准和执行记录完全隔离。

在测试账号验证过的规则可以作为正式账号的候选，但不能因为测试通过就自动获得正式账号执行权限。

## 28. 公式知识层

后期伤害、治疗、护盾、成长和收益计算需要单独的公式知识层：

```text
FormulaKnowledgeBase
├── FormulaClaim
├── FormulaDefinition
├── FormulaVariableDefinition
├── FormulaExample
├── BuildRecommendationClaim
└── FormulaValidationRun
```

AI可以负责搜索、阅读、比较和提取公式，但最终计算仍由版本化表达式或模型执行。

## 29. `FormulaClaim`

网络攻略、游戏说明或用户测试首先产生候选：

```text
FormulaClaim
├── claim_id
├── subject
├── raw_formula_or_description
├── parsed_expression_candidate
├── variable_candidates
├── assumptions

├── source_ref
├── source_snapshot_ref
├── author_or_publisher

```

候选状态可以是：

```text
IMPORTED_CANDIDATE
PARSED
EXAMPLE_VERIFIED
GAME_TESTED
ACTIVE
CONTRADICTED
STALE
```

## 30. 公式来源和优先级

可能来源包括：

```text
游戏内属性和技能说明
官方帮助、公告和更新日志
社区实测公式
角色与装备攻略
视频或表格测试结果
游戏内推荐套装
用户自己的实验记录
```

来源权威性与公式正确性不是同一个字段。官方说明可能省略内部取整，社区公式也可能过期。系统需要保存来源快照、版本和验证结果。

网络来源必须记录访问时间和原始链接；重要公式最好保留合法范围内的摘要、引用片段或结构化快照，避免链接失效后无法追溯。

## 31. AI在公式知识中的职责

AI可以：

- 搜索角色攻略和公开公式；
- 阅读游戏内说明；
- 提取变量、条件和取整顺序候选；
- 比较多个来源的差异；
- 根据目标推荐需要验证的装备组合；
- 解释公式和计算结果；
- 设计低风险游戏内测试。

AI不能：

- 把单个攻略直接发布为确定公式；
- 忽略游戏版本和适用场景；
- 在变量缺失时编造精确伤害；
- 用自然语言心算替代确定性计算器；
- 把游戏推荐套装当作数学最优结论；
- 自动在正式账号消耗材料验证配装。


伤害计算可能涉及：

```text
基础倍率
```

## 33. 实测验证

公式可以用公开示例和游戏内测试验证：

```text
固定角色和装备
-> 记录完整属性
-> 选择已知敌人和状态
-> 记录技能、增益和伤害数字
-> 计算预测值
-> 比较误差
-> 调整候选取整或隐藏系数
```

测试必须保存当前游戏版本、敌人状态、输入、连续帧和OCR证据。画面特效遮挡或伤害数字漏检时，本次样本不能当作公式反例。

## 34. 配装推荐不是公式

攻略或游戏内推荐套装应保存为：

```text
BuildRecommendationClaim
├── character_or_role
├── equipment_set
├── stat_priority
├── scenario
├── assumptions
├── source_ref
├── game_version
└── validation_status
```

它表达“某来源建议这样搭配”，不等同于：

```text
这一定是最高伤害
这适合所有队伍
这适合用户现有材料
```

用户选择某个配装候选后，可以将缺少的装备和强化材料转换成新的`MaterialGoal`，再交给资源规划器计算。

## 35. 公式版本和过期

游戏更新可能改变：

- 技能倍率；
- 装备属性；
- 敌人防御和抗性；
- 反应公式；
- 套装效果；
- 取整或快照机制。

新版本不能覆盖旧公式。应创建新的`FormulaDefinition`版本，并将不再适用的版本标记为`STALE`或`RETIRED`。历史执行和回放继续引用当时固定版本。

## 36. 与规则合成系统的连接

资源规划中的计算可以使用：

```text
DerivedValueRule
CalibrationRule
TemporalRule
ReconciliationRule
ExpressionGraph
```

AI提取的获取条件、兑换说明和伤害公式先进入`RuleHypothesis`或`FormulaClaim`，经过Schema检查、示例验证、离线回放和必要实验后再发布。

## 37. 与物品账本的连接

```text
ItemCatalog
-> 物品、配方、获取来源和时间规则

InventoryLedger
-> 当前数量、实例、预留和真实变化事件

MaterialPlan
-> 读取上述事实并形成未来计划
```

材料计划不能直接重写`InventoryLedger`。执行后由实际`InventoryEvent`更新账本，再重新计算剩余计划。

## 38. 与Trace Core的连接

首期`Trace Core`提供：

```text
帧与输入对齐
OCR和图标未来可复用的证据窗口
窗口与账号操作归属
执行前后画面
离线回放
```

没有可靠证据时，商店价格、库存变化和公式实测都无法验证。因此资源规划和伤害公式属于Trace Core之后的领域能力。

## 39. 分阶段验证

### 阶段一：手工库存和简单目标

用户手工输入库存和目标，只验证缺口、批次和多层材料展开。

### 阶段二：一种商店兑换

使用OCR读取价格和库存，但只生成计划，不执行消耗。

### 阶段三：审核和版本

用户修改材料数量，验证旧审核和旧批准自动失效，并生成清晰差异。

### 阶段四：测试账号执行

在测试账号执行一笔低价值、可重复兑换，验证执行前检查、后置证据和库存事件。

### 阶段五：一种家园种植

验证容量、生长周期、收获和重新播种的简单时间计划。

### 阶段六：一条大世界采集路线

验证点位数量、路线耗时、刷新规则和保守完成时间。

### 阶段七：多计划预留

建立两个竞争计划，验证同一库存不会被重复承诺。

### 阶段八：公式候选

从一段游戏说明和一篇公开攻略提取同一技能公式候选，记录来源差异但不发布。

### 阶段九：伤害示例验证

使用已有公开示例运行确定性计算器，验证变量、取整和版本记录。

### 阶段十：游戏内实测

最后在测试账号执行受控伤害测试，对比预测值和画面观测。

## 40. 第一版验收标准

- 计划预计消耗不会直接修改实际库存；
- 数量、批次和多层需求可以确定性复算；
- OCR数值保留原文、画面和置信度；
- 多个计划不会重复占用同一库存；
- 用户修改计划后旧审核和旧批准自动失效；
- AI审核只能提出检查结果和建议，不能替代用户批准；
- 执行前价格、库存、账号和时间发生变化时会暂停；
- 实际消耗只有在游戏后置证据确认后才进入账本；
- 家园种植和采集刷新可以给出数量及时间计划；
- 随机产出区分保证值、期望值和保守值；
- 测试账号与正式账号的库存、批准和执行记录隔离；
- 网络公式保留来源、访问时间、游戏版本和适用条件；
- AI提取公式后由确定性表达式执行计算；
- 配装推荐和伤害公式不会混为同一种知识；
- 旧版本公式仍可复现历史计算。

## 41. 当前结论

资源规划的第一版可以保持简单：

```text
物品目标
-> 库存缺口
-> 合成、兑换或采集步骤
-> 数量和时间计算
-> 确定性校验
-> AI审核提醒
-> 用户确认
-> 受控执行和真实对账
```

AI的价值主要在发现计划遗漏、解释说明文本、比较获取路径和后期收集公式；基础算术、批次取整、资源预留、批准边界和实际库存更新必须保持确定性。

后期伤害计算虽然高度依赖AI查找和理解资料，但最终仍应收束为有来源、有版本、有假设并可由确定性引擎复算的公式知识。
