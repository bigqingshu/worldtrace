## 1. 核心结论

ZipDepth可以作为快速、稠密的相对几何线索来源，但不能单独作为游戏场景的几何真值或可通行真值。

早期更现实的目标不是直接输出米制距离、精确坡度和完整三维网格，而是从连续画面中形成以下可验证判断：

```text
近处 / 中距离 / 远处 / UNKNOWN
平面 / 缓坡候选 / 陡坡候选 / 近似竖直面
连续路面 / 台阶候选 / 裂隙候选 / 落差候选
可走 / 可跨 / 可跳 / 受阻 / UNKNOWN
```

其中前两行主要来自视觉几何线索，后两行必须结合角色能力、动作参数、多帧变化和实际执行结果。

整体路线为：

```text
原始画面
-> 原始相对逆深度
-> 近远层级和局部深度剖面
-> 地面、边缘、平台和竖直面候选
-> 条件化移动能力边界
-> 有限动作或用户示范
-> 新鲜画面验证
-> 成功、失败或UNKNOWN证据
-> 更新或拒绝更新经验
```

这条路线允许系统在不知道真实米数的情况下，逐步学会“当前角色在当前状态下能否通过”。

## 2. ZipDepth实际提供什么

### 2.1 原始输出不是米制深度

ZipDepth官方评估代码明确说明，模型输出为`affine-invariant inverse depth`（仿射不变逆深度）。可以近似理解为：

```text
q(u, v) = a * (1 / Z(u, v)) + b
```

其中：

- `q(u, v)`是模型原始输出；
- `Z(u, v)`是真实深度；
- `a`是未知尺度；
- `b`是未知偏移。

因此不能：

- 把原始数值直接当作米或游戏单位；
- 简单使用`1 / q`恢复真实距离；
- 直接对原始数组求差后宣称得到坡度角；
- 假设不同画面的同一个数值天然代表同一个距离。

官方评估需要先利用真实深度，在逆深度空间为每张图拟合尺度和偏移，再转换为深度。实际游戏运行中通常没有这份真实深度，因此必须另外建立标定、多视图约束或只使用相对关系。

### 2.2 不能使用着色图亮度作为距离

ZipDepth推理代码可以把深度结果保存为彩色图，但彩色图主要用于人眼观察。着色过程会根据当前帧的数值范围重新归一化并套用色图。

这意味着：

```text
当前帧中的某种颜色或亮度
!= 下一帧中的同一真实距离
```

而且色图颜色不一定与视觉亮度保持单调关系。因此实验必须读取原始`.npy`数组或直接取得模型张量，彩色图只能用于调试展示。

### 2.3 视频推理没有时序一致性

ZipDepth的视频模式仍然逐帧执行单图推理。异步流水线负责读取、推理、着色和保存效率，不提供：

- 跨帧注意力；
- 光流对齐；
- 循环状态；
- 时序一致性损失；
- 原生不确定度输出。

官方论文也将视频闪烁列为限制。相同静态表面在连续帧中的输出可能变化，因此任何移动判断都不能只依赖一个瞬时结果。

### 2.4 游戏画面的证据仍然不足

ZipDepth展示了合成场景样例，并在Unreal合成画面上报告过深度边缘相关实验，这是积极信号，但还不足以证明它能够稳定处理任意游戏。

现有量化评估主要来自现实世界数据集。以下游戏画面因素仍需单独验证：

- 卡通、像素、描边或非真实比例渲染；
- 雾、水面、玻璃、镜面、发光材质和屏幕空间特效；
- 第三人称角色、第一人称武器和HUD遮挡；
- 重复纹理、弱纹理、运动模糊和景深；
- 镜头碰撞、动态FOV、瞄准缩放和过场镜头；
- 视觉模型看到的表面与游戏碰撞体不一致。

因此ZipDepth在本项目中的合理身份是候选实验依赖，而不是已经确认的视觉基础设施。

## 3. 简单远近图的第一版定义

### 3.1 第一版目标

第一版远近图只回答：

```text
同一画面内，哪些区域相对更近或更远？
沿候选移动方向，深度关系是否连续？
哪里出现了稳定的深度突变？
```

暂不回答：

```text
距离是多少米？
坡度精确是多少度？
这个区域在语义上一定是地面还是墙？
角色一定能否通过？
```

### 3.2 候选处理流程

```text
选择新鲜游戏帧
-> 裁剪到真实3D视口
-> 遮罩HUD、黑边、人物或武器等污染区域
-> ZipDepth原始推理
-> 保存原始逆深度
-> 在有效视口内做稳健归一化
-> 量化为近、中、远和UNKNOWN
-> 保留归一化参数与模型版本
```

稳健归一化可以先比较：

- 有效区域分位数；
- 中位数与MAD；
- 固定相机片段中的稳定背景锚点；
- 多帧对齐后的共同静态区域。

不能默认“逐帧分位数量化”就适合跨帧比较，因为画面构成变化会导致分位数整体移动。实验需要分别验证：

```text
帧内近远排序
镜头片段内相对稳定性
跨镜头或跨场景可比性
```

### 3.3 候选实验字段

下面字段只用于描述实验产物，不是已经确认的公共契约：

```text
frame_id
model_revision
camera_mode
raw_inverse_depth
relative_depth_level
valid_mask
normalization_scope
normalization_parameters
temporal_stability
```

所有衍生结果都必须能够追溯到原始帧、模型版本和归一化方法，避免以后把相对结果误当成真实深度。

## 4. 从远近图提取局部结构

远近图本身不直接输出“裂隙”“墙体”或“道路”。第一版可以从人物所在区域出发，构造`ground corridor`（地面走廊）候选。

```text
人物落脚锚点或画面底部锚点
-> 沿预计前进方向向远处追踪
-> 查找连续且变化平滑的深度带
-> 记录中断、突变、顶面和竖直面候选
```

局部结构可以暂时分为：

| 候选结构 | 相对深度表现 | 仍需补充的证据 |
| --- | --- | --- |
| 连续平地 | 沿移动方向平滑变化 | 相机模式、连续帧和实际移动 |
| 坡面 | 连续但偏离平地基准剖面 | 镜头俯仰、地面锚点和多帧一致性 |
| 台阶或矮障碍 | 地面结束、出现局部竖直面和上方顶面 | 顶面面积、相对高度和角色能力 |
| 裂隙 | 近侧地面结束，随后出现远侧平台候选 | 多视角、边缘稳定性和实际跨越结果 |
| 墙体 | 地面终止并连接大面积近似竖直面 | 顶面是否可见、碰撞和绕行结果 |
| 落差 | 地面结束，下方或远处深度明显变化 | 换视角确认，单帧不能确认隐藏深度 |

大深度梯度也可能来自角色轮廓、树木、栏杆、前景装饰或粒子效果，不能直接等同于裂隙或悬崖。

## 5. 裂隙跨度与跨越能力

### 5.1 不能只使用屏幕像素宽度

同样宽度的像素带，在近处和远处代表的实际跨度不同。裂隙判断至少需要联合观察：

- 近侧边缘的屏幕位置与相对距离；
- 远侧边缘的屏幕位置与相对距离；
- 两侧深度剖面的变化；
- 远侧平台的面积和稳定性；
- 接近裂隙时上述特征如何连续变化；
- 当前是走、跑、冲刺还是跳跃；
- 起跳提前量、按键持续时间和接近速度。

因此早期不必强行计算“裂隙宽多少米”，可以先学习：

```text
相对几何特征
+ 角色与移动状态
+ 动作参数
-> 成功跨越概率和不确定度
```

### 5.2 从实际结果学习能力边界

系统可以将用户自然游玩和低风险实验转化为条件化经验：

```text
较小跨度成功
-> 形成当前条件下的已证实可行下界

较大跨度因距离不足失败
-> 形成当前条件下的不可行上界候选

失败原因不明确
-> 保留证据，但不更新几何能力边界
```

在其他条件相同的情况下，可以使用弱单调先验：

- 裂隙更宽通常不会更容易；
- 远侧平台更高通常不会更容易；
- 可落脚面积更大通常更安全；
- 更充足的起跳距离通常不应降低成功率。

游戏中的抓边、二段跳、冲刺、自动翻越和特殊动画可能破坏简单单调关系，因此不同能力和角色状态必须分开记录。

## 6. 远侧高度、平台与墙体

### 6.1 高度判断必须与跨度联合

跨越裂隙时，远侧平台高度和裂隙跨度共同决定动作是否可行：

```text
较远但较低
-> 可能能够跳到或落到远侧

较近但明显较高
-> 可能需要攀爬、翻越或更强跳跃

较远且较高
-> 风险通常更高
```

不能为跨度和高度各设一个互不相关的固定阈值。更适合的是形成条件化二维或多维能力边界。

### 6.2 区分平台候选与墙体候选

可以优先寻找以下结构关系：

```text
近侧地面
-> 近侧边缘
-> 深度断裂
-> 远侧竖直断面
-> 远侧顶面
-> 可落脚面积
```

如果能够稳定看到远侧顶面，可以形成落脚平台候选。如果只看到连续竖直面而没有顶面，则更接近墙体、过高障碍或不可观测状态。

仍需注意：

- 顶面可见不代表存在对应碰撞体；
- 视觉墙面可能允许穿过；
- 可攀爬墙面与普通墙面可能外观相同；
- 角色头部可能撞到上方结构；
- 角色落到平台后可能继续滑落。

这些差异最终需要动作后置验证。

### 6.3 精确高度需要的条件

若后续需要米制或游戏单位高度，至少需要：

1. 相机FOV、焦距、主点和视口裁剪关系；
2. 恢复ZipDepth逆深度的尺度与偏移；
3. 相机姿态和世界重力方向；
4. 目标上下边界或可见表面分割；
5. 多帧共同坐标或其他尺度锚点。

只有满足这些条件后，才能将深度反投影为局部点云并计算真实高度。早期经验学习不要求先完成这一步。

## 7. 平地、坡面、台阶与跳上物体

### 7.1 使用平地基准剖面

透视投影下，正常平地的相对深度本来就会从画面下方向远处连续变化，不能把所有梯度都解释为坡面。

可以针对固定`camera_mode`（相机模式）、FOV和镜头姿态，在已知安全平地上记录基准剖面：

```text
当前地面走廊剖面接近平地基准
-> 平地候选

当前剖面连续但系统性偏离基准
-> 上坡或下坡候选

当前剖面发生局部突变并出现顶面
-> 台阶或可跳物体候选

当前剖面突然终止
-> 障碍、裂隙或落差候选
```

相机俯仰、镜头距离或FOV变化会直接改变基准剖面，因此旧基准必须降级或失效。

### 7.2 不能只比较脚点和最近物体

最近物体可能是：

- 人物身体；
- 第一人称武器；
- 树木或栏杆；
- HUD元素；
- 画面侧面的无关前景；
- 不在预计移动方向上的装饰物。

正确问题应是：

> 在当前移动走廊内，是否存在与脚下地面具有合理关系的候选表面，以及该表面是否具有足够落脚面积？

### 7.3 坡度角不是原始逆深度梯度

原始逆深度中的未知偏移会扭曲直接反投影得到的表面法向。若要计算真实坡度角，需要：

- 标定后的深度；
- 相机内参；
- 地面区域；
- 相机姿态；
- 世界重力方向；
- 稳健平面拟合。

在这些条件不足时，只输出“平坦、缓坡候选、陡坡候选、UNKNOWN”等相对类别。

## 8. 第一人称与第三人称必须分开

| 视角模式 | 地面起点 | 可利用的锚点 | 主要风险 |
| --- | --- | --- | --- |
| 第一人称 | 画面底部中央附近推断 | 相机高度、准星、平地基准剖面 | 看不到脚、武器遮挡、镜头俯仰影响大 |
| 第三人称 | 角色脚部接触点附近 | 角色脚点、人物高度、接触阴影 | 人物遮挡、镜头环绕、镜头距离变化 |

### 8.1 第一人称

第一人称没有稳定可见脚点时，可以从画面底部中央建立候选地面走廊，并使用已知安全平地记录相机模式基准。

第一轮实验应固定：

- 分辨率和视口；
- FOV或缩放；
- 镜头俯仰范围；
- 武器或手臂遮罩；
- 普通移动状态。

镜头抬头或低头后，不能继续套用原基准。

### 8.2 第三人称

第三人称可以使用角色脚部接触点作为局部起点，并将人物高度作为弱尺度参照。但人物本身会污染场景深度，应尽量将人物区域从地形分析中排除，同时保留脚点锚定信息。

需要独立记录：

- 普通移动、瞄准、锁定和特殊镜头；
- 镜头俯仰和环绕方向；
- 镜头与人物距离；
- 角色是否被遮挡；
- 移动输入相对镜头还是相对角色。

第一人称和第三人称可以共享“证据与结果”框架，但不应直接共享同一套屏幕几何阈值。

## 9. 玩得越久越精准需要什么

### 9.1 学习对象不是全局固定阈值

需要学习的是条件化移动能力边界，而不是一个适用于所有场景的“最大跳跃距离”。经验至少应绑定：

- 游戏和游戏版本；
- 角色、载具或形态；
- 走、跑、冲刺、跳跃或特殊能力；
- 角色属性、装备、增益和体力状态；
- 控制配置和输入后端；
- 第一人称或第三人称模式；
- FOV、缩放和镜头模式；
- 视觉模型、归一化和特征版本。

上述条件变化后，旧经验可以作为候选先验，但不能继续视为同一环境下的直接证据。

### 9.2 成功和失败必须正确归因

现有运行共识中的`ExecutionOutcome`（执行结果）、`FailureAttribution`（失败归因）和`SampleDisposition`（样本处置）适合约束经验更新。

一次跳跃失败可能来自：

- 裂隙确实过宽；
- 远侧平台确实过高；
- 起跳输入没有被游戏接收；
- 接近速度不足；
- 镜头或角色方向错误；
- 被敌人、动画或网络延迟打断；
- 上方碰撞导致跳跃轨迹改变；
- 已经落地但随后滑落；
- 输入前后画面不是新鲜帧。

只有能够归因于几何条件或角色能力的样本，才能更新对应能力边界。无法区分原因时应返回`UNKNOWN`或拒绝用于学习，不能把所有失败都标记为“跳不过去”。

### 9.3 先观察用户，再主动试探

早期优先从用户自然游玩中收集：

- 用户成功走过、跨过或跳过的场景；
- 用户失败后重新尝试成功的场景；
- 不同起跳距离、速度和按键持续时间；
- 成功落地后的稳定画面；
- 用户主动避开的高风险区域。

主动试探只应发生在明确的安全训练区域，并具有停止、失败预算和恢复方式。不能为了收集失败样本而在可能掉落、死亡、损失资源或触发不可逆事件的场景盲目尝试。

## 10. 人物落脚锚点、速度与方位估计

裂隙和平台几何只是跳跃条件的一部分。系统还需要知道人物从哪里起跳、正向哪里移动、当前处于什么速度阶段，以及什么时候到达边缘。

### 10.1 落脚锚点不是同一种屏幕坐标

可以使用`GroundContactAnchor`（人物落脚锚点）统一表达人物与当前承载表面的关系，但第一人称和第三人称的观测方式不同。

#### 第一人称

第一人称可以把相机作为自运动跟踪锚点，但相机中心不等于人物脚底。物理落脚点大致满足：

```text
人物落脚位置
= 相机位置
+ 沿指向地面的重力方向移动约一个视点高度
```

如果直接把相机中心当作脚底，以下变化会被错误解释为地形高度变化：

- 走路时的镜头上下晃动；
- 起跳和下落；
- 下蹲、滑铲或攀爬；
- 武器后坐力或受击震动；
- 游戏主动改变相机高度。

早期可以使用固定相机高度和安全平地作为弱基准，并从画面底部中央推断地面走廊。进入跳跃、下蹲、载具或特殊动画后，旧基准应降级。

#### 第三人称

第三人称优先使用人物模型与承载表面的接触位置。候选证据包括：

- 人物遮罩底部；
- 脚部关键点；
- 双脚与局部地面的深度关系；
- 接触阴影；
- 跑步、起跳、空中和落地动画阶段；
- 连续帧中的垂直速度变化。

人物遮罩底部不天然等于真实脚点。例如披风、裙摆、坐骑、草木遮挡和角色倾斜都可能改变遮罩最低点，因此需要连续跟踪和局部地面共同确认。

落脚状态可以先离散为：

```text
GROUNDED
TAKEOFF
AIRBORNE
LANDING
SLIPPING_OR_FALLING
UNKNOWN
```

只有落地后在稳定表面保持一段时间，才能确认跳跃成功。短暂接触后继续滑落不能标记为稳定落地。

### 10.2 场景向后变化是自运动线索，不是速度真值

人物向前移动时，静态场景参考物通常向画面后方或外侧移动。技术上可以通过`Optical Flow`（光流）和`Visual Odometry`（视觉里程计）观察这种变化。

但完整画面运动同时包含：

```text
人物或相机平移
+ 镜头yaw、pitch和roll旋转
+ FOV或缩放变化
+ 第三人称摄像机跟随
+ 人物动画和镜头抖动
+ 动态角色、粒子和UI
```

因此不能直接把平均像素位移解释为人物速度。更合理的候选流程为：

```text
连续帧
+ 深度或相对深度
+ 人物、HUD和动态区域遮罩
+ 已知输入上下文
-> 跟踪静态背景参考点
-> 估计并扣除镜头旋转
-> 排除FOV变化和异常运动
-> 分析剩余平移光流与深度关系
-> 输出移动方向、速度阶段和时间特征
```

键鼠输入可以作为运动先验，但不能替代视觉验证。例如系统发送了向前键，只能说明请求向前移动，不能证明人物已经产生对应速度。

### 10.3 第一人称与第三人称的速度来源

#### 第一人称速度

普通第一人称相机通常随人物平移，静态背景光流较接近人物自运动。仍需排除：

- 鼠标转向；
- 呼吸和走路晃动；
- 武器动画；
- 瞄准和FOV变化；
- 受击、后坐力和镜头脚本；
- 移动平台带来的整体运动。

当深度只具有相对尺度时，可以先得到速度等级和相对变化；当深度具有可信度量尺度并且相机内参已知时，才有条件估计米制或游戏单位速度。

#### 第三人称速度

第三人称摄像机经常主动跟随人物，使人物长期保持在画面中央。人物框在屏幕上几乎不动，并不代表人物静止。

需要组合：

```text
人物脚点相对附近地面参考点的变化
+ 静态背景光流
+ 摄像机跟随滞后
+ 人物跑步动画阶段
+ 输入持续时间
+ 深度变化
```

第三人称相机的平移速度不一定等于人物速度，特别是在镜头碰撞、锁定目标、绕人物旋转、冲刺拉远或停止回弹时。人物运动和摄像机运动必须分开估计。

### 10.4 SAM与经典计算机视觉的分工

`SAM`（万物分割模型）主要提供区域遮罩，不直接计算人物速度、移动方向或脚部接触状态。`OpenCV`（经典计算机视觉工具库）更适合承担第一轮运动与几何验证。

| 任务 | 候选方法 |
| --- | --- |
| 分出人物、地面、平台和障碍候选 | SAM、SAM2或其他分割模型 |
| 遮罩HUD、黑边、武器和人物 | 静态规则、人工标注或分割模型 |
| 连续跟踪静态参考点 | KLT光流、特征点匹配或稠密光流 |
| 排除镜头旋转 | 单应性、基础矩阵、本质矩阵或已验证的视角变化 |
| 估计相机平移趋势 | 视觉里程计、深度加权运动场或多帧几何 |
| 识别人物脚部和动作阶段 | 姿态估计、人物专用跟踪和动画外观变化 |
| 确认脚与地面接触 | 脚点、局部深度、阴影和连续帧联合判断 |

第一轮实验不一定需要SAM。可以先人工或静态指定人物、武器和HUD遮罩，验证运动场是否足以区分静止、加速、稳定移动和转向。只有遮罩成为主要误差来源后，再引入分割模型。

### 10.5 先学习速度阶段，而不是强求真实单位

人执行跳跃时通常不会持续计算米制速度，更接近于判断：

```text
我是否已经跑起来？
是否还在加速？
是否已经接近稳定速度？
按照当前速度多久会到达边缘？
```

候选`MotionState`（运动状态）可以先包含：

```text
motion_direction
speed_phase = STOPPED / ACCELERATING / CRUISING / DECELERATING / UNKNOWN
speed_band = SLOW / MEDIUM / FAST / UNKNOWN
ground_contact_state
time_to_edge
camera_motion_state
evidence_stability
```

这些字段仍是实验候选，不是公共契约。

可以在安全平地上执行受控标定：

```text
从静止开始按住前进
-> 跟踪静态背景和地面特征
-> 观察光流幅度与深度变化如何增长
-> 找到加速段和相对稳定段
-> 释放按键
-> 观察减速和停止过程
```

由此得到的是当前游戏、角色、移动方式和相机模式下的速度响应曲线。坡面、泥地、体力、装备和游戏补丁都可能使曲线失效。

### 10.6 使用到边缘剩余时间选择起跳时机

`TimeToContact`（接触剩余时间）描述按照当前视觉运动趋势，预计多久到达某个边缘或表面。它比单独的屏幕像素距离更接近人的起跳判断。

对于裂隙，可以使用：

```text
近侧边缘的连续屏幕位置
+ 静态地面光流
+ 当前速度阶段
+ 帧时间间隔
-> time_to_edge候选
```

起跳条件可以逐步学习为：

```text
速度阶段
+ 移动方位
+ time_to_edge
+ 裂隙相对跨度
+ 远侧相对高度
+ 落脚区域大小
+ 跳跃按键时机和持续时间
-> 成功概率与不确定度
```

这里的`TimeToContact`不能只由单帧估计，也不能在镜头剧烈旋转、FOV变化或边缘跟踪丢失时继续使用。证据失效时应返回`UNKNOWN`。

### 10.7 落地验证也是运动估计的一部分

跳跃成功不能只依赖画面看起来已经越过边缘。后置验证至少观察：

- 人物或相机的上升阶段结束；
- 出现合理下落过程；
- 脚点或推断落脚点与远侧表面接触；
- 垂直运动停止；
- 人物没有继续滑落、坠落或卡住；
- 背景运动与恢复地面移动相符；
- 新鲜帧连续确认当前承载表面稳定。

失败样本还应区分起跳过早、起跳过晚、速度不足、方位偏差、平台过高、落脚区域过小和落地后滑落。

## 11. 度量深度与受控多帧高度判断

### 11.1 度量深度可以作为条件化证据源

部分单目模型能够输出`metric depth`（度量深度）或直接预测三维点图。若某个模型在目标游戏、目标FOV和当前渲染风格下经过验证，可以为高度、宽度和速度提供更直接的数值证据。

但“模型类别支持度量深度”不代表它在任意游戏中保持真实尺度。仍需验证：

- 模型是否知道或能够正确估计相机FOV；
- 游戏人物和场景比例是否接近训练分布；
- 相机裁剪、缩放和宽高比是否正确；
- 深度尺度是否随场景内容、镜头模式或画质变化漂移；
- 透明、反射、天空盒和特效是否产生错误深度；
- 人物模型与真实碰撞体是否一致。

因此高度证据可以来自多种实现：

```text
度量深度模型
或 相对深度 + 尺度与偏移标定
或 多视图三角测量
或 人物身高、相机高度和已知场景参照
或 游戏实验得到的可跨越结果
```

每种结果都应保存来源、标定条件、残差和适用环境，不能用一个“高度值”覆盖所有来源差异。

### 11.2 多帧只有产生视差时才能增加几何约束

系统能够控制镜头是一项优势，但需要区分纯旋转与视点平移：

```text
只在原地旋转镜头
-> 可以看到更多表面并改善边界观察
-> 不能单靠三角测量恢复真实深度

人物横移、前进或摄像机真实绕行
-> 产生视点平移和视差
-> 可以为深度、高度和表面关系增加几何约束
```

适合的受控观测包括：

- 第一人称小幅左右横移；
- 在安全距离内向障碍缓慢接近；
- 第三人称摄像机真实绕人物平移，而不是只改变朝向；
- 从不同站位观察同一台阶、平台或裂隙；
- 保持目标静止并记录准确帧时间和输入上下文。

如果摄像机轨迹本身未知，可以同时估计相机运动和场景结构，但普通单目多视图通常仍只有统一比例尺度。人物高度、相机高度、度量深度或其他已知参照可以补充尺度。

### 11.3 高度结论应由多份证据收束

可以将高度判断理解为逐级收束：

```text
单帧相对深度
-> 给出同高、较高、较低或UNKNOWN候选

度量模型或标定模型
-> 给出带残差的数值高度候选

受控视点平移
-> 验证边缘、顶面和断面关系

人物实际走、跳或攀爬结果
-> 验证当前能力能否通过
```

最终可以同时保留两个不同结论：

```text
几何结论：平台相对较高，估计高度范围为某一区间
能力结论：当前角色以当前速度和动作参数通过成功
```

几何估计错误不应自动推翻已重复验证的行为能力；一次行为成功也不应反向宣称几何高度已经精确测量。

## 12. 可通行判断仍需执行闭环

视觉观察只能提出候选：

```text
视觉认为可跨
-> 不是成功事实

动作已经发送
-> 不是成功事实

人物到达远侧稳定表面
+ 当前窗口、帧和控制上下文仍有效
+ 没有继续跌落或卡住
-> 才能形成成功证据
```

同样，视觉认为是墙也不能证明一定不可通行，因为游戏中可能存在：

- 可穿过装饰物；
- 隐形通道；
- 自动翻越；
- 攀爬或抓边；
- 只在特定能力状态下可通过的表面。

几何线索、游戏碰撞和角色能力必须作为不同事实来源保存。

## 13. 建议的最小实验

### 13.1 代码归属

若后续开始验证，建议：

```text
reference_repos/zipdepth
-> 保存固定版本的ZipDepth原仓库

experiments/depth_geometry_zipdepth
-> 保存WorldTrace自己的离线适配、样本、评估和结论
```

实验代码不直接进入正式`capture`、`timeline`或未来视觉模块。只有输入、输出、失败方式和验收结果稳定后，才讨论正式归属。

### 13.2 测试场景

优先选择一个游戏或可控渲染场景，固定一种视角模式，并准备：

- 平地；
- 多档已知坡度；
- 低台阶和高台阶；
- 多档跨度裂隙；
- 相同跨度、不同远侧高度；
- 有可见断面的落差；
- 只有边缘、断面不可见的落差；
- 已知高宽的箱体、门洞和通道；
- 不同FOV、俯仰、材质、光照和HUD开关组合。

如果测试环境能够提供真实深度、相机参数和几何尺寸，应只将其作为实验真值，不把游戏内部深度缓冲作为未来运行前提。

### 13.3 分阶段验证

#### 阶段A：原始相对测试

只验证：

- 同帧近远排序；
- 地面走廊连续性；
- 深度断裂边缘；
- 平面和坡面候选；
- 不同输入分辨率下的细节损失。

#### 阶段B：真实值对齐上限

利用实验真值拟合每帧尺度和偏移，测量ZipDepth在理想对齐后的几何上限。这一步只用于回答“模型本身是否有足够信息”，不能作为可部署结果。

#### 阶段C：可部署标定

只使用运行时可能获得的条件，例如：

- 已知相机FOV；
- 人物高度或相机高度；
- 两个不同距离的稀疏锚点；
- 安全平地基准；
- 多帧相机运动约束。

在完全未参与标定的画面上评估结果。

#### 阶段D：时序融合

检查：

- 静止场景连续帧闪烁；
- 镜头轻微转动后的对应关系；
- 接近裂隙时边缘估计是否连续；
- 人物和特效短暂遮挡后的恢复；
- 归一化方法是否导致近远层级跳变。

#### 阶段E：落脚锚点与运动状态

分别在固定第一人称和第三人称场景验证：

- 人物落脚锚点是否稳定；
- 落地、起跳、空中和落地中是否可区分；
- 镜头旋转和人物平移是否可分离；
- 静止、加速、稳定移动和减速阶段是否可区分；
- 前进、斜向和横向移动方向是否可区分；
- 接近固定边缘时`TimeToContact`是否连续收敛；
- 镜头抖动、FOV变化和摄像机跟随是否会制造虚假速度。

#### 阶段F：行为结果学习

使用用户示范或安全试验记录：

- 视觉特征；
- 角色和相机上下文；
- 动作参数；
- 输入前后帧；
- 是否到达目标表面；
- 失败归因；
- 样本是否允许更新能力边界。

先验证成功与失败样本是否在特征空间中形成可解释边界，再决定使用查表、单调模型、概率模型或更复杂学习方法。

### 13.4 评估指标

至少记录：

- 近远成对排序准确率；
- 深度断裂边界Precision、Recall和F1；
- 平地、坡面、台阶、墙体和裂隙候选混淆情况；
- 对齐后高宽相对误差和坡度角误差；
- 连续帧估计方差和跳变次数；
- 人物落脚锚点位置误差和接触状态混淆情况；
- 移动方向、速度阶段和速度等级混淆情况；
- 预测到达边缘时间与实际到达帧的时间误差；
- 纯镜头运动被误判为人物平移的比例；
- 可跨、可跳、受阻判断的成功率与误报率；
- `UNKNOWN`比例及其是否正确阻止高风险动作；
- 目标硬件上的P50/P95延迟、显存和端到端吞吐；
- 不同FOV、材质、视角和HUD条件下的分组结果。

官方RTX 3090模型推理数据不能代替本机端到端结果。

## 14. 与Trace Core的关系

当前正式第一阶段仍以`Trace Core`（轨迹核心）为主，不接入深度模型。深度实验可以先离线消费手工样本，未来再消费Trace Core保存的帧和回放记录。

合理关系为：

```text
Trace Core
-> 提供带frame_id、时间线和窗口身份的可靠帧

深度几何实验
-> 离线生成相对深度和候选结构

执行证据
-> 提供动作结果和失败归因

经验分析
-> 判断哪些条件可以形成移动能力边界
```

深度实验不应自行临时截图，也不应绕过统一时间线保存无法追溯的结果。

## 15. 候选输入、输出与不负责范围

以下内容用于约束未来实验，不代表正式公共契约。

### 15.1 候选输入

- 带`frame_id`的新鲜RGB帧；
- 帧单调时间戳和连续帧窗口；
- 真实3D视口范围；
- 视角模式与可选相机参数；
- HUD、角色或武器遮罩；
- 可选用户输入、动作参数和执行结果。

### 15.2 候选输出

- 原始逆深度及模型版本；
- 近、中、远和`UNKNOWN`层级图；
- 地面走廊与局部深度剖面；
- 人物落脚锚点及接触状态；
- 人物与摄像机运动的候选分解；
- 移动方向、速度阶段、速度等级和`TimeToContact`；
- 边缘、平台、竖直面、坡面和落差候选；
- 条件化可通行估计与不确定度；
- 标定、归一化、时序稳定性和证据引用。

### 15.3 不负责范围

- 不直接宣布真实米制距离；
- 不直接宣布精确坡度角；
- 不从单帧恢复被遮挡的完整断面；
- 不把视觉表面等同于游戏碰撞体；
- 不根据已发送输入直接宣称人物具有对应速度；
- 不独立决定高风险跳跃；
- 不在没有失败归因时自动更新经验；
- 不替代窗口、帧、输入和运行证据模块。

- 使用独立实验环境；
- 记录模型权重哈希和导出方式；
- 验证README与实际依赖文件的版本差异；
- 分别测试PyTorch、ONNX或其他候选运行后端；
- 不把模型权重放入主项目Git历史。

## 17. 总结

这项构想最值得验证的不是：

> ZipDepth能否从任意游戏截图精确还原真实三维世界。

而是：

> 在固定游戏、角色、视角和控制条件下，相对深度结构能否稳定区分平地、坡面、台阶、墙体、裂隙和落差候选，并与真实动作结果共同形成可复用的移动能力边界。

第一版应坚持：

```text
使用原始逆深度，不使用着色图亮度
-> 先验证帧内近远和局部结构
-> 分开第一人称与第三人称
-> 用多帧和动作结果确认
-> 只有正确归因的样本才能学习
-> 高风险和不可观测情况返回UNKNOWN
```

这能保留“玩得越久越精准”的方向，同时避免把视觉模型的合理猜测误写成物理事实。
