# 面向游戏的视觉移动、地形判断与场景记忆方案

## 1. 目标概述

本方案面向游戏视觉智能体，目标不是一开始就完整重建整个三维世界，而是先实现一种更现实、成本更低的能力：

- 能识别当前属于第一人称还是第三人称视角；
- 能根据角色位置或画面中心判断移动方向；
- 能利用连续画面、深度、阴影、轮廓等信息判断道路是否连续；
- 能识别墙体、台阶、坡面、悬崖和明显路面断层；
- 能利用游戏小地图完成全局导航；
- 能通过轻量场景指纹记住曾经走过的位置；
- 能将视觉判断、小地图路线和历史经验组合成路线节点与事件链。

整体思路不是让系统一次性“理解整个游戏世界”，而是让它像人一样：

> 看小地图确定大方向，看当前画面判断眼前能不能走，走过一次后记住关键路口和标志场景。

---

## 2. YOLO、SAM、OpenCV 与三维方向的关系

YOLO、SAM 本身主要处理二维视觉问题。

### 2.1 YOLO

主要负责：

- 目标检测；
- 判断画面中有什么；
- 输出人物、怪物、门、箱子、障碍物等目标框；
- 提供目标中心点和大致位置。

### 2.2 SAM

主要负责：

- 像素级区域分割；
- 提取人物、地面、墙体、道路、阴影等区域；
- 生成更精确的轮廓和遮罩；
- 辅助判断目标边界和接触位置。

### 2.3 OpenCV

主要负责：

- 特征点检测与匹配；
- 光流跟踪；
- 透视与几何计算；
- 相机姿态估计；
- 轮廓、边缘、主方向和消失点分析；
- 感知哈希与低分辨率特征提取。

### 2.4 三维方向需要额外计算

需要区分三类方向：

| 判断内容 | 典型输出 |
|---|---|
| 镜头朝向 | 偏航、俯仰、翻滚 |
| 镜头运动 | 向左转、向右转、抬头、低头、前进 |
| 角色或物体朝向 | 左前、右前、背对镜头、朝向目标 |

YOLO 和 SAM 可以提供目标位置与轮廓，但三维方向需要结合：

- 连续帧光流；
- 特征匹配；
- 相机姿态估计；
- 已知物体几何；
- 深度估计；
- 小地图和方向箭头；
- 多帧历史状态。

## 3. 从连续画面判断镜头运动

连续画面比单张截图更适合判断相机转动。

基本流程：

```text
前一帧
  ↓
提取背景特征点
  ↓
在后一帧中跟踪这些点
  ↓
排除人物、怪物、特效和UI
  ↓
计算整体光流或相机姿态变化
  ↓
得到镜头转动方向与大致幅度
```

典型现象：

- 背景整体向左移动：镜头大概率向右转；
- 背景整体向右移动：镜头大概率向左转；
- 背景整体向下移动：镜头大概率向上抬；
- 背景整体向上移动：镜头大概率向下压；
- 特征从中心向外扩散：镜头或角色可能向前移动；
- 特征向中心收缩：镜头或角色可能后退；
- 特征围绕画面中心旋转：可能发生镜头翻滚。

为了降低误判，应当：

1. 用 YOLO 或 SAM 排除人物、怪物、粒子特效和UI；
2. 只保留背景特征；
3. 使用 RANSAC 排除异常点；
4. 对多帧结果进行平滑；
5. 将镜头运动与键鼠输入、角色位置变化结合判断。

单目画面通常可以较可靠地得到相对旋转，但无法仅凭普通画面准确获得真实移动距离。

## 4. 第一人称与第三人称视角适配

不能使用同一套坐标原点处理所有游戏视角。

推荐先建立视角模式识别层：

```text
游戏画面
   ↓
视角模式识别
   ├─ 第三人称普通移动
   ├─ 第三人称瞄准
   ├─ 第一人称普通移动
   ├─ 第一人称瞄准
   ├─ 过场、菜单、特殊镜头
   └─ 无法确定
```

---

## 5. 第三人称视角处理

第三人称模式下，角色本身是最重要的视觉锚点。

### 5.1 需要检测的数据

```text
角色中心位置
角色脚底位置
角色头部位置
角色身体朝向
角色运动方向
角色尺寸
角色是否被遮挡
角色与画面中心的偏移
```

其中最重要的是角色脚底位置，因为脚底更接近角色在地面上的实际位置。

### 5.2 角色检测方式

可以组合：

- YOLO：检测角色框；
- SAM：提取角色轮廓；
- 姿态模型：检测头、肩、髋、腿和脚；
- ByteTrack、SORT 或光流：连续跟踪角色；
- 历史位置预测：短时间漏检时继续保持角色状态。

### 5.3 第三人称移动坐标

第三人称一般以角色脚底作为局部位置原点：

```text
角色脚底 P
目标位置 T
可通行区域 M
障碍区域 O
```

可以先做近似判断：

- 目标在角色左上方：左前方向；
- 目标在角色正上方：向前；
- 目标在角色右上方：右前方向；
- 目标位于侧面：横向移动或先转镜头。

但需要注意：

> 画面上方不一定等于角色身体前方，也不一定永远等于游戏世界前方。

需要分别记录：

- 角色身体朝向；
- 镜头朝向；
- 角色实际运动方向；
- 游戏移动输入是相对镜头还是相对角色。

大多数第三人称游戏采用相对镜头移动，即：

```text
W：向镜头前方移动
A：向镜头左侧移动
S：向镜头后方移动
D：向镜头右侧移动
```

## 6. 第一人称视角处理

第一人称看不到完整角色身体时，应以画面中心作为主要方向原点。

### 6.1 第一人称核心坐标

```text
画面中心 C
目标位置 T
目标偏移 = T - C
```

例如：

- 目标在中心左侧：向左转镜头；
- 目标在中心右侧：向右转镜头；
- 目标在中心上方：向上抬镜头；
- 目标位于中心附近：已经基本对准。

### 6.2 第一人称主要分析内容

- 画面中心方向；
- 准星位置；
- 地面和道路区域；
- 前方障碍物；
- 路面断层；
- 背景光流；
- 镜头水平和垂直转动；
- 武器、手臂或瞄准镜UI。

第一人称移动通常是：

```text
鼠标控制镜头
WASD控制相对镜头的移动
```

因此第一人称更依赖镜头方向、光流和地面分析。

## 7. 不能简单使用“检测不到角色 = 第一人称”

第三人称角色也可能暂时消失，例如：

- 被墙体遮挡；
- 被草木或特效遮挡；
- 镜头贴近角色；
- 运动模糊；
- 角色进入阴影；
- 角色在翻滚、跳跃或特殊动作中；
- 角色跑到画面边缘；
- 摄像机碰撞墙体；
- 进入菜单、过场或特殊镜头。

因此视角判断必须结合多种证据。

### 7.1 第三人称证据

```text
检测到稳定的玩家角色
角色位于画面中下部
角色位置连续变化
存在完整人物轮廓
人体关键点成立
角色尺寸符合历史范围
```

### 7.2 第一人称证据

```text
连续多帧未检测到角色
画面中心存在固定准星
画面下方存在武器或手臂
镜头运动与鼠标输入高度一致
游戏本身支持第一人称模式
```

### 7.3 瞄准状态证据

```text
出现准星
画面视野缩窄
人物偏移到左肩或右肩位置
角色局部仍然可见
屏幕边缘出现瞄准UI
镜头转动变得更精细
```

---

## 8. 建议使用四种主要视角状态

至少区分：

```text
第三人称普通
第三人称瞄准
第一人称普通
第一人称瞄准
```

### 8.1 第三人称普通

- 人物通常靠近画面中下部；
- 以角色脚底作为位置锚点；
- 镜头与角色身体朝向可能不一致；
- 适合普通行走和探索。

### 8.2 第三人称瞄准

- 人物可能偏到画面左侧或右侧；
- 准星成为主要瞄准锚点；
- 角色仍然可用于判断自身状态；
- 移动与镜头控制逐渐接近第一人称逻辑。

### 8.3 第一人称普通

- 画面中心代表主要前进方向；
- 重点识别道路、地面和障碍；
- 使用光流判断转向和位移趋势。

### 8.4 第一人称瞄准

- 准星或瞄准镜中心是主要锚点；
- 可缩小分析范围；
- 重点追踪目标相对准星的位置。

## 9. 视角状态机

视角不应因为一帧检测结果就立即切换。

建议使用状态机：

```text
第三人称普通
   ├─ 出现准星、人物偏肩 → 第三人称瞄准
   ├─ 角色消失且第一人称证据成立 → 第一人称普通
   └─ 画面异常 → 无法确定

第三人称瞄准
   ├─ 准星消失、角色恢复中心 → 第三人称普通
   └─ 角色消失、武器视角出现 → 第一人称瞄准

第一人称普通
   ├─ 出现稳定玩家角色 → 第三人称普通
   └─ 出现瞄准UI → 第一人称瞄准

第一人称瞄准
   ├─ 瞄准状态结束 → 第一人称普通
   └─ 出现稳定完整角色 → 第三人称瞄准或普通
```

建议加入：

- 连续帧确认；
- 状态保持时间；
- 切换冷却时间；
- 状态置信度；
- 未知状态；
- 历史视角模式。

## 10. 角色位置变化不能直接代表角色移动

角色在画面中的位置变化可能来自：

```text
角色本身移动
镜头移动
摄像机碰撞
进入瞄准模式
视野缩放
角色被遮挡或检测框变化
```

因此需要同时记录：

```text
角色画面位置变化
背景整体光流
角色肢体动作
键盘输入
鼠标输入
视野变化
准星状态
```

例如：

```text
角色向左移动，背景基本稳定
→ 更可能是角色横向移动

角色位置向左，背景也整体向左
→ 更可能是镜头或摄像机发生移动

角色突然固定在画面侧边，准星出现
→ 更可能进入第三人称瞄准模式
```

## 11. 利用阴影关系判断三维场景

阴影可以用于辅助地形判断，但不应作为主要深度来源。

更合理的定位是：

> 深度、透视和多帧运动负责搭建简易地形；阴影负责补充接地关系、表面方向和高度变化。

### 11.1 阴影可提供的信息

#### 接地关系

角色脚底附近的接触阴影可以辅助判断：

- 角色是否站在地面；
- 是否跳起；
- 是否正在下落；
- 脚底点是否检测正确；
- 当前表面是否发生高度变化。

#### 地面连续性

阴影经过平坦地面时通常比较连续，经过台阶、墙角、坑洞或斜坡时可能：

- 断裂；
- 折转；
- 拉伸；
- 长度突变。

这些变化可以作为路面变化的辅助证据。

#### 表面朝向

连续明暗变化可以辅助估算：

- 平面；
- 斜坡；
- 局部凸起；
- 局部凹陷；
- 表面法线方向。

#### 高度关系

在光源方向已知、地面近似平面、阴影符合真实几何的情况下，可以根据物体与阴影的关系近似估算高度。

### 11.2 游戏阴影的限制

游戏中的阴影可能是：

- 烘焙进贴图的静态阴影；
- 屏幕空间阴影；
- 接触阴影；
- 环境光遮蔽；
- 材质深色；
- 手工制作的假阴影；
- 固定圆形角色阴影；
- 超出渲染距离后消失的动态阴影。

因此系统应当尽量区分：

```text
投射阴影
接触阴影
环境遮蔽
材质深色
角色固定假阴影
```

阴影只能作为辅助证据，而不能单独决定是否存在坑洞或悬崖。

## 12. 建立局部 2.5D 地形图

无需一开始建立完整三维网格。

更适合的是以角色为中心建立局部 2.5D 地形图。

2.5D 可以理解为：

```text
地面坐标 X、Y
+
每个位置的大致高度 Z
+
是否可通行
```

输出可以是：

```text
正前方：平地，可通行
左前方：缓坡，可通行
右前方：墙体，不可通行
前方较远：高度突然下降，疑似悬崖
人物脚下：稳定接地
```

---

## 13. 地形判断的数据融合

建议将多种视觉证据进行融合：

```text
当前游戏画面
  ├─ 语义分割
  │    ├─ 地面
  │    ├─ 墙体
  │    ├─ 台阶
  │    ├─ 水面
  │    └─ 角色和动态物体
  │
  ├─ 单目深度
  │    ├─ 相对距离
  │    ├─ 深度图
  │    └─ 表面方向
  │
  ├─ 连续帧分析
  │    ├─ 光流
  │    ├─ 相机转动
  │    └─ 多视角一致性
  │
  ├─ 阴影分析
  │    ├─ 接地关系
  │    ├─ 表面连续性
  │    └─ 高度变化提示
  │
  ├─ 轮廓与边缘
  │    ├─ 道路边界
  │    ├─ 墙面边界
  │    └─ 断层边缘
  │
  └─ 融合
       ↓
局部地形状态图
```

### 13.1 建议证据权重

```text
多帧视差：高
小地图位置：高
单目深度：中高
地面语义分割：中高
边缘与轮廓：中高
透视线与消失点：中
阴影关系：中低
单帧颜色明暗：低
```

例如：

```text
深度模型判断前方存在断层
+ 地面分割在该位置中断
+ 轮廓存在明显横向边缘
+ 阴影也发生断裂
→ 前方疑似悬崖，置信度较高
```

如果只有画面变暗，而深度、轮廓和连续帧都没有变化，则应更倾向于：

```text
可能是材质或光照变化
不直接判定为障碍
```

## 14. 第三人称与第一人称的地形判断差异

### 14.1 第三人称

以角色脚底为局部地图原点：

```text
角色脚底
  ↓
附近地面区域
  ↓
估算左右和前方高度
  ↓
结合角色阴影判断接地
```

适合判断：

- 跳跃和落地；
- 台阶高度；
- 是否站在坡面；
- 脚底前方是否有落差；
- 角色是否被地形卡住；
- 人物是否走出道路区域。

### 14.2 第一人称

角色不可见时主要依赖：

- 画面下半部分地面分割；
- 单目深度；
- 透视消失点；
- 相机运动视差；
- 场景内固定物体；
- 道路边界和断层边缘。

第一人称中的阴影权重应更低，因为缺少稳定的角色脚底与阴影对应关系。

## 15. 小地图负责全局导航

大多数游戏已经提供小地图、方向箭头、任务路线或点位引导。

因此没有必要完全依靠视觉重新探索整个地图。

小地图主要解决：

- 当前大致位置；
- 目标点方向；
- 路线折点；
- 当前朝向；
- 与目标的距离趋势；
- 是否走偏。

总体结构：

```text
小地图导航层
  ↓
给出大方向、目标点、路线折点

视觉移动层
  ↓
判断道路、墙体、断层、障碍、角色位置

场景记忆层
  ↓
判断这里是否走过，回忆接下来应该怎么走
```

小地图负责“往哪里去”，视觉负责“眼前能不能走”。

---

## 16. 小地图寻路的使用方式

可以识别：

- 玩家箭头；
- 目标标记；
- 路线引导线；
- 道路轮廓；
- 路口；
- 地图旋转方向；
- 距离数值；
- 特殊区域图标。

运行时：

```text
读取小地图目标方向
  ↓
判断角色当前朝向
  ↓
计算需要转动的方向
  ↓
观察主画面前方道路
  ↓
执行短距离移动
  ↓
再次检查小地图位移
```

小地图不一定能够告诉系统：

- 前方是否有悬崖；
- 是否需要跳跃；
- 门是否关闭；
- 是否被怪物或物体挡住；
- 是否走到路边；
- 是否卡在墙角。

因此视觉地形判断作为局部安全修正层。

## 17. 局部安全修正层

小地图与视觉的关系可以是：

```text
小地图：继续向前

视觉判断：
├─ 前方地面连续 → 继续
├─ 前方有小台阶 → 继续或跳跃
├─ 前方出现明显断层 → 停止
├─ 前方是墙 → 调整方向
├─ 道路偏左 → 轻微左修正
├─ 道路偏右 → 轻微右修正
└─ 无法判断 → 减速或重新定位
```

核心原则：

> 小地图解决全局路线，视觉解决最后几米。

## 18. 轻量场景指纹

为了让系统记住走过的位置，可以生成轻量场景指纹，而不是保存大量原始截图。

建议场景指纹包含：

```text
低分辨率深度结构
颜色分布
边缘与轮廓结构
地面可通行区域
小地图局部图案
镜头大致方向
当前视角模式
角色在小地图中的位置
```

### 18.1 一个轻量实现示例

```text
深度图：缩小到 16×9，量化为 16 个等级
颜色图：缩小到 8×8，保存主要颜色
轮廓图：32×18 二值边缘
感知哈希：64～256 位
小地图局部块：16×16 或 32×32
方向：量化为 8 或 16 个方向
```

单个节点只需要几十到几百字节。

### 18.2 为什么要同时保存多种特征

单独使用颜色的问题：

- 白天与黑夜；
- 天气变化；
- 技能光效；
- 阴影变化；
- 画质设置变化。

单独使用深度的问题：

- 镜头稍微转动就会变化；
- 人物和怪物遮挡；
- 深度模型本身有波动；
- 相似走廊深度结构接近。

因此应使用组合相似度：

```text
场景相似度 =
深度结构相似度
+ 轮廓结构相似度
+ 颜色分布相似度
+ 小地图位置相似度
+ 镜头方向相似度
+ 路线进度相似度
```

建议权重：

```text
小地图局部结构：高
深度和道路结构：高
固定边缘轮廓：中高
镜头方向：中高
整体颜色：中低
动态目标：尽量忽略
```

---

## 19. 不对每一帧保存场景

只在关键地点建立记忆节点：

- 道路分叉；
- 转弯；
- 门口；
- 楼梯口；
- 桥头；
- 高低落差；
- 进入或离开建筑；
- 小地图路线明显改变；
- 目标点附近；
- 行走失败或卡住的位置；
- 视觉状态发生明显变化的位置。

形成拓扑路线：

```text
节点 A：桥头
  ↓ 向前
节点 B：道路分叉
  ↓ 右转
节点 C：石门
  ↓ 进入
节点 D：大厅
```

拓扑地图不要求知道精确距离，只需要知道：

```text
这里是什么位置
从这里应该执行什么动作
接下来会看到什么位置
```

## 20. 场景识别的候选筛选

不应将当前画面与整个场景数据库逐一比较。

先使用：

- 小地图当前位置；
- 路线进度；
- 上一个节点；
- 当前方向；
- 最近经过的节点；
- 当前区域或地图名称；

筛选少量候选节点。

然后再进行场景指纹比较：

```text
当前小地图大致位置
  ↓
筛选附近候选节点
  ↓
当前场景指纹与候选节点比较
  ↓
确认最相似节点
  ↓
加载该节点之后的行为
```

例如：

```text
候选节点 17：相似度 0.48
候选节点 18：相似度 0.91
候选节点 19：相似度 0.63

结果：当前更可能位于节点 18
```

## 21. 处理视角变化

同一个地点从不同方向观察时，画面可能完全不同。

因此每个地点可以保存多个方向指纹：

```text
地点节点
├─ 朝北场景指纹
├─ 朝东场景指纹
├─ 朝南场景指纹
└─ 朝西场景指纹
```

也可以按照实际路线保存：

```text
节点
├─ 进入方向指纹
├─ 离开方向指纹
├─ 左转确认指纹
└─ 右转确认指纹
```

再次经过时，根据：

- 小地图箭头方向；
- 当前路线方向；
- 上一个节点；
- 镜头旋转量；
- 预计到达方向；

推测应使用哪个场景指纹。

## 22. 使用短场景序列提高识别稳定性

单帧可能很相似，但连续几帧的变化序列更难完全相同。

例如：

```text
石墙
→ 左侧出现灯柱
→ 道路开始右弯
→ 前方出现拱门
```

可以保存：

```text
节点前指纹
节点中心指纹
节点后指纹
```

匹配时比较最近几秒的场景变化，而不是只比较当前一帧。

这种动态场景指纹适合解决：

- 重复走廊；
- 相似街道；
- 对称房间；
- 相似门口；
- 单帧视觉不稳定。

## 24. 路线节点建议结构

```text
路线节点
├─ 节点编号
├─ 地图或区域名称
├─ 小地图局部指纹
├─ 小地图坐标或相对位置
├─ 场景深度指纹
├─ 场景颜色指纹
├─ 轮廓结构指纹
├─ 镜头方向
├─ 视角模式
├─ 角色脚底位置
├─ 地面可通行方向
├─ 断层风险
├─ 阴影辅助信息
├─ 到下一节点的操作
├─ 预计移动时间
├─ 下一节点编号
├─ 历史成功率
└─ 失败和修正记录
```

如果路线执行成功，可以提高这条路线边的可信度。

如果经常出现：

- 撞墙；
- 掉落；
- 偏航；
- 卡住；
- 进入错误路口；

则修正节点操作或增加新的中间节点。

## 25. 运行循环

完整运行过程可以是：

```text
读取小地图目标
  ↓
识别当前第一/第三人称模式
  ↓
识别角色位置或画面中心
  ↓
计算目标相对方向
  ↓
分析前方地面、道路和障碍
  ↓
判断路面是否连续
  ↓
执行短时间移动
  ↓
检查小地图位移是否符合预期
  ↓
生成当前场景指纹
  ↓
匹配历史地点
  ↓
更新路线节点与经验
  ↓
继续下一轮观察
```

不建议一开始长时间持续按键。

更适合：

```text
观察
→ 前进 100～300 毫秒
→ 再观察
→ 修正方向
```

道路判断稳定后，可以根据置信度延长控制周期。

## 26. 阶段性实现顺序

### 第一阶段：视角与角色锚点

实现：

- 第一人称、第三人称识别；
- 角色检测；
- 角色脚底估算；
- 准星识别；
- 画面中心坐标；
- 简单状态机。

输出：

- 当前视角模式；
- 当前移动参考原点；
- 角色或准星位置。

### 第二阶段：小地图方向读取

实现：

- 小地图区域截取；
- 玩家箭头识别；
- 目标点识别；
- 路线引导线识别；
- 当前方向与目标方向计算。

输出：

- 目标位于左前、正前、右前等方向；
- 当前是否偏离路线。

### 第三阶段：局部道路判断

实现：

- 地面区域分割；
- 道路边界；
- 墙体和障碍；
- 简单断层判断；
- 角色脚底周围可通行区域。

输出：

- 前方可通行；
- 前方疑似墙体；
- 前方疑似断层；
- 建议左修正或右修正。

### 第四阶段：连续帧与镜头运动

实现：

- 背景光流；
- 镜头转向判断；
- 角色运动与镜头运动区分；
- 多帧地面连续性验证。

输出：

- 镜头相对转动；
- 当前是否在移动；
- 地形判断是否稳定。

### 第五阶段：轻量场景记忆

实现：

- 深度图缩略；
- 颜色缩略；
- 边缘指纹；
- 小地图局部指纹；
- 场景相似度比较。

输出：

- 是否到达历史节点；
- 最可能的候选地点；
- 后续路线行为。

### 第六阶段：拓扑路线学习

实现：

- 关键地点自动建节点；
- 节点之间建立路线边；
- 保存操作和结果；
- 统计成功率；
- 失败后修正路线。

输出：

- 可复用路线；
- 已学习节点；
- 可靠路径和风险位置。

## 27. 核心结论

整个方案可以概括为：

> 利用小地图完成全局导航，利用角色位置或画面中心建立移动参考，利用深度、分割、轮廓、多帧运动和阴影判断局部道路，再通过轻量场景指纹记住走过的位置。

其中：

```text
YOLO：识别目标
SAM：提取区域
OpenCV：处理几何、光流和哈希
深度模型：判断远近和路面结构
阴影：辅助判断接地与局部高度变化
小地图：负责全局方向
场景指纹：负责地点记忆
拓扑节点：负责路线复用
```

最终目标不是完整理解整个三维世界，而是实现一种实用的能力：

```text
会看地图
会看路
会避开明显断层
会认出走过的地方
会记住关键路口
会根据成功经验复用路线
```

这已经明显高于固定按键和固定时间宏，同时又比完整三维重建、通用游戏智能体更容易逐步落地。
