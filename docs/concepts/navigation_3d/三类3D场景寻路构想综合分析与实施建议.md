# 三类3D场景寻路构想综合分析与实施建议

> 文档性质：对三篇3D场景寻路构想的综合分析、架构收束与实施顺序建议
>
> 原始构想：[视觉移动、地形判断与场景记忆](面向游戏的视觉移动_地形判断与场景记忆方案.md) · [游戏立体地图与分层寻路](游戏立体地图与分层寻路方案.md) · [无小地图游戏副本探索与交互](无小地图游戏副本的视觉探索与交互方案.md)
>
> 现有架构基础：[分层关系网与复合能力子图构想](../interface_discovery/分层关系网与复合能力子图构想.md) · [3D场景视角方向观测与闭环控制构想](../interface_discovery/3D场景视角方向观测与闭环控制构想.md)
>
> 执行与故障基础：[Whimbox自动跑图视觉闭环](../game_ai_planning/12-Whimbox自动跑图视觉闭环.md) · [游戏瞬态故障判读与置信度隔离构想](../interface_discovery/游戏瞬态故障判读与置信度隔离构想.md)

## 1. 总体判断

三篇文档的方向整体成立，而且彼此互补，不是三个需要竞争取舍的完整方案。

它们分别对应三个不同尺度：

```text
局部控制层
-> 眼前怎样安全移动

空间拓扑层
-> 地点、楼层和入口怎样连接

副本任务层
-> 机关、战斗、收集和场景事件怎样推进
```

最合适的组合方式是：

| 文档 | 推荐定位 | 主要职责 |
| --- | --- | --- |
| 视觉移动、地形判断与场景记忆 | 通用局部移动底座 | 视角、短距离移动、局部风险、场景候选检索 |
| 游戏立体地图与分层寻路 | 分层空间拓扑 | `MapSpace`、楼层、Portal、RouteEdge和跨层规划 |
| 无小地图副本探索与交互 | `DungeonExplorer`复合能力 | 走廊、房间扫描、互动、事件进度和有界探索 |

三篇共同选择“不先完整重建三维世界”，这是正确的工程方向。真正需要调整的是数据边界、证据语义、图类型和实现顺序。

## 2. 推荐的总体系统结构

三篇构想可以组合为：

```text
副本目标和ProgressFacts
-> 决定下一项任务目标

SceneTopology / SpatialTopology
-> 选择目标地点、出口或Portal

TraversalDefinition
-> 引用已发布CapabilitySpec

LocalNavigationController
-> 根据局部风险执行短距离移动

ViewDirectionController
-> 对路、扫描、对准目标

StepAttempt
-> 保存前置观察、真实输入、后置验证和结果

RecoveryRun
-> 独立处理重定位、返回、重载和其他恢复
```

这个结构中，LLM可以解释地点、任务和未知现象，也可以从已发布能力中生成候选计划，但不能决定地形是否安全、输入是否成功或关系是否成立。

## 3. 必须分开的四类图

三篇文档多次使用“地图、节点、关系网、状态图”，但这些结构不能混成一张图。

### 3.1 地图配准图

```text
节点：地图块、局部坐标帧、位姿候选
边：重叠、坐标变换、回环约束
```

它负责回答地图块之间的几何关系。

### 3.2 空间拓扑图

```text
节点：PlaceAnchor、PortalNode、房间、路口、楼层入口
边：TraversalDefinition、RouteEdge
```

它负责回答地点之间是否相连，可以存在道路回环、单向跳落和支路。

### 3.3 进度和状态关系

```text
事实：door_open、switch_active、battle_complete、chest_collected
转换：执行能力后事实怎样变化
```

同一个房间在门开启前后仍可以是同一个地点，只是进度事实不同，不必复制成两个空间节点。

### 3.4 能力模块DAG

```text
能力：follow_corridor、scan_room、use_elevator、approach_target
模块：DungeonExplorer、StairTraversal、ElevatorTraversal
依赖：CapabilitySpec、GraphModule、Adapter
```

定义依赖可以约束为DAG；空间拓扑本身允许回环。`SceneTopology`不是`GraphModule`。

## 4. 第一篇：视觉移动、地形判断与场景记忆

## 4.1 值得保留的设计

以下内容方向正确：

- 不追求完整三维重建；
- 第一人称和第三人称使用不同视觉锚点；
- 检测不到角色不直接等于第一人称；
- 身体朝向、镜头朝向和实际运动方向分开；
- 小地图提供全局方向，主画面处理局部风险；
- 采用短时间输入、重新截图、继续修正的闭环；
- 只在路口、门口、楼梯等关键位置建立场景记忆；
- 同一地点保存多个方向指纹；
- 使用短序列而不是单帧确认重复场景。

这些内容适合成为后续所有大世界、立体地图和无小地图副本共用的局部移动底座。

## 4.2 可通行性不是纯视觉属性

当前构想容易把“视觉上像地面”直接映射为“角色可以通过”。真实关系应为：

```text
Traversability
= 地形几何证据
× 当前角色能力
× 移动模式
× 游戏规则
× 风险预算
```

同一片水面、墙体、台阶或悬崖，在以下状态下结论可能不同：

- 普通角色；
- 可以攀爬的角色；
- 游泳状态；
- 飞行状态；
- 特殊技能状态；
- 载具状态；
- 游戏禁止操作的剧情状态。

因此视觉模块应输出地形和风险证据，最终可通行判定由`ControlContext`及能力守卫完成。

## 4.3 第一版不要承诺米制2.5D地图

普通单目画面存在以下限制：

- 深度通常只有相对尺度；
- FOV、镜头俯仰和摄像机高度会改变投影；
- 纯旋转不能产生可用平移视差；
- 桥梁、楼梯和悬空平台不满足单值高度场；
- 风格化画面、透明材质和特效会干扰深度模型。

第一版更适合输出自我中心风险格：

```text
EgocentricRiskGrid
├── direction_sector
├── distance_band: near / middle / far
├── ground_continuity_probability
├── obstacle_probability
├── drop_risk
├── evidence_ids
└── UNKNOWN
```

它不要求恢复真实米制坐标，只回答下一小段动作是否可以继续。

## 4.4 固定证据权重不能作为运行规则

“多帧视差高、深度中高、阴影中低”可以作为研究直觉，但不能直接成为固定融合公式。

证据有效性随上下文变化：

- 多帧视差只有在存在平移、场景近似刚性且跟踪可靠时才有效；
- 小地图位置不是悬崖证据；
- 阴影和深度可能同时被同一种渲染效果误导；
- 镜头抖动、FOV变化和特效会污染光流。

安全门禁应采用：

```text
证据充分且一致
-> 允许有限移动

证据冲突或不足
-> UNKNOWN
-> 减速或停止
-> 改变观察姿态
-> 仍不明确则换路
```

应优先统计“把危险误判成安全”的次数，而不是只看总体准确率。

## 4.5 模型名称不等于已经获得语义能力

YOLO、SAM、姿态模型和OpenCV的真实边界是：

- SAM可以提供掩码，但不会自动知道掩码属于地面还是墙体；
- YOLO需要游戏相关类别和标注；
- 通用人体姿态模型可能无法处理二次元服装、背视角和技能特效；
- 光流会被动态背景、粒子和镜头碰撞干扰；
- 深度模型需要针对真实游戏画面验证。

每个模型都需要游戏Adapter、固定回放集和明确失败状态，不能把算法名称直接当成稳定模块能力。

## 4.6 四种视角只能作为首个Profile

第三人称普通、第三人称瞄准、第一人称普通和第一人称瞄准适合第一批实验，但不是通用视角本体。

后续还会出现：

```text
锁定目标
固定镜头
俯视模式
载具
游泳
攀爬
飞行
拍照
特殊技能
过场
摄像机碰撞
输入异常
```

公共层应使用因子化`ViewStateSnapshot`，具体游戏Profile声明可用模式和转换证据。

## 4.7 小地图应是可替换定位Provider

“小地图负责全局”不能成为固定架构依赖。小地图可能旋转、缩放、隐藏、换层或不存在。

建议抽象为：

```text
GlobalLocalizationProvider
├── MinimapProvider
├── WorldMapProvider
├── LandmarkSequenceProvider
└── BreadcrumbProvider
```

无小地图副本只是替换全局定位Provider，不应重新实现另一套视角和局部移动闭环。

## 4.8 路线节点需要拆分

原文的路线节点同时保存地点、指纹、风险、动作、下一节点、成功率和失败记录，职责过多。

建议拆成：

```text
PlaceAnchor
-> 地点、MapSpace和位置候选

SceneDescriptorVariant
-> 某地点、方向和版本下的视觉指纹

TraversalDefinition
-> from、to、守卫、capability_ref、成本和风险

LocalTraversabilityObservation
-> 当前帧或短序列的临时风险图

StepAttempt
-> 一次真实执行、证据和ExecutionOutcome

CalibrationProfile
-> 输入、镜头、FOV和移动响应模型
```

运行记录不能写回定义节点。

## 4.9 场景指纹只负责候选召回

低分辨率深度、颜色、边缘和感知哈希不足以单独证明地点身份。

场景检索至少需要：

- `top-k`候选；
- 第一名和第二名的分数间隔门禁；
- 前驱与后继序列一致性；
- 行进方向和`MapSpace`约束；
- 描述器、游戏版本和画质版本；
- 动态对象屏蔽与特征TTL；
- 回环确认后再合并节点；
- 无法消歧时保留多个位置假设。

不需要在第一阶段承诺“每个节点只有几十到几百字节”。元数据、版本和索引通常远大于缩略特征本身。

## 5. 第二篇：游戏立体地图与分层寻路

## 5.1 核心方向成立

以下总体结构适合第一代立体地图：

```text
全局使用分层2.5D拓扑
-> 层内使用二维定位和寻路
-> 层间通过楼梯、电梯、跳落和传送连接
-> 局部视觉判断眼前通行风险
```

它能够处理地面、高架、地下、建筑楼层和洞穴等常见重叠空间。

## 5.2 不使用全局整数楼层作为位置身份

推荐空间位置结构：

```text
SpatialLocation
├── map_space_id
├── coordinate_type
├── local_position: LocalMapPx或局部位置候选
├── floor_label
├── local_height_relation
├── localization_candidates
└── evidence_ids
```

`floor_label=地下一层`只是语义标签，不是全局坐标。不同`MapSpace`只有在存在经过验证的`CoordinateTransform`时才能直接比较位置。

## 5.3 “层级+1”只能作为先验

楼梯事件可能漏记，电梯可能跨多层，角色也可能传送、死亡或重新加载。

正确过程是：

```text
执行上楼能力
-> 预测目标MapSpace或楼层候选
-> 观察楼层UI、出口场景和地标
-> 确认后更新当前空间
-> 无法确认则返回UNKNOWN
```

不能只根据事件累计无限维护整数层级。

## 5.4 楼层不一定等于MapSpace

`MapSpace`应按“能否使用同一连续坐标和定位方法”划分：

- 同一楼层的两个不连续区域可能是两个MapSpace；
- 连续盘山道路可能跨越多个高度带但仍是同一MapSpace；
- 很长且需要独立定位的楼梯可以成为连接空间；
- 电梯或加载式入口可能直接连接两个不相邻MapSpace。

## 5.5 层间连接的推荐结构

```text
PortalNode
├── source_map_space
├── target_map_space_candidates
├── entry_anchor
├── exit_anchor
├── directionality
├── applicability
├── risk
├── availability_state
└── executor_ref

RouteEdge
├── from
├── to
├── preconditions
├── postcondition_verifier
├── capability_ref
├── expected_cost
└── metric_profile_ref
```

楼梯可以由`ContinuousController`或`CompositeCapability`执行；电梯更适合作为`GraphModule`，运行时创建`GraphCallRun`。

## 5.6 单目深度只作为局部安全门禁

第一阶段中，深度和地形模块只建议输出：

```text
继续
减速
需要更多证据
禁止前进
```

它们不能直接创建楼梯边、悬崖边或修改楼层身份。

## 5.7 动态可用性必须与空间关系分开

门、电梯、平台、任务状态和角色能力可能改变路线当前是否可用。

需要分别维护：

```text
空间关系是否存在
当前是否可通行
条件执行可靠性
感知可靠性
输入路由健康
瞬态游戏故障率
恢复成功率
```

电梯按钮变灰或游戏瞬态异常不能降低楼层连接本身的关系正确性。

## 5.8 完全三维区域单独处理

飞行、水下和太空区域不能简单理解为二维移动增加“上、下”两个动作。

它们还可能涉及：

- 三维位置和姿态；
- 俯仰与翻滚；
- 惯性和速度；
- 上浮、下潜或升力；
- 障碍体积；
- 能量、氧气和能力状态；
- 不同控制模式。

因此应作为独立`LocomotionProfile`和专用控制器，在分层地面导航稳定后再验证。

## 6. 第三篇：无小地图副本探索与交互

## 6.1 推荐定位

这篇最适合实现为`DungeonExplorer`复合能力：

```text
局部可通行区域跟随
+ 房间主动扫描
+ 目标视觉伺服
+ 交互后置验证
+ 稀疏空间拓扑
+ 副本进度事实
+ 有界异常恢复
```

它比通用大世界3D自主寻路更适合作为第一批落地场景，但适用范围必须限制为：

- 单线或少量支路；
- 没有复杂跳跃；
- 可以停下来观察；
- 失败能够返回或重新进入；
- 场景具有较稳定的走廊、房间和门口结构。

## 6.2 不需要完整地图，但仍需要两类地图

更准确的表述是：

> 不需要长期维护全局稠密坐标地图，但仍需要短时局部可通行图和持久稀疏拓扑图。

```text
LocalNavigationPatch
-> 自由空间、障碍、危险边界和当前运动响应

SceneTopology
-> 房间、走廊、入口、出口和TraversalEdge
```

## 6.3 空间拓扑和副本进度必须分开

```text
SceneTopology
-> 我在哪里、哪些地点相连

ProgressFacts
-> 哪些机关已完成、哪些门已打开、战斗是否结束
```

同一个房间在门开启前后通常仍是同一个`PlaceAnchor`，只是`door_open`事实变化。

## 6.4 固定左中右扫描没有覆盖保证

房间扫描应以稳定参考方向划分重叠扇区。例如以入口反方向作为局部`0°`，记录：

```text
ScanCoverage
├── horizontal_sectors
├── pitch_bands
├── observed_sectors
├── occluded_sectors
├── rescan_required
├── target_observation_refs
└── verified_exit_pose
```

扫描结束后需要恢复一个已验证的移动姿态。否则系统旋转多轮后，不知道扫描是否完整，也不知道如何继续离开房间。

## 6.5 场景指纹不能独立保证原路返回

返回支路至少需要保存：

- 入口视觉锚点；
- 出口视觉锚点；
- 节点局部参考方向；
- 到达时的镜头和身体姿态；
- 中间地标序列；
- 边是否可逆；
- 反向通过条件。

场景指纹只帮助召回当前位置候选，真正返回还需要执行反向TraversalEdge并验证每个中间节点。

## 6.6 目标观察和持久目标分开

屏幕中的发光点首先只是`TargetObservation`。经过多帧跟踪、场景绑定和身份验证后，才能形成`TargetHypothesis`。

否则可能出现：

- 镜头旋转后重复创建同一目标；
- 把两个相似金币错误合并；
- 把装饰光效当成可交互物；
- 目标消失后错误记录为拾取成功。

## 6.7 主路线使用Frontier而不是立即确定

道路宽度、灯光、门框和远景都只是弱证据。

建议建立：

```text
FrontierEdge
├── state: UNKNOWN / EXPLORED / BLOCKED / ONE_WAY
├── route_score
├── reversibility
├── risk
├── information_gain
├── progress_relevance
└── evidence_ids
```

对于少量支路，可以使用有预算DFS或回溯探索。进入不可逆边、跳落点或可能触发剧情的门之前，先检查未完成的可选目标。

## 6.8 目标优先级需要风险策略

固定“高价值宝箱、机关、普通拾取物”顺序不够安全。评分至少考虑：

```text
是否任务必需
是否即将消失
是否不可逆
是否可能触发剧情或锁门
回收成本
风险
用户是否要求全收集
```

## 6.9 未知解密必须有安全边界

未知规则不能默认有限试探一定能够解决。试探前需要判断：

- 操作是否可逆；
- 是否存在惩罚或资源消耗；
- 是否具有可靠重置方式；
- 状态数量和搜索预算；
- 是否可能触发不可逆剧情；
- 何时请求用户示范。

状态不可可靠识别、动作不可逆或搜索空间增长过快时，应停止自动探索。

## 6.10 战斗与探索分离是正确方向

战斗会破坏光流、场景指纹、可通行判断和目标跟踪，因此应通过独立模式和能力处理：

```text
探索
-> 战斗中断
-> 战斗结束验证
-> 收集掉落
-> 重新扫描房间
-> 重新定位
-> 创建新的探索StepAttempt
```

战斗结束不代表原探索Attempt自动成功。

## 7. 场景记忆的正确作用

场景描述器应作为节点的观察模型，而不是节点机器身份本身。

推荐结构：

```text
PlaceAnchor
├── map_space_id
├── local_reference_frame
├── incoming_edges
├── outgoing_frontiers
└── descriptor_variant_refs

SceneDescriptorVariant
├── viewing_direction
├── camera_mode
├── progress_fact_scope
├── visual_features
├── detector_revision
├── game_version
└── ttl_or_validity
```

地点确认应使用：

```text
当前视觉候选
+ 上一个地点
+ 刚经过的TraversalEdge
+ 当前方向
+ ProgressFacts
+ 多帧序列
```

无法消歧时保留位置候选，不强制选择最高相似度节点。

## 8. 公共执行契约

三篇都应复用现有执行协议：

```text
PlanRun
-> CapabilityRun
-> StepAttempt
-> 可选GraphCallRun
-> 可选RecoveryRun
```

每次转向、短移动、跨层、扫描和互动都应产生可验证Attempt。

公共结果统一为：

```text
ExecutionOutcome = SUCCEEDED / FAILED / UNKNOWN / CANCELLED / BLOCKED
```

专业模块只提供`reason_code`，统一归因流程生成`FailureAttribution`和`SampleDisposition`。

输入错投、截图旧帧、游戏Bug、感知失败和用户取消不能直接降低路线或关系可信度。

## 9. 输入与上下文安全

所有连续移动和视角控制至少需要：

```text
game_control:<window_instance_id>
desktop_physical_input
FocusLease和focus_epoch
control_schema_epoch
新鲜frame_id
停止与按键释放
无推进和振荡看门狗
```

固定`100～300ms`只能作为初始探测参数。正式控制周期应根据角色速度、风险距离、感知延迟和停止响应动态调整。

## 10. 建议的统一实施顺序

### 第一阶段：限定环境与采集协议

- 固定一个游戏；
- 固定第三人称普通模式；
- 选择安全平坦区域；
- 统一截图、输入、窗口epoch、帧时间和MapSpace；
- 建立离线回放数据集。

### 第二阶段：基础视角和移动原语

- 小角度水平转向；
- 目标方向对准；
- 短距离前进；
- 停止和按键释放；
- 输入归属验证；
- 撞墙与无推进检测。

### 第三阶段：走廊跟随

- 直线走廊；
- 缓慢弯道；
- 普通楼梯；
- 死路；
- 危险边界停止；
- 暂不加入物品和解密。

### 第四阶段：房间扫描与单目标互动

- 走廊和房间状态切换；
- 有覆盖记录的扇区扫描；
- 一种静态目标；
- 目标居中和接近；
- 交互提示绑定；
- 后置结果验证。

### 第五阶段：稀疏拓扑与支路返回

- 两个房间；
- 一个岔路；
- 一条短支路；
- 反向返回；
- 重复纹理和场景候选消歧；
- Frontier状态和探索预算。

### 第六阶段：分层空间

- 人工建立两个MapSpace；
- 一个楼梯；
- 一个单向跳落点；
- 出口重定位；
- 跨层路径计算；
- 电梯GraphModule。

### 第七阶段：局部地形风险

- 平地与墙体；
- 道路边界；
- 坡面和台阶；
- 动态障碍；
- 最后单独验证悬崖和断层。

### 第八阶段：进度、战斗和解密

- 门和机关ProgressFacts；
- 战斗中断和恢复；
- 固定解密；
- 有界未知解密；
- 用户示范；

### 第九阶段：复杂运动模式

- 载具；
- 连续高度；
- 飞行和水下专用控制器。

## 11. 第一阶段验收重点

第一批验收目标不应是“自动通关整个副本”，而应分别证明：

```text
能够安全沿一段路移动
能够在UNKNOWN时及时停止
能够完整扫描一个房间
能够可靠处理一种互动目标
能够识别并返回一个岔路
能够通过一个楼梯并重新确认MapSpace
```

建议记录：

- 每米碰撞次数；
- 危险误判为安全的次数；
- `UNKNOWN`比例；
- 停止延迟和停止距离；
- 输入错投次数；
- 场景假回环率；
- 地点`top-k`召回率；
- 支路返回成功率；
- 跨层重定位成功率；
- 互动后置验证准确率；
- 故障样本归因正确率。

## 12. 当前最明显的问题

三篇当前没有引用现有架构文档，也没有使用已经统一的公共契约。主要需要回填：

```text
StateDefinition / TransitionDefinition / CapabilitySpec
MapSpace / LocalMapPx
ViewStateSnapshot / ViewDirectionController
ContinuousController / CalibrationProfile
PlanRun / CapabilityRun / StepAttempt
GraphCallRun / RecoveryRun
ExecutionOutcome
FailureAttribution / SampleDisposition
focus_epoch / control_schema_epoch
```

另外还应修改以下旧口径：

| 当前表述 | 推荐调整 |
| --- | --- |
| 状态置信度 | 拆分视角、定位、地形、地点匹配和证据新鲜度 |
| 历史成功率 | 改为条件执行可靠性并先做故障归因 |
| 层级+1 | 只作位置预测，出口证据确认后更新 |
| 场景指纹确认地点 | 只召回候选，结合拓扑和序列消歧 |

| 小地图固定负责全局 | 改为可替换GlobalLocalizationProvider |
| 有限试探解决解密 | 增加可逆性、重置方法、预算和风险门禁 |

## 13. 最终结论

三篇构想可以组合为一套可逐步实现的3D场景导航体系：

```text
视觉移动文档
-> 提供局部安全移动和场景观察

立体地图文档
-> 提供MapSpace、层间Portal和空间规划

无小地图副本文档
-> 提供DungeonExplorer、ProgressFacts和探索策略
```

最值得坚持的方向是：

> 不先追求完整三维重建，而是使用局部风险观察、稀疏空间拓扑、任务进度事实和可验证能力闭环，逐步获得“会看路、会认路、会跨层、会探索、会交互”的能力。

最需要避免的是：

> 把视觉相似度当成地点事实，把单目深度当成可通行真值，把楼层事件当成最终定位，把一次成功率直接写回关系网，以及把空间拓扑、任务状态和能力DAG混成同一张图。
