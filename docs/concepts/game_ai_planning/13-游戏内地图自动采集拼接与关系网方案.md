# 游戏内地图自动采集、拼接与关系网方案

## 1. 文档目标

本文讨论一个不依赖人工获取完整大世界地图的替代方案：

> 由工具自动截取游戏内大地图，拼接成可用于视觉定位的局部或全局底图，并将传送锚点、入口和路线组织成关系网。

本文重点回答：

1. 能否直接利用游戏内大地图自动建图；
2. 没有游戏原生世界坐标时如何建立自己的坐标；
3. 传送锚点会干扰还是帮助建图；
4. 只有小地图时能否边走边建图；
5. OCR、YOLO、CLIP、SAM 和传统视觉分别承担什么职责；
6. 如何按基础模块逐步验证，而不是完成整套系统后再测试。

## 2. 核心结论

可以不人工获取完整世界地图，也不需要一开始就拥有游戏原生坐标。

当前更合适的总体方向是：

```text
游戏内大地图自动拼接
→ 形成视觉栅格底图

传送锚点、入口和地点识别
→ 形成语义关系节点

游戏主界面小地图
→ 负责运行时连续定位

用户实际走过的路线
→ 形成节点之间的可执行边
```

最终系统保存的不应只有一张大图，而应由四层组成：

```text
地图栅格层
+
地点关系网
+
动作执行记录
+
定位与执行置信度
```

这比单纯复制 Whimbox 的“固定地图 PNG + 路线点”更适合关系网驱动的规划系统。

## 3. 三种可选建图方式

| 方案 | 实现难度 | 全局一致性 | 适合场景 |
| --- | ---: | ---: | --- |
| 自动截取并拼接游戏内大地图 | 中 | 较高 | 游戏有可平移、可缩放的大地图 |
| 只靠小地图边走边拼接 | 高 | 较低，需要回环修正 | 游戏没有完整大地图或大地图不可拖动 |
| 不生成完整地图，只建立地点关系网 | 低到中 | 不要求连续全局坐标 | 主要目标是复现步骤和规划节点路径 |

推荐使用混合方案：

```text
大地图提供低成本全局底图
小地图提供实时位置更新
关系网负责语义、规划和执行
```

没有必要在项目第一阶段直接挑战完全依赖小地图的视觉 SLAM。

## 4. 方案一：自动截取游戏内大地图

### 4.1 为什么优先使用游戏内大地图

游戏内大地图通常具有以下特征：

- 地图朝向固定，通常北方朝上；
- 缩放级别可以控制；
- 拖动主要表现为二维平移；
- 地形纹理在一次游戏版本中相对稳定；
- 可以反复打开和重新采集；
- 传送锚点、地区入口等地标位置固定；
- 单次截图覆盖范围远大于小地图。

这使它比主界面小地图更容易完成几何拼接。

### 4.2 自动采集主流程

推荐的第一版流程：

```text
打开游戏内大地图
→ 确认地图页面稳定
→ 固定游戏窗口分辨率
→ 固定地图缩放级别
→ 检测并裁出地图有效显示区域
→ 截取第一张地图块
→ 拖动地图并截取下一张
→ 计算相邻截图的真实重叠位移
→ 写入地图块坐标
→ 到达边界后换行
→ 使用蛇形路径覆盖区域
```

建议相邻地图块保留 30%～50% 的重叠区域。重叠太少会降低配准稳定性；重叠太多则会增加截图和拼接数量。

### 4.3 蛇形扫描

完整区域可以按蛇形顺序采集：

```text
第1行：左 → 右
                ↓
第2行：右 → 左
                ↓
第3行：左 → 右
```

这样可以减少每行结束后返回同一侧的额外拖动。

系统需要记录：

- 当前扫描行列；
- 上一张截图；
- 请求拖动量；
- 实际图像位移；
- 地图块在自定义地图坐标中的位置；
- 当前缩放级别；
- 地图边界状态；
- 配准置信度。

### 4.4 不要直接相信鼠标拖动距离

地图移动量不能简单假设为：

```text
地图位移 = 鼠标移动像素
```

实际结果可能受到以下因素影响：

- 游戏窗口分辨率；
- 地图缩放等级；
- 鼠标输入缩放；
- 地图拖动惯性；
- 边界吸附；
- 拖动过程中的掉帧；
- UI 动画；
- 鼠标事件整数截断。

因此，每次拖动后应通过图像本身测量真实位移：

```text
上一张地图块
+
当前地图块
→ 图像配准
→ 实际(dx, dy)
→ 更新地图块坐标
```

鼠标移动量只用于产生动作，不应直接作为最终地图坐标证据。

地图拖动应实现为`ContinuousController`，而不是普通鼠标宏：

```text
观察当前地图中心和缩放级别
-> 读取匹配环境指纹的CalibrationProfile
-> 发送有限拖动量
-> 图像配准测量实际位移
-> 检查边界、滞回和无推进
-> 继续、重定位、重校准或停止
```

控制器提交拖动前必须持有`desktop_physical_input`和有效`focus_epoch`。窗口尺寸、DPI、地图缩放或输入后端变化时，旧校准立即失效。

## 5. 地图块的图像配准

### 5.1 配准目标

对于固定朝向、固定缩放的大地图，相邻截图之间通常只有平移，理想情况下不需要完整透视变换。

第一阶段需要估计：

```text
current_tile = previous_tile + translation(dx, dy)
```

只有在实际测试发现地图存在缩放动画、旋转或透视变化时，才升级到更复杂的仿射或单应性模型。

### 5.2 可选算法

| 方法 | 优点 | 局限 | 建议用途 |
| --- | --- | --- | --- |
| 相位相关 `phaseCorrelate` | 对纯平移快，输出直接 | 需要足够纹理，怕大面积UI遮挡 | 固定缩放地图首选验证 |
| ORB/AKAZE | 免费、速度较快 | 弱纹理和重复图案下不稳定 | CPU基础实现 |
| SIFT | 特征稳定、尺度适应较好 | 计算量较高 | 精度验证和回环匹配 |
| 模板匹配 | 简单、直观 | 搜索范围大时成本高 | 已知拖动方向和范围 |
| 学习型关键点 | 复杂场景更强 | 模型、部署和GPU成本更高 | 后期升级，不用于第一版 |

第一版建议先验证：

```text
固定缩放 + 固定朝向 + 相位相关/模板匹配
```

如果地图纹理重复导致误匹配，再加入 ORB、SIFT 或多候选验证。

### 5.3 配准不能只输出一个坐标

推荐输出结构化结果：

```json
{
  "translation": [-812.4, 2.1],
  "method": "phase_correlation",
  "confidence": 0.93,
  "overlap_ratio": 0.42,
  "inlier_count": 0,
  "status": "accepted"
}
```

如果使用特征点方法，还应保存：

- 原始匹配数量；
- RANSAC 内点数量；
- 内点比例；
- 位移方差；
- 候选之间的分数差。

## 6. 没有游戏世界坐标时如何建立基准

### 6.1 定义自有坐标 LocalMapPx

系统可以自行定义地图坐标，不要求与游戏内部坐标一致。

例如第一张地图截图的中心定义为：

```text
LocalMapPx = (0, 0)
```

后续通过图像配准得到：

```text
第一张中心：(0, 0)
第二张中心：(820, 3)
第三张中心：(1638, 2)
```

少量纵向偏移可能来自配准误差，应由全局优化或回环检测进一步修正。

### 6.2 LocalMapPx 的用途

所有系统内部空间数据都可以记录为 `LocalMapPx`：

- 地图块位置；
- 传送锚点位置；
- 区域入口；
- 任务目标；
- 路线点；
- 已探索范围；
- 关系节点空间位置；
- 节点周围视觉特征。

只要采集、定位、路线和节点都使用同一坐标，就不需要第一阶段获得游戏原生坐标。

### 6.3 多区域地图

如果不同地图区域不连续，不应强行拼进同一张无限画布。可以为每个区域建立独立坐标系：

```text
MapSpace: miraland_main
MapSpace: home
MapSpace: underground_01
MapSpace: dungeon_12
```

不同 `MapSpace` 之间通过关系边连接：

```text
传送
区域入口
电梯
楼梯
副本加载
剧情切换
```

这比强行要求所有地点共享一个二维连续坐标更适合立体或分层游戏世界。

## 7. 传送锚点的作用

### 7.1 传送锚点不是主要障碍

传送锚点不会阻止地图拼接。处理正确时，它们反而是非常有价值的固定语义地标。

推荐将地图信息拆为两层：

```text
基础地图层：地形、道路、河流、建筑轮廓
语义节点层：传送锚点、入口、商店、任务点
```

传送锚点不应直接烧录为基础地形的一部分，而应独立保存为语义节点。

### 7.2 传送锚点作为关系节点

一个锚点节点可以保存：

```json
{
  "node_id": "teleporter_florawish_001",
  "type": "teleporter",
  "name": "搭配师协会前",
  "map_space": "miraland_main",
  "position": [18230.5, 14520.2],
  "visual_evidence": [],
  "unlock_state": "confirmed",
  "confidence": 0.98
}
```

节点可以连接：

```text
锚点A
├─ 传送到锚点B
├─ 向北步行到区域入口
├─ 向东步行到采集点
└─ 打开地图后选择某地区
```

### 7.3 传送也是重新定位机会

传送成功后，角色会出现在一个已知锚点附近。系统可以利用这一点重置累计定位误差：

```text
执行传送
→ OCR/页面判断确认成功
→ 小地图确认地点特征
→ 当前节点设置为目标锚点
→ LocalMapPx重置到锚点坐标
```

所以传送边不仅是快速移动手段，也可以作为定位校准边。

### 7.4 相同图标造成的误匹配

许多传送锚点使用相同图标。如果直接把图标像素交给地图拼接或地点识别，可能出现：

- 不同锚点被误认为同一地点；
- 特征匹配集中在重复图标；
- 地图块被错误对齐；
- 选中、未选中、悬停状态产生外观变化。

建议：

1. 拼接基础地图时屏蔽锚点图标区域，或降低其特征权重；
2. 单独检测锚点图标；
3. 使用锚点周围的地形上下文确定身份；
4. 点击锚点后使用 OCR 读取名称；
5. 不仅凭图标形状判定具体锚点。

## 8. 地图有效区域和UI遮挡

### 8.1 先识别地图画布

完整游戏截图中通常还包括：

- 地图标题；
- 区域切换按钮；
- 缩放按钮；
- 任务列表；
- 筛选按钮；
- 角色或光标标记；
- 地图边框；
- 弹出说明框。

拼接前应提取稳定的地图画布 ROI：

```text
完整游戏截图
→ 页面确认
→ 固定ROI裁剪或画布检测
→ UI遮罩
→ 地图块
```

第一版优先使用固定 ROI，因为它可验证、成本低。只有窗口布局变化频繁时，再引入 SAM 或目标检测自动提取画布。

### 8.2 动态覆盖层

需要屏蔽或单独保存的动态元素包括：

- 当前玩家位置；
- 鼠标悬停高亮；
- 选中的传送点；
- 任务追踪圆；
- 临时活动图标；
- 队友位置；
- 地图提示气泡；
- 未探索迷雾。

不要把动态元素直接混入基础地图拼接，否则同一位置在不同时刻会出现不同像素。

## 9. 如何判断扫描到地图边界

地图拖到边界时，鼠标仍然可能移动，但地图画面不再按照请求量变化。

可以综合判断：

```text
请求拖动量明显不为0
+
图像配准测得实际位移接近0
+
连续多次结果一致
→ 判定到达地图边界
```

还可以观察：

- 新地图块有效内容增长是否停止；
- 重叠区域是否接近100%；
- 地图背景边界颜色是否出现；
- 屏幕坐标是否出现限制动画；
- 拖动方向是否被游戏吸附回原位。

边界判断必须依赖实际图像变化，不能只看鼠标位置。

## 10. 地图块保存格式

### 10.1 第一版建议

第一版不需要直接生成一张超大 PNG。建议保存为地图块和清单：

```text
maps/
└─ miraland_main/
   ├─ manifest.json
   ├─ tiles/
   │  ├─ tile_000001.png
   │  ├─ tile_000002.png
   │  └─ tile_000003.png
   ├─ masks/
   └─ landmarks.json
```

`manifest.json` 可以记录：

```json
{
  "map_space": "miraland_main",
  "coordinate_type": "LocalMapPx",
  "zoom_level": 3,
  "capture_resolution": [1920, 1080],
  "tile_size": [1280, 900],
  "created_at": "",
  "game_version": "",
  "tiles": []
}
```

### 10.2 为什么不立即拼成单张大图

地图块形式更适合：

- 增量更新；
- 只采集需要的区域；
- 重新配准错误地图块；
- 保存不同版本；
- 局部加载；
- 避免超大图内存占用；
- 并行处理；
- 记录每块独立置信度。

需要展示或离线匹配时，再生成合成预览图或多级缩放金字塔。

## 11. 只有小地图时的建图方式

### 11.1 可以实现，但难度更高

如果游戏没有可拖动的大地图，仍然可以在角色移动过程中不断截取小地图并拼接。

基本流程：

```text
获取小地图
→ 识别或消除当前旋转角
→ 屏蔽中心人物箭头
→ 屏蔽动态标记
→ 与上一帧配准
→ 累积局部位移
→ 写入局部地图
```

### 11.2 主要困难

小地图建图面临：

- 显示范围小；
- 可能随镜头旋转；
- 中心人物箭头遮挡；
- 任务标记不断变化；
- 行走输入没有精确里程计；
- 相似道路容易误匹配；
- 误差随时间累计；
- 角色无法到达区域无法采集；
- 不同高度可能显示相似二维地图。

### 11.3 北向固定与旋转小地图

如果小地图北向固定，可以直接做平移配准。

如果小地图会随镜头旋转，则需要：

```text
识别当前镜头角度
→ 将小地图反向旋转回北向
→ 再进行平移配准
```

角度误差会直接进入位置误差，因此镜头角度识别必须先单独验证。

### 11.4 回环检测

只靠连续帧累加位移会产生漂移。系统需要在重新经过旧地点时识别“这是以前来过的位置”：

```text
当前位置视觉特征
→ 在历史地点库中搜索
→ 找到高可信旧地点
→ 建立回环约束
→ 修正累计坐标误差
```

这已经接近简化版视觉 SLAM。因此第一阶段不建议直接把“小地图全自动建图”作为主要目标。

## 12. 不建完整地图的关系网方案

如果目标是让系统复现用户操作并规划步骤，并不一定需要连续完整的大地图。

可以直接建立拓扑关系网：

```text
节点：锚点、入口、菜单、路口、地点、任务区域
边：步行、传送、按键、交互、进入、退出
```

例如：

```text
[花愿镇锚点]
  ├─ 传送 → [搭配师协会锚点]
  ├─ 步行路线A → [协会入口]
  └─ 打开地图 → [花愿镇地图状态]
```

每个节点只需要保存足够的视觉证据和执行方法，不要求所有节点都拥有严格连续的全局坐标。

完整地图可以在后续按需补充，作为节点之间距离估计和可视化的辅助层。

### 12.1 三种图不能混成一张图

本方案会同时出现三类结构：

| 图 | 节点和边 | 主要职责 |
| --- | --- | --- |
| 空间栅格或配准图 | 地图块、位姿和重叠约束 | 计算连续坐标与回环修正 |
| 地点拓扑图 | 锚点、入口、楼层、地点和可执行连接 | 规划空间路径 |
| 能力模块图 | `CapabilitySpec`、`GraphModule`和调用依赖 | 复用传送、开地图、跑图等执行方法 |

`MapSpace`是空间坐标作用域，不等于`GraphModule`。定义层的模块依赖可以约束为DAG，但地点拓扑图允许道路回环；两者不能因为都叫“关系网”而共享未标型节点。

## 13. 推荐的混合架构

```text
游戏内大地图截图
→ 地图块采集器
→ 图像配准器
→ LocalMapPx地图底图

地图截图
→ 锚点/入口检测器
→ OCR命名
→ 语义节点库

用户实际移动
→ 小地图定位器
→ 当前LocalMapPx或当前节点

节点 + 路线执行记录
→ 关系边
→ 规划器选择执行计划
```

在这个架构中：

- 栅格地图解决“空间上在哪里”；
- 关系网解决“有哪些可执行连接”；
- 小地图解决“当前运行到哪里”；
- 执行记录解决“这条边是否可靠”；
- LLM 负责命名、解释、提问和组合计划，不参与底层几何拼接。

每个区域只引用通用的“打开地图、拖动地图、选择锚点、传送、步行路线”等`GraphModule`。游戏或区域差异通过`Adapter`提供页面、坐标和控件绑定，不能把同一套系统子图复制进每个地点图。执行时由`GraphCallRun`固定子图、Adapter、检测器和校准版本，并通过`ReturnContext`回到上层计划。

## 14. OCR、YOLO、CLIP、SAM与传统视觉的职责

| 模块 | 最适合的职责 | 不建议承担的职责 |
| --- | --- | --- |
| OpenCV相位相关/特征匹配 | 地图块几何对齐、平移估计、重叠检测 | 地点语义命名 |
| OCR | 区域名、锚点名、地图标题、楼层名 | 精确几何定位 |
| YOLO | 锚点、入口、图标、玩家标记、UI控件检测 | 像素级地图拼接 |
| SAM | 地图画布分割、UI覆盖区域分割、复杂遮罩 | 第一版固定ROI场景 |
| CLIP | 地点语义标签、相似地点检索、自然语言查询 | 精确地图块配准 |

核心原则：

> 精确地图拼接优先使用几何方法，不能主要依赖 CLIP。

CLIP 可以回答“这像是森林还是城镇”，但不适合回答“两张地图相差精确多少像素”。

## 15. 按基础模块逐步实施

本方案应继续遵循“单个基础识别模块测试完成，再逐步组合”的开发方式。

### 阶段1：地图画布截图

目标：稳定获取游戏内大地图有效区域。

验证内容：

- 不同分辨率；
- 16:9与16:10；
- 地图打开动画；
- UI弹窗；
- 固定ROI是否可靠；
- 输出截图尺寸和颜色格式。

此阶段不拖地图、不拼接。

### 阶段2：两张地图块位移估计

目标：只验证两张重叠截图能否得到稳定 `(dx, dy)`。

测试数据应覆盖：

- 城镇高纹理区域；
- 森林重复纹理；
- 海面低纹理；
- 大量锚点图标；
- 地图边界；
- 选中图标变化。

此阶段不做自动扫描。

### 阶段3：单方向连续拼接

目标：连续向一个方向拖动，生成一条地图带。

需要验证：

- 位移累计误差；
- 实际拖动与图像位移差异；
- 地图边界检测；
- 重复地图块处理；
- 失败后是否可以从上一可信块恢复。

### 阶段4：二维蛇形扫描

目标：覆盖一个完整区域并生成地图块坐标表。

需要增加：

- 换行策略；
- 行间对齐；
- 全局误差优化；
- 重复覆盖检测；
- 未探索区域标记。

### 阶段5：锚点和图标处理

目标：将动态或重复图标从基础地图中分离。

步骤：

```text
YOLO/模板检测锚点
→ 生成图标mask
→ 地图配准时降低权重
→ 点击后OCR读取名称
→ 写入语义节点层
```

### 阶段6：传送关系网

目标：将锚点变成可执行节点和边。

验证：

- 锚点是否解锁；
- 传送按钮状态；
- 传送成功页面；
- 目标地点视觉确认；
- 失败和重试证据。

### 阶段7：小地图连续定位

目标：在已经拥有底图的区域中，用小地图跟踪当前位置。

此阶段只做“底图内定位”，不直接做小地图建图，可显著降低难度。

### 阶段8：按需地图扩展

目标：执行任务遇到未建图区时，自动进入地图采集模式扩充地图块，而不是预先扫描整个世界。

## 16. 按需建图策略

项目初期不建议强制采集整个游戏世界。可以采用懒加载式建图：

```text
任务需要进入某区域
→ 检查区域地图块是否存在
→ 不存在则进入采集模式
→ 只采集任务相关范围
→ 建立锚点和入口节点
→ 返回任务执行
```

优点：

- 减少早期工作量；
- 更快发现基础模块问题；
- 不必等待完整世界采集完成；
- 地图更新时只重建受影响区域；
- 允许不同区域使用不同定位策略；
- 更符合关系网逐步生长的设计。

## 18. 第一版明确不做的内容

为了控制范围，第一版建议明确不做：

- 从地图图片自动识别所有道路；
- 从零构建通用导航网格；
- 完整视觉SLAM；
- 自动解决多楼层三维地图；
- 使用CLIP进行精确几何配准；
- 一次性扫描全部游戏区域；
- 自动理解所有地图图标语义；
- 在配准未验证前接入完整规划器。

第一版只需要证明：

```text
工具能稳定截取地图画布
+
两张地图块能可靠计算相对位移
+
若干地图块能组成一致的局部底图
```

这三个基础能力稳定后，再加入锚点、关系网和小地图定位。

## 19. 最终建议

当前最务实的路线不是寻找或制作一张完美的完整世界地图，而是：

1. 先自动截取游戏内大地图；
2. 验证固定缩放下的两图配准；
3. 从单条地图带扩展到局部二维地图；
4. 把传送锚点作为语义节点单独管理；
5. 使用 OCR 给节点命名；
6. 使用小地图在已建底图中连续定位；
7. 用户走过一次后，把路线收束为节点之间的可执行边；
8. 只在任务需要时扩建新的地图区域。

这一方案允许地图、关系网和执行证据同时逐步生长，不要求理论一次成型，也符合当前“每个基础模块独立测试，再慢慢组成关键功能”的实施方向。
