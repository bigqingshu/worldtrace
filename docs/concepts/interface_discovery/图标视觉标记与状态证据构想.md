## 1. 核心想法

游戏图标是非常重要的状态证据。系统不需要先理解图标代表“背包”“技能”“任务完成”还是其他含义，也可以记录图标并利用它判断界面变化和操作反馈。

最重要的原则是：

> 图标不是状态本身，而是状态成立、状态变化或操作结果的一项视觉证据。

例如：

```text
用户按下B
-> 某个页签图标高亮
-> 背包内容区域出现
-> 原HUD区域消失
-> 多项证据共同支持“已进入背包界面”
```

系统可以只知道：

```text
token_00421从NORMAL变为SELECTED
token_00137消失
region_00008出现稳定布局
```

即使这些视觉标记没有中文名称，也不妨碍状态判定、关系网寻路和操作后置验证。

## 2. 图标记录不等于图标理解

图标身份和图标语义必须分开。

```text
视觉身份
-> 这个图案是否与以前记录的图案属于同一类

视觉状态
-> 它当前是正常、高亮、变灰、冷却还是消失

语义解释
-> 它在人类看来代表什么功能
```

系统实时运行只依赖前两项。语义解释属于可选信息，可以在用户提问时，把图标、所在区域和前后画面交给LLM分析，再由用户确认。

建议使用独立语义状态：

```text
UNLABELED
LLM_SUGGESTED
USER_CONFIRMED
```

LLM给出的名称不能改变图标身份，也不能因为名称变化导致关系网失效。

## 3. 图标、控件和状态必须分开

屏幕上的图标可能是：

- 可点击按钮的一部分；
- 键盘快捷键提示；
- 当前能力或角色状态指示；
- 任务、邮件或物品角标；
- 冷却、进度或资源数量显示；
- 纯装饰元素；
- 某个更大控件中的局部图案。

因此不能直接建立：

```text
检测到图标
-> 这是按钮
-> 可以点击
```

应保持以下边界：

```text
VisualTokenDefinition
-> 记录“看到了什么”

ControlSlotDefinition
-> 记录“哪里可能接受操作”

ContextualBinding
-> 记录“当前上下文中该槽位绑定什么能力”

StateDefinition
-> 记录“哪些证据共同定义一个状态”
```

用户在图标附近点击并产生界面变化，只能增加“图标与控件槽位相关”的证据。经过重复观察或用户确认后，才能形成稳定的操作绑定。

## 4. 定义层和观测层

系统必须区分长期定义与单次运行观测，不能把每一帧中的每一个图标都创建成关系网节点。

### 4.1 `VisualTokenDefinition`

`VisualTokenDefinition`表示一个可重复识别的图标视觉身份：

```text
VisualTokenDefinition
├── token_id
├── game_profile_id
├── context_constraints
├── expected_regions
├── visual_variant_refs
├── descriptor_version
├── optional_semantic_label
├── semantic_status
├── created_from_evidence_ids
└── lifecycle_status
```

其中：

- `token_id`是稳定机器身份，例如`token_00421`；
- `context_constraints`限制它通常出现在哪类界面或HUD区域；
- `expected_regions`只用于缩小检测范围，不能假设位置永远固定；
- `optional_semantic_label`可以为空；
- `descriptor_version`记录模板、特征或模型版本；
- 原始截图和裁剪图保存在证据存储中，定义层只保存引用。

### 4.2 `VisualVariantDefinition`

同一个图标可能具有多个视觉变体：

```text
VisualVariantDefinition
├── variant_id
├── token_id
├── visual_state
├── template_or_descriptor_refs
├── valid_capture_contexts
└── validation_evidence_ids
```

第一版可支持：

```text
NORMAL
SELECTED
ACTIVE
DISABLED
COOLDOWN
HIDDEN
UNKNOWN
```

这些名称描述视觉表现，不自动等同于业务语义。例如`DISABLED`只说明视觉上像是禁用，是否为正常前置条件不足、游戏Bug或识别错误，需要其他证据判读。

### 4.3 `VisualTokenObservation`

`VisualTokenObservation`表示某一帧或短时间窗中的一次真实观测：

```text
VisualTokenObservation
├── observation_id
├── frame_id或window_id
├── window_instance_id
├── focus_epoch
├── token_candidates
├── variant_candidates
├── bbox与roi_ref
├── detection_confidence
├── evidence_freshness
├── occlusion_state
└── evidence_ids
```

观测允许保留多个候选。无法可靠匹配时应返回`UNKNOWN`，不能为了形成关系而强行绑定已有图标。

## 5. 图标变化事件

状态和操作反馈更关心图标如何变化，而不是单张截图中是否存在一个图案。

建议产生以下`VisualTokenEvent`：

```text
APPEARED
DISAPPEARED
VARIANT_CHANGED
VALUE_CHANGED
MOVED
UNKNOWN
```

事件至少记录：

```text
VisualTokenEvent
├── event_id
├── token_id或候选集合
├── event_type
├── before_observation_ids
├── after_observation_ids
├── temporal_window
├── stability_duration
├── associated_action_id
└── confidence
```

### 5.1 出现与消失

单帧出现或单帧漏检不能立即生成事件。应要求：

- 输入帧有效且足够新鲜；
- 目标区域没有被弹窗、特效或角色遮挡；
- 图标在若干连续帧中稳定出现或稳定缺失；
- 检测器在当前分辨率和UI缩放下有效。

尤其是`DISAPPEARED`，只有在“目标区域本应可见且观测有效”时才是可靠负证据。

### 5.2 变灰、高亮和冷却

图标状态区域与图标身份区域应尽量分开：

```text
identity_region
-> 判断它还是不是同一个图标

state_region
-> 判断遮罩、高亮、冷却环和角标
```

这样冷却蒙版、数字倒计时或按下动画不会导致系统把同一图标误建成大量新身份。

### 5.3 数字和角标变化

`VALUE_CHANGED`首先只表示局部视觉值发生变化。后续可以按需接入OCR读取具体数值，但不需要在第一版图标记录中强制理解数字。

## 6. 状态证据表达

状态定义不直接保存截图，而是引用可验证的视觉条件：

```text
StateDefinition
-> VisualEvidencePredicate集合
```

建议支持：

```text
TOKEN_PRESENT
TOKEN_ABSENT
TOKEN_VARIANT_IS
TOKEN_EVENT_OCCURRED
TOKEN_LAYOUT_MATCHES
TOKEN_COUNT_IN_RANGE
```

单个图标通常只能提供一项证据。稳定界面状态可组合：

```text
页签图标处于SELECTED
AND 背包网格区域存在
AND 战斗HUD标记缺失
AND 画面在时间窗内保持稳定
```

系统可以为不同证据分配可靠性，但应保留每项证据的来源和版本，不能只保存一个无法解释的总置信度。

## 7. 操作反馈的三个阶段

图标变化可以用于判断操作结果，但必须区分输入接受、执行过程和最终完成。

```text
输入被接受
-> 按钮按下动画、技能图标变灰或冷却开始

操作正在进行
-> 冷却环变化、进度图标持续或状态标记存在

操作最终完成
-> 完成标记出现、目标图标消失或目标界面成立
```

因此：

> 技能图标变灰通常只能证明游戏可能接收了输入，不能单独证明任务已经完成。

`TransitionDefinition`可以分别引用：

```text
precondition_predicates
acceptance_predicates
progress_predicates
success_predicates
failure_predicates
```

一次真实执行仍保存在`StepAttempt`中：

```text
StepAttempt
├── action_id
├── pre_action_observations
├── post_action_observations
├── visual_token_events
├── matched_predicates
├── ExecutionOutcome
└── evidence_ids
```

## 8. 两个示例

### 8.1 进入背包

```text
前置证据：
token.hud_main存在

操作：
press_key(B)

输入接受证据：
主HUD开始消失

成功证据：
token.inventory_tab变为SELECTED
AND inventory_grid_layout出现
AND 画面稳定
```

这些标识可以先保持机器编号，不需要知道“inventory”的中文含义。上面的语义名称只用于解释示例。

### 8.2 使用技能

```text
前置证据：
token.skill_q为NORMAL

操作：
press_key(Q)

输入接受证据：
token.skill_q从NORMAL变为COOLDOWN

执行中证据：
冷却区域持续变化

最终成功证据：
由技能目标决定，不能只依赖冷却图标
```

## 9. 图标自动发现流程

第一版不要求在整张画面中理解所有图标。更合理的流程是围绕用户输入和稳定界面变化发现候选：

```text
FrameStream
-> 选择输入前后时间窗
-> 对齐并寻找变化区域
-> 从稳定帧提取小型候选区域
-> 生成模板、感知哈希和视觉描述器
-> 与已有token聚类
-> 多帧追踪
-> 生成VisualTokenObservation
-> 形成VisualTokenEvent
-> 作为状态或操作证据候选
```

优先使用低成本方法：

- 图像差分定位操作前后变化区域；
- 模板匹配确认已知图标；
- 感知哈希进行近似去重；
- 局部特征或轻量视觉嵌入处理缩放和轻微风格变化；
- CLIP只在候选召回或用户询问语义时按需使用；
- LLM不进入高频检测闭环。

## 10. 上下文和版本

相同图案在不同位置、界面或游戏中可能具有不同作用。图标记录必须携带捕获上下文：

```text
game_profile_id
game_version
window_instance_id
ui_scale
resolution
language
graphics_profile
parent_region_or_slot
screen_state_candidates
```

游戏更新改变图标素材时，应建立新的视觉变体或外观版本。只有经过证据或用户确认后，才能把新旧外观归入同一个`token_id`。

版本更新不能直接覆盖旧模板，否则历史回放将无法使用原来的检测器复现。

## 11. 故障和置信度隔离

图标缺失可能来自：

- 截图失败或返回旧帧；
- 目标窗口不是当前预期实例；
- 弹窗、特效或其他UI遮挡；
- UI缩放、分辨率或语言变化；
- 检测器失效；
- 游戏功能正常隐藏；
- 游戏偶发Bug确实漏绘图标。

这些情况不能统一写成“状态不成立”或“操作失败”。建议分别记录：

```text
token_detection_confidence
variant_detection_confidence
predicate_confidence
detector_reliability
evidence_freshness
occlusion_state
FailureAttribution
SampleDisposition
```

如果图标证据缺失但其他独立证据支持操作成功，本次结果可以继续成立，同时把图标检测样本标为不适合更新检测器可靠性。证据冲突无法消解时返回`UNKNOWN`。

## 12. 与关系网的边界

以下内容进入定义图：

- 稳定图标身份及其视觉变体；
- 状态引用的视觉证据条件；
- 转换引用的输入接受、进度和结果条件；
- 已确认的控件槽位与上下文绑定。

以下内容只进入运行和证据存储：

- 某一帧中的一次图标检测；
- 操作前后的裁剪图；
- 单次出现、消失或变体变化事件；
- 本次匹配分数、候选列表和失败原因。

这样可以避免“每帧一个节点、每个冷却状态一个节点”导致关系网无限膨胀。

## 13. 与Trace Core的关系

首期`Trace Core`不需要实现图标识别，但必须提前保存未来识别所需的事实：

```text
frame_id
单调时间戳
window_instance_id
focus_epoch
action_id
输入前帧窗口
输入后帧窗口
截图新鲜度
原始证据引用
```

只要这些数据可靠保存，后续图标模块就可以反复离线分析同一段用户操作，不需要重新录制。

## 14. 分阶段验证

### 阶段一：离线候选提取

从一段用户操作记录中提取输入前后发生变化的小区域，人工检查候选是否覆盖关键图标。

### 阶段二：无语义聚类

不提供图标名称，只验证同一图标能否归入相同`token_id`，不同图标是否能保持分离。

### 阶段三：视觉变体

验证正常、高亮、变灰和冷却是否属于同一图标的不同`variant_id`，而不是产生大量重复身份。

### 阶段四：状态证据

选择一个基础菜单和一个游戏内HUD状态，用多个视觉条件进行稳定区分，并在证据不足时返回`UNKNOWN`。

### 阶段五：操作后置验证

选择一个页面切换操作，验证“输入前观测、输入、变化事件、目标状态”能够在离线回放中重复得到相同结论。

### 阶段六：可选语义解释

用户主动询问时，向LLM提供图标裁剪、周围区域和前后时间窗。LLM输出建议名称和解释，用户确认后再写入语义元数据。

## 15. 第一版验收标准

- 无需图标名称，也能稳定复用同一个`token_id`；
- 能区分图标身份变化与正常视觉变体；
- 能把图标事件与正确的`action_id`和帧时间窗对齐；
- 能将图标作为状态证据和操作后置条件；
- 不会仅凭图标存在就认定它是可点击按钮；
- 不会把输入接受证据误当作任务最终成功；
- 遮挡、漏检或截图异常时能返回`UNKNOWN`；
- 单次观测不会被写成永久关系网节点；
- LLM缺席时，检测、状态判断和执行闭环仍然可以运行。

## 16. 当前结论

图标记录应成为界迹感知体系中的基础能力，但它不是新的语义中心，也不是一套独立关系网。它的正确位置是：

```text
图标视觉身份
-> 多帧观测和变化事件
-> 状态证据与操作反馈
-> StateDefinition和TransitionDefinition引用
```

系统先学会稳定地说“这个视觉标记出现了、消失了或改变了”，再在确有需要时由用户和LLM回答“它是什么意思”。
