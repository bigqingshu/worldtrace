## 1. 核心问题

很多游戏在切换以下内容时，会改变HUD上的图标、按钮、快捷键和布局：

- 当前角色；
- 队伍成员；
- 武器；
- 服装或能力套装；
- 普通形态与特殊形态；
- 载具；
- 战斗姿态；
- 职业或技能配置；
- 瞄准、潜行、游泳、飞行等控制模式。

同一个屏幕位置和同一个按键，在不同上下文下可能具有完全不同的语义：

```text
角色A + 普通形态 + E
-> 火焰冲刺

角色B + 普通形态 + E
-> 治疗

角色A + 载具状态 + E
-> 下车

角色A + 特殊变身 + E
-> 形态专属技能
```

如果系统把图标、按钮位置、按键和能力直接绑定成同一个固定节点，角色切换后就容易继续执行旧能力。

核心原则是：

> 槽位描述在哪里操作，图标描述当前看起来是什么，上下文绑定描述当前槽位代表什么能力，语义Capability描述用户真正希望完成什么。

## 2. 四个概念分开

```text
ControlSlot
-> 稳定或半稳定的操作槽位

VisualVariant
-> 当前槽位显示的图标和视觉状态

ContextualBinding
-> 当前上下文中槽位绑定的语义能力

Capability
-> 用户和规划器使用的稳定语义目标
```

错误绑定：

```text
右下角E图标
=
治疗能力
```

正确表达：

```text
slot.ability_e
+ active_control_context
-> 当前绑定ability.heal
```

## 3. 控件槽位

```text
ControlSlotDefinition
├── slot_id
├── parent_hud_region
├── anchor_type
├── identity_region
├── state_region
├── text_region
├── action_region
├── forbidden_regions
├── default_input_binding
├── interaction_type
├── supported_visual_states
└── slot_detector_ref
```

区域职责必须分开：

| 区域 | 作用 |
| --- | --- |
| `identity_region` | 识别槽位边框、固定锚点和当前视觉变体 |
| `state_region` | 识别冷却遮罩、禁用色、能量或选中态 |
| `text_region` | OCR读取快捷键、数字和提示原因 |
| `action_region` | 鼠标点击时允许落点的安全范围 |
| `forbidden_regions` | 相邻技能、聊天、购买或其他高风险区域 |

键盘能力可以没有鼠标`action_region`，但仍应保存身份区和状态区；鼠标可点击槽位则不能直接把检测框当成安全点击框。

示例：

```yaml
slot_id: slot.ability_e
parent_hud_region: hud.combat_actions
anchor_type: SCREEN_FIXED_RELATIVE_TO_HUD
default_input_binding: E
interaction_type: KEY_OR_CLICK
```

槽位可以保持稳定，但它的图标、能力和运行状态会变化。

某些角色会改变槽位数量或布局，此时需要不同的`HUDLayoutVariant`，但仍然可以把对应功能映射到规范槽位或角色专属槽位。

## 5. 当前控制上下文

```text
ActiveControlContext
├── active_character
├── active_form
├── active_weapon
├── active_outfit
├── active_stance
├── party_configuration
├── game_mode
├── vehicle_state
├── combat_state
├── aiming_state
├── ability_set_revision
└── control_schema_epoch
```

页面仍可能是：

```text

```

但控制上下文发生变化：

```text
active_character: character_a -> character_b
ability_set_revision: 17 -> 18
control_schema_epoch: 103 -> 104
```

不需要为每个角色和每个技能组合复制整套游戏世界节点，只需要让能力守卫和绑定解析读取当前上下文。

## 6. 上下文绑定

```text
ContextualBinding
├── binding_id
├── slot_id
├── context_predicate
├── capability_id
├── visual_variant_id
├── input_binding
├── availability_rules
├── resource_rules
├── outcome_contract
├── binding_revision
└── binding_confidence
```

示例：

```yaml
binding_id: binding.character_b.heal
slot_id: slot.ability_e

context_predicate:
  active_character: character_b
  active_form: normal
  vehicle_state: false

capability_id: ability.heal
visual_variant_id: visual.character_b.heal
input_binding: E
```

另一个绑定：

```yaml
binding_id: binding.vehicle.exit
slot_id: slot.ability_e

context_predicate:
  vehicle_state: true

capability_id: vehicle.exit
visual_variant_id: visual.vehicle.exit
input_binding: E
```

## 7. `control_schema_epoch`

`control_schema_epoch`用于防止角色或能力切换后，旧异步任务继续使用过期绑定。

以下变化可以让epoch递增：

- 切换角色；
- 切换武器；
- 切换服装或能力套装；
- 进入或退出特殊形态；
- 上下载具；
- 进入瞄准、潜行或特殊控制模式；
- HUD布局和能力槽位集合发生变化；
- 游戏重连或重新进入世界。

例如：

```text
旧计划：
  capability: ability.heal
  resolved_slot: slot.ability_e
  resolved_input: E
  control_schema_epoch: 103

角色已经切换：
  slot.ability_e -> ability.fire_dash
  control_schema_epoch: 104
```

旧任务准备发送E时：

```text
expected_epoch: 103
current_epoch: 104
-> 拒绝发送输入
-> 重新识别控制上下文
-> 重新解析语义能力绑定
-> 重新编译后续步骤
```

## 8. 能力切换会使输入队列失效

切换角色、武器或形态时：

```text
停止创建新的能力输入
-> 使旧control_schema_epoch失效
-> 清空未发送的旧能力动作
-> 允许已经注入的动作完成或安全停止
-> 进入CONTROL_SCHEMA_TRANSITIONING
-> 等待新HUD稳定
```

不能继续执行：

```text
按E
-> 等待
-> 按Q
```

因为E和Q的能力绑定可能已经变化。

## 9. 切换不是立即完成的原子事件

角色切换过程可能是：

```text
发送切换输入
-> 角色头像开始变化
-> 角色模型切换
-> 部分HUD暂时隐藏
-> 能力图标逐个替换
-> 冷却遮罩和资源条更新
-> 新控制Schema稳定
```

完整切换能力：

```text
switch_character(target_character)
-> 验证切换输入已发送
-> 检测目标角色身份
-> 等待角色模型或头像稳定
-> 等待HUD布局稳定
-> 连续多帧确认能力图标集合不再变化
-> 识别新的能力绑定
-> 生成新control_schema_epoch
-> 返回SUCCESS
```

HUD仍在变化时：

```text
control_schema_state: TRANSITIONING
```

此时不能调用能力。

## 10. HUD稳定判定

可以同时观察：

- 角色头像连续多帧一致；
- 角色名称或身份特征一致；
- 能力槽位数量稳定；
- 槽位位置稳定；
- 多个能力图标不再替换；
- 能量条和资源条类型稳定；
- 切换动画结束；
- 当前控制模式不再变化；
- 页面和覆盖层没有加载状态。

```text
ControlSchemaStability
├── character_stable
├── layout_stable
├── slot_set_stable
├── icon_set_stable
├── resource_ui_stable
├── control_mode_stable
├── stable_frame_count
└── confidence
```

## 11. 角色切换和图标Bug分开

### 11.1 正常上下文切换

```text
角色头像改变
+ 角色模型改变
+ 多个技能图标同时有规律变化
+ 新图标集合与已知角色能力集合匹配
```

判断为：

```text
EXPECTED_CONTEXT_VARIANT
```

### 11.2 能力运行状态变化

角色和能力绑定没有变化，只是图标进入：

```text
COOLDOWN
CHARGING
ACTIVE
DISABLED
RESOURCE_INSUFFICIENT
```

保存：

```text
capability_id: ability.heal
runtime_state: COOLDOWN
```

不能把冷却图标错误识别成新能力。

### 11.3 疑似图标异常

```text
角色未切换
形态未切换
HUD布局未切换
control_schema_epoch未变化
该槽位历史上应当存在
图标突然消失或变成异常占位
```

进入：

```text
CONTROL_ICON_MISSING
UI_ASSET_TRANSIENT_FAULT
UNKNOWN
```

而不是创建新能力绑定。

## 12. 使用HUD整体指纹

不要只看单个技能图标。

```text
ControlSchemaFingerprint
├── character_identity_evidence
├── portrait_fingerprint
├── character_model_evidence
├── slot_count
├── slot_positions
├── ability_icon_set
├── energy_bar_type
├── resource_counter_type
├── hud_layout_variant
├── input_prompts
└── game_mode
```

角色切换通常会同步改变：

- 角色头像；
- 名称或血条；
- 多个技能图标；
- 能量条；
- 武器或形态图标；
- 快捷键提示；
- HUD布局；
- 场景内角色外观。

多个元素同时形成一致的新组合，说明控制上下文发生了正常变化。

只有一个图标异常，而其他上下文保持不变，更像局部UI资源问题或检测失败。

## 13. 语义调用，不按键调用

高层计划不应写：

```text
按E
```

而应写：

```text
use_capability(ability.heal)
```

执行器运行时：

```text
识别当前角色和形态
-> 检查当前control_schema_epoch
-> 查询ability.heal在当前上下文中的绑定
-> 找到实际槽位和输入
-> 判断能力READY / COOLDOWN / UNKNOWN
-> 再次确认HUD不处于切换过程
-> 取得desktop_physical_input并固定focus_epoch
-> 创建带两个epoch的StepAttempt
-> 发送实际输入
-> 验证治疗效果
```

只要`focus_epoch`或`control_schema_epoch`任一变化，尚未提交的动作立即失效；已经提交但缺少后置证据的尝试返回`UNKNOWN`，不能在新上下文中续跑旧输入序列。

如果当前角色没有治疗能力：

```text
查找拥有治疗能力的角色
-> 规划switch_character(target)
-> 等待ControlSchema稳定
-> 重新解析ability.heal绑定
-> 执行治疗
```

## 14. 语义能力与实现绑定

```text
Capability: ability.heal

Possible Implementations:
  - character_b / slot.ability_e / key E
  - character_c / slot.ability_q / key Q
  - item.quick_heal / slot.item_1 / key 1
```

规划器可以根据：

- 当前角色；
- 切换成本；
- 能量和冷却；
- 风险；
- 能力可靠性；
- 角色是否可切换；

选择具体实现。

## 15. 通用能力系统与角色Adapter

```text
game.system.ability
```

负责：

```text
识别当前控制上下文
-> 查询语义能力
-> 检查可用性
-> 解析槽位和输入
-> 执行能力
-> 验证实际效果
```

角色差异由Adapter处理：

```text
character_a.ability_adapter
character_b.ability_adapter
vehicle.ability_adapter
special_form.ability_adapter
```

Adapter可以定义：

- 角色专属图标；
- 能力名称；
- 输入槽位；
- 能量需求；
- 冷却规则；
- 前置姿态；
- 形态切换；
- 角色专用后置证据。

如果不同角色控制方式完全不同，可以使用专用子图，但仍对外导出统一Capability契约。

## 17. 绑定发现

发现新角色或新能力时：

```text
切换角色或形态
-> 检测新的ControlSchemaFingerprint
-> 创建CANDIDATE控制上下文
-> 记录槽位、图标和输入提示
-> 观察用户实际使用
-> 保存输入前后效果
-> 生成能力绑定候选
-> 在相同上下文中重复验证
-> 提升为ACTIVE ContextualBinding
```

绑定的语义抽象、验证成熟度和发布状态分轴保存：

```text
binding_scope:
  LOCAL_CONTEXT / CHARACTER_REUSABLE / GAME_SYSTEM

validation_status:
  UNVALIDATED / OFFLINE_VALIDATED / SHADOW_VALIDATED / LIVE_VALIDATED

release_status:
  DRAFT / CANDIDATE / SHADOW / ACTIVE / DEGRADED / RETIRED
```

发现新角色只会产生`CANDIDATE`绑定；即使语义名称已经由用户确认，也不能跳过效果验证直接进入`ACTIVE`。

初始机器名称可以是：

```text
character_candidate_007
slot_variant_021
capability_candidate_034
binding_candidate_052
```

LLM可以提出语义名称，但不能代替后置状态验证。


如果用户在角色B状态按E，多次出现稳定治疗结果，才逐步建立：

```text
character_b + slot.ability_e
-> ability.heal
```

## 19. 置信度分开

```text
character_identity_confidence
control_context_confidence
control_schema_confidence
slot_existence_confidence
slot_binding_confidence
visual_variant_confidence
ability_availability_confidence
ability_execution_reliability
```

这些是领域证据或指标视图，不形成第二套独立统计系统。推荐映射为：

| 动态控件字段 | 公共指标或事实 |
| --- | --- |
| `character_identity_confidence`、`control_context_confidence` | 当前`StateSnapshot`的状态证据 |
| `slot_existence_confidence`、`visual_variant_confidence` | 当前感知置信度及`detector_reliability`样本 |
| `slot_binding_confidence` | 绑定关系正确性，不等于当前可用性 |
| `ability_availability_confidence` | `availability_probability`与当前运行状态 |
| `ability_execution_reliability` | `conditional_execution_reliability`的能力维度投影 |

输入错投、截图失效、角色切换动画和图标缺失分别由`INPUT_ROUTING_INVALID`、`PERCEPTION_INVALID`、暂态过滤和UI完整性处置，不直接更新绑定关系。

示例：

```yaml
slot_id: slot.ability_e
active_character: character_b
bound_capability: ability.heal

character_identity_confidence: 0.96
control_schema_confidence: 0.93
slot_existence_confidence: 0.99
slot_binding_confidence: 0.91
visual_variant_confidence: 0.82
availability: READY
```

图标识别不清只影响`visual_variant_confidence`。只要角色身份、槽位和实际效果证据仍然可靠，就不应直接降低“角色B拥有治疗能力”的关系置信度。

## 20. 绑定冲突

可能出现：

```text
相同上下文 + 相同槽位
-> 两个不同Capability候选
```

原因可能是：

- 角色身份识别错误；
- 能力根据短期状态变化；
- 同一按键支持点按和长按两种能力；
- 瞄准目标不同导致效果不同；
- 形态或武器变量没有进入上下文；
- 用户输入序列被切分错误；
- 图标检测器混淆。

冲突不能通过简单覆盖解决。应：

```text
保留多个候选
-> 寻找缺失上下文变量
-> 重新切分输入类型
-> 增加实机验证
-> 必要时询问用户
```

## 21. 点按、长按和组合输入

同一槽位可能根据输入方式产生不同能力：

```text
E短按 -> 普通技能
E长按 -> 瞄准或蓄力技能
E松开 -> 释放蓄力结果
```

绑定键应包含：

```text
InputGesture
├── key_or_button
├── press_type
├── hold_duration_range
├── release_required
├── modifier_keys
└── target_context
```

因此：

```text
slot + context + gesture
-> capability
```

而不是只有：

```text
slot + key
```

## 22. 能力可用性

```text
AbilityRuntimeState
├── READY
├── COOLDOWN
├── CHARGING
├── ACTIVE
├── DISABLED_EXPECTED
├── RESOURCE_INSUFFICIENT
├── LOCKED
├── CONTROL_SCHEMA_TRANSITIONING
├── ICON_MISSING
└── UNKNOWN
```

只有：

```text
control_schema_epoch匹配
+ slot_binding已验证
+ runtime_state == READY
+ 当前前置条件满足
```

时，能力才能进入正式执行。

## 23. 切换失败和恢复

```text
角色切换输入已发送
-> 目标角色身份未稳定
-> HUD能力集合持续变化
-> 超过有限稳定等待时间
```

公共`outcome=BLOCKED`，并返回专业`reason_code`：

```text
CONTROL_SCHEMA_NOT_STABLE
```

恢复可以是：

```text
重新观察
-> 确认实际活动角色
-> 必要时重新发送一次安全切换
-> 切换菜单并返回
-> 重新进入游戏世界
```

恢复后必须生成新的epoch和绑定快照，不能复用切换前计划。

## 24. 图标变化的指标更新

| 观察 | 关系置信度 | 更新内容 |
| --- | ---: | --- |
| 角色切换后多个图标按预期变化 | 不降低 | 增加ControlSchema切换样本 |
| 同一能力进入冷却视觉态 | 不降低 | 更新运行状态识别 |
| 图标缺失但语义能力仍可验证 | 不降低 | 更新UI资产故障率 |
| 槽位位置改变但新布局稳定 | 不降低 | 新增HUDLayoutVariant |
| 角色未变但绑定效果改变 | 暂不更新 | 进入绑定冲突调查 |
| 健康上下文中能力效果长期改变 | 重新审查 | 游戏版本或Capability定义 |
| 旧epoch任务被拒绝 | 不降低 | 更新调度安全统计 |

## 27. 示例：使用治疗能力

高层计划：

```text

```

当前上下文：

```text
active_character: character_a
character_a没有ability.heal
```

规划器查找：

```text
character_b
-> 提供ability.heal
```

执行：

```text
switch_character(character_b)
-> epoch 103失效
-> 等待角色B身份稳定
-> 等待HUD能力集合稳定
-> 生成epoch 104
-> 查询ability.heal绑定
-> 解析为slot.ability_e / key E
-> 验证READY
-> 发送E
-> 验证治疗后置效果
```

如果切换后图标缺失，但：

```text
角色身份明确

操作风险可接受
治疗结果可验证
```

可以根据策略使用退化实现；否则返回`ABILITY_ICON_MISSING`并等待恢复或用户确认。

## 28. 与关系网结合

关系网保存：

```text
角色B具有治疗能力
治疗能力在正常上下文可用
使用治疗能力可能到达生命恢复状态
```

不需要为以下完整组合建立节点：

```text
角色B + E槽位 + 图标亮态
角色B + E槽位 + 图标冷却态
角色B + E槽位 + 图标缺失态
```

这些属于：

```text
ControlContextSnapshot
+ SlotBindingSnapshot
+ AbilityRuntimeState
```

高层关系保持稳定，动态绑定在运行时解析。

## 29. LLM边界

LLM可以：

- 为新角色、形态和能力提出名称；
- 解释图标可能代表的语义；
- 在绑定冲突时提出澄清问题；
- 把用户目标映射到语义Capability；
- 解释为什么当前角色无法执行某能力。

LLM不能：

- 仅凭图标外观直接确认能力绑定；
- 忽略`control_schema_epoch`强行使用旧按键；
- 把冷却图标当成新能力；
- 把图标缺失当成能力关系失效；
- 未经验证自动发布新的角色Adapter。

## 30. 最小验证计划

| 实验 | 操作 | 验收重点 |
| --- | --- | --- |
| 角色切换 | A切到B后立即触发旧技能动作 | 旧`control_schema_epoch`动作在提交前被拒绝 |
| 焦点同时变化 | 切换角色期间其他窗口取得焦点 | `focus_epoch`和`control_schema_epoch`任一失效都阻止输入 |
| 图标正常变化 | 切换角色后多个槽位同步替换 | 建立新上下文，不误报UI故障 |
| 单图标缺失 | 保持角色与HUD不变并遮蔽一个图标 | 不创建新能力，进入UI完整性处置 |
| 布局变化 | 载具或特殊形态改变槽位数量 | 生成候选HUDLayoutVariant并重新绑定 |
| 手势差异 | 同一槽位分别短按、长按和松开 | 形成不同InputGesture，不互相覆盖 |
| 切换振荡 | 人工制造A/B角色识别反复变化 | 看门狗在预算内阻断，不持续重发切换键 |

每项实验保存公共`StepAttempt`和专业`AbilityBindingAttemptPayload`，统计旧epoch拒绝率、绑定混淆率、图标故障误建绑定率和后置效果验证率。

## 31. 总结

角色、武器、形态和能力切换引起的UI变化，应通过动态控制Schema处理：

```text
识别当前角色、形态和游戏模式
-> 形成ActiveControlContext
-> 角色或能力切换时使旧control_schema_epoch失效
-> 等待HUD和能力集合稳定
-> 重新识别槽位、图标和运行状态
-> 根据ContextualBinding把槽位映射到语义Capability
-> 高层计划按Capability调用
-> 执行前取得desktop_physical_input并同时验证focus_epoch与control_schema_epoch
-> 用后置状态确认真实能力效果
```

最终边界是：

> 角色切换只改变控制上下文、槽位绑定和视觉变体，不需要复制整个关系网；任何旧绑定在新epoch下都不能继续发送真实输入。
