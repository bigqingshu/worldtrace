# 游戏瞬态故障判读与置信度隔离构想

> 文档性质：游戏功能偶发失效、恢复判读、故障归因与关系网置信度隔离构想
>

>

## 1. 核心问题

游戏可能出现偶发性异常：

```text
功能按钮突然变灰
某项交互没有响应
角色能力暂时无法使用
页面存在但入口不可点击
视角或输入模式异常
服务器状态没有正确同步
```

重新加载场景、传送、返回登录界面或重启客户端后，功能又恢复正常。

如果系统把每一次这种现象都记为：

```text
关系边执行失败
-> 降低节点或关系置信度
```

就会把游戏客户端故障错误归因到已经正确学习的能力定义上。

最重要的原则是：

> 游戏Bug应进入环境故障和恢复模型，不应直接污染关系结构置信度。只有在功能可用、前置条件满足、环境健康且感知有效时，真实执行仍然失败，才应降低能力执行可靠性。

## 2. 不能只维护一个“置信度”

建议至少拆分：

| 指标 | 回答的问题 |
| --- | --- |
| `state_confidence` | 当前是否真的处于这个状态 |
| `transition_confidence` | 能力X是否真实表达状态A到状态B的关系 |
| `availability_probability` | 在给定上下文中功能是否可用 |
| `conditional_execution_reliability` | 功能可用且环境健康时执行成功率 |
| `transient_fault_rate` | 游戏偶发失效频率 |
| `recovery_success_rate` | 传送、重载或重登后恢复概率 |
| `detector_reliability` | 感知模块能否稳定判断状态和可用性 |
| `input_health` | 窗口焦点和真实键鼠输入是否健康 |

其中当前事实、单次证据和长期指标不能混为一项：

| 层级 | 输入侧 | 感知侧 |
| --- | --- | --- |
| 当前状态 | `input_health` | 当前`state_confidence`与感知有效性 |
| 单次尝试 | `input_delivery_confidence` | `perception_confidence`与证据完整性 |
| 长期统计 | `input_routing_reliability` | `detector_reliability` |

`input_health=HEALTHY`不能替代某次输入送达证据；同样，检测器历史可靠也不能证明当前帧一定识别正确。

真正有意义的执行可靠性是：

```text
P(
  SUCCEEDED
  |
  PRECONDITION_OK
  AND AVAILABLE
  AND ENVIRONMENT_HEALTHY
  AND PERCEPTION_VALID
)
```

而不是：

```text
成功次数 / 所有调用次数
```

## 3. “变灰”首先属于可用性判定

同一个功能控件可以具有：

```text
ENABLED
DISABLED_EXPECTED
DISABLED_SUSPECTED_BUG
DISABLED_CONFIRMED_TRANSIENT
HIDDEN
UNKNOWN
```

### 3.1 `ENABLED`

存在足够证据表明当前功能可以执行：

- 控件处于启用视觉状态；
- 交互提示存在；
- 已知前置条件满足；
- 没有阻塞弹窗；
- 游戏和输入环境健康。

### 3.2 `DISABLED_EXPECTED`

存在合理游戏规则：

- 战斗中禁止打开；
- 当前处于过场；
- 技能或功能处于冷却；
- 材料、体力或货币不足；
- 等级、任务或系统尚未解锁；
- 当日次数已经耗尽；
- 当前区域或副本不允许；
- 服务器规则限制；
- 有其他页面或弹窗阻塞。

这种情况应帮助系统学习新的能力守卫：

```text
capability.available_if
  game.combat == false
  AND game.cutscene == false
  AND resource.count >= required
```

它不应降低关系结构置信度。

### 3.3 `DISABLED_SUSPECTED_BUG`

系统观察到：

- 页面和控件身份正确；
- 已知前置条件都满足；
- 过去在相同上下文中稳定可用；
- 没有发现合理的禁用原因；
- 功能仍然变灰或无响应。

此时只能标为疑似客户端异常，不能立即确定。

### 3.4 `DISABLED_CONFIRMED_TRANSIENT`

在主要语义条件没有发生有效变化的情况下，通过已知恢复动作立即恢复，并且该现象多次重复出现，才逐步提升为确认瞬态故障。

### 3.5 `UNKNOWN`

没有足够证据判断：

- 是规则限制；
- 是游戏客户端Bug；
- 是服务器状态；
- 是检测器误判；
- 是页面仍在动画；
- 是截图过期。

此类样本暂时隔离，不更新主要关系统计。

## 4. 识别启用、禁用和未知状态

可用性证据可以来自：

### 4.1 视觉外观

- 控件亮度、饱和度和对比度；
- 图标是否灰化；
- 是否出现锁定、禁用或冷却遮罩；
- 边框、高亮和悬停态；
- 按钮文字颜色；
- 透明度；
- 是否存在可交互提示。

### 4.2 OCR和提示原因

- “战斗中无法使用”；
- “等级不足”；
- “功能尚未解锁”；
- “冷却中”；
- “次数不足”；
- “当前区域不可用”。

如果悬停不会产生副作用，可以读取禁用提示；否则优先使用被动证据。

### 4.3 用户行为证据

- 用户看到变灰后没有点击；
- 用户尝试后立刻切换页面；
- 用户反复打开菜单确认；
- 用户主动传送、重登或重启；
- 恢复后用户立即再次使用同一功能。

### 4.4 历史上下文

- 相同账号、角色和区域中过去是否可用；
- 当前任务、资源和状态是否与成功样本一致；
- 当前版本是否出现过相同故障签名；
- 当前应用会话是否已经运行很久。

## 5. 执行前增加健康门

不要先点击变灰控件，再把无结果记成执行失败。

```text
准备执行Capability
-> 验证目标窗口和输入归属
-> 验证截图新鲜度
-> 验证页面稳定
-> 验证游戏没有加载、掉线或同步异常
-> 验证控件存在
-> 判断控件ENABLED / DISABLED / UNKNOWN
-> 验证已知前置条件
```

只有满足：

```text
PRECONDITION_OK
+ AVAILABLE
+ ENVIRONMENT_HEALTHY
+ PERCEPTION_VALID
```

时，才创建可以参与条件执行可靠性统计的正式`StepAttempt`。

功能变灰时，首先记录：

```text
AvailabilityObservation
```

而不是：

```text
CapabilityExecutionFailure
```

## 6. 环境健康状态

```text
EnvironmentHealth
├── HEALTHY
├── LOADING
├── DISCONNECTED
├── INPUT_UNHEALTHY
├── WINDOW_FOCUS_LOST
├── CLIENT_DESYNC_SUSPECTED
├── SERVER_STATE_UNKNOWN
├── TRANSIENT_GAME_FAULT
├── RECOVERY_IN_PROGRESS
└── UNKNOWN
```

环境健康是与页面状态正交的维度：

```text
ui.page: INVENTORY
environment.health: CLIENT_DESYNC_SUSPECTED
```

不能因为页面识别为背包，就认为其中所有功能必然健康。

## 7. 判断瞬态Bug的恢复前后对照

```text
发现功能异常变灰或无响应
-> 保存当前StateSnapshot和全部前置证据
-> 保存控件、页面和环境证据
-> 执行一个有限、明确的恢复动作
-> 重新观察主要语义状态
-> 再次判断功能可用性
```

恢复动作可以逐级尝试：

```text
等待画面稳定并重新截图
-> 关闭并重新打开当前菜单
-> 切换到其他页面再返回
-> 重新聚焦窗口
-> 传送或重新加载场景
-> 返回登录界面并重新进入
-> 最后才考虑重启客户端
```

如果恢复后：

```text
账号、角色、任务、资源、区域等主要语义事实基本不变
+ 功能立即恢复可用
```

可以提高`GAME_CLIENT_TRANSIENT`归因概率。

## 8. 上下文等价性

恢复前后并不要求所有像素和临时状态完全相同，但需要验证影响功能可用性的主要事实。

```text
ContextEquivalenceDecision
├── account_same
├── character_same
├── game_mode_compatible
├── region_compatible
├── task_state_compatible
├── resource_state_compatible
├── cooldown_state_compatible
├── server_state_compatible
└── confidence
```

如果恢复同时改变了：

- 冷却时间；
- 玩家区域；
- 战斗状态；
- 服务器同步结果；
- 任务阶段；
- 当日次数；

就不能简单得出“重载修复了Bug”。它可能只是合法前置条件发生了变化。

## 9. 疑似和确认分开

```text
SUSPECTED_TRANSIENT_GAME_FAULT
```

适用于：

- 当前没有合理禁用原因；
- 恢复后功能重新可用；
- 但上下文不完全等价，或只发生过一次。

```text
CONFIRMED_TRANSIENT_GAME_FAULT
```

可以要求：

- 相同故障签名多次出现；
- 多次由相同恢复动作解决；
- 恢复前后主要语义条件等价；
- 检测器和截图证据可靠；
- 没有发现新的游戏规则解释。

归因应随证据逐渐变化，而不是一次恢复就写成永久事实。

## 10. StepAttempt和RecoveryRun分开

不要写成：

```text
第一次失败
-> 重载
-> 第二次成功
-> 最终覆盖为SUCCEEDED
```

应保存：

```text
StepAttempt 1
  outcome: BLOCKED
  reason_code: TRANSIENT_ENVIRONMENT_FAULT
  availability: DISABLED
  attribution: SUSPECTED_GAME_CLIENT_FAULT

RecoveryRun
  action: REENTER_GAME
  outcome: SUCCEEDED

StepAttempt 2
  outcome: SUCCEEDED
  availability: ENABLED
```

最终汇总为：

```text
关系边仍然有效
功能出现一次瞬态故障样本
重新进入游戏成功恢复
计划增加了恢复时间和成本
```

原始异常不能被恢复后的成功覆盖。

### 10.1 统一执行结果封套

运行层级统一使用：

```text
PlanRun
-> CapabilityRun
-> StepAttempt
```

滚轮缩放、输入归属、角色绑定等专业尝试只作为`StepAttempt.professional_payload`，公共结果固定为：

```text
ExecutionOutcome
├── outcome
├── reason_code
├── failure_attribution_ref
├── sample_disposition_ref
└── evidence_package_ref
```

`outcome`只使用：

```text
SUCCEEDED
FAILED
UNKNOWN
CANCELLED
BLOCKED
```

四层含义必须分开：

| 层级 | 回答的问题 | 示例 |
| --- | --- | --- |
| `outcome` | 本次尝试是否达成后置条件 | `FAILED` |
| `reason_code` | 专业模块观察到什么直接原因 | `FOCUS_EPOCH_EXPIRED` |
| `FailureAttribution` | 故障应该归因到哪里 | `INPUT_ROUTING` |
| `SampleDisposition` | 该样本可以更新哪些长期统计 | `INPUT_ROUTING_INVALID` |

专业模块可以立即提供`reason_code`，但不能自行宣布最终归因或修改长期指标。归因和样本处置必须在统一证据验证后完成。

`RecoveryRun`始终独立保存：

```text
StepAttempt 1: FAILED / CONTROL_NOT_RESPONDING
RecoveryRun 1: SUCCEEDED / REENTER_GAME
StepAttempt 2: SUCCEEDED
```

这三项记录不能压缩成一次成功。

## 11. 样本处置类型

```text
SampleDisposition
├── VALID_SUCCESS
├── VALID_CAPABILITY_FAILURE
├── EXPECTED_UNAVAILABLE
├── TRANSIENT_ENVIRONMENT_FAULT
├── PERCEPTION_INVALID
├── INPUT_ROUTING_INVALID
├── INTERRUPTION_HANDLED
├── USER_CANCELLED
├── ATTRIBUTION_UNKNOWN
└── QUARANTINED
```

### `VALID_SUCCESS`

参与能力成功率统计。

### `VALID_CAPABILITY_FAILURE`

前置、可用性、环境和感知均有效，但能力仍未达到后置状态。它才会降低条件执行可靠性。

### `EXPECTED_UNAVAILABLE`

更新能力守卫和可用性模型，不降低关系结构置信度。

### `TRANSIENT_ENVIRONMENT_FAULT`

更新客户端故障率和恢复模型，不进入能力失败分母。

### `PERCEPTION_INVALID`

更新检测器可靠性，不评价关系边。

### `INPUT_ROUTING_INVALID`

更新桌面输入健康，不评价游戏能力。

### `INTERRUPTION_HANDLED`

奖励弹窗、公告、网络提示等正交通用中断已经被识别并处理。它更新中断频率和处理器可靠性，不评价原能力关系；恢复原计划时必须创建新的`StepAttempt`。

### `USER_CANCELLED`

记录停止和清理，不参与普通成功率。

### `ATTRIBUTION_UNKNOWN`

暂不更新主要指标，等待更多证据。

### `QUARANTINED`

数据不完整、冲突或版本无法对齐，禁止进入自动学习统计。

## 12. 故障归因分类

```text
FailureAttribution
├── EXPECTED_UNAVAILABLE
├── EXPECTED_INTERRUPTION
├── GAME_CLIENT_TRANSIENT
├── GAME_SERVER_OR_RULE
├── AUTOMATION_ENVIRONMENT
├── INPUT_ROUTING
├── PERCEPTION_FAILURE
├── EXECUTOR_FAILURE
├── CAPABILITY_DEFINITION_ERROR
├── GAME_VERSION_INCOMPATIBLE
└── UNKNOWN
```

### 12.1 `EXPECTED_INTERRUPTION`

已识别的奖励弹窗、公告、确认框或网络提示正交打断了业务步骤。它交给中断处理器，不评价原能力关系。

### 12.2 `GAME_CLIENT_TRANSIENT`

不直接降低关系结构置信度，更新瞬态故障率。

### 12.3 `GAME_SERVER_OR_RULE`

用于学习服务器或游戏规则守卫。

### 12.4 `AUTOMATION_ENVIRONMENT`

例如窗口最小化、捕获失败、系统弹窗和桌面状态异常。

### 12.5 `INPUT_ROUTING`

输入发给错误窗口、焦点epoch失效或鼠标捕获异常。

### 12.6 `PERCEPTION_FAILURE`

页面、按钮、灰化状态或OCR识别错误。

### 12.7 `EXECUTOR_FAILURE`

能力条件有效，但确定性执行器自身失败。

### 12.8 `CAPABILITY_DEFINITION_ERROR`

前置、动作、后置条件或`ExecutionOutcome`映射本身不正确。它才真正影响关系结构可信度。

### 12.9 `GAME_VERSION_INCOMPATIBLE`

游戏更新导致页面、规则或能力定义不再兼容，应触发版本降级和重新验证。

## 13. 指标更新矩阵

| 结果 | 关系结构置信度 | 条件执行可靠性 | 可用性模型 | 瞬态故障率 | 恢复成功率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 正常条件下成功 | 保持或提高 | 提高 | 可更新 | 不更新 | 不更新 |
| 合理规则导致不可用 | 不降低 | 不更新 | 更新 | 不更新 | 不更新 |
| 疑似客户端Bug | 不降低 | 不更新 | 可记录 | 更新疑似样本 | 视恢复结果更新 |
| 确认客户端瞬态故障 | 不降低 | 不更新 | 可记录 | 更新 | 更新 |
| 截图或识别不确定 | 不更新 | 不更新 | 不更新 | 不更新 | 不更新 |
| 输入发到错误窗口 | 不更新 | 不更新 | 不更新 | 不更新 | 更新桌面恢复指标 |
| 通用中断已识别并处理 | 不更新 | 不更新 | 不更新 | 不更新 | 更新中断处理器指标 |
| 用户取消 | 不更新 | 不更新 | 不更新 | 不更新 | 不更新 |
| 环境健康且能力真实失败 | 可能降低 | 降低 | 不更新 | 不更新 | 视后续恢复决定 |
| 多次重载仍稳定失败 | 重新审查 | 可能降低 | 重新审查 | 可能不是瞬态Bug | 更新失败样本 |

## 14. Bug签名

重复出现的瞬态故障可以形成：

```text
BugSignature
├── bug_signature_id
├── application_id
├── game_version
├── affected_capability
├── page_state
├── visual_symptoms
├── disabled_control_fingerprint
├── satisfied_preconditions
├── absent_expected_reason
├── successful_recovery_capability
├── recurrence_count
├── recovery_success_rate
├── first_seen
├── last_seen
└── confidence
```

例如：

```text
bug.nikki.inventory_button_grey

症状：
  背包按钮存在但处于灰化状态

已满足：
  正常世界
  非过场
  非战斗
  输入健康

有效恢复：
  重新进入游戏

恢复历史：
  9 / 10
```

下一次遇到相同签名：

```text
停止继续盲目点击
-> 展示疑似已知游戏异常
-> 按风险策略调用已验证恢复能力
-> 恢复后重新检查可用性
```

## 15. Bug签名不能变成绝对规则

即使视觉症状相同，也可能来自：

- 新的任务限制；
- 服务器活动规则；
- 账号状态变化；
- 游戏版本更新；
- 检测器误判；
- 用户当前处于特殊模式。

所以Bug签名只能提供归因先验，仍需执行当前上下文检查。

## 16. 恢复能力与故障签名绑定

```text
BugSignature
-> RecoveryPolicy
```

例如：

```yaml
bug_signature: bug.nikki.inventory_button_grey

recovery_policy:
  - action: REOBSERVE
    max_attempts: 2
  - action: REOPEN_MENU
    max_attempts: 1
  - action: TELEPORT_TO_SAFE_ANCHOR
    requires_confirmation: false
  - action: REENTER_GAME
    requires_confirmation: true
```

每个恢复动作后都要重新判断：

```text
功能是否重新可用
主要语义上下文是否仍然兼容
原计划是否还可以继续
```

## 17. 恢复不等于原能力成功

```text
恢复到健康状态
```

只表示系统可以重新尝试或重新规划，不表示原`StepAttempt`已经完成。

如果原操作可能已经产生副作用，但后续功能变灰或证据丢失，应返回：

```text
UNKNOWN
```

恢复后需要根据当前真实状态决定：

- 原目标已经完成；
- 可以创建新的`StepAttempt`重试；
- 重试可能重复副作用，必须询问用户；
- 原计划已经失效，需要重新规划。

## 18. 按游戏版本和环境统计

统计至少关联：

```text
game_version
server
account_profile
character_profile
region
game_mode
application_session_id
session_age
resolution
window_mode
input_backend
detector_revision
capability_revision
recovery_revision
```

游戏更新后：

- 旧Bug可能消失；
- 新Bug可能出现；
- 页面灰化规则可能改变；
- 检测器可能失效；
- 原恢复动作可能不再适用。

旧版本统计不能直接永久累加到新版本。

可以采用：

```text
同版本近期样本权重高
同版本旧样本逐渐衰减
跨大版本默认隔离
跨小版本先进入兼容性验证
```

## 19. 规划器怎样使用瞬态故障数据

关系结构可信，但瞬态故障率较高时，可以把能力标为：

```text
ACTIVE
-> DEGRADED
```

`DEGRADED`不表示能力定义错误，而表示当前环境下运行成本和风险增加。

规划成本可以加入：

```text
expected_cost
=
base_execution_cost
+ transient_fault_probability × expected_recovery_cost
```

例如：

```text
路径A：步骤少，但功能偶发变灰并需要重登
路径B：步骤多，但稳定且不需要恢复
```

规划器可以根据：

- 当前任务是否允许中断；
- 用户是否允许重新登录；
- 恢复耗时；
- 操作风险；
- 当前版本Bug发生率；

选择更合适的路径，而不是把路径A直接判成错误关系。

## 20. 何时真正降低关系或能力可靠性

只有以下证据成立时，才考虑降低条件执行可靠性：

```text
前置状态明确匹配
AND 功能明确ENABLED
AND 窗口与输入健康
AND 截图和检测有效
AND 游戏没有加载、掉线或同步异常
AND 执行器确实发出了预期输入
AND 后置状态明确未达到
```

进一步降低关系结构置信度还需要证明：

- 不是单次执行器故障；
- 不是游戏版本兼容性变化；
- 不是缺失了新的前置条件；
- 多个独立样本都否定原状态转换；
- 定义中的前置、动作或后置关系确实不成立。

## 21. 统计更新事务

一次运行结束后，不应由业务Task直接修改长期置信度。

推荐：

```text
StepAttempt完成
-> EvidenceValidator检查证据完整性
-> FailureAttributionEngine生成归因候选
-> SampleDisposition决定样本是否可学习
-> MetricsUpdater按归因更新对应指标
```

如果归因仍为`UNKNOWN`：

```text
进入QuarantineSampleStore
```

后续可以通过：

- 更多重复样本；
- 用户确认；
- 新版本规则；
- 故障签名匹配；
- 离线证据分析；

重新处理，但不能在证据不足时自动更新关系权重。

## 23. 示例：背包按钮偶发变灰

### 23.1 初始观察

```text
页面：正常游戏世界
输入：健康
背包按钮：存在但灰化
已知战斗状态：false
已知过场状态：false
冷却或限制提示：未发现
```

系统输出：

```text
availability: DISABLED_SUSPECTED_BUG
sample_disposition: ATTRIBUTION_UNKNOWN
```

### 23.2 恢复

```text
重新打开菜单：无效
传送到安全点：无效
返回登录并重新进入：恢复
```

### 23.3 恢复后

```text
账号相同
角色相同
资源相同
任务状态相同
背包按钮重新启用
```

系统保存：

```text
StepAttempt 1: BLOCKED / TRANSIENT_ENVIRONMENT_FAULT
RecoveryRun: REENTER_GAME / SUCCEEDED
StepAttempt 2: SUCCEEDED
```

更新：

```text
transition_confidence: 不降低
conditional_execution_reliability: StepAttempt 1不进入分母
transient_fault_rate: 增加一个疑似样本
recovery_success_rate(REENTER_GAME): 增加成功样本
```

重复多次后，才可能建立确认Bug签名。

## 24. 用户与LLM的角色

确定性系统负责：

- 页面与控件状态识别；
- 已知前置条件检查；
- 环境健康检查；
- 恢复前后状态对照；
- 样本隔离和指标更新规则；
- 运行证据保存。

LLM可以：

- 解释为什么系统怀疑是游戏Bug；
- 阅读提示文字并提出候选原因；
- 汇总多个故障样本；
- 向用户询问是否允许重登或重启；
- 帮助命名BugSignature。

LLM不能：

- 在证据不足时直接宣布是游戏Bug；
- 把失败样本自行排除出统计；
- 修改关系置信度；
- 自行执行高风险恢复；
- 把恢复后的成功覆盖到原始`StepAttempt`。

## 25. 按钮图标或控件缺失

功能异常不一定表现为按钮变灰。有些游戏Bug会导致：

```text
按钮底板存在，但图标消失
图标存在，但文字消失
整个按钮槽位为空
部分UI纹理没有加载
整个页面布局不完整
按钮被移动到异常位置
```

这种情况不能直接判定为：

```text
按钮不存在
-> 能力定义失效
```

更准确的处理是先判断页面和控件的UI完整性。

### 25.1 图标不是按钮本身

一个控件的身份应由多类证据构成：

```text
ControlIdentity
├── 所属页面
├── 面板或按钮容器
├── 相对布局位置
├── OCR文字
├── 图标
├── 邻近控件
├── 悬停反馈
├── 按压反馈
├── 历史点击区域
└── 已知后置状态
```

例如背包图标没有显示，但仍然观察到：

```text
背包入口槽位存在
+ 周围按钮布局正常
+ OCR仍能读到“背包”
+ 鼠标悬停时该区域高亮
+ 候选区域与历史位置一致
```

此时应判断为：

```text
PRESENT_ICON_MISSING
```

而不是：

```text
CONTROL_MISSING
```

### 25.2 控件视觉状态

```text
ControlVisualState
├── PRESENT_COMPLETE
├── PRESENT_ICON_MISSING
├── PRESENT_LABEL_MISSING
├── PRESENT_VISUAL_DEGRADED
├── HIDDEN_EXPECTED
├── OCCLUDED
├── LAYOUT_MOVED
├── MISSING_SUSPECTED_BUG
├── MISSING_CONFIRMED_TRANSIENT
└── UNKNOWN
```

#### `PRESENT_COMPLETE`

容器、图标、文字和主要交互反馈完整。

#### `PRESENT_ICON_MISSING`

控件槽位、底板、文字或悬停反馈仍存在，只缺少图标资产。

#### `PRESENT_LABEL_MISSING`

图标和容器存在，但文字或字体没有正确显示。

#### `PRESENT_VISUAL_DEGRADED`

控件存在，但显示内容残缺、花屏、占位或与正常模板明显不同。

#### `HIDDEN_EXPECTED`

根据当前规则本来就不应显示：

- 功能尚未解锁；
- 当前模式不允许；
- 只有特定角色或对象才出现；
- 需要滚动后才进入可见区域；
- 当前页面变体不包含该功能。

#### `OCCLUDED`

控件存在，但被游戏弹窗、提示、其他面板或桌面窗口遮挡。

#### `LAYOUT_MOVED`

控件因分辨率、UI缩放、语言、窗口比例或游戏版本移动到其他位置。

#### `MISSING_SUSPECTED_BUG`

页面和前置条件正确，但整个预期控件或槽位不存在，也没有合理规则解释。

### 25.3 页面完整性状态

```text
UIIntegrityHealth
├── HEALTHY
├── PARTIAL_ASSET_MISSING
├── CONTROL_SLOT_EMPTY
├── FONT_ASSET_MISSING
├── TEXTURE_ATLAS_FAILURE
├── LAYOUT_CORRUPTED
├── PAGE_INCOMPLETE
└── UNKNOWN
```

例如：

```text
10个按钮中有9个正常
只有一个按钮图标为空
按钮底板和槽位仍然存在
```

更像：

```text
PARTIAL_ASSET_MISSING
```

如果整个页面的图标都消失，只剩按钮底板，则可能是：

```text
TEXTURE_ATLAS_FAILURE
```

如果按钮、文字、布局和页面元素都不完整，则可能是：

```text
PAGE_INCOMPLETE
```

### 25.4 判读流程

```text
预期控件没有被正常检测到
-> 重新取得新鲜截图
-> 连续观察多帧，排除加载和动画
-> 重新确认页面身份
-> 检查弹窗、遮挡和滚动位置
-> 检查分辨率、语言和UI缩放
-> 查找预期控件槽位
-> 检查容器、文字、图标和邻近布局
-> 必要时进行安全悬停探测
-> 区分图标缺失、控件缺失、布局移动和页面不完整
```

可以同时比较：

```text
目标窗口截图
+ 桌面组合截图
+ 历史正常页面原型
+ 当前游戏版本的布局Profile
```

排除窗口遮挡、截图源错误或旧帧。

### 25.5 悬停探测优先于盲目点击

如果候选槽位仍然存在，可以先执行低风险悬停：

```text
把鼠标移动到候选区域
-> 不点击
-> 观察是否出现高亮、边框、提示文字或局部动画
```

结果：

```text
出现稳定悬停反馈
-> 控件存在概率提高

没有反馈
-> 可能是控件缺失、禁用、坐标错误、遮挡或页面不完整
```

只有满足以下条件时，才考虑点击视觉退化区域：

```text
控件身份足够明确
+ 操作风险低
+ 后置状态能够可靠验证
+ 点击失败不会产生危险副作用
```

购买、删除、账号、角色选择和不可逆操作，即使历史坐标高度一致，也不能只凭位置点击。

### 25.6 控件存在、控件身份和操作安全分开

```text
control_existence_confidence
control_identity_confidence
icon_asset_health
capability_availability
safe_to_interact
```

例如：

```yaml
control_id: nikki.inventory_button

existence_confidence: 0.91
identity_confidence: 0.84
icon_asset_health: MISSING
availability: UNKNOWN
safe_to_interact: false
```

系统可能较确定“这里存在一个控件槽位”，但无法证明它仍是背包按钮，因此仍不能自动点击。

### 25.7 语义能力与视觉实现分开

不要把：

```text
打开背包
```

等同于：

```text
点击背包图标
```

一个语义能力可以有多个实现：

```text
Capability: nikki.open_inventory

Implementations:
  1. 按B快捷键
  2. 点击基础菜单中的背包按钮
  3. 使用键盘菜单导航进入背包
```

如果背包图标缺失：

```text
click_inventory_icon
-> TEMPORARILY_UNAVAILABLE

press_inventory_shortcut
-> AVAILABLE
```

规划器可以选择另一个实现，并继续使用背包页面后置状态验证。

因此，一个视觉实现异常只影响该实现的可用性，不应自动让整个语义能力失效。

### 25.8 恢复前后对照

```text
检测到图标或控件缺失
-> 保存页面完整性和控件证据
-> 关闭并重新打开页面
-> 必要时切换标签再返回
-> 必要时传送、重新加载或重新进入游戏
-> 再次检测同一控件
```

如果：

```text
主要语义条件基本不变
+ 重载后控件和图标恢复
```

可以记录：

```text
UI_ASSET_TRANSIENT_FAULT
```

如果重载后：

```text
图标仍然缺失
但容器、文字、悬停和实际功能正常
```

可能属于：

- 长期资源显示异常；
- 特定画质、语言或主题问题；
- 当前版本的新视觉变体；
- 图标检测器不兼容。

如果多个健康会话中整个按钮都不再出现，需要检查：

```text
GAME_VERSION_UI_CHANGE
DETECTOR_INCOMPATIBLE
NEW_LAYOUT_VARIANT
EXPECTED_RULE_CHANGE
```

### 25.9 故障视觉不能污染正常模板

系统在Bug期间观察到空白槽位时，不能立即把它学习成按钮的正常外观。

应保存为：

```text
FaultAppearanceVariant
  control_id: nikki.inventory_button
  visual_state: PRESENT_ICON_MISSING
```

正常原型和故障变体分开：

```text
CanonicalControlAppearance
FaultAppearanceVariants[]
LayoutVariants[]
DisabledAppearanceVariants[]
```

只有经过明确验证的新游戏版本外观，才能提升成新的正常视觉修订。

### 25.10 指标更新规则

| 观察结果 | 是否降低关系置信度 | 主要更新对象 |
| --- | ---: | --- |
| 图标缺失，但快捷键成功打开页面 | 否 | UI资产故障率和替代实现统计 |
| 图标缺失，悬停证明控件仍存在 | 否 | 退化控件样本 |
| 整个按钮缺失，重载后恢复 | 否 | 瞬态UI故障率和恢复率 |
| 页面被弹窗遮挡 | 否 | 遮挡和页面完整性状态 |
| UI缩放导致按钮移动 | 否 | 布局适配器和检测器 |
| 捕获源没有正确显示图标 | 否 | Capture可靠性 |
| 多个健康会话中按钮永久消失 | 重新审查 | 游戏版本、布局和能力定义 |
| 控件明确存在且启用，执行仍失败 | 可能 | 具体实现可靠性 |

```text
CONTROL_PRESENT
CONTROL_PRESENT_DEGRADED
CONTROL_ICON_MISSING

CONTROL_OCCLUDED

UNSAFE_TO_INTERACT

```

这些结果属于UI完整性和能力实现选择，不应未经归因直接转换成：

```text

```

### 25.13 完整处理链

```text
预期按钮未被检测到
-> 不立即判定能力失败
-> 检查页面、布局、遮挡、滚动位置和截图健康
-> 使用容器、文字、位置、邻居和悬停重新确认
-> 区分图标缺失、整个控件缺失和布局移动
-> 判断当前实现是否仍安全可用
-> 优先选择快捷键等替代实现
-> 必要时执行页面重载、传送或重新进入游戏
-> 根据恢复前后结果形成UI故障归因
-> 分别更新UI完整性、实现可用性和故障统计
```

核心边界是：

> 图标只是控件身份的一项证据，不是按钮本身；一个视觉实现失效，也不等于语义能力和关系边失效。

## 26. 统一执行证据包

单个错误码无法支撑故障归因。每个`StepAttempt`、`GraphCallRun`和`RecoveryRun`都应引用同一类证据包：

```text
ExecutionEvidencePackage
├── package_id
├── plan_run_id
├── capability_run_id
├── step_attempt_id
├── graph_call_run_ids
├── recovery_run_ids
├── recent_frame_ring
├── desktop_and_window_identity
├── focus_epoch
├── control_schema_epoch
├── action_events_and_delivery_evidence
├── perception_results_and_raw_scores
├── expected_and_observed_states
├── pinned_revisions
├── watchdog_trace
├── interruption_trace
└── integrity_status
```

`recent_frame_ring`至少覆盖故障前、动作提交、预期响应窗口和故障后若干帧。`pinned_revisions`包含能力、关系图、检测器、资源、`ContinuousController`和`CalibrationProfile`修订。

证据包是不可变运行事实。后续可以追加归因记录和用户结论，但不能重写原始帧、动作和模型分数。证据不完整时，样本进入`QUARANTINED`，不能依靠猜测补齐后更新指标。

## 27. 行为看门狗与中断归因

看门狗不能只检查固定超时，还应分析运行序列：

```text
同一个动作连续重复
两个状态或按钮之间A/B振荡
动作次数增加但计划没有推进
画面长时间无有效变化
截图链路持续返回旧帧或黑帧
恢复动作重复调用原失败能力
```

看门狗触发时：

```text
停止继续提交动作
-> 使当前有效性令牌失效
-> 释放desktop_physical_input和按键状态
-> 固化最近帧、动作序列和调用栈
-> 返回BLOCKED或UNKNOWN及专业reason_code
-> 进入统一故障归因
```

如果原因是已识别的通用弹窗或网络提示，应由中断处理器执行有限恢复，并将原样本标记为`INTERRUPTION_HANDLED`。如果是截图停滞、输入错投或感知冲突，则分别进入`AUTOMATION_ENVIRONMENT`、`INPUT_ROUTING`或`PERCEPTION_FAILURE`，不能统称为能力失败。

## 28. 最小故障注入实验

第一阶段使用可重复注入的故障验证“指标不串线”：

| 注入场景 | 预期归因或处置 | 不应更新 |
| --- | --- | --- |
| 合法条件导致按钮变灰 | `EXPECTED_UNAVAILABLE` | 关系与执行可靠性 |
| 图标缺失但快捷键有效 | UI完整性退化 | 语义能力关系 |
| 捕获返回旧帧或黑帧 | `PERCEPTION_INVALID`或`AUTOMATION_ENVIRONMENT` | 能力失败率 |
| 输入作用于其他窗口 | `INPUT_ROUTING_INVALID` | 游戏能力与检测器可靠性 |
| 奖励弹窗打断正常步骤 | `INTERRUPTION_HANDLED` | 原转换可靠性 |
| 前置有效且游戏真实不响应 | `VALID_CAPABILITY_FAILURE` | 无关检测器指标 |
| 重载后恢复且上下文等价 | `TRANSIENT_ENVIRONMENT_FAULT` | 原StepAttempt结果 |
| A/B动作振荡 | 看门狗阻断并生成证据包 | 继续无限重试 |

验收时对同一证据包重复运行`EvidenceValidator -> FailureAttributionEngine -> SampleDisposition -> MetricsUpdater`，结果必须幂等；缺帧、缺版本或epoch不一致的样本必须进入隔离区。

## 29. 总结

功能变灰、图标缺失、控件消失或其他偶发失效都不能直接解释为关系边错误。完整判读链应为：

```text
识别控件存在、启用、禁用或未知
-> 检查控件图标、文字、容器和页面完整性
-> 检查游戏规则和能力前置条件
-> 检查窗口、输入、截图和客户端健康
-> 决定是否允许创建正式执行StepAttempt
-> 异常时保存AvailabilityObservation
-> 执行有限分级恢复
-> 比较恢复前后的语义上下文
-> 形成故障归因和样本处置
-> 分别更新可用性、执行可靠性、瞬态故障率和恢复成功率
```

最终需要保持以下边界：

```text
关系正确性
-> 能力在满足契约时是否能产生目标状态

当前可用性
-> 当前游戏规则是否允许调用

环境健康
-> 客户端、窗口、输入和服务器是否正常

条件执行可靠性
-> 可用且健康时执行器是否稳定

瞬态故障率
-> 游戏偶发异常出现频率

恢复可靠性
-> 故障后恢复能力是否有效
```

> 不让一次游戏Bug把正确关系降权，也不让恢复后的成功掩盖原始异常；每个`StepAttempt`使用统一的`ExecutionOutcome`和证据包，专业模块只提供`reason_code`，故障归因与样本处置决定长期指标如何更新。
