## 1. 核心想法

系统不应只拿一张截图询问“这是什么页面”，而应把用户游玩理解为一段连续的因果过程：

```text
用户看到了什么
-> 用户把鼠标移动到哪里
-> 用户按下了什么
-> 哪些画面区域发生变化
-> 游戏进入了什么新状态
-> 该变化能否在相似条件下重复
```

按钮不只是“长得像按钮的矩形”，菜单也不只是“画面上出现了许多文字”。更可靠的定义是：

> 按钮依靠操作因果识别，2D与3D依靠运动几何识别，菜单类别依靠进入条件、返回行为、导航拓扑和持久化影响识别。

系统初期可以只生成机器名称：

```text
state_cluster_017
visual_layer_006
affordance_042
transition_103
```

待机器事实稳定后，再由LLM提出“背包按钮”“设置页面”“NPC商店”等语义名称，并在不确定时询问用户。

## 2. 不把整张截图强行归为一种界面

一张游戏截图通常同时包含多个层：

```text
3D游戏世界
+ 2D HUD
+ 依附于世界对象的3D交互标记
+ 固定在屏幕上的2D交互提示
+ 临时通知或弹窗
```

因此，推荐把当前观测表达成组合状态：

```text
ObservationState
├── WorldLayer
├── HudLayer
├── WorldAnchoredInteractionLayer
├── OverlayStack
├── FocusMode
└── AvailableAffordances
```

例如玩家站在NPC面前时，当前状态可能是：

```text
WorldLayer: WORLD_3D
HudLayer: HUD_2D
WorldAnchoredInteractionLayer: NPC_MARKER_3D
OverlayStack: [PRESS_F_PROMPT_2D]
FocusMode: CHARACTER_CONTROL
AvailableAffordances: [MOVE, ROTATE_CAMERA, INTERACT_WITH_NPC]
```

进入对话后则可能变成：

```text
WorldLayer: WORLD_3D_BACKGROUND
HudLayer: PARTIALLY_HIDDEN
OverlayStack: [NPC_DIALOGUE_2D]
FocusMode: CURSOR_OR_DIALOGUE_SELECTION
AvailableAffordances: [SELECT_OPTION, CONTINUE, EXIT_DIALOGUE]
```

这里不是从一个状态完全替换成另一个状态，而是世界层、覆盖层和输入焦点发生了组合变化。

## 3. 画面层级的初步分类

| 类型 | 含义 | 主要观察信号 |
| --- | --- | --- |
| `WORLD_3D` | 透视三维游戏世界 | 镜头旋转、远近视差、遮挡、景物缩放和透视光流 |
| `WORLD_2D` | 平面或近似正交游戏世界 | 精灵、瓦片、分层滚动、整体平移，透视变化较弱 |
| `HUD_2D` | 固定屏幕坐标的状态信息 | 镜头和角色移动时仍固定在同一屏幕位置 |
| `WORLD_UI_3D` | 世界中的交互标记或实体面板 | 随世界物体移动、缩放、旋转或被遮挡 |
| `CONTEXT_OVERLAY_2D` | 由游戏情境触发的2D覆盖界面 | 依赖NPC、物品、战斗或当前场景，退出后返回现场 |
| `BASE_MENU_2D` | 可从多数正常游戏状态直接打开的基础菜单 | 与玩家位置关系较弱，固定快捷键跨场景可达 |
| `SETTINGS_MENU_2D` | 修改游戏本体运行参数的设置菜单 | 滑块、开关、键位、应用、取消、持久化变化 |
| `TRANSIENT_OVERLAY` | 通知、奖励、加载或临时提示 | 生命周期短，通常不形成完整导航分支 |

这些类型不要求一次识别正确。系统可以先保留多个候选：

```text
candidate_types:
  BASE_MENU_2D: 0.52
  CONTEXT_OVERLAY_2D: 0.41
  SETTINGS_MENU_2D: 0.07
```

后续通过更多用户操作逐渐收敛。

## 4. 2D与3D不按照美术风格判断

一个按钮即使有立体阴影，只要它始终固定在屏幕右上角，仍然属于2D界面元素。

相反，一个看起来像平面图标的交互标记，如果它：

- 随镜头旋转改变屏幕位置；
- 随玩家靠近而变大；
- 会被墙壁或角色遮挡；
- 与某个世界对象保持投影关系；

它就更接近3D世界交互元素。

### 4.1 3D世界的运动特征

```text
摄像机旋转
-> 不同深度区域产生不同方向或幅度的运动
-> 出现透视、视差、遮挡和消失点变化
```

### 4.2 2D世界的运动特征

```text
角色或镜头移动
-> 大片区域以相近方向平移
-> 精灵和瓦片保持近似固定大小
-> 可能存在若干平行滚动层
```

### 4.3 2D HUD的运动特征

```text
世界画面大幅变化
-> 某些图标、文字、血条和快捷栏保持屏幕坐标不变
-> 将其从世界运动场中分离为HUD候选
```

因此，系统可以利用用户自然进行的移动、转镜头、缩放和开关菜单，把这些操作当作免费的“运动实验”。

## 5. 不只发现按钮，而是发现可供性

建议使用“可供性（Affordance）”作为比按钮更通用的机器概念。

```text
Affordance
├── 视觉或世界锚点
├── 视觉身份区域
├── 状态证据区域
├── 文字区域
├── 安全操作区域
├── 禁止操作区域
├── 触发方式
├── 前置条件
├── 反馈过程
├── 后置状态候选
└── 重复成功统计
```

这些区域可以重叠，但职责不同：

| 区域 | 用途 |
| --- | --- |
| 视觉身份区域 | 判断这是哪个控件、槽位或对象 |
| 状态证据区域 | 判断悬停、按下、禁用、冷却和选中态 |
| 文字区域 | 交给OCR读取名称、数值和提示原因 |
| 安全操作区域 | 允许点击、拖动或滚轮聚焦的范围 |
| 禁止操作区域 | 相邻危险按钮、边缘、遮挡和容易误触的位置 |

不能因为图标区域最适合识别，就直接点击图标中心；也不能因为用户曾在某一点成功点击，就把该点当成完整命中区域。

可供性可以包括：

- 单击；
- 双击；
- 长按；
- 鼠标悬停；
- 拖拽；
- 滚动；
- 键盘快捷键；
- 组合键；
- 方向键选择后确认；
- 靠近对象后按交互键；
- 瞄准对象后交互；
- 点击任意空白区域关闭提示。

这样，“按F与NPC对话”就不必被错误建模为一个固定屏幕按钮，而可以表达为：

```text
前置条件：玩家位于NPC交互范围内
视觉条件：出现NPC标记和交互提示
触发：按F
后置候选：NPC对话、商店、任务或未知交互菜单
```

## 6. 怎样从用户操作中发现按钮

一次点击不足以证明某处是按钮。系统可以持续积累以下证据。

### 6.1 鼠标行为证据

- 多次点击集中在相近位置；
- 鼠标进入后局部颜色、边框、亮度或大小改变；
- 按下与松开时出现不同视觉状态；
- 用户在此处经常短暂停留后点击；
- 点击点会随着同一个面板移动，而不是固定在绝对屏幕坐标；
- 不同分辨率下，点击点仍对应同一个相对区域。

### 6.2 因果变化证据

- 点击后总是进入相同或相似状态；
- 状态变化集中发生在某个面板或覆盖层；
- 点击附近其他位置不会产生相同结果；
- 点击失败时用户会迅速调整位置并再次点击；
- 用户返回上一状态后会再次使用同一区域完成相同操作。

### 6.3 视觉结构证据

- OCR文字与图标长期组成一个稳定区域；
- 区域具有边框、背景、圆角、卡片或标签结构；
- 同一面板中存在多个外观相近的同类元素；
- 选中态、禁用态、悬停态和普通态之间存在稳定变化。

最终可以形成：

```text
affordance_id: affordance_042
anchor_type: SCREEN_FIXED
trigger: LEFT_CLICK
identity_region: normalized_polygon
state_region: normalized_polygon
text_region: normalized_polygon
action_region: normalized_polygon
forbidden_regions: []
pre_state: state_cluster_017
post_state_candidates:
  - state_cluster_021
success_count: 18
evidence_refs: [observation_018, observation_024]
candidate_status: SHADOW
```

失败点击不能直接累加到一个笼统的`failed_attempt_count`后降低关系置信度。它可能来自误触、错误窗口、控件禁用、暂态动画或识别失败，必须先经过统一`FailureAttribution`和`SampleDisposition`。

## 7. 三类菜单应该按进入条件区分

不同菜单可能使用同一套美术组件，仅看截图很难准确区分。更可靠的是观察它从哪里来、需要什么条件、退出后回到哪里。

## 8. 2D或3D游戏内交互菜单

游戏内交互菜单依赖当前世界上下文。

常见例子：

```text
靠近NPC -> 按F -> 对话或商店
靠近箱子 -> 按F -> 拾取列表
站在制作台旁 -> 打开制作界面
战斗结束 -> 进入结算或奖励界面
驾驶载具 -> 出现载具专用控制界面
```

它的典型特征包括：

- 玩家位置、朝向、瞄准对象或任务状态是前置条件；
- 同一个交互键面对不同对象会产生不同菜单；
- 离开对象或场景后可能无法再次打开；
- 退出后通常回到刚才的世界现场；
- 内容经常携带NPC、物品、任务、战斗或场景数据。

### 8.1 2D上下文交互菜单

菜单本身覆盖在屏幕上，例如：

- 对话框；
- NPC商店；
- 拾取列表；
- 制作配方；
- 战斗结算；
- 任务选择。

虽然菜单是2D的，但它的可达性由3D或2D游戏世界状态决定。

### 8.2 3D实体交互菜单

菜单可能直接存在于世界空间，例如：

- 游戏中的电脑屏幕；
- 驾驶舱控制面板；
- 世界内按钮或拉杆；
- 立体轮盘；
- 投影在某个物体表面的菜单。

这类元素会随镜头和距离变化，并可能被遮挡。它们的交互区域需要绑定世界锚点，而不是只保存一个屏幕坐标。

## 9. 游戏基础菜单

游戏基础菜单不依赖玩家跑到特定对象旁边。

例如：

```text
B -> 背包
M -> 地图
C -> 角色
J -> 任务
ESC -> 暂停或系统入口
```

其核心特征是“跨场景稳定可达”：

- 用户在多个地点都能通过相同输入进入；
- 玩家坐标和附近对象对进入结果影响较小；
- 菜单结构较稳定；
- 经常是包含多个子页面的导航枢纽；
- 退出后回到打开菜单前的游戏状态；
- 不需要角色移动或找到某个世界实体。

系统如果反复观察到：

```text
地点A按B -> 状态X
地点B按B -> 状态X
地点C按B -> 状态X
```

就可以逐渐推断状态X属于全局基础菜单，而不是某个场景的交互菜单。

## 10. 游戏本体设置菜单

设置菜单的核心不是“出现了设置两个字”，而是它能够修改游戏运行参数。

强特征包括：

- 大量滑块、开关、下拉框和单选项；
- 分辨率、画质、帧率、音量、语言和键位等字段；
- “应用”“取消”“恢复默认”等动作；
- 修改后画面比例、音量、渲染效果或操作方式发生变化；
- 某些变化跨页面或跨启动保留；
- 可能出现保存确认、倒计时恢复或重新启动提示；
- 通常可以从暂停菜单、标题界面或系统菜单进入。

设置菜单还需要比普通菜单更谨慎，因为它可能改变后续识别系统依赖的环境：

```text
分辨率改变
-> 截图尺寸和坐标换算改变

界面缩放改变
-> OCR区域、按钮大小和模板尺度改变

键位改变
-> 已学习的输入映射失效

画质改变
-> 模板、颜色和模型分布改变
```

所以设置菜单不仅是一个页面类别，也是会改变感知与执行环境的高影响状态。

## 11. 三类菜单的行为签名

| 观察维度 | 游戏内交互菜单 | 游戏基础菜单 | 游戏设置菜单 |
| --- | --- | --- | --- |
| 是否依赖玩家位置 | 通常依赖 | 通常不依赖 | 通常不依赖 |
| 是否依赖世界对象 | 经常依赖 | 很少依赖 | 不依赖 |
| 跨地点是否可重复进入 | 较低 | 较高 | 较高，但入口可能经过系统菜单 |
| 退出后返回哪里 | 原交互现场 | 打开前的游戏状态 | 上一级系统或暂停菜单 |
| 内容是否随对象变化 | 经常变化 | 相对稳定 | 相对稳定 |
| 是否包含通用配置控件 | 少量 | 少量 | 大量 |
| 是否产生跨页面持久影响 | 通常不会 | 通常不会 | 经常会 |
| 是否可能影响识别环境 | 较少 | 较少 | 很高 |

这些不是绝对规则，而是逐步累计的行为证据。

## 12. 从操作片段形成状态转换

系统可以围绕用户输入切分片段：

```text
稳定观测窗口
-> 用户输入开始
-> 输入组合或短操作序列
-> 过渡动画
-> 新的稳定观测窗口
```

每个片段保存：

```text
TransitionObservation
├── before_observation
├── input_provenance
├── input_events
├── cursor_track
├── intended_target
├── input_delivery_evidence
├── changed_regions
├── motion_field
├── transient_frames
├── after_observation
├── after_stability_window
├── interruption_evidence
├── candidate_affordance
├── candidate_transition
├── evidence_refs
└── confidence_factors
```

`input_provenance`至少区分：

```text
USER_NATURAL_INPUT
AUTOMATION_STEP_ATTEMPT
AUTHORIZED_ACTIVE_PROBE
UNKNOWN
```

用户自然输入形成被动发现样本；系统主动输入必须关联公共`StepAttempt`以及当时的`focus_epoch`、`control_schema_epoch`。无法确定输入来源或送达目标时，这条观测可以保留，但不能自动发布为关系边。

`TransitionObservation`是发现阶段的观察样本，不等同于执行阶段的`StepAttempt`。前者用于提出`TransitionDefinition`候选，后者用于按已固定能力执行一次受控尝试；两者可以通过证据ID关联，但不能互相覆盖。

同类片段重复出现后，可以聚合成稳定关系边：

```text
基础游戏状态
-> 按B
-> 背包状态
```

或带世界条件的边：

```text
世界状态 + NPC交互条件
-> 按F
-> NPC对话状态
```

## 13. 菜单分类依靠关系网拓扑继续收敛

菜单性质也可以从关系图形状中推断。

### 13.1 基础菜单通常像枢纽

```text
多个世界状态
-> 同一快捷键
-> 同一个菜单状态
-> 多个固定子页面
```

### 13.2 上下文菜单通常像条件分支

```text
特定世界状态 + 特定对象
-> 交互输入
-> 对象相关菜单
-> 退出后回到原世界状态附近
```

### 13.3 设置菜单通常像系统子树

```text
暂停或标题菜单
-> 设置入口
-> 图像/声音/控制/语言等稳定分支
-> 应用或取消
-> 产生持久环境变化
```

因此，菜单分类可以随着关系网扩大不断修正，而不要求第一次看到它时立即定论。

## 14. 用户行为本身可以提供弱监督

用户不会专门教系统标注，但自然操作会泄露大量信息：

- 点击失败后立刻微调位置再次点击，说明附近可能存在较小命中区；
- 按ESC后连续返回，说明当前可能位于多层覆盖菜单；
- 频繁在不同地点使用同一快捷键，说明对应页面可能是基础菜单；
- 打开页面后只使用方向键和确认键，说明输入焦点已经从角色控制转到菜单导航；
- 移动鼠标时世界镜头不动但光标出现，说明进入了光标界面；
- 修改选项后重新进入确认，说明该控件可能具有持久化效果；
- 长按鼠标并产生连续区域变化，说明这是拖拽而非按钮点击。

系统可以把这些行为当作弱标签，而不要求用户中断游戏逐项说明。

## 15. 置信度不只来自视觉模型

一个交互元素或界面类别的置信度可以由多种证据组成：

```text
视觉结构一致性
+ 点击位置聚类稳定性
+ 悬停与按压反馈
+ 状态转换重复性
+ 跨场景可达性
+ 进入条件稳定性
+ 返回路径稳定性
+ 持久化影响
+ 运动锚点类型
```

需要分别保存证据，而不是只保留一个不可解释的总分。

例如：

```text
classification: BASE_MENU_2D
confidence: 0.86
evidence:
  cross_scene_entry: 0.95
  fixed_shortcut: 0.98
  location_independence: 0.89
  stable_navigation_graph: 0.77
  persistent_setting_effect: 0.04
```

这里的`confidence`只表示当前界面分类证据，不等同于`transition_confidence`、`conditional_execution_reliability`、可用性、输入健康或检测器长期可靠性。各类证据只能更新自己能够说明的指标，具体处置遵循故障与指标规范。

## 16. LLM在这里仍然只承担语义层职责

机器层负责确定：

- 哪些像素或对象随世界运动；
- 哪些元素固定在屏幕上；
- 用户实际执行了什么输入；
- 哪些区域出现悬停、按压或点击反馈；
- 前后状态是否发生变化；
- 同一转换是否能够重复；
- 菜单是否依赖玩家位置和世界对象；
- 设置操作是否产生持久影响。

LLM可以负责：

- 为`state_cluster_017`建议“背包页面”等名称；
- 为`affordance_042`建议“关闭按钮”等名称；
- 解释两个候选分类为什么难以区分；
- 向用户提出“这是NPC商店还是通用商城”等问题；
- 根据关系网组织候选计划。

LLM不能仅凭一张截图直接把候选状态写成机器事实，也不能自行宣布某个区域已经被验证为按钮。

## 17. 可以进一步想象的方向

### 17.1 每个游戏逐渐形成自己的“界面DNA”

系统可以学习同一游戏中反复出现的：

- 字体；
- 按钮形状；
- 高亮颜色；
- 选中框；
- 图标尺寸；
- 面板间距；
- 返回按钮位置；
- 标签页结构；
- 设置控件样式。

发现一个可靠按钮后，可以用它帮助寻找同风格的其他候选，但最终仍要通过用户操作因果进行验证。

### 17.2 自动发现菜单的进入和退出配对

系统观察：

```text
状态A -> 输入X -> 状态B
状态B -> ESC或关闭按钮 -> 状态A'
```

如果`A'`与`A`高度相似，就可以推断状态B是覆盖菜单，而不是角色已经传送到另一个世界场景。

### 17.3 利用失败点击学习命中边界

成功点击和失败点击共同形成按钮命中区：

```text
成功点击云
+ 失败点击云
+ 悬停反馈区域
-> 估计真实可点击多边形
```

这比只保存一次点击坐标更适合不同分辨率、动画和轻微布局变化。

### 17.4 识别“不可交互的伪按钮”

有些区域外观像按钮，但用户从不点击，或者点击后没有任何反馈。系统应允许它长期保持为：

```text
VISUAL_CONTROL_CANDIDATE
```

而不是因为外观相似就自动发布成可执行按钮。

### 17.5 识别输入控制权的切换

系统可以把以下变化视为独立状态：

```text
CHARACTER_CONTROL
CAMERA_CONTROL
CURSOR_UI
MENU_SELECTION
TEXT_INPUT
DRAGGING
CUTSCENE_LOCKED
```

同一按键在不同控制模式下可能具有完全不同的含义。输入焦点应成为关系网状态的一部分，而不是隐藏条件。

## 18. 可校准连续交互节点

> 相关基础：[Whimbox键鼠执行](../game_ai_planning/05-Whimbox键鼠执行.md) · [错误恢复与执行证据](../game_ai_planning/10-Whimbox错误恢复与执行证据.md)

普通按钮通常产生离散状态变化：

```text
点击一次
-> 打开页面、关闭弹窗或切换标签
```

滑动条、滚动条、旋钮、地图拖拽和镜头控制则属于连续交互：

```text
输入一个目标量
-> 系统计算连续鼠标输入
-> 观察实际变化
-> 纠正误差并验证结果
```

因此，系统需要一种独立的“可校准连续交互节点”，而不是把连续控件继续保存成固定鼠标宏。

### 18.1 节点表达的是目标，不是固定鼠标位移

错误的宏式表达是：

```text
鼠标移动到(620, 440)
-> 按下左键
-> 向右拖动20像素
-> 松开左键
```

更合适的语义表达是：

```text
将主音量设置为65%
```

鼠标位移只是执行器根据当前画面、控件几何结构和校准结果临时计算出的动作参数。

节点可以包含三个内部能力：

```text
control.master_volume
├── calibrate()              建立或更新输入公式
├── set_value(target=0.65)   把控件设置到目标值
└── verify(target=0.65)      重新观察并验证结果
```

这里不需要为0%、1%、2%直到100%分别建立101个关系图节点。页面仍是一个离散状态：

```text
state.settings.audio
```

连续数值作为该状态携带的变量：

```text
state.settings.audio
  master_volume: 0.65
  music_volume: 0.80
  voice_volume: 0.70
```

关系图中的动作则是带参数的连续Step：

```text
state.settings.audio
-> set_control_value(control.master_volume, target=0.65)
-> state.settings.audio(master_volume≈0.65)
```

### 18.2 连续控件的基本模型

```text
ContinuousController
├── controller_id + revision_id
├── control_id
├── control_type
├── detector_ref
├── geometry_model
├── value_observer
├── actuator
├── calibration_policy
├── verification_policy
├── safety_policy
└── calibration_profile_ref
```

其中：

- `detector_ref`负责找到滑轨、滑块、滚动区域或世界锚点；
- `geometry_model`描述横向、纵向、角度或二维平面运动；
- `value_observer`负责读取百分比、数字、滑块位置或内容位置；
- `actuator`决定使用拖动、滚轮、按键增减还是相对鼠标移动；
- `calibration_policy`决定何时自检以及探测幅度；
- `verification_policy`定义允许误差和纠偏次数；
- `safety_policy`决定该控件是否允许自动探测。

### 18.3 微量自检闭环

连续节点第一次使用或校准失效时，可以执行一次小幅、可逆的主动探测：

```text
取得游戏控制资源
-> 确认当前页面和控件身份
-> 识别滑轨、滑块和当前值
-> 选择远离边界的安全探测方向
-> 按一个很小但高于死区的单位拖动或滚动
-> 等待界面稳定
-> 重新识别滑块、数值或内容位移
-> 计算实际响应
-> 尝试反向操作恢复原值
-> 保存校准结果和证据
```

“很小的单位”不能永远写死为一个屏幕像素，因为不同分辨率、缩放和控件长度下，一个像素可能无效或过大。可以使用：

```text
probe_delta = max(最小可注入位移, 滑轨有效长度 × 小比例)
```

例如从滑轨长度的1%开始，并根据是否出现响应逐渐扩大。

自检至少要确认：

- 控件确实发生了变化；
- 变化方向是否符合预期；
- 输入量与观测变化是否具有稳定关系；
- 是否存在最小死区；
- 是否存在固定刻度或吸附；
- 正向和反向结果是否对称；
- 反向操作能否恢复到原值；
- 操作是否错误触发页面跳转或其他按钮。

### 18.4 普通线性滑动条公式

假设已经识别出横向滑轨：

```text
有效范围：[x_min, x_max]
当前滑块位置：x0
微量探测位移：Δx
观测数值变化：Δv
```

可以建立初步线性关系：

```text
a = Δv / Δx
v = a × x + b
```

得到目标值后：

```text
x_target = (v_target - b) / a
```

如果界面没有显示明确数字，可以直接使用归一化位置：

```text
p = clamp((x - x_min) / (x_max - x_min), 0, 1)
```

此时：

```text
p=0.0 代表最左端
p=0.5 代表中间
p=1.0 代表最右端
```

目标位置可以计算为：

```text
x_target = x_min + p_target × (x_max - x_min)
```

对于普通UI滑动条，只要滑轨和滑块能够稳定检测，优先拖到计算后的绝对目标位置，通常比长期累计相对鼠标位移更稳定。

### 18.5 公式不一定是简单直线

不同控件需要不同响应模型：

| 控件 | 推荐模型 |
| --- | --- |
| 普通横向音量条 | 绝对位置线性映射 |
| 纵向亮度或音量条 | 纵轴线性映射，并通过自检确认增减方向 |
| 带整数刻度的滑块 | 量化线性映射 |
| 非线性灵敏度设置 | 分段单调映射或采样表 |
| 页面滚动条 | 滑块位置到内容窗口位置映射 |
| 鼠标滚轮列表 | 滚轮格数到内容位移的局部增量模型 |
| 旋钮 | 鼠标输入或角度到数值的环形映射 |
| 地图拖拽 | 二维鼠标位移到地图偏移的二维映射 |
| 游戏镜头 | 相对鼠标位移到镜头角度变化的动态映射 |

如果自检发现：

```text
相同Δx在不同位置产生不同Δv
```

就不应继续使用单一比例，而可以保存多个采样点：

```text
[(x0, v0), (x1, v1), (x2, v2), ...]
```

再使用分段插值或单调查找计算目标。

如果控件存在固定刻度，则还要保存：

```text
minimum_step
snap_positions
display_rounding
```

### 18.6 校准记录与节点定义分开

连续控件的机器定义可以相对稳定，但一次校准结果依赖具体环境，不应直接写死在节点版本中。

```text
ContinuousController
-> 定义这个控件是什么、如何观察、允许怎样操作

CalibrationProfile
-> 记录当前环境下具体的输入和结果关系
```

校准配置可以保存：

```text
calibration_id + revision_id
controller_id + controller_revision
environment_fingerprint
validation_status
runtime_status
control_id
control_type
axis_or_geometry
track_bounds
thumb_bounds
semantic_min / semantic_max
formula_type
formula_parameters
minimum_effective_delta
quantization_step
dead_zone
hysteresis
resolution
window_size
ui_scale
input_backend
game_version
visual_fingerprint
sample_ids
verified_at
confidence
```

`ContinuousController`属于可发布的能力定义，`CalibrationProfile`属于特定环境下的可失效参数。二者都需要修订ID，但发布生命周期和校准有效性分别管理。

这样，更换分辨率、窗口大小、UI缩放或输入后端时，可以让旧校准自动失效，而不需要把整个关系图节点删除。

### 18.7 下次调用可以跳过完整自检，但不能跳过验证

存在有效校准记录时：

```text
识别当前控件和当前值
-> 读取匹配当前环境的校准公式
-> 计算目标位置或输入量
-> 执行拖动、滚动或旋转
-> 等待稳定
-> 重新读取实际结果
```

结果可以分成：

```text
误差在容差范围内
-> outcome: SUCCEEDED

存在小误差
-> 根据残差执行一次有限局部修正

方向错误、没有响应或误差过大
-> CALIBRATION_INVALID
-> 重新进行微量自检
```

因此，缓存公式只用于减少完整校准成本，不能把“公式预测已经发送”当成设置成功。

### 18.8 校准失效条件

遇到以下情况时，应使当前校准降级或失效：

- 找不到原来的滑轨或滑块；
- 控件几何位置、长度或方向明显变化；
- 分辨率、窗口尺寸或UI缩放变化；
- 游戏版本、页面版本或主题发生变化；
- 当前值落在公式无法解释的位置；
- 输入后完全没有响应；
- 实际变化方向与预测相反；
- 实际变化量与公式预测差距超过阈值；
- 连续局部纠偏仍无法达到目标；
- 出现新的死区、吸附或动画延迟；
- 操作后进入了意外页面。

失效不应直接覆盖旧记录。旧记录仍可用于分析发生了什么变化，但不能继续作为活动执行公式。

### 18.9 数值滑动条与页面滚动条分开建模

两者视觉上可能相似，但观测目标不同。

#### 数值滑动条

滑块移动后通常表现为：

- 邻近数字、百分比或刻度改变；
- 音量、亮度、灵敏度等属性改变；
- 大片内容区域不会整体平移。

它的目标是：

```text
把某个连续变量设置到指定值
```

#### 页面滚动条

滑块移动后通常表现为：

- 大片列表内容上下或左右移动；
- 部分内容进入可见区域，另一些内容离开；
- 滑块长度可能反映可见内容占总内容的比例；
- 页面本身仍是同一个状态，只是视口发生变化。

它的目标可以是：

```text
滚动到某个归一化比例
```

但更多时候应该是：

```text
滚动直到目标元素进入可见区域
```

对应闭环为：

```text
小幅拖动或滚动
-> 检测目标元素
-> 未出现则继续有限滚动
-> 出现后停止
-> 确认目标元素稳定可交互
```

这比盲目滚到固定百分比更能适应列表长度变化。

### 18.10 微量自检也可以反向识别控件类型

系统面对未知候选控件时，可以在安全条件下进行一次可逆探测：

```text
只有滑块位置和邻近数字改变
-> 数值滑动条候选

滑块移动且大片内容区域发生同轴平移
-> 页面滚动条候选

拖动后世界镜头旋转
-> 镜头控制候选

拖动后地图整体平移
-> 可拖拽地图候选

拖动无连续反馈，但单击后切换页面
-> 普通按钮或标签页候选
```

因此，自检不仅用于计算执行公式，也可以验证系统是否正确理解了这个交互区域。

### 18.11 安全边界

主动自检只适用于可逆、低风险的连续控件。

通常可以优先考虑：

- 普通列表滚动；
- 音量滑块；
- 不会立即提交的页面内预览控件；
- 可以可靠恢复原位的地图或面板拖动。

需要谨慎或禁止自动自检的控件包括：

- 分辨率和全屏模式；
- 键位修改；
- 账号、服务器和语言切换；
- 购买、删除或资源消耗；
- 无法确认能否恢复的世界交互；
- 拖动即立即提交且不可撤销的控件。

高影响控件可以只观察用户真实操作来学习，不主动发送探测输入；或者在执行自检前要求用户明确批准。

### 18.12 推荐的执行状态

连续交互使用公共`ExecutionOutcome`。顶层`outcome`只返回`SUCCEEDED / FAILED / UNKNOWN / CANCELLED / BLOCKED`，以下名称作为专业`reason_code`：

```text
CALIBRATION_REQUIRED
CALIBRATION_INVALID
NO_RESPONSE
SATURATED
TARGET_NOT_REACHED
UNSAFE_TO_PROBE
```

其中：

- `SATURATED`表示已经到达控件边界，无法继续向目标方向变化；
- `NO_RESPONSE`表示输入已发出但没有观察到有效变化；
- `TARGET_NOT_REACHED`表示控件有响应，但有限纠偏后仍未达到目标；
- `UNKNOWN`表示输入可能生效，但后置观测不足以确认；
- `UNSAFE_TO_PROBE`表示当前策略不允许自动自检。

### 18.13 最终闭环

```text
连续控制节点被调用
-> 检查当前页面和控件身份
-> 检查活动校准是否匹配当前环境
-> 必要时进行微量、自恢复的主动探测
-> 根据公式计算目标输入
-> 执行拖动、滚动或旋转
-> 重新观察实际结果
-> 允许有限局部纠偏
-> 达标则保存成功证据
-> 不达标则使校准失效并重新自检或请求用户
```

它把“拖动多少像素”的固定宏升级为一个能够观察、标定、预测、执行、验证和纠错的连续控制器。

## 19. 暂态过滤与候选生命周期

画面发生变化不等于出现新状态。发现层先按时间稳定性和可重复性分流：

```text
RawObservationCluster
├── TRANSIENT
├── CANDIDATE_STATE
├── CANDIDATE_VISUAL_VARIANT
├── CANDIDATE_INTERRUPTION
└── UNKNOWN_BLOCKING
```

按钮按压态、淡入淡出、页面滑动、加载帧、角色切换动画和技能冷却动画通常只作为`TransitionObservation.transient_frames`，不建立正式`StateDefinition`。

状态候选的成熟过程建议分轴管理：

```text
validation_status:
  UNVALIDATED
  -> OFFLINE_VALIDATED
  -> SHADOW_VALIDATED
  -> LIVE_VALIDATED

release_status:
  DRAFT
  -> CANDIDATE
  -> SHADOW
  -> ACTIVE
  -> DEGRADED
  -> RETIRED
```

候选提升至少检查：

- 在稳定窗口中持续存在，而不是自动消失的动画帧；
- 能够在相似前置条件下重复进入；
- 可以承接操作或形成稳定后置行为；
- 与已有状态、视觉变体和已知中断完成对齐；
- 输入来源、窗口归属和感知证据可追溯；
- 多次证据没有被故障处置标为无效或隔离。

## 20. 从观察假设到运行事实

发现层和执行层使用不同对象：

```text
原始帧与输入事件
-> ObservationState：感知模块提出的组合假设
-> EvidenceValidator：检查时间、来源、模型版本和冲突
-> StateSnapshot：当前已融合的运行事实
-> StateDefinition / TransitionDefinition候选
```

已有关系网是先验，当前观察是新证据。出现冲突时先判断视觉变体、上下文变化、暂态、故障和版本差异，不立即覆盖旧定义。无法归因的分支留在候选区，等待后续重复观察或用户确认。

截图、差分、OCR和目标检测必须保持只读。主动悬停或微量探测属于明确授权的`StepAttempt`，不能隐藏在观察函数中，否则系统无法区分变化来自用户、计划还是感知模块自身。

## 21. 分层感知与专业模块链接

高频发现优先使用画面差分、颜色、哈希和局部模板；OCR、YOLO、CLIP、SAM只在对应不确定性上按需运行。所有结果保留区域、原始分数、模型修订和时间戳，再由证据融合决定候选状态。

## 22. 最小验证计划

第一阶段先对录制数据做离线发现，再进入低风险主动验证：

| 实验 | 数据与场景 | 验收重点 |
| --- | --- | --- |
| 时间切片 | 录制打开/关闭菜单并包含动画 | 稳定窗口可复现，动画不会批量生成状态节点 |
| 控件发现 | 同一按钮的悬停、点击、失败微调 | 身份区、状态区和安全操作区分别收敛 |
| 输入来源 | 混合用户操作、自动StepAttempt和未知输入 | 未知来源不自动发布关系边 |
| 菜单分类 | 多地点基础菜单、NPC菜单和设置菜单 | 依赖进入条件与返回拓扑，不依赖单帧美术风格 |
| 故障隔离 | 插入旧帧、错窗口输入和图标缺失样本 | 无效样本不会降低Transition或Capability可靠性 |
| 候选发布 | 同一片段跨会话重复出现 | 完整经历验证和发布双轴，不越级进入ACTIVE |

建议记录暂态误建率、候选合并准确率、控件命中区域误触率、关系边复现率和需要用户确认的比例。每个失败样本都通过公共证据包回放。

## 23. 总结

这套构想的核心不是训练一个模型把截图分成“游戏”“菜单”“设置”，而是建立一个会随用户游玩不断积累证据的观察系统：

```text
持续采集画面和输入
-> 利用运动分解世界层与界面层
-> 利用用户行为发现可供性
-> 利用前后变化建立状态转换
-> 利用进入条件区分上下文菜单、基础菜单和设置菜单
-> 利用微量探测标定滑动条、滚动条等连续控件
-> 利用暂态过滤和候选生命周期控制关系网增长
-> 利用统一故障归因隔离输入、感知和环境异常
-> 利用重复执行与关系图拓扑提高置信度
-> 最后由LLM辅助命名、解释和提问
```

最终系统理解的不是一组孤立截图，而是一套由世界、覆盖层、输入焦点、交互条件、连续控制变量和状态转换共同组成的游戏交互结构。
