## 1. 核心问题

当桌面同时运行多个游戏时，系统不能只根据“任务属于哪个游戏”推断真实输入目标。

可能发生：

```text
计划要求控制无限暖暖
-> 后台原神仍持有或重新取得鼠标相关状态
-> 系统发送相对鼠标移动
-> 实际发生变化的是原神窗口
```

也可能发生：

```text
无限暖暖仍是前台窗口
-> 游戏内部偶发输入状态异常
-> 游戏没有正常取得相对鼠标控制
-> 鼠标在桌面上移动，但镜头不旋转
```

这两种情况表面上都是“鼠标控制不对”，但故障位置不同：

| 故障 | 含义 |
| --- | --- |
| 输入发送给错误窗口 | 桌面焦点、输入捕获或多窗口调度错误 |
| 目标窗口收到焦点但镜头不响应 | 游戏内部控制模式或相对鼠标状态异常 |

系统必须分别识别，不能统一采用“再多移动几次鼠标”的处理方式。

## 2. 三个概念必须分开

```text
截图来自哪个窗口
!=
当前前台窗口是谁
!=
真实输入被哪个程序消费
```

例如：

- `PrintWindow`可能取得无限暖暖画面；
- 桌面前台窗口可能是无限暖暖；
- 但某个后台游戏仍可能通过自身输入机制产生响应；
- 或无限暖暖虽然在前台，却没有进入正常角色视角控制模式。

因此：

> 窗口截图只能证明系统看到了什么，不能证明键鼠输入发给了谁。

`PrintWindow`、Windows Graphics Capture等都属于捕获手段，不是后台输入路由手段。

## 3. 从游戏执行层提升到桌面调度层

如果系统未来需要操作不同游戏和普通软件，就需要在所有应用适配器之上增加桌面级控制层。

```text
DesktopOrchestrator
├── WindowRegistry
├── CaptureRouter
├── FocusBroker
├── GlobalInputArbiter
├── InputOwnershipVerifier
├── ControlHealthMonitor
├── RecoverySupervisor
└── ApplicationAdapters
```

### 3.1 `WindowRegistry`

保存受管理应用的：

```text
application_id
window_id / HWND
process_id
executable_path
window_title
window_class
client_rect
screen_rect
monitor_id
DPI
visible / minimized / occluded
capture_capabilities
input_policy
```

窗口标题和句柄可能发生变化，因此长期身份应结合进程、可执行文件、窗口类和应用配置，而不是只保存一次HWND。

### 3.2 `CaptureRouter`

根据应用和当前状态选择：

- Windows Graphics Capture；
- `PrintWindow`；
- DXGI桌面复制；
- 桌面截图后裁剪窗口区域；
- 应用适配器提供的特殊捕获方式。

### 3.3 `FocusBroker`

负责请求激活目标窗口，并验证激活是否真正成功。

### 3.4 `GlobalInputArbiter`

为整个桌面的物理键鼠提供唯一仲裁入口。

### 3.5 `InputOwnershipVerifier`

通过窗口元数据和实际视觉响应共同判断谁消费了输入。

### 3.6 `ControlHealthMonitor`

判断目标游戏的角色控制、视角控制、鼠标捕获和输入反馈是否健康。

### 3.7 `RecoverySupervisor`

按风险和成本逐级调用通用恢复与游戏专用恢复。

## 4. 物理键鼠必须是桌面级独占资源

原来的窗口级资源可以表示：

```text
game_control:<window_id>
```

但多窗口环境还需要：

```text
desktop_physical_input
```

资源关系可以是：

```text
后台截图、OCR和目标检测
-> 可以对多个窗口并行执行

真实键盘或鼠标注入
-> 必须独占desktop_physical_input
```

因此两个游戏可以同时被观察，但不能同时认为自己拥有物理键鼠。

```text
Application A读取画面
Application B读取画面
Application C读取日志
-> 可以并行

Application A发送键鼠
Application B发送键鼠
-> 必须排队
```

对于标准桌面应用，如果UI Automation或正式API支持后台定向操作，可以声明不同资源策略；但游戏使用的前台输入、Raw Input或DirectInput通常不能依赖普通窗口消息可靠后台操作。

### 4.1 实例间隔离，实例内串行

每个受管理游戏实例拥有独立的：

```text
application_session_id
StateSnapshot
CapabilityRun调用树
模型与关系上下文
截图队列
故障与恢复预算
```

实例可以放在独立工作进程中，避免一个游戏的模型、状态或崩溃污染另一个实例。同一实例内部一次只允许一个计划进入真实动作提交阶段；多个实例的OCR、YOLO和截图可以并行，但所有前台物理输入仍必须经过全局`desktop_physical_input`串行仲裁。

这里存在两层串行约束：

```text
application_instance_execution
-> 防止同一游戏的两个计划争用状态

desktop_physical_input
-> 防止不同应用同时提交前台物理输入
```

## 5. 焦点租约与`focus_epoch`

每次准备向目标窗口发送输入时，系统应先建立焦点租约：

```text
取得desktop_physical_input
-> 记录目标窗口和进程
-> 请求激活目标窗口
-> 验证实际前台窗口
-> 检查目标窗口可见状态
-> 采集桌面和目标窗口画面
-> 验证输入就绪
-> 生成focus_epoch
-> 允许本轮执行
```

例如：

```text
FocusLease
  target_application: infinity_nikki
  target_hwnd: 0x0012038A
  focus_epoch: 108
  acquired_at: ...
  verified: true
```

如果其他窗口抢走焦点或系统检测到输入归属变化：

```text
focus_epoch: 108 -> 109
```

所有仍携带108的异步任务和工作线程都必须拒绝继续发送输入。

这种设计可以阻止：

```text
系统已经切到原神
-> 无限暖暖旧任务仍在后台发送鼠标
```

焦点变化时还应：

- 清空尚未注入的动作队列；
- 阻止新的鼠标和键盘动作；
- 释放系统已经记录为按下状态的键和鼠标按钮；
- 结束或暂停当前StepAttempt；
- 保存焦点变化前后的桌面证据。

## 6. 输入前验证流程

```text
取得全局输入资源
-> 关闭旧窗口仍未完成的输入序列
-> 激活目标窗口
-> 验证前台HWND与目标一致
-> 验证进程ID、窗口区域和DPI
-> 检查鼠标位置与限制区域
-> 采集目标窗口和桌面画面
-> 确认游戏处于允许输入的状态
-> 执行安全微量探测
-> 验证实际响应来自目标窗口
-> 固定focus_epoch和适用的control_schema_epoch
-> 创建公共StepAttempt
-> 才进入正式执行
```

任何真实动作提交前都重新检查两个epoch。`focus_epoch`证明桌面输入租约仍有效，`control_schema_epoch`证明游戏内部槽位和按键语义仍有效；任一变化都使旧动作失效。

Windows可提供的辅助信息包括：

- 当前前台窗口；
- 活动窗口和焦点窗口；
- GUI线程状态；
- 窗口可见、最小化和区域信息；
- 当前鼠标位置；
- 当前鼠标限制矩形；
- 前台、焦点和窗口事件通知。

但游戏可能使用Raw Input等机制，不存在一个对所有游戏都可靠的“全局鼠标归属”字段。因此系统最终仍需要视觉响应验证。

## 7. 验证真实输入接收者

以无限暖暖视角控制为例：

```text
确认无限暖暖窗口处于前台
-> 在安全状态发送极小水平鼠标量
-> 捕获无限暖暖画面
-> 估计镜头是否按预期变化
-> 同时观察其他受管理游戏是否发生意外变化
```

可能结果：

```text
无限暖暖镜头按预期变化
-> INPUT_READY

无限暖暖不变，原神发生变化
-> INPUT_OWNERSHIP_VIOLATION

两个窗口都没有可见变化
-> NO_RESPONSE或MOUSE_CAPTURE_LOST

桌面光标移动，但无限暖暖镜头不动
-> GAME_RELATIVE_MOUSE_NOT_CAPTURED

无限暖暖出现了菜单选择而不是镜头移动
-> WRONG_CONTROL_MODE
```

所以：

> 窗口处于前台只是必要条件；目标游戏对微量输入产生正确反馈，才是输入就绪的充分证据。

## 8. 多来源截图

建议同时保留三类观察源。

| 来源 | 主要用途 |
| --- | --- |
| 目标窗口截图 | 判断游戏内部页面、HUD和角色状态 |
| 整个桌面截图 | 判断实际前台、遮挡、弹窗、任务栏和鼠标位置 |
| 其他受管理窗口的低频截图 | 判断输入是否错误作用到其他应用 |

### 8.1 目标窗口截图

可根据应用能力选择：

- Windows Graphics Capture；
- `PrintWindow`；
- 应用专用捕获；
- 桌面截图裁剪。

### 8.2 桌面截图

桌面截图表达用户实际看到的组合画面，适合发现：

- 哪个窗口真正位于顶部；
- 是否出现系统弹窗；
- 鼠标是否逃离目标窗口；
- 目标窗口是否被其他窗口遮挡；
- 多窗口布局是否发生变化。

### 8.3 其他窗口见证

其他游戏不需要始终高帧率捕获。系统可以在输入验证期或出现异常时，对受管理窗口进行低频截图和差异比较。

如果目标窗口不变而另一个窗口在探测输入后出现符合鼠标移动的变化，就形成了重要的输入错投证据。

## 9. 捕获方法的边界

`PrintWindow`可能对某些DirectX、独占全屏、最小化或受保护窗口返回：

- 黑帧；
- 旧帧；
- 不完整画面；
- 与用户实际看到的画面不同的内容。

Windows Graphics Capture通常更适合现代窗口，但也可能受到应用、权限、最小化或保护机制限制。

DXGI桌面复制更接近真实桌面组合结果，但只能看到最终桌面表面，无法穿透完全遮挡的窗口。

因此可以为每个应用定义：

```text
ApplicationProfile
  capture_methods:
    - windows_graphics_capture
    - print_window
    - desktop_crop

  capture_validation:
    reject_black_frame: true
    reject_stale_frame: true

  input_policy:
    foreground_required: true

  focus_verification:
    desktop_confirmation: true
    visual_probe_required: true
```

任何捕获方法都不能单独证明该窗口正在接收输入。

## 10. 桌面和游戏状态分层

关系网不能只保存游戏内部页面，还需要保存桌面控制状态。

```text
DesktopState
├── foreground_window
├── focused_window
├── active_process
├── input_owner_candidate
├── cursor_position
├── cursor_clip_region
├── registered_applications
├── focus_epoch
└── desktop_input_lease
```

每个应用另有：

```text
ApplicationState
├── application_id
├── window_id
├── visible_state
├── page_state
├── control_mode
├── input_readiness
├── view_control_health
└── last_verified_focus_epoch
```

游戏Step的完整前置条件可以变成：

```text
desktop.foreground_window == target_hwnd
AND desktop.focus_epoch == step.focus_epoch
AND application.page_state == GAMEPLAY
AND application.control_mode == CHARACTER_CONTROL
AND application.view_control_health == HEALTHY
```

## 11. 视角控制健康状态

```text
ViewControlHealth
├── UNKNOWN
├── HEALTHY
├── WRONG_FOREGROUND_WINDOW
├── MOUSE_CAPTURE_LOST
├── RELATIVE_MOUSE_NO_RESPONSE
├── CURSOR_ESCAPED_CLIENT
├── UNEXPECTED_OTHER_WINDOW_RESPONSE
├── WRONG_CONTROL_MODE
└── RECOVERY_REQUIRED
```

### 11.1 健康检查

```text
确认当前处于可控制角色的游戏状态
-> 记录当前镜头角度或视觉特征
-> 记录桌面鼠标位置
-> 发送极小水平鼠标探测
-> 捕获目标窗口新鲜画面
-> 估计镜头变化方向和幅度
-> 检查桌面鼠标是否异常逃逸
-> 检查其他窗口是否发生意外响应
-> 必要时发送反向输入恢复
```

如果光标在桌面上发生明显移动，而游戏镜头没有变化，可以把“游戏未正常取得相对鼠标控制”作为高概率候选，但仍需排除当前处于菜单、过场或其他禁止视角输入的状态。

## 12. 恢复总原则

恢复方式应像人一样逐级尝试，但必须满足：

- 每一级都有限次和总超时；
- 每一级完成后重新观察，不假设已经修复；
- 每次输入前重新确认焦点租约；
- 高风险恢复需要用户批准；
- 任何恢复失败都不能继续原来的过期输入序列；
- 恢复成功后从当前真实状态重新规划；
- 原始失败、恢复动作和恢复结果分别保存。

## 13. 第一级：停止和重新观察

```text
停止新的键鼠注入
-> 使当前focus_epoch失效
-> 清空未发送动作
-> 释放所有已记录按键和鼠标按钮
-> 等待画面稳定
-> 捕获桌面和目标窗口
-> 重新判断页面、焦点和控制模式
```

这是所有恢复的共同入口。

系统不能在输入归属未知时继续尝试更多视角移动，否则可能进一步操作错误窗口。

## 14. 第二级：重新取得窗口焦点

```text
请求激活目标窗口
-> 验证实际前台窗口
-> 必要时采用该应用声明的安全聚焦方式
-> 等待窗口稳定
-> 执行视角微量探测
```

安全聚焦方式可以包括：

- 正常窗口激活请求；
- 用户已经批准的任务栏切换；
- 窗口化应用的非客户区；
- 游戏适配器声明的安全画面区域；
- 已验证不会产生游戏副作用的快捷键。

不能把“点击游戏窗口中央”作为通用聚焦方案，因为该位置可能对应攻击、购买、确认或其他危险操作。

## 15. 第三级：切换游戏内部控制模式

如果窗口焦点正确，但游戏没有恢复相对鼠标控制，可以尝试低风险模式切换：

```text
打开ESC菜单
-> 确认菜单出现
-> 关闭菜单
-> 确认返回角色控制
-> 再次验证视角
```

或者：

```text
进入地图或背包
-> 返回游戏世界
-> 再次验证视角
```

这些恢复能力必须由游戏适配器提供，不能假设所有游戏的ESC、地图和返回行为相同。

## 16. 第四级：游戏内恢复能力

针对无限暖暖，可以定义：

```text
nikki.teleport_to_safe_anchor
```

恢复流程：

```text
确认允许传送
-> 打开地图
-> 传送到已知安全位置
-> 等待加载和HUD稳定
-> 确认角色控制状态
-> 重新执行视角健康探测
```

必须明确：

```text
传送完成
!=
视角控制已经恢复
```

传送只是恢复候选动作，最终结果仍由视角响应验证决定。

## 17. 第五级：重新进入游戏世界

如果传送仍无法修复：

```text
安全退出当前世界
-> 返回登录或标题界面
-> 重新选择账号、角色或服务器
-> 进入游戏世界
-> 等待角色、HUD和场景稳定
-> 验证窗口焦点
-> 验证角色控制
-> 验证视角控制
```

该恢复可能：

- 中断当前任务；
- 丢失临时状态；
- 触发排队或登录验证；
- 进入与原计划不同的位置；
- 需要用户重新确认账号或服务器。

因此应由风险策略决定是否要求用户批准。

## 18. 第六级：重启客户端

重启是最后手段，需要考虑：

- 未保存进度；
- 当前战斗或副本；
- 启动器与游戏进程关系；
- 游戏更新；
- 登录验证码；
- 多账号窗口对应关系；
- 用户是否允许关闭进程；
- 重启后如何恢复到可执行状态。

重启完成后不能直接恢复旧Step。系统需要重新发现窗口、建立新应用实例、重新识别状态并重新规划。

## 19. 通用能力与游戏专用能力分开

### 19.1 通用桌面能力

```text
desktop.release_all_inputs
desktop.activate_window
desktop.verify_foreground
desktop.switch_window
desktop.capture_desktop
desktop.verify_input_owner
desktop.invalidate_focus_lease
```

### 19.2 游戏通用能力

```text
game.verify_character_control
game.verify_view_control
game.refocus_client
game.toggle_menu_and_return
```

### 19.3 游戏专用能力

```text
nikki.teleport_to_safe_anchor
nikki.return_to_login
nikki.reenter_world
```

其他游戏可以提供自己的：

```text
genshin.open_paimon_menu_and_return
game_x.reload_scene
game_y.return_to_title
```

恢复监督器先使用通用能力，再按应用配置选择游戏专用恢复。

## 20. 恢复能力的风险与成本

| 恢复动作 | 风险 | 成本 | 是否通常需要确认 |
| --- | --- | --- | --- |
| 释放输入并重新观察 | 低 | 低 | 否 |
| 重新激活窗口 | 低 | 低 | 否 |
| 安全切换菜单并返回 | 低至中 | 低 | 通常否 |
| 游戏内传送 | 中 | 中 | 按任务策略决定 |
| 返回登录并重新进入 | 中至高 | 高 | 通常需要 |
| 重启客户端 | 高 | 很高 | 需要 |

恢复规划器不应只选择“最可能修好”的动作，还要考虑：

- 当前任务能否中断；
- 是否存在副本或战斗损失；
- 是否会改变角色位置；
- 是否需要重新登录；
- 恢复后还能否继续原计划；
- 用户是否允许自动执行。

### 20.1 恢复预算与振荡看门狗

每个`PlanRun`、应用实例和故障签名都需要独立恢复预算：

```text
max_refocus_attempts
max_mode_toggle_attempts
max_reentry_attempts
max_total_recovery_cost
max_recovery_duration
```

看门狗识别以下无进展模式：

```text
窗口A -> 窗口B -> 窗口A反复抢焦点
重新聚焦 -> 探测失败 -> 重新聚焦循环
打开菜单 -> 返回游戏 -> 打开菜单振荡
恢复成功声明后控制健康仍未变化
```

触发后停止动作、释放`desktop_physical_input`、使当前`focus_epoch`失效并固化最近帧与焦点事件。它返回公共`BLOCKED`加专业`reason_code`，由统一故障归因决定是否请求用户或结束计划。

## 21. 输入错误投递的完整场景

```text
无限暖暖正在执行视角控制
-> 原神抢走焦点或鼠标相关状态
-> 前台事件、桌面观察或视觉探测发现异常
-> focus_epoch立即失效
-> 清空尚未注入的动作队列
-> 释放键盘键和鼠标按钮
-> 保存桌面、无限暖暖和原神画面证据
-> 判断原神是否产生意外响应
-> 重新激活无限暖暖
-> 建立新的focus_epoch
-> 执行极小视角探测
```

探测成功：

```text
重新识别当前游戏状态
-> 判断原Step是否仍然适用
-> 适用则创建新的StepAttempt继续
```

探测失败：

```text
切换菜单并返回
-> 再次探测
-> 仍失败则尝试游戏内传送
-> 再次探测
-> 仍失败则请求用户批准重新进入游戏
```

任何一级恢复成功后，都不应从出错前尚未完成的鼠标序列中间继续。

公共部分保存顶层`ExecutionOutcome`、`reason_code`、`FailureAttribution`、`SampleDisposition`和统一证据包引用。恢复运行始终独立于原失败`StepAttempt`，恢复成功后也只能创建新的尝试。

这样可以回答：

- 输入计划发送给谁；
- 发送时谁是前台窗口；
- 哪个窗口实际发生了变化；
- 系统如何判断焦点错误；
- 尝试了哪些恢复；
- 恢复后是否真的通过视角健康检查。


### 23.1 普通桌面软件

优先使用：

- 官方API；
- UI Automation；
- 可访问性接口；
- 标准窗口控件；
- 明确支持的窗口消息。

### 23.2 游戏软件

通常采用：

- 目标窗口或桌面截图；
- 明确前台焦点；
- 操作系统级输入；
- 输入后的视觉验证；
- 游戏专用控制健康检查。

### 23.3 真正并发输入

Windows同一个交互桌面通常只有一套物理前台键鼠语义。若未来要求两个游戏真正同时、独立接收各自输入，仅靠切换窗口和后台消息并不可靠。

更明确的隔离方式可能需要：

- 不同Windows会话；
- 虚拟机；
- 不同物理设备；
- 游戏自身正式支持的多实例控制接口。

在单桌面方案中，最稳妥的策略仍然是并行观察、串行输入和严格验证。

## 24. 安全边界

- 不在输入归属未知时继续发送键鼠；
- 不把`SetForegroundWindow`等激活请求的返回当作焦点已经就绪；
- 不把`PrintWindow`成功当作窗口能够接收后台输入；
- 不用未知的窗口中心点击作为通用聚焦方式；
- 不强制假设所有游戏都支持后台消息输入；
- 不无限循环切换窗口、传送或重新登录；
- 不在未确认风险时自动重启客户端；
- 不在恢复后直接复用旧的输入队列；
- 不通过注入游戏进程或规避保护机制解决输入路由问题；
- 每种游戏的自动化方式都应符合其使用规则和用户授权。

## 25. 建议的结果状态

公共`ExecutionOutcome`只使用`SUCCEEDED / FAILED / UNKNOWN / CANCELLED / BLOCKED`。以下名称均作为桌面输入模块的`reason_code`或当前健康状态，不再充当顶层结果：

```text
INPUT_READY
FOCUS_REQUIRED
FOCUS_ACTIVATION_FAILED
FOCUS_LOST
FOCUS_EPOCH_EXPIRED
WRONG_FOREGROUND_WINDOW
INPUT_OWNERSHIP_VIOLATION
MOUSE_CAPTURE_LOST
RELATIVE_MOUSE_NO_RESPONSE
CURSOR_ESCAPED_CLIENT
WRONG_CONTROL_MODE
UNEXPECTED_OTHER_WINDOW_RESPONSE
RECOVERY_REQUIRED
RECOVERY_SUCCEEDED
RECOVERY_FAILED
USER_CONFIRMATION_REQUIRED
UNKNOWN
```

这些结果应进入调度和恢复策略，而不是只写一条“鼠标移动失败”的日志。

## 26. 最小验证计划

| 实验 | 场景 | 验收重点 |
| --- | --- | --- |
| 抢焦点 | 两个受管理游戏交替取得前台 | 旧focus_epoch立即失效，物理输入不并发 |
| 错误接收者 | 向目标窗口探测时让见证窗口产生响应 | 返回输入归属reason_code，不评价游戏能力 |
| 捕获失效 | 注入PrintWindow旧帧、黑帧和桌面遮挡 | 捕获健康与输入归属分开判定 |
| 队列失效 | 输入序列中途改变focus_epoch | 未提交事件被清空，按键和鼠标按钮被释放 |
| 双epoch | 焦点不变但角色控制Schema切换 | control_schema_epoch阻止旧按键语义继续执行 |
| 视角异常 | 前台正确但相对鼠标不响应 | 逐级恢复，每一级都重新探测控制健康 |
| 恢复振荡 | 人工制造反复聚焦或菜单A/B循环 | 在预算内BLOCKED并生成完整证据包 |
| 实例隔离 | 一个游戏工作进程崩溃 | 另一实例继续观察，状态与恢复预算不串线 |

记录错误投递漏检率、错误投递误报率、焦点切换到输入就绪延迟、旧队列残留数、输入释放完整率和各级恢复成功率。所有真实输入实验先使用低风险页面和最小探测量。

## 27. 总结

多窗口环境下，系统不能把“目标窗口句柄”直接等同于“真实输入接收者”。完整闭环应为：

```text
注册和识别桌面应用
-> 并行捕获目标窗口、桌面和必要的见证窗口
-> 取得全局物理输入资源
-> 激活并验证目标窗口
-> 建立带focus_epoch的焦点租约
-> 固定适用的control_schema_epoch
-> 通过微量视觉探测确认真实输入归属
-> 创建公共StepAttempt并执行正式游戏Step
-> 持续监控焦点和控制健康
-> 异常时立即停止、释放输入和保存证据
-> 按重新聚焦、模式切换、传送、重新登录和重启逐级恢复
-> 每一级恢复后重新验证并从真实状态规划
```

最终边界是：

> 后台窗口可以并行观察，物理键鼠必须串行仲裁；每次输入都必须证明目标窗口真正取得了控制权。
