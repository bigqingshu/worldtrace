# 鼠标场景模式辅助判定与RAW操作轨迹分层记录构想

> 文档性质：实验阶段方向草案，不是正式架构决定或 Trace Core 公共契约
>
> 当前实验：[Raw Mouse Visualizer（原始鼠标可视化实验）](../../../experiments/raw_mouse_visualizer/README.zh-CN.md)
>
> 相关构想：[3D场景视角方向观测与闭环控制构想](3D场景视角方向观测与闭环控制构想.md) · [多窗口输入归属与游戏视角异常恢复构想](多窗口输入归属与游戏视角异常恢复构想.md) · [基于用户游玩监控的界面与交互要素发现构想](基于用户游玩监控的界面与交互要素发现构想.md)

## 1. 当前方向

鼠标观测同时服务于两个不同目标：

1. **场景交互模式辅助判定**：帮助区分定位式 2D 界面交互和相对式 3D 镜头控制，为后续分类识别与分类执行提供候选条件。
2. **用户鼠标操作轨迹记录**：保存用户真实操作，用于后续自学习、动作归纳、按帧对齐和执行方案实验。

两个目标不能共用同一套精度要求：

- 场景判定只需要低成本、可重复的辅助标志，不需要完整还原游戏内部鼠标机制；
- 操作学习需要先保留高精度基准，再通过实验判断哪些数据能够安全简化。

因此当前原则是：

> 场景分类使用少量鼠标现象作为辅助证据；操作学习默认以完整 RAW 输入作为基准，采样和简化只生成派生结果，不提前替代原始事实。

## 2. 当前机器上的实验观察

以下内容来自当前机器和当前游戏配置下的用户观察，尚不能推广为所有版本、窗口模式、远控方式或输入设备的通用事实。

### 2.1 原神

- 进入角色控制场景后，鼠标表现为向窗口中心吸附或反复回正；
- RAW（原始输入）仍可产生相对 `dx/dy`；
- 绝对屏幕光标位置不能直接代表镜头移动量；
- 这种现象适合形成“中心吸附”辅助标志。

### 2.2 无限暖暖

- 鼠标活动范围可被限制在游戏窗口或客户区边界内；
- 限制区域明显大于单一中心点，较大鼠标位移仍可在区域内发生；
- 单纯检测“是否固定在中心”无法覆盖这种实现；
- 这种现象适合形成“目标客户区约束”辅助标志。

### 2.3 光标显示状态

- 光标不可见可能出现在相对式 3D 控制中；
- 光标可见不能排除游戏正在使用相对输入；
- 远控、权限、窗口切换和接口失败都可能造成无法可靠取得光标显示状态；
- 游戏在非前台时仍可能残留裁剪、捕获或吸附，甚至影响前方窗口的鼠标操作。

因此必须区分：

```text
已确认光标隐藏
!=
光标可见性无法获取
```

前者可作为普通辅助证据，后者最多作为弱提示，不能单独证明正在使用 3D 镜头控制。

## 3. 场景交互模式辅助判定

### 3.1 判定目标

第一版不试图回答：

```text
游戏内部究竟调用了哪一种鼠标 API？
```

只尝试回答：

```text
当前更像定位式 2D 指针交互，
还是相对式 3D 镜头控制？
```

该结果仍是候选，不是已经确认的游戏状态。

### 3.2 鼠标辅助标志

可观察的低成本标志包括：

| 辅助标志 | 含义 | 证据强度 |
| --- | --- | --- |
| 中心吸附或反复回正 | 绝对光标长期接近目标窗口中心，RAW 仍有相对运动 | 中等 |
| 客户区边界约束 | 光标无法越过目标客户区，约束区域随窗口几何变化 | 中等 |
| RAW 与绝对位置分离 | RAW 持续变化，但绝对光标静止、回正或只在受限区域内变化 | 中等 |
| 已确认光标隐藏 | Windows 明确报告当前光标不显示 | 弱到中等 |
| 光标可见性无法获取 | 接口没有给出可靠结果 | 弱 |
| 目标捕获或裁剪 | 捕获、裁剪或活动窗口信号属于目标 | 中等 |
| 非前台仍残留约束 | 可能存在残留捕获或异常状态 | 反证或故障证据 |

中心吸附和客户区约束是两种不同现象，但对第一版分类而言都可作为“相对式控制可能正在使用鼠标”的辅助标志。

### 3.3 画面变化是主要因素

鼠标约束只能说明指针路径发生了特殊变化，不能证明游戏画面真正消费了输入。

主要证据应来自：

```text
RAW方向与运动量
+
随后一段时间内的画面运动
+
运动方向、时间和作用区域的一致性
```

第一版可先使用低成本 CV（计算机视觉）方法：

- 灰度帧差；
- 稀疏或稠密光流；
- 中央场景区域的主运动方向；
- 边缘 HUD 相对稳定、背景大范围运动的比例；
- RAW 方向反转后，画面主运动方向是否随之反转；
- 输入到画面响应的时间延迟。

画面自身动画、角色待机、粒子、天气和 UI 滚动都可能产生运动，因此不能只用单帧变化量。需要把运动与 RAW 的时间和方向相关性一起考虑。

### 3.4 第一版候选结果

第一版只需要保留以下语义，具体英文类型名暂不冻结：

- 定位式 2D 交互候选；
- 相对式 3D 控制候选；
- 混合或过渡状态；
- 捕获或裁剪残留；
- `UNKNOWN`（未知）。

目标不在准确前台、窗口身份改变、客户区几何不稳定或证据互相冲突时，应保持 `UNKNOWN` 或标记为过渡/残留，不能仅凭光标吸附写入确认状态。

## 4. 用户操作轨迹记录

### 4.1 为什么先保留完整 RAW

在采集入口直接每隔若干样本合并，虽然可以保持一组的净 `dx/dy`，但可能丢失：

- 快速回头；
- 小幅修正；
- 瞬时速度变化；
- 移动与点击之间的精确时间关系；
- 组内正反方向相互抵消的实际运动。

例如：

```text
+5 -> -5
```

净位移为零，但用户确实完成了一次往返修正。若采集入口只保存合并后的 `(0, 0)`，后续算法无法恢复这个事实。

因此当前 `raw_mouse_visualizer` 中的完整获取、间隔1次和间隔N次，首先用于比较性能与偏差；在误差边界尚未验证前，间隔模式不能默认成为自学习的权威数据。

### 4.2 三层数据

建议将鼠标记录分成三层，以下名称只描述职责，不冻结正式类型名。

#### 第一层：完整 RAW 基准

至少保留：

```text
monotonic_timestamp
device_identity
dx / dy
button_down / button_up
wheel_delta
source_sequence
focus_epoch
target_identity
```

它用于：

- 比较各种简化算法；
- 回查丢失的转向和微调；
- 重新生成不同粒度的派生轨迹；
- 评估输入与画面变化之间的关系。

#### 第二层：派生简化轨迹

从完整 RAW 中生成关键点和分段，优先保留：

- 起点和终点；
- 方向变化；
- 回头；
- 停顿；
- 速度等级变化；
- 按钮和滚轮边界；
- 设备、焦点或目标变化。

该结果可以反复调整参数并重新生成，不应覆盖原始基准。

#### 第三层：画面帧对齐动作

视觉自学习最终观察的是一帧到下一帧的结果，因此可按相邻画面帧的时间区间汇总 RAW：

```text
frame_before_id
frame_after_id
sum_dx / sum_dy
absolute_motion_sum
source_sample_count
direction_change_count
peak_step
first_timestamp / last_timestamp
button_and_wheel_edges
```

它把每秒数百到数千个硬件报告转换为与截图频率一致的动作摘要，适合学习“这段鼠标输入使画面发生了什么变化”。

### 4.3 合并时不能只保存净位移

任何派生聚合至少还应考虑保存：

- 源样本数量；
- 时间跨度；
- 净 `dx/dy`；
- `abs(dx)` 与 `abs(dy)` 累计；
- 方向变化次数；
- 最大单步位移或峰值速度；
- 是否包含按钮、滚轮、设备或焦点边界。

这样即使净位移接近零，系统仍能知道该窗口内存在明显鼠标运动。

## 5. 精度、点数与性能的分层取舍

“精确记录、少点和低性能开销”不能通过采集入口直接删除数据同时获得，但可以通过不同频率的分层管线兼顾：

```text
完整RAW采集
-> 有界内存与批量传输
   -> GUI低频刷新
   -> 场景分类辅助特征
   -> 按画面帧生成动作摘要
   -> 停止后生成简化轨迹
```

应分别控制：

| 环节 | 推荐方向 |
| --- | --- |
| Windows RAW 接收 | 尽量完整、回调内只做轻量工作 |
| 跨进程传输 | 固定结构、批量传输或共享有界缓冲 |
| GUI 绘制 | 约 30～60 Hz 刷新，不按每个 RAW 样本重绘 |
| 在线场景特征 | 使用短时间窗摘要，不保留全部 Python 对象 |
| 轨迹简化 | 停止后或独立工作线程批量处理 |
| 长期保存 | 由显式开关和实验方案决定，不默认写文件 |

鼠标在 500～1000 Hz 回报率下，如果采用紧凑固定结构，原始数据通常只是几十 KB/s 量级。真正更容易造成开销的是逐样本创建大量 Python 对象、逐条进程间通信、逐点 GUI 重绘和 JSON 文本膨胀。

因此性能优化顺序应优先考虑：

1. 降低绘制频率；
2. 批量跨进程传输；
3. 有界环形缓冲；
4. 按帧或按时间生成派生摘要；
5. 最后才根据实测偏差决定是否在采集入口降采样。

## 6. 需要比较的简化方法

后续实验应以同一段完整 RAW 为基准，比较：

| 方法 | 优点 | 主要风险 |
| --- | --- | --- |
| 按数量合并 | 实现简单，输出数量稳定 | 丢失组内方向与时间细节 |
| 按固定时间合并 | 容易与控制周期对应 | 高速与低速动作精度不一致 |
| 按画面帧合并 | 最适合视觉结果学习 | 依赖稳定的统一时间线和帧时间戳 |
| 方向关键点简化 | 保留轨迹形状，点数较少 | 阈值需要按设备和游戏实验 |
| 混合方法 | 可同时保存帧动作和关键点 | 契约和调试复杂度更高 |

比较指标至少包括：

- 总 `dx/dy` 偏差；
- 绝对运动量偏差；
- 转向与回头召回率；
- 按钮边界时间偏差；
- 每帧动作摘要偏差；
- 处理耗时；
- 峰值内存；
- 进程间消息数量；
- GUI 刷新稳定性；
- 与画面光流变化的相关性。

## 7. 当前实验边界

### 当前应继续做

- 使用 `raw_mouse_visualizer` 形成不同游戏、窗口模式和远控方式的鼠标现象基线；
- 保留完整 RAW 作为简化实验的对照；
- 继续验证间隔合并与关键点简化的实际偏差；
- 建立 RAW 与连续帧的统一时间关系；
- 用低成本帧差或光流验证画面是否响应；
- 始终把候选结果与确认的游戏状态分开。

### 当前不应做

- 为识别每一种游戏内部鼠标 API 而无限增加 Win32 特例；
- 把中心吸附当成所有 3D 游戏的必要条件；
- 把客户区约束单独当成已确认 3D 场景；
- 把“无法取得光标可见性”直接等同于“光标隐藏”；
- 在没有误差评估前删除完整 RAW 基准；
- 根据收到 RAW 或发送成功推断游戏已经消费输入；
- 把实验候选直接写入确认的游戏状态。

## 8. 推荐实施顺序

1. 固定现有鼠标辅助标志，不继续追求完美的纯 Win32 分类器；
2. 为完整 RAW 建立短时、批量、有界的基准记录；
3. 将帧时间戳与 RAW 时间戳放入同一时间线；
4. 实现低成本画面运动量和主方向观测；
5. 输出“2D定位式 / 3D相对式 / 过渡 / 残留 / 未知”候选；
6. 对同一段 RAW 离线比较四类简化方法；
7. 根据偏差、性能和自学习效果决定默认记录粒度；
8. 在边界稳定后，再决定是否形成正式模块与公共契约。

## 9. 第一轮验收重点

- 原神中心吸附和无限暖暖客户区约束都能形成独立辅助标志；
- 光标隐藏、光标可见性未知和后台残留能够明确区分；
- 没有画面响应时，鼠标辅助标志不能单独确认 3D 场景；
- 完整 RAW、派生简化轨迹和帧对齐动作可以同时比较；
- 任一简化结果都能追溯到同一段完整 RAW 基准；
- 简化前后总位移、方向变化、按钮边界和每帧动作偏差可量化；
- GUI 显示频率与 RAW 采集频率相互独立；
- 默认不写入确认的游戏状态，也不默认产生长期轨迹文件。

## 10. 当前结论

当前鼠标方向无需继续追求“只靠光标位置完美识别所有锁定模式”。

更实际的组合是：

```text
简单鼠标辅助标志
+ RAW与绝对光标的关系
+ 目标窗口和前台身份
+ 画面运动与RAW方向的相关性
-> 场景交互模式候选
```

而自学习记录采用：

```text
完整RAW基准
-> 可重建的简化轨迹
-> 与画面帧对齐的动作摘要
```

前者追求足够可靠和低成本，后者先追求可追溯，再通过实验寻找精度、点数和性能之间的实际平衡。
