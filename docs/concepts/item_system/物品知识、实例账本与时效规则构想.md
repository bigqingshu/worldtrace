## 1. 核心问题

系统以后不仅需要知道“画面中出现了一个物品图标”，还可能需要回答：

- 这是什么种类的物品；
- 用户是否实际拥有它；
- 当前拥有多少个；
- 它在哪里获得、怎样获得；
- 获取是否受到区域、时间、天气、任务或活动限制；
- 它有什么固定属性和随机属性；
- 同名物品是否其实是不同实例；
- 图标变化是素材版本变化、强化变化还是另一种物品；
- 物品何时失效、何时消失；
- 本次没看到它，是确实消失还是库存没有扫描完整。

如果把这些信息全部塞入一个“物品节点”，定义知识、用户库存、单次截图和历史事件就会混在一起，最终难以更新、追溯和判断错误来源。

核心原则是：

> 物品种类知识、用户拥有的具体实例和屏幕上的单次观测必须分开管理。

## 2. 三层数据结构

建议将物品系统拆成三层：

```text
ItemCatalog
-> 物品种类、属性定义、获取来源和时间规则

InventoryLedger
-> 用户实际拥有的实例、堆叠数量和完整变化历史

ItemEvidence
-> 截图、图标、OCR文本、库存扫描范围和单次识别结果
```

三层通过稳定ID和证据引用连接，但不能互相覆盖。

### 2.1 `ItemCatalog`

回答游戏知识问题：

```text
这个物品是什么
有哪些已知属性
在哪里获得
怎样获得
什么时候可以获得或使用
```

### 2.2 `InventoryLedger`

回答用户资产问题：

```text
用户当前拥有多少
具体实例的随机属性是什么
它何时获得、强化、装备、转移或消耗
```

### 2.3 `ItemEvidence`

回答证据问题：

```text
系统在哪一帧看到了什么
识别覆盖了哪些库存页面
OCR原文是什么
本次判断使用了哪些图标和界面证据
```

## 3. “物品位置”必须拆分

“每个物品留一个位置记录”中的位置至少有三种完全不同的含义。

### 3.1 `AcquisitionLocation`

表示物品在游戏世界中的获取位置：

```text
AcquisitionLocation
├── map_space_id
├── place_anchor_id
├── region_id
├── npc_or_enemy_id
├── activity_or_dungeon_id
├── local_position_or_area
└── evidence_ids
```

同一种物品可以有多个获取位置，也可以只有活动、商店或配方而没有固定空间位置。

### 3.2 `StorageLocation`

表示用户当前把物品放在哪里：

```text
背包
角色装备栏
仓库
邮件
交易或拍卖暂存区
活动专用容器
其他角色或队伍
UNKNOWN
```

装备、转移和进入邮件不等于物品消失，只是`StorageLocation`发生变化。

### 3.3 `ObservationLocation`

表示本次截图中的屏幕位置：

```text
inventory_tab
page_or_scroll_range
grid_slot
bbox
frame_id
```

排序、筛选、分页和分辨率变化都会改变屏幕位置，因此`ObservationLocation`只能属于单次证据，不能作为物品身份或永久位置。

## 4. 物品种类、实例、堆叠和同质批次

不同游戏物品需要不同粒度，不能全部强行建立独立实例。

### 4.1 `ItemTypeDefinition`

表示一种物品概念：

```text
ItemTypeDefinition
├── item_type_id
├── game_profile_id
├── display_name_variants
├── category
├── rarity_definition
├── fixed_attribute_refs
├── visual_variant_refs
├── description_source_refs
├── acquisition_rule_refs
├── temporal_rule_refs
├── content_version_range
└── lifecycle_status
```

显示名称不是唯一键。不同物品可能同名，同一物品也可能因为语言、版本或简称具有多个名称。

### 4.2 `ItemStack`

材料、货币和消耗品通常只需要记录数量：

```text
ItemStack
├── stack_id
├── item_type_id
├── container_id
├── quantity
├── last_confirmed_at
└── evidence_ids
```

数量变化通过事件追加，不直接覆盖而丢失历史。

### 4.3 `ItemInstance`

具有独立随机属性、强化等级或装备状态的物品需要实例：

```text
ItemInstance
├── instance_id
├── item_type_id
├── instance_attributes
├── mutable_attributes
├── storage_location
├── acquired_at
├── last_seen_at
├── lineage_refs
└── evidence_ids
```

圣遗物、武器、装备和带随机词条的物品通常属于这一类。

### 4.4 `ItemLot`

如果两个实例名称、等级、图标和属性完全一致，游戏也没有暴露内部ID，系统无法凭视觉可靠地区分它们。此时不应虚构身份，而应使用同质批次：

```text
ItemLot
├── lot_id
├── item_type_id
├── shared_instance_signature
├── multiplicity
└── evidence_ids
```

当其中一个物品被强化、装备或锁定，产生可观察差异后，再从批次中分离出独立`ItemInstance`。

## 5. 属性分层

物品属性至少分为四类。

### 5.1 类型固有属性

同一物品种类共同拥有：

```text
物品类别
所属套装
基础稀有度
固定说明
固定用途
默认获取方式
```

### 5.2 实例随机属性

每个实例可能不同：

```text
主词条
副词条
随机数值
随机品质
生成时附带效果
```

### 5.3 实例可变属性

会随着玩家操作变化：

```text
强化等级
突破阶段
经验
锁定状态
耐久
剩余次数
绑定状态
```

### 5.4 运行时状态

只在当前上下文成立：

```text
当前装备角色
当前是否可使用
是否被任务临时禁用
是否处于冷却
是否满足活动阶段
```

类型属性、实例属性和运行状态不能写进同一个不可区分的`attributes`字典。

## 6. 原始文本和结构化属性

游戏内说明文本必须作为原始事实保存：

```text
ItemDescriptionEvidence
├── raw_text
├── language
├── game_version
├── frame_id
├── roi_ref
├── ocr_confidence
└── source_context
```

分析后的属性另存为结构化候选：

```text
AttributeClaim
├── item_type_id或instance_id
├── attribute_key
├── normalized_value
├── unit
├── source_quote
├── extraction_method
├── confidence
└── validation_status
```

必须保留原文，原因包括：

- OCR可能识别错误；
- LLM可能误解条件范围；
- 游戏更新可能修改说明；
- 不同语言翻译可能产生语义差异；
- 后续解析器升级时需要重新提取。

## 7. AI在物品知识中的边界

AI适合把自然语言说明转换为候选结构，例如：

```text
原文：
“仅在夜间于星湖附近采集，活动结束后失效。”

AI候选：
acquisition_method = GATHER
acquisition_region = 星湖附近
clock_domain = GAME_WORLD_CLOCK
time_window = NIGHT
usage_valid_until = EVENT_END
```

AI输出必须包含：

```text
source_quote
source_evidence_id
extractor_id与版本
candidate_fields
ambiguities
confidence
```

候选知识状态建议为：

```text
UNVERIFIED
LLM_SUGGESTED
USER_CONFIRMED
OBSERVED_IN_GAME
CONTRADICTED
STALE
```

LLM不能直接：

- 把模糊说明改成确定时间点；
- 根据名称自动合并两个物品类型；
- 根据一次漏检认定物品消失；
- 修改用户实际库存数量；
- 在没有时间源的情况下宣布物品已经过期。

## 8. 获取方式知识

物品获取不能只保存一段文本，建议形成可查询的`AcquisitionRule`：

```text
AcquisitionRule
├── acquisition_rule_id
├── item_type_id
├── source_type
├── location_refs
├── action_or_capability_refs
├── prerequisite_facts
├── temporal_constraints
├── weather_or_world_conditions
├── expected_quantity_or_range
├── respawn_rule_ref
├── cost_or_resource_requirements
├── provenance
└── validation_status
```

`source_type`可以包含：

```text
GATHER
ENEMY_DROP
CHEST
QUEST_REWARD
EVENT_REWARD
DUNGEON_REWARD
CRAFT
SHOP
EXCHANGE
MAIL
ACHIEVEMENT
UNKNOWN
```

同一物品可以引用多个获取规则。例如既能在地图采集，也能通过活动商店兑换。

用户真实游玩还可以产生获取事件候选：

```text
操作前数量 = 12
当前MapSpace = area_03
用户完成采集动作
拾取提示出现
操作后数量 = 13

-> 生成一次OBSERVED_IN_GAME获取证据
```

一次事件只能证明“这次在这里获得成功”，不能自动证明所有时间、天气和前置条件都不重要。

## 9. 时间域模型

物品的获取、使用、刷新和删除可能依赖完全不同的时间源。

```text
ClockDomain
├── WALL_CLOCK
├── SERVER_CLOCK
├── GAME_WORLD_CLOCK
├── EVENT_PHASE
├── ACQUISITION_ELAPSED
├── ACTIVATION_ELAPSED
├── SESSION_ELAPSED
└── UNKNOWN
```

### 9.1 `WALL_CLOCK`

现实世界绝对时间，例如官方活动于某个日期结束。需要记录时区和来源。

### 9.2 `SERVER_CLOCK`

服务器时间、每日或每周重置。它可能与电脑时间、账号所在区服和夏令时规则不同。

### 9.3 `GAME_WORLD_CLOCK`

游戏内部昼夜时间。它可能加速、暂停、跳时或因副本切换而改变，不能用系统时钟代替。

### 9.4 `EVENT_PHASE`

不是具体时间点，而是活动或任务事实，例如：

```text
event.spring_2026.phase_2 = ACTIVE
```

### 9.5 相对时间

物品可能在获得、激活或进入场景后持续一定时长：

```text
ACQUISITION_ELAPSED
SESSION_ELAPSED
ACTIVATION_ELAPSED
```

建议的时间规则：

```text
TemporalRule
├── rule_id
├── clock_domain
├── start_condition
├── end_condition
├── recurrence
├── timezone_or_server_region
├── pause_behavior
├── clock_provider_ref
├── source_claim_refs
└── validation_status
```

LLM负责从文本中提议规则类型，确定性`ClockProvider`负责提供当前时间事实并执行已经确认的规则。

## 10. 可获取、可使用和自动移除必须分开

活动结束可能产生不同结果：

```text
无法继续获取，但已有物品仍可使用
已有物品变为不可使用，但仍显示在背包
已有物品被系统自动删除
已有物品按比例转换成另一种货币
活动入口关闭，但物品仍保留说明
```

因此至少需要三种规则：

```text
AcquisitionAvailabilityRule
-> 当前还能不能获得

UsageValidityRule
-> 当前还能不能使用

RemovalOrConversionRule
-> 到期后是否删除或转换
```

不能只使用一个`expires_at`字段表示全部含义。

## 11. 同名、同图标和图标变化

物品身份不能只依赖名称，也不能只依赖图标。

### 11.1 同名不同物品

可能来自：

- 不同活动使用相同显示名称；
- 不同品质或阶段共用名称；
- 翻译把不同原名映射成同一中文名；
- 实例名称固定但随机属性完全不同。

应结合：

```text
game_profile_id
category
description_signature
attribute_schema
visual_token_candidates
acquisition_context
content_version
```

### 11.2 同物品不同图标

可能来自：

- 游戏更新替换素材；
- 稀有度、强化或突破阶段变化；
- 活动期间使用特殊皮肤；
- 锁定、装备、过期等覆盖标记；
- 不同分辨率或UI主题。

这些外观先记录为`ItemVisualVariant`，经过证据或用户确认后再绑定同一个`item_type_id`。

### 11.3 图标变化还是物品转化

如果只有显示素材变化，原实例继续存在；如果名称、类别或核心属性发生变化，则可能是物品转化：

```text
旧ItemInstance
-> TRANSFORMED事件
-> 新ItemInstance或新ItemType
```

必须保存前后谱系，不能直接覆盖旧记录。

## 12. 库存观测和扫描覆盖

系统看到的库存通常只是局部页面，而不是完整事实。每次扫描应记录覆盖范围：

```text
InventoryScanCoverage
├── container_id
├── category_or_tab
├── active_filters
├── sort_mode
├── page_range
├── scroll_range
├── start_frame_id
├── end_frame_id
├── completeness
└── capture_health
```

随后形成：

```text
InventorySnapshot
├── snapshot_id
├── coverage_id
├── observed_stack_entries
├── observed_instance_or_lot_entries
├── unresolved_candidates
└── evidence_ids
```

只有覆盖范围足够完整、截图健康并且识别器有效时，快照差异才可以用于推断物品减少或消失。

## 13. 库存事件账本

库存变化应采用追加式事件，不应只保存当前最终值。

```text
InventoryEvent
├── inventory_event_id
├── event_type
├── item_type_id
├── instance_or_stack_refs
├── quantity_delta
├── source_action_id
├── before_snapshot_ref
├── after_snapshot_ref
├── temporal_context
├── attribution
├── confidence
└── evidence_ids
```

建议支持：

```text
ACQUIRED
QUANTITY_INCREASED
QUANTITY_DECREASED
CONSUMED
SOLD_OR_DISCARDED
EQUIPPED
UNEQUIPPED
TRANSFERRED
ENHANCED
LOCKED_OR_UNLOCKED
TRANSFORMED
EXPIRED
EVENT_REVOKED
RECOVERED
MISSING_DETECTED
REMOVAL_CONFIRMED
UNKNOWN_CHANGE
```

同一动作可能产生多个事件，例如强化会消耗材料、增加装备等级并改变属性。

## 14. 物品消失判读

最重要的原则是：

> 本次没有观察到物品，不等于物品已经消失。

建议使用以下流程：

```text
本次未观察到
-> 检查InventoryScanCoverage
-> 检查筛选、排序、分页和滚动范围
-> 检查装备栏、仓库、邮件和其他角色
-> 关联最近的消耗、出售、强化和转移动作
-> 检查已确认的时间、活动和转换规则
-> 重新加载并执行完整扫描
-> 仍无法确认则保留MISSING_UNCONFIRMED
```

可能归因为：

```text
CONSUMED
SOLD_OR_DISCARDED
EXPIRED
TRANSFORMED
EQUIPPED_OR_TRANSFERRED
EVENT_REVOKED
QUANTITY_DECREASED
SCAN_NOT_COVERED
FILTERED_OR_HIDDEN
DETECTION_FAILURE
GAME_SYNC_ERROR
ACCOUNT_OR_CHARACTER_CHANGED
UNKNOWN_REMOVAL
```

### 14.1 不使用单一生命周期状态

物品是否存在、是否有效以及存在哪里是不同状态轴：

```text
ExistenceState
-> PRESENT / MISSING_UNCONFIRMED / REMOVED_CONFIRMED / UNKNOWN

ValidityState
-> VALID / NOT_YET_VALID / EXPIRED / DISABLED / UNKNOWN

StorageState
-> INVENTORY / EQUIPPED / STORAGE / MAIL / TRANSIT / UNKNOWN
```

例如活动物品可以仍然`PRESENT`，但已经`EXPIRED`；装备到角色后仍然`PRESENT`，只是`StorageState`改变。

### 14.2 不物理删除历史

确认消失后也不删除`ItemInstance`或事件历史。使用终止状态和最后证据：

```text
last_confirmed_present_at
removal_confirmed_at
removal_reason
terminal_event_id
evidence_ids
```

这样以后发现识别错误或物品重新出现时，可以通过`RECOVERED`事件恢复，而不是重新创建一个无关联实例。

## 15. 实例匹配和变化关联

游戏通常不向画面暴露稳定实例ID，系统只能建立本地身份假设。

匹配可以综合：

```text
item_type_id
图标与视觉变体
等级与稀有度
主词条和副词条
锁定状态
装备角色
库存排序邻域
操作前后时间关联
```

但库存排序邻域和屏幕格子只能作为弱证据。强化操作的前后帧关联通常比重新扫描后的格子位置更可靠。

无法区分多个相同实例时保留`ItemLot`，不能为了满足数据结构而强行选定一个实例。

## 16. 图、账本和证据的边界

### 16.1 物品知识图

适合保存：

```text
ItemTypeDefinition
AttributeDefinition
AcquisitionRule
PlaceAnchor
ActivityDefinition
TemporalRule
RecipeDefinition
用途和前置关系
```

### 16.2 库存实例账本

适合保存：

```text
ItemStack
ItemInstance
ItemLot
InventoryEvent
当前投影状态
```

大量圣遗物实例不应该全部成为主关系网中的规划节点。需要规划时，由查询层把“满足某些属性的可用实例”作为结果提供给规划器。

### 16.3 证据存储

适合保存：

```text
原始帧与裁剪图
OCR原文
图标观测
库存扫描覆盖
识别候选和置信度
操作前后时间窗
```

定义图和账本只保存`evidence_id`引用，避免把大图和重复观测塞入关系图。

## 17. 置信度和故障隔离

至少需要区分：

```text
item_type_match_confidence
instance_match_confidence
attribute_parse_confidence
quantity_read_confidence
scan_completeness
temporal_rule_confidence
acquisition_claim_confidence
detector_reliability
evidence_freshness
```

以下情况不能降低物品知识关系本身的可信度：

- 截图失败或返回旧帧；
- 当前库存扫描不完整；
- 过滤器隐藏物品；
- OCR暂时无法读取随机词条；
- 游戏客户端同步异常；
- 用户切换了账号、角色或区服；
- 图标素材更新导致旧检测器失效。

只有在上下文一致、扫描完整、感知有效且证据明确冲突时，才更新对应知识或实例匹配可靠性。

## 18. 与图标系统和Trace Core的关系

图标系统负责回答：

```text
画面中出现了哪个视觉标记
视觉标记是否发生变化
```

物品系统负责回答：

```text
这个视觉标记可能对应哪个物品类型或实例
本次变化意味着数量、属性、位置还是生命周期发生变化
```

首期`Trace Core`只需保证：

```text
FrameStream
InputRecorder
WindowRegistry
Timeline
FrameRingBuffer
EvidenceStore
ReplayTool
```

这些事实可靠后，物品识别、OCR解析和库存差异都可以在同一段记录上离线重复验证。

## 19. 分阶段验证

### 阶段一：一种堆叠物品

只处理一种材料，验证图标、名称、数量和操作前后数量差异。

### 阶段二：库存覆盖

记录分页、筛选和滚动范围，证明系统能够区分“未扫描到”和“完整扫描后不存在”。

### 阶段三：获得与消耗事件

分别完成一次获得和一次消耗，保存前后快照、用户输入、提示图标和数量变化证据。

### 阶段四：一种随机属性物品

选择一种圣遗物或装备，记录固定名称、等级、主词条、副词条和随机数值。

### 阶段五：同质实例

准备两个视觉和属性完全一致的物品，验证系统使用`ItemLot`而不是伪造可区分身份。

### 阶段六：转移和强化

验证装备、卸下、仓库转移和强化不会被误判为消失。

### 阶段七：时间规则

先实现一种有明确服务器结束时间的活动物品，再单独验证游戏世界昼夜或获得后相对时间。

### 阶段八：AI候选提取

让LLM从游戏说明中提取获取区域、获取方式和时间条件，检查所有字段是否保留原文引用并允许用户纠正。

## 20. 第一版验收标准

- 同名不再被直接视为同一`item_type_id`；
- 堆叠物品和独立实例使用不同记录方式；
- 随机词条属于具体实例，不污染物品种类定义；
- 每项AI提取属性都能追溯到原始说明文本；
- 现实时间、服务器时间和游戏世界时间不会混用；
- 物品过期、不可使用和被删除能够分别表达；
- 不完整库存扫描不会产生确定消失结论；
- 强化、装备、转移和转换保留完整事件历史；
- 已确认消失的实例仍保留终止记录和证据；
- 大量具体实例不会膨胀主关系网。

## 21. 当前结论

物品系统不应只是“物品节点加属性”，而应由三部分共同组成：

```text
物品知识图
-> 物品种类、属性、获取方式、地点和时间规则

库存实例账本
-> 用户真实拥有的数量、实例和变化历史

视觉与文本证据
-> 图标、OCR、库存覆盖和操作前后画面
```

AI适合把说明文本转换成可追溯的候选知识；确定性的时间源、库存对账和证据规则负责判断当前事实。物品未被观察到时，系统先承认“不知道它去了哪里”，再通过覆盖检查、事件关联和重新扫描逐步收束原因。
