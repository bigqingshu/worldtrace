## 1. 总体结论

行业中的“3D场景识别”不是依赖某一种深度图特征完成的单一任务。对于只读取游戏截图的WorldTrace，至少要区分：

```text
场景分类
-> 这里是什么类型的地方？

视觉地点识别
-> 这里是否是以前见过的某个地方？

视觉定位
-> 当前摄像机在地图中的具体位置和朝向是什么？

局部地形理解
-> 眼前结构是什么，能否行走、跨越或跳跃？
```

深度图主要帮助最后一项，也可以增强地点核验和相机定位。真正判断“这里是不是以前来过的地方”，通常依靠：

```text
全局外观召回
+ 局部特征对应
+ 几何一致性
+ 连续帧顺序
+ 路线拓扑
+ 稳定语义地标
+ 可选深度和3D结构
```

主流工程流程是粗到细：

```text
全局描述子快速检索Top-K候选
-> 路线和时间序列重排
-> 局部特征匹配
-> RANSAC几何验证
-> 必要时使用深度、语义布局或2D-3D PnP
-> 输出地点候选、观察朝向和UNKNOWN
```

这比让单个大模型直接宣布地点更容易验证、调试和替换。

## 2. 三种容易混淆的任务

| 任务 | 英文名称 | 回答的问题 | 典型输出 | 是否需要历史地图 |
| --- | --- | --- | --- | --- |
| 场景分类 | `Scene Classification` | 森林、洞穴、走廊还是城市 | 场景类别和语义标签 | 不一定 |
| 视觉地点识别 | `Visual Place Recognition` | 是否来过这里，对应哪个地点候选 | Top-K关键帧或拓扑节点 | 通常需要图像库 |
| 六自由度视觉定位 | `6DoF Visual Localization` | 摄像机具体在哪里、朝向哪里 | `x,y,z,roll,pitch,yaw` | 需要几何地图或3D点 |

### 2.1 场景分类不能证明地点身份

Places365、CLIP或普通分类网络可以判断：

```text
洞穴
森林
室内走廊
城市街道
桥梁附近
```

但两个不同洞穴、两条不同走廊可能具有相同语义。语义类别适合缩小搜索范围，不适合直接建立永久地点事实。

### 2.2 地点识别只产生候选

地点识别通常将当前画面与历史关键帧库比较，输出相似度最高的若干候选。

`Recall@K`表示正确地点是否进入前K名，不代表排名第一已经被证明正确。游戏中存在大量复制房间和复用资产，直接采用最高相似度会产生严重误报。

### 2.3 精确位姿需要几何对应

若要获得摄像机的六自由度位姿，需要：

- 当前图像中的2D特征；
- 地图中的3D点或已知参考位姿；
- 可靠的2D-3D对应；
- PnP和RANSAC；
- 重投影误差和内点分布验证。

没有3D地图时，可以做相对相机运动和地点候选，但不能直接得到完整世界坐标。

## 3. 常见特征体系总览

| 特征族 | 典型内容 | 主要用途 | 主要局限 |
| --- | --- | --- | --- |
| 全局描述子 | GIST、BoVW、VLAD、NetVLAD、DINOv2聚合、SALAD | 大规模快速召回地点候选 | 压缩空间细节，重复场景易误召回 |
| 局部特征 | SIFT、ORB、SuperPoint、DISK、ALIKED | 找到墙角、纹理和物体拐角的对应 | 弱纹理、模糊、雾、水面和重复贴图会失败 |
| 局部匹配器 | 最近邻、SuperGlue、LightGlue、LoFTR | 建立两张图之间的局部对应 | 错配仍需几何验证 |
| 线段与布局 | 线段、角点、消失点、地平线、门窗和墙面布局 | 增强人造场景和低纹理场景结构 | 相同模块布局仍会重复 |
| 深度与表面 | 深度边缘、法向、平面、坡面、遮挡和点云 | 通行判断、结构核验和3D配准 | 单目深度尺度和时序可能不稳定 |
| 语义地标 | 门、楼梯、桥、雕像、传送点及空间关系 | 跨视角和长期地点证据 | 同类对象重复，动态对象不稳定 |
| 时序序列 | 连续关键帧、出现顺序、移动方向和速度比例 | 消除单帧感知混淆 | 传送、逆行和跳帧需要处理 |
| 几何约束 | 单应矩阵、本质矩阵、基础矩阵、PnP、ICP | 最终核验和位姿估计 | 成本较高，不能直接搜索整个图库 |

没有一种特征在所有环境中占优。系统通常先使用低成本全局描述子召回，再让局部、时序和几何证据逐步提高精度。

## 4. 全局描述子负责快速召回

### 4.1 传统整体外观

早期方法使用：

- 颜色直方图；
- 纹理统计；
- 边缘方向分布；
- GIST空间包络；
- 感知哈希；
- Bag of Visual Words视觉词袋；
- VLAD局部描述子聚合。

这些方法成本低，适合建立基线。感知哈希和颜色统计对近重复画面有效，但视角、光照和遮挡变化稍大时容易失效。

GIST等整体布局特征关注空间频率、方向和粗场景结构，可区分开放、封闭、规则、粗糙等场景外观，但不适合证明具体地点身份。

### 4.2 NetVLAD

[NetVLAD](https://arxiv.org/abs/1511.07247)将CNN局部响应聚合成一个全局地点向量，用于从大规模图库检索候选地点。

优点：

- 查询速度快；
- 适合最近邻检索；
- 对一定程度的视角和外观变化具有鲁棒性；
- 工程资料和基准较成熟。

局限：

- 全局向量丢失精确空间关系；
- 同类建筑和重复走廊容易混淆；
- 在现实街景上的结果不能直接外推到游戏渲染。

### 4.3 DINOv2与AnyLoc

[DINOv2](https://arxiv.org/abs/2304.07193)提供自监督视觉patch特征。[AnyLoc](https://github.com/AnyLoc/AnyLoc)使用DINOv2局部patch特征与VLAD聚合生成地点全局描述子，目标是跨室内、室外、洞穴、空中和水下等不同域的地点识别。

这类特征比纯语义向量保留更多局部结构信息，是游戏画面的优先实验候选之一，但仍需目标游戏自己的测试集。

AnyLoc证明了跨多种现实和机器人视觉域的泛化价值，没有证明任意卡通、像素或强特效游戏都可靠。

### 4.4 SALAD及其他VPR描述子

[SALAD](https://arxiv.org/abs/2311.15937)同样使用DINOv2骨干，并以最优传输方式聚合地点描述子。MixVPR、EigenPlaces、CosPlace和Patch-NetVLAD也是可比较的视觉地点识别路线。

这些项目适合在统一游戏数据集上横向比较，不应只根据公开自然图像榜单直接选型。

### 4.5 CLIP和Places365的边界

[CLIP](https://arxiv.org/abs/2103.00020)和[Places365](https://github.com/CSAILVision/places365)更适合作为场景类别和语义旁证：

```text
森林
洞穴
有桥的区域
城市街道
室内大厅
```

CLIP有意学习语义不变性，因此可能把两个语义相同但地点不同的画面放得很近。它不能独立证明“就是这个地点”。

## 5. 局部特征负责精确核验

### 5.1 传统局部特征

常见方法：

- SIFT：成熟，具有尺度和旋转适应性，成本相对较高；
- ORB：二进制描述子，速度快，适合低成本基线；
- AKAZE、BRISK：可作为其他传统对比。

局部特征通常在墙角、纹理斑点、门框、道路边缘和物体拐角处产生稳定关键点。

### 5.2 学习式关键点与描述子

- [SuperPoint](https://arxiv.org/abs/1712.07629)；
- DISK；
- ALIKED；
- D2-Net；
- R2D2。

这些方法尝试在视角、光照和尺度变化下生成更可重复的局部特征。

### 5.3 学习式匹配器

- SuperGlue；
- [LightGlue](https://github.com/cvg/LightGlue)；
- LoFTR。

LightGlue可以根据图像对自适应停止和裁剪关键点，适合做Top-K候选之间的局部匹配。LoFTR属于无检测器稠密匹配路线，在部分低纹理区域更有优势，但成本和错误模式不同。

### 5.4 匹配数量不能单独证明同一地点

游戏复用贴图可能产生大量错误匹配。局部匹配后还需检查：

- 双向或互相最近邻一致性；
- 描述子距离和比率；
- RANSAC内点比例；
- 内点是否覆盖画面多个区域；
- 几何模型残差；
- 匹配是否集中在HUD、人物或动态对象；
- 当前FOV和相机模式是否匹配。

同一块重复墙砖即使产生很多匹配，也可能只集中在画面一小片区域，不能作为地点确认。

## 6. 几何约束负责排除外观误报

### 6.1 Homography单应矩阵

单应矩阵适合：

- 主要内容近似同一平面；
- 摄像机接近纯旋转；
- 平面跟踪；
- 全景拼接或视角旋转补偿。

普通3D场景存在多层深度和视差时，一个单应矩阵无法解释整个画面。

### 6.2 Fundamental与Essential Matrix

`Fundamental Matrix`（基础矩阵）适合内参未知的两视图几何；`Essential Matrix`（本质矩阵）在相机内参已知时使用。

它们可以验证静态点匹配是否符合共同相机运动，并估计相对旋转和平移方向。

单目两视图通常无法获得绝对平移尺度。纯旋转没有三角化视差，也不能仅凭本质矩阵恢复真实深度。

### 6.3 PnP与RANSAC

若已有3D地图和2D-3D特征对应，可以使用`PnP`（透视n点位姿求解）和RANSAC估计摄像机六自由度位姿：

```text
地点检索得到候选关键帧
-> 当前帧与候选局部匹配
-> 将2D关键点关联到地图3D点
-> PnP + RANSAC
-> 重投影误差和内点分布验证
```

这也是[hloc](https://github.com/cvg/Hierarchical-Localization)层次化定位工具箱的典型流程。

## 7. 点、线、面和深度结构

### 7.1 点特征

点特征在纹理丰富环境中有较强的地点辨识力，也适合三角化稀疏3D点。

局限是纯色墙、雾、水面、玻璃、强反射和运动模糊可能缺少可靠关键点。

### 7.2 线段和消失点

人造建筑、走廊和室内房间常包含：

- 长直线；
- 门框；
- 墙角；
- 地平线；
- 消失点；
- 平行和垂直关系。

线段和布局在低纹理建筑中可能比点更稳定。PL-SLAM等项目尝试组合点和线段。

但大量相同平墙和模块化房间仍会产生布局重复，需要其他证据消歧。

### 7.3 平面和表面法向

有深度、双目或多视图重建时，可以提取：

- 地面与墙面；
- 平面法向；
- 平面交线；
- 曲率和表面变化；
- 坡面与台阶；
- 局部点云。

这些特征适合结构理解、局部对齐和可通行判断。

### 7.4 深度图不能独立承担地点身份

相同模块构建的两条走廊可能拥有几乎相同的深度布局；同一地点换一个观察方向，深度图又可能完全不同。

学习式单目深度还可能存在：

- 尺度和偏移不确定；
- 跨帧闪烁；
- 游戏域偏移；
- 透明和反射错误；
- 细边缘和薄物体丢失。

因此深度更适合：

```text
局部结构描述
几何匹配增强
候选地点核验
地形可通行判断
```

而不是单独生成永久`place_id`。

### 7.5 点云特征

若后续得到稳定点云，可以尝试：

- FPFH局部点云描述子；
- ICP精配准；
- RANSAC全局配准；
- Scan Context等整体空间描述子；
- 点云平面和结构图。

点云路线属于后续重型实验，不应成为第一版地点识别的前置条件。

## 8. 语义地标与场景关系

### 8.1 稳定语义地标

游戏中可能具有较强辨识力的对象包括：

- 独特雕像；
- 桥梁；
- 楼梯和门；
- 传送装置；
- 大型机械；
- 特殊建筑轮廓；
- 固定路标；
- 稳定地形边界。

比单个类别更有价值的是空间关系：

```text
楼梯在门的左侧
桥后方存在高塔
传送点位于圆形平台中央
道路在雕像右侧分叉
```

### 8.2 瞬时对象不能成为永久地点事实

以下对象应降权或隔离：

- NPC和敌人；
- 掉落物；
- 粒子和技能特效；
- 临时任务标记；
- 开关状态可变的门；
- 可破坏物；
- 玩家人物和第一人称武器。

语义地标需要记录稳定性、可见方向、游戏版本和环境条件。

## 9. 时序序列与路线拓扑

### 9.1 单帧感知混淆

`Perceptual Aliasing`（感知混淆）指不同地点具有高度相似的视觉表现。游戏中的复制房间、重复走廊和复用贴图会放大这一问题。

有些场景从单帧信息上理论上就无法唯一判断，必须保留多个候选。

### 9.2 SeqSLAM序列思想

[SeqSLAM](https://doi.org/10.1109/ICRA.2012.6224623)使用连续图像序列而不是单帧比较路线。即使单帧外观因季节或天气变化较大，一段连续顺序仍可能形成可靠证据。

对游戏可以使用：

```text
最近若干关键帧描述子
+ 出现顺序
+ 人物移动方向
+ 视角旋转历史
+ 输入事件
+ 上一个拓扑节点
-> 重排当前地点候选
```

### 9.3 序列先验的失效条件

以下事件应打断或降低路线连续性先验：

- 传送；
- 死亡回城；
- 加载界面；
- 剧情切场；
- 快速旅行；
- 大幅跳帧；
- 用户倒走或绕行；
- 载具高速跨越；
- 多窗口切换或错误目标窗口。

序列应支持正向、逆向和速度变化，而不能只匹配固定帧间隔。

## 10. SfM、视觉里程计与SLAM

### 10.1 SfM

`Structure-from-Motion`（运动恢复结构，SfM）通常离线从多张重叠图像恢复：

- 相机相对位姿；
- 稀疏3D点；
- 可选稠密重建；
- 图像之间的共视关系。

典型流程：

```text
关键点和描述子
-> 图像对匹配
-> 几何验证
-> 相对位姿
-> 三角化
-> Bundle Adjustment束调整
```

[COLMAP](https://colmap.github.io/tutorial.html)是成熟的SfM和MVS参考实现。

### 10.2 Visual Odometry

`Visual Odometry`（视觉里程计）使用连续帧估计局部相机运动。它适合短时间跟踪，但长期积分会漂移，需要地图或回环重新锚定。

光流是短期对应线索之一，不适合独立证明地点身份。

### 10.3 SLAM

`SLAM`（同步定位与建图）在视觉里程计基础上增加：

- 地图维护；
- 关键帧；
- 回环检测；
- 位姿图；
- 局部和全局优化；
- 多地图管理。

[ORB-SLAM3](https://github.com/UZ-SLAMLab/ORB_SLAM3)支持单目、双目、RGB-D和视觉惯性配置，是完整SLAM参考，但其依赖、平台和GPL许可使它更适合参考或隔离实验，不宜直接假定为WorldTrace核心依赖。

### 10.4 纯旋转与视差

系统控制镜头是一项优势，但需要区分：

```text
原地纯旋转
-> 获得同一地点更多观察方向
-> 有利于地点识别和地标发现
-> 不提供三角化深度

人物横移、前进或摄像机真实平移
-> 产生视差
-> 可以增强相对位姿和3D结构估计
```

对地点识别，多方向纯旋转仍然非常有价值；对3D重建，则需要视点平移。

## 11. hloc代表的粗到细工程流程

[Hierarchical Localization](https://arxiv.org/abs/1812.03506)和[hloc](https://github.com/cvg/Hierarchical-Localization)提供了清晰的参考架构：

```text
为数据库图像提取全局与局部特征
-> 建立SfM参考模型
-> 用全局检索找当前查询图像的候选数据库图像
-> 对候选执行局部特征匹配
-> 建立2D-3D对应
-> 求解相机位姿
-> 保存匹配、RANSAC内点和位姿日志
```

hloc支持NetVLAD等图像检索、SIFT和SuperPoint等特征、LightGlue等匹配器，并可结合COLMAP或pycolmap。

对WorldTrace最值得参考的不是直接引入整个工具箱，而是这条边界：

```text
召回允许误报
-> 几何验证负责拒绝误报
-> 位姿求解只对少量候选运行
-> 原始匹配和内点证据可调试
```

## 12. 游戏场景的特殊问题

### 12.1 固定屏幕元素会制造错误身份

HUD、小地图、准星、第一人称武器和第三人称人物长期出现在固定屏幕位置。全局描述子和局部特征可能学到这些固定元素，而不是场景。

应：

- 裁剪真实3D视口；
- 遮罩HUD和黑边；
- 遮罩人物、武器和大面积特效；
- 将小地图作为独立证据源；
- 保存遮罩版本和覆盖范围。

### 12.2 复用资产造成强感知混淆

游戏可能复用：

- 墙砖和地面纹理；
- 房间模块；
- 建筑外立面；
- 树木、岩石和道路素材；
- 整个副本区块。

这会同时欺骗全局描述子和局部匹配。路线邻接、序列顺序、稳定地标和几何内点分布尤其重要。

### 12.3 动态画面变化

需要处理：

- NPC和敌人；
- 粒子、天气和技能；
- 开关门和可破坏物；
- 昼夜和光照；
- 运动模糊；
- FOV变化；
- 后处理和画质设置；
- 加载和转场。

动态对象应尽量排除，稳定环境结构应增权。

### 12.4 不应追求完全旋转不变

同一地点从不同方向看可能差异极大。过度追求旋转不变性会丢失路线朝向信息。

更适合游戏跑图的是：

```text
地点身份
+ 观察朝向分桶
+ 相机模式
+ FOV或缩放
+ 进入和离开方向
```

一个地点可以保存多方向原型，而不是强行压缩成一个完全方向无关的向量。

## 13. 第一人称与第三人称差异

### 13.1 第一人称

需要：

- 遮罩手、武器和准星；
- 区分普通、瞄准、冲刺和脚本镜头；
- 记录FOV、镜头晃动和后坐力；
- 将相机位姿与人物位姿关系作为当前模式假设。

普通第一人称中，摄像机与人物关系较固定，视觉定位更接近人物定位，但跳跃、下蹲和脚本镜头仍会改变关系。

### 13.2 第三人称

需要：

- 遮罩人物和接触阴影；
- 区分人物朝向和镜头朝向；
- 记录镜头距离、俯仰和环绕方向；
- 处理人物静止但镜头围绕旋转；
- 处理人物移动但摄像机将人物保持在画面中央。

视觉定位首先得到的是摄像机地点候选或位姿。若要推断人物位置，还需人物脚点、镜头跟随关系和输入历史。

## 14. 对WorldTrace的候选证据层

### 14.1 第0层：帧和上下文门控

```text
确认窗口实例
-> 选择新鲜稳定帧
-> 排除菜单、加载和过场
-> 裁剪3D视口
-> 应用HUD、人物和动态区域遮罩
-> 记录相机模式、FOV和方向区间
```

### 14.2 第1层：低成本近重复判断

- 感知哈希；
- 低分辨率颜色统计；
- 边缘和轮廓；
- ORB关键点；
- 最近节点和输入历史。

适合判断短时间内是否仍在相近视角，不能独立处理大视角变化。

### 14.3 第2层：全局地点召回

- NetVLAD；
- DINOv2 + VLAD；
- AnyLoc；
- SALAD或其他VPR描述子。

输出Top-K候选和相似度，不输出最终地点事实。

### 14.4 第3层：序列与拓扑重排

- 上一个地点节点；
- 合法邻接关系；
- 最近关键帧顺序；
- 移动和视角输入历史；
- 是否发生传送或加载；
- 预计进入方向。

### 14.5 第4层：局部与几何验证

- SIFT或ORB基线；
- SuperPoint、DISK或ALIKED；
- LightGlue、SuperGlue或LoFTR；
- RANSAC；
- 单应、本质或基础矩阵；
- 内点覆盖和残差。

### 14.6 第5层：结构和语义交叉验证

- 深度布局；
- 地面、墙面和门框；
- 线段和消失点；
- 稳定语义地标；
- 小地图和路线信息。

### 14.7 第6层：可选精确位姿

需要时再使用：

- SfM地图；
- 2D-3D对应；
- PnP；
- 束调整；
- SLAM或多地图管理。

## 15. 候选运行输出

正式契约尚未确定，参考流程至少应保留：

```text
query_frame_id
view_context
global_descriptor_revision
top_k_place_candidates
sequence_and_topology_scores
local_match_counts
geometric_inlier_counts
geometric_residuals
depth_and_semantic_evidence
camera_pose_candidate
evidence_freshness
rejection_reasons
UNKNOWN_reason
```

不能只保存最终相似度和地点编号。后续需要知道候选为什么被接受或拒绝。

## 16. 第一轮实验建议

### 16.1 游戏内数据集

为一个目标游戏准备：

- 同一地点多个朝向；
- 同一地点多个FOV和镜头模式；
- 同一地点不同昼夜、天气和动态对象；
- 外观高度相似的不同地点；
- 复制走廊和模块化房间；
- 正向、逆向和不同速度路线序列；
- 传送、加载和死亡回城中断；
- 第一人称或第三人称固定子集。

需要人工或可靠方法标记地点身份和可接受位置范围。

### 16.2 对比阶梯

```text
A. 感知哈希 + 颜色 + 边缘
B. ORB局部匹配
C. DINOv2或AnyLoc全局检索
D. 全局检索 + ORB/RANSAC
E. 全局检索 + SuperPoint/LightGlue/RANSAC
F. E + 连续帧序列和拓扑
G. F + 深度与语义布局
```

每一级只在前一级无法解决的问题上增加成本。

### 16.3 优先回答的问题

- 游戏贴图是否已经足够让ORB稳定工作？
- AnyLoc或其他全局描述子能否召回同地点不同视角？
- 复制场景的误报能否被局部几何拒绝？
- 连续帧是否能解决相似走廊？
- 深度加入后到底改善了哪些场景？
- 第一人称和第三人称是否需要独立模型或阈值？
- 控制镜头采集多方向原型是否比强旋转不变更可靠？

## 17. 评估指标

至少记录：

- Recall@1、Recall@5和Recall@K；
- 复制场景和相似走廊误报率；
- 同地点不同视角召回率；
- FOV、昼夜和动态对象分组结果；
- 局部匹配数量和RANSAC内点率；
- 内点空间覆盖；
- 几何残差和PnP重投影误差；
- 序列重排挽救率；
- 序列先验导致的错误锁定率；
- 深度和语义证据的增量收益；
- `UNKNOWN`比例和错误确认率；
- 每层P50/P95延迟；
- 描述子存储大小和数据库增长速度；
- 相同回放的结果可重复性。

评价必须区分“正确地点进入Top-K”和“地点已经几何确认”。

## 19. 不应直接照搬的部分

- 不把自然街景榜单成绩直接外推到游戏；
- 不让全局相似度直接创建永久地点节点；
- 不把CLIP语义当作地点身份；
- 不把深度图当作唯一地点指纹；
- 不在全部历史帧上运行昂贵局部匹配；
- 不将HUD、小地图、人物和武器混入场景特征；
- 不强求同一地点所有观察方向完全不变；
- 不把摄像机位姿直接等同于第三人称人物位姿；
- 不在传送和加载后继续使用旧路线连续性；
- 不引入许可证与运行环境不匹配的重型依赖作为正式核心。

## 20. 对WorldTrace的最终启示

最值得验证的不是“哪个模型能一次理解整个3D世界”，而是以下组合能否在目标游戏中形成可靠证据链：

```text
稳定帧与视图上下文
-> 全局地点候选召回
-> 路线与连续帧重排
-> 局部特征和几何确认
-> 深度、布局与语义交叉验证
-> 地点候选、观察朝向、可选位姿或UNKNOWN
```

深度图负责回答“眼前结构是什么”；全局和局部外观负责回答“这里像不像以前来过的地方”；几何约束负责回答“这些对应是否在同一个相机模型下成立”；时序和拓扑负责回答“沿当前路线，这个候选是否合理”。

第一轮最务实的比较是：

```text
ORB低成本基线
vs DINOv2/AnyLoc全局召回
vs 全局召回 + 局部RANSAC验证
vs 再加入序列和深度证据
```

只有目标游戏数据能够证明哪种组合值得迁入正式系统。
