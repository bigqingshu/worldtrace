## 1. 总体定位

AzurLaneAutoScript最值得参考的不是现有类结构，而是一套围绕确定性自动化建立的核心思想：

> 可靠自动化不是“准确点击”，而是把每次操作都变成可观察、可验证、可重试、可恢复的状态转换。

ALAS长期服务于单一游戏、固定界面和固定设备环境，因此很多实现与《碧蓝航线》、Android模拟器、固定分辨率和专用资源紧密绑定。这种高耦合并不等于其中的方法没有价值，而是它通过专用化换取了执行稳定性和开发效率。

对新系统更合适的参考方式是：

```text
提取闭环、验证、恢复、取证等思想
-> 重新定义独立模块和明确契约
-> 不复制游戏专用类体系与全局状态
```

三个系统可暂时这样定位：

| 来源 | 主要参考价值 |
| --- | --- |
| ALAS | 确定性执行闭环、固定UI处理、连续控制、看门狗、故障证据 |
| Whimbox | 任务生命周期、事件通信、插件、资源和前后端调度 |
| 新系统 | 用户行为发现、分层关系网、动态上下文、置信度隔离、多窗口仲裁 |

## 2. 观察驱动的执行闭环

ALAS最重要的执行思想可以概括为：

```text
获取画面
-> 判断当前状态
-> 选择一个动作
-> 执行动作
-> 获取新画面
-> 判断是否产生预期变化
```

这里最重要的原则是：

```text
输入已经发送 != 操作已经成功
```

例如点击“背包”后，执行层只能证明鼠标点击已经发出，不能立即宣布“已经进入背包”。只有后续画面出现背包界面的稳定特征，才能确认状态转换成功。

因此，新系统中的一条关系边不应只记录：

```text
按下B -> 背包
```

而应表达为：

```text
前置状态：游戏正常游玩状态
动作尝试：按下B
预期结果：进入背包界面
后置证据：背包标题、布局、控件或其他稳定特征出现
时间约束：限定时间内完成
转换结果：成功、未响应、被中断或无法判定
```

这能将三个问题分开处理：

1. 输入有没有发送到正确窗口。
2. 游戏有没有正确响应输入。
3. 感知模块有没有正确识别响应结果。

它也意味着动作API只能返回“动作尝试已经提交”，能力是否成功必须由后置观察决定。

## 3. 一次只推进一个可验证动作

ALAS的典型流程不是连续发送大量输入，然后在最后统一检查结果，而是：

```text
识别当前画面
-> 执行一个有明确意图的动作
-> 重新截图
-> 根据新画面决定下一步
```

这样做看似比纯宏慢，但能够及时发现：

```text
意外弹窗
网络提示
奖励页面
加载延迟
焦点丢失
误入页面
游戏没有响应
```

如果把多次输入打包成一整段宏，上述任意一个中断都可能使后续输入落到错误界面，最终难以判断从哪里开始偏离。

对新系统而言，可以将执行节点划分为：

| 节点类型 | 典型内容 | 验证方式 |
| --- | --- | --- |
| 原子动作节点 | 点击、按键、短拖动、滚轮一步 | 确认输入及局部画面响应 |
| 连续控制节点 | 滑块、滚动、缩放、视角调整 | 估算数值或视口变化并迭代纠偏 |
| 复合能力节点 | 打开背包、传送、切换角色 | 调用多个节点并验证最终后置状态 |

复合能力可以提高计划层的可读性，但内部仍应由可验证的小步骤组成。

## 4. 页面关系图只提供导航建议

ALAS维护已知页面之间的有向跳转关系。当系统需要前往目标页面时，可以从关系图中计算下一步，再执行对应入口操作。

它真正值得参考的地方不是静态页面表，而是：

> 关系图负责提出路径，当前真实画面负责决定系统实际上位于哪里。

因此每完成一次跳转，都需要重新识别当前页面。如果实际结果和计划不一致，应以观察结果为准重新定位、重新规划，而不是继续强行执行原路径。

放到新系统中可以形成以下职责边界：

```text
关系网：提出候选路径
状态识别器：确认当前状态
执行器：尝试关系边上的动作
验证器：判断是否到达预期状态
规划器：根据实际状态继续、改道或停止
```

ALAS的页面图主要由人工维护，适合固定界面导航；新系统的关系网可能由用户行为逐步发现，还包含复合能力子图、条件上下文和动态状态。因此可以借鉴其“逐边执行、逐边验证”的方式，不能把固定页面图直接当成学习关系网。

## 5. 通用中断优先于正常计划

正常计划执行时，游戏可能突然出现并不属于当前任务的界面，例如：

```text
确认弹窗
奖励弹窗
网络提示
登录界面
公告页面
重新连接提示
误入其他页面
```

ALAS会优先处理这些通用状态，然后重新截图，再决定是否能继续原流程。这种思想可以抽象为“中断处理器”：

```text
执行正常计划
-> 每轮观察当前画面
-> 检查是否存在高优先级中断
   -> 存在：处理中断，重新观察
   -> 不存在：继续原计划
```

未来每个中断处理器应显式声明：

| 属性 | 含义 |
| --- | --- |
| 适用条件 | 哪些游戏、界面和上下文可以调用 |
| 优先级 | 是否必须先于当前计划处理 |
| 风险等级 | 错误操作可能造成什么后果 |
| 自动化权限 | 可自动处理、需确认或只能报告 |
| 成功条件 | 哪些证据证明中断已经解除 |
| 返回语义 | 能否恢复原计划，还是必须重新规划 |

例如“关闭普通奖励弹窗”通常风险较低，可以自动处理；“退出账号并重新登录”风险较高，需要更严格的状态确认和权限限制。

这种插件式处理器比一个不断增长的顺序判断链更适合跨游戏系统。

## 6. 分层识别与成本路由

ALAS不会对所有画面直接运行最昂贵的识别方法，而是根据目标选择不同成本的检测方式。可以将这种思想扩展为：

```text
画面变化和颜色检测
-> 固定区域模板匹配
-> 大范围目标检测
-> OCR文字识别
-> 语义相似性判断
-> 目标精细分割
-> LLM解释和用户确认
```

结合当前计划中的模块，可以形成以下分工：

| 模块 | 最适合承担的任务 |
| --- | --- |
| 颜色、差分、哈希 | 高频检查画面是否变化、区域是否稳定 |
| 模板匹配 | 稳定图标、固定按钮、已知UI局部特征 |
| OCR | 标题、菜单项、数值、提示文字 |
| YOLO | 按钮、角色、物品、通用控件及其大致位置 |
| CLIP | 未知画面的语义归类、视觉变体相似性 |
| SAM | 已知大致位置后的精确边界和可操作区域提取 |
| LLM | 状态命名、解释、提出疑问和生成候选计划 |

运行原则应是：

```text
便宜检测负责高频运行
昂贵模型负责消除关键不确定性
LLM负责解释，不负责实时闭环和最终事实判定
```

此外，识别结果不宜过早压缩成单个布尔值。应尽可能保留原始分数、来源、时间、区域和模型版本，供多证据融合及后续归因使用。

## 7. 识别区域与操作区域分离

ALAS中一个很实用的思想是：用于识别控件的区域，不一定等于实际点击区域。

同一个按钮可能同时具有：

```text
最稳定的图标区域
适合OCR的文字区域
能够判断可用性的颜色区域
最安全的点击区域
容易误触其他控件的禁止区域
```

因此，新系统的控件模型不应只保存一个矩形框，而可以分开描述：

| 区域 | 用途 |
| --- | --- |
| 视觉身份区域 | 判断这是哪个控件或槽位 |
| 状态证据区域 | 判断启用、禁用、选中、冷却等状态 |
| 文字区域 | 交给OCR读取名称和数值 |
| 可操作区域 | 允许点击、拖动或滚动的安全范围 |
| 禁止区域 | 应避开的边缘、遮挡和相邻控件区域 |

这对角色和能力动态切换尤其重要。角色切换后，技能图标内容可能改变，但技能槽位的位置、边框、冷却层和附近HUD结构仍然稳定。系统可以先确认“这是某个控制槽位”，再判断“当前槽位绑定了哪项能力”。

## 8. 连续控件归一化与反馈校准

ALAS对滚动条的处理不是单纯保存固定拖动距离，而是检测轨道和滑块，将当前位置归一化到：

```text
0.0 = 最上方或最左侧
1.0 = 最下方或最右侧
```

系统根据目标值计算拖动操作，操作后再通过新画面识别实际位置，必要时继续纠偏。

这个思想可以推广到：

```text
音量和亮度滑块
横向、纵向滚动条
列表滚动
鼠标滚轮缩放
地图拖动
视角旋转
角色或物体的连续位置调整
```

在此基础上，新系统还应补充自校准过程：

```text
微量探测
-> 观察实际变化量
-> 拟合输入量与结果量的映射
-> 保存环境指纹和校准参数
-> 正式操作后验证
-> 偏差过大时使旧参数失效并重新校准
```

因此连续控制节点保存的不是录制宏，而是一套在当前环境中有效、可验证、可更新的控制规律。

## 9. 暂态不能过早建立为正式节点

ALAS处理开关和动画状态时体现了一个重要判断：短时间出现的未知画面可能只是切换动画，而不一定是新的稳定状态。

游戏中常见的暂态包括：

```text
按钮按下效果
淡入淡出
页面滑动过程
加载动画
图标替换动画
技能冷却动画
角色切换过渡帧
```

如果系统把每一帧不同画面都建立成节点，关系网会迅速膨胀。因此状态发现需要稳定性筛选：

```text
短暂出现并自动消失
=> 暂态，只作为转换过程证据

持续稳定且可以重复进入
=> 候选状态节点

持续未知并阻断执行
=> 异常状态或待用户确认状态
```

节点是否成立，至少要考虑持续时间、重复出现次数、可重入性、是否能承接操作以及是否拥有稳定后置行为。

## 10. 截图和输入需要统一能力层

ALAS把截图、点击、滑动、应用控制等操作放在统一设备接口后面，具体使用哪种后端由设备环境决定。这个设备门面思想值得保留，但Windows游戏场景需要重新设计实现。

可以把底层能力划分为：

| 能力类别 | 可能包含的能力 |
| --- | --- |
| 截图能力 | 窗口截图、桌面截图、游戏采集、区域裁剪 |
| 输入能力 | 物理键鼠、定向窗口输入、滚轮、相对鼠标移动 |
| 窗口能力 | 激活、置顶、焦点确认、客户区坐标转换 |
| 环境能力 | 分辨率、DPI、全屏模式、鼠标锁定、遮挡状态 |

上层能力节点不直接依赖某个具体截图或输入实现，而只声明需求，例如：

```text
需要实时窗口画面
需要物理鼠标独占
需要窗口处于前台
需要相对鼠标移动
需要桌面截图与窗口截图互证
```

设备层再根据当前环境选择后端，并报告实际获得的能力。这样以后更换截图技术、输入方案或增加新游戏时，不必重写全部能力节点。

## 11. 看门狗需要识别异常行为模式

可靠看门狗不能只判断“执行是否超过固定时间”，还需要观察行为是否发生异常循环。ALAS中值得参考的信号包括：

```text
同一个按钮被连续重复点击
两个按钮之间反复振荡
长时间等待同一个元素
操作次数很多但状态没有推进
画面长时间没有有效变化
游戏退出或截图链路失效
```

新系统可以同时监控：

| 维度 | 关注内容 |
| --- | --- |
| 时间 | 当前步骤、节点和整个计划持续多久 |
| 次数 | 相同识别、动作和恢复重复多少次 |
| 状态变化 | 是否出现有效的新状态或只是在视觉抖动 |
| 动作序列 | 是否重复点击或在两个动作之间振荡 |
| 计划进度 | 是否真正接近目标状态 |
| 环境健康 | 截图、焦点、输入和游戏进程是否正常 |

例如：

```text
A -> 点击X -> B -> 点击Y -> A -> 点击X -> B
```

这可能表示两个弹窗互相触发、两个状态被错误区分，或者执行器在两个节点之间形成循环。此时继续普通重试没有意义，应停止当前边的尝试并进入诊断或恢复流程。

## 12. 错误现场与执行证据包

ALAS会保留最近一段时间的截图和日志。真正值得参考的是：错误发生后不能只留下一个异常名称，而应保存错误前后的完整现场。

新系统可以建立统一的执行证据包：

```text
最近若干帧截图
窗口身份、位置、焦点和focus_epoch
输入动作及目标窗口记录
识别结果、原始分数和证据区域
当前计划、节点调用栈和返回上下文
预期状态与实际观察状态
模型、资源、关系图和校准参数版本
执行过的恢复动作及结果
```

证据包需要帮助回答：

```text
感知是否识别错误？
输入是否送到错误窗口？
游戏是否没有响应？
按钮是否缺失或暂时不可用？
关系边是否已经失效？
恢复动作是否破坏了原上下文？
```

它既用于人工调试，也可以用于后续自动聚类故障、建立Bug特征和改进识别模块。

## 13. 故障分类与置信度隔离

一次能力执行失败可能来自完全不同的原因。例如“按B打开背包”失败，可能是：

```text
游戏失去焦点
输入被其他窗口接收
角色处于不可打断动画
功能暂时被禁用
网络延迟
游戏客户端Bug
识别器漏掉已经打开的背包
用户修改了按键绑定
关系本身已经失效
```

这些原因不能统一记作“关系边失败”。建议至少拆分维护：

| 指标 | 回答的问题 |
| --- | --- |
| 关系正确性 | 这条关系是否真实表达状态转换 |
| 当前可用性 | 当前上下文中该能力能否使用 |
| 条件执行可靠性 | 条件满足且环境健康时成功率如何 |
| 输入可信度 | 输入是否送达正确目标 |
| 感知可信度 | 后置状态是否被可靠识别 |
| 环境故障率 | 游戏、窗口和采集链路是否异常 |
| 恢复成功率 | 对应恢复方法能否解除异常 |

只有在以下条件都能得到足够证据时，才适合降低关系本身的可信度：

```text
前置条件满足
AND 功能可用
AND 输入正确送达
AND 游戏环境健康
AND 感知结果有效
AND 后置状态仍然没有成立
```

这正是避免游戏Bug污染关系网的关键。

## 14. 静态先验与动态观察融合

ALAS的地图系统会保存预先定义的地图结构，再通过当前截图识别局部画面，并把局部观察对齐到全局模型。

这个思想可以推广为：

```text
已有关系网 = 静态先验
当前画面和用户操作 = 动态观察
```

动态观察不应立即覆盖已有知识，而应依次判断：

1. 是否只是已有状态的视觉变体。
2. 是否由角色、区域、时间、分辨率或游戏版本变化造成。
3. 是否只是动画、加载或一次瞬态异常。
4. 是否真正发现了新的稳定节点或关系边。
5. 与旧知识冲突时是否应保留候选分支等待更多证据。

还可以借鉴地图移动中的“预期位移与实际位移比较”思想：

```text
执行器预测动作结果
-> 视觉模块测量实际变化
-> 比较预期与实际
-> 更新当前位置或校准参数
-> 必要时重新规划
```

它不仅适用于地图，也适用于拖动、滚动、缩放、视角移动和关系边验证。

## 15. 实例间隔离，实例内串行

ALAS采用不同实例相互隔离、同一实例内部串行执行的思路。这个边界很适合多游戏和多窗口场景。

```text
不同游戏实例
-> 可以拥有独立进程、独立状态和独立关系上下文

同一个游戏实例
-> 同一时刻只允许一个计划提交物理键鼠输入
```

OCR、YOLO、CLIP等识别任务可以在资源允许时并行计算，但最终动作提交需要经过串行仲裁。否则两个能力节点同时发送输入，会产生无法归因的状态变化。

前端也不应承担识别和执行工作，只负责发出命令、订阅状态、展示进度与证据。这样即使模型加载缓慢、执行层卡住或游戏进程崩溃，用户界面仍能正常显示、停止任务和查看现场。

## 16. 配置、运行状态和任务记录应分离

ALAS中有一些值得参考的持久化思想，例如定义与生成物分离、资源按需加载、写入时尽量保证完整性。但其部分配置、任务调度和运行记录共享同一套数据结构，不适合直接复制到新系统。

新系统更适合明确区分：

```text
用户配置
模型与资源配置
能力和关系图定义
任务队列
当前运行状态
历史执行记录
故障证据和统计数据
```

这些数据生命周期、写入频率和并发要求不同。分开管理后，既能减少互相覆盖，也便于关系图版本化、回放和分析。

## 17. 不应直接移植的部分

以下内容与ALAS的专用环境绑定较深，不适合作为新系统底座直接移植：

```text
固定1280×720坐标和碧蓝航线专用视觉资源
Android ADB等输入后端作为Windows多窗口方案
复杂多重继承形成的隐式能力组合
全局页面表、服务器状态和可变资源对象
截图过程中夹带业务点击等观察副作用
配置、任务队列和运行记录共用同一数据模型
通过函数名和字符串约定进行隐式命令分发
把大多数未知故障直接升级为重启或人工接管
```

尤其应避免让“观察”产生操作副作用。截图和识别原则上应保持只读，否则系统无法判断画面变化是用户、计划还是观察模块自身造成的。

ALAS采用GPLv3许可证。借鉴设计思想没有问题；如果以后直接复制或改写其代码，需要提前确定新项目的开源和许可证策略。

## 18. 对新系统的最终启示

从ALAS中最值得提炼的不是某个算法，而是一条“确定性主干”：

```text
概率感知提供证据
-> 关系网提出路径
-> 执行器提交一次受控尝试
-> 后置观察验证实际结果
-> 故障归因决定重试、恢复或改道
-> 完整证据进入统计和后续学习
```

在这条主干中：

```text
LLM可以解释和命名
关系网可以规划和复用
视觉模型可以提供概率证据
执行器可以尝试动作
但任何模块都不能单独宣布世界状态已经改变
```

状态变化最终必须由多源观察和明确的验证规则确认。

因此，对新系统最稳妥的参考边界是：

> 使用ALAS的闭环执行、分层检测、设备门面、连续控制、恢复分级、看门狗和错误取证思想；使用Whimbox的任务、事件、插件和资源调度思想；重新设计关系发现、模块DAG、动态上下文、置信度隔离和桌面输入仲裁。
