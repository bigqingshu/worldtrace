## 1. 当前问题

界迹没有一个能够直接照搬的同类开源项目。Whimbox、UIAgent和AzurLaneAutoScript可以提供截图、识别、执行、调度和错误恢复经验，但不能直接回答：

- 怎样从用户游玩中自行发现状态和操作关系；
- 怎样将图标、物品、数值和地形现象组合成证据；
- 怎样从实验结果生成计算逻辑和关系逻辑；
- 怎样判断某个构想仅靠画面是否可能实现；
- 怎样在不知道最终算法时先保存足够的原始数据。

因此当前阶段需要同时进行开放构想和实验收束。开放构想用于扩大问题空间，实验用于确定实际输入能够提供什么事实。

## 2. 核心方法

```text
构想收集
-> 问题和假设拆分
-> 可观测性审计
-> 最小实验
-> 原始与派生数据分析
-> 证据能力收束
-> 数据契约和基础算子
-> 规则生成与模块实现
```

最重要的原则是：

> 构想允许天马行空，但进入实现的每项能力必须说明它依赖什么可观测事实，以及这些事实已经通过什么实验验证。

## 3. 天马行空的作用

开放讨论不是浪费，它可以提前发现：

- 原本没有考虑的状态分支；
- 游戏Bug和暂时缺失现象；
- 同名物品、图标变化和时间域差异；
- 计划、执行和真实事件之间的边界；
- 需要版本、证据和用户确认的位置；
- 某些死循环其实缺少一个独立输入或状态轴；
- 某些复杂问题可以通过保存原始数据延迟解决。

但构想不能直接成为事实或实现任务。每个构想都需要进入统一收束流程。

## 4. 构想生命周期

```text
IdeaStatus
├── IDEA
├── HYPOTHESIS
├── OBSERVABILITY_MAPPED
├── EXPERIMENT_READY
├── TESTED
├── SUPPORTED
├── REJECTED
├── DEFERRED
└── SUPERSEDED
```

### 4.1 `IDEA`

只记录可能性和价值，不要求当前可实现。

### 4.2 `HYPOTHESIS`

已经转换成可以被证据支持或反驳的描述。

### 4.3 `OBSERVABILITY_MAPPED`

已经列出直接证据、间接证据、反证、上下文和不可观测部分。

### 4.4 `EXPERIMENT_READY`

已有最小实验、输入条件、输出数据和判定标准。

### 4.5 `SUPPORTED`与`REJECTED`

实验在限定上下文中支持或反驳假设。它们都不是全局永久结论，必须携带实验范围和版本。

### 4.6 `DEFERRED`

当前输入、模型、数据量或安全条件不足，保留原始问题和需要补充的条件。

## 5. 构想的停止条件

“讨论足够多”不能依靠感觉，需要停止条件。

对一个场景完成以下内容后，可以暂时停止扩展：

- 已明确需要判断的事实；
- 已列出直接、间接、反向和实验性证据；
- 已标记当前不可观测部分；
- 已确定最小原始数据要求；
- 已设计一个或多个有界实验；
- 已定义成功、失败和`UNKNOWN`；
- 新想法不再改变数据契约、实验方案或安全边界。

如果新想法只增加案例，不改变上述内容，应追加为案例而不是继续扩展架构。

## 6. 可观测性审计

每个问题都应填写：

```text
ObservationQuestion
├── question_id
├── target_fact
├── decision_or_action_affected
├── direct_evidence
├── indirect_evidence
├── negative_evidence
├── contextual_evidence
├── experimental_evidence
├── required_raw_inputs
├── current_extractors
├── ambiguity
├── unobservable_parts
└── proposed_experiments
```

审计回答的不是“最终模型是什么”，而是“现有输入是否包含足以区分答案的信息”。

## 7. 证据类别

```text
EvidenceClass
├── DIRECT
├── DERIVED
├── TEMPORAL
├── EXPERIMENTAL
├── CONTEXTUAL
├── NEGATIVE
└── UNOBSERVABLE
```

### 7.1 `DIRECT`

游戏明确显示与目标事实直接相关的信息，例如物品数量、页面标题、冷却数字和状态图标。

这里的“直接”是相对于目标问题而言。OCR仍然是一个感知过程，因此必须保留识别置信度和原始图像。

### 7.2 `DERIVED`

由多个基础观测计算出的事实，例如：

```text
图标位置变化
+ 页签高亮
+ 布局出现
-> 候选页面状态
```

### 7.3 `TEMPORAL`

依赖前后时间关系：

```text
输入前状态
-> 用户输入
-> 输入后变化
```

### 7.4 `EXPERIMENTAL`

系统或用户主动改变一个变量后产生的证据，例如轻微移动滑块、按一次安全按键或前进一个短步。

### 7.5 `CONTEXTUAL`

窗口、角色、地图区域、游戏版本、账号、控制模式和界面状态等适用范围。

### 7.6 `NEGATIVE`

确认某个预期现象没有出现。负证据只有在观测范围完整、截图健康、目标区域可见且检测器有效时才成立。

### 7.7 `UNOBSERVABLE`

现有画面、输入和上下文无法区分目标事实。它是有效审计结果，不是失败。

## 8. 直接、间接和不可观测的边界

### 8.1 进入背包

```text
直接证据：
背包标题、页签高亮、物品数量或分类文字

间接证据：
战斗HUD消失、物品网格出现、背景布局变化

时间证据：
按B后在限定时间内出现上述变化
```

### 8.2 物品被消耗

```text
直接证据：
完整库存范围中的数量减少

间接证据：
使用动画、按钮变灰、提示信息

不能单独成立：
只有按钮动画但无法确认库存
```

### 8.3 地形可通行

```text
通常没有绝对直接证据

间接证据：
相对深度、地面连续性、边界、光流、角色运动响应

实验性证据：
安全短步后确实产生预期位移且没有碰撞或坠落
```

### 8.4 隐藏服务器状态

如果游戏画面、交互结果和本地数据都没有暴露某项服务器内部状态，则当前属于`UNOBSERVABLE`。系统不能靠反复截图推导不存在的信息。

## 9. `ObservationCapabilityMatrix`

所有构想最终汇总为可观测能力矩阵：

| 字段 | 说明 |
| --- | --- |
| `scenario_or_question` | 构想或待判断问题 |
| `required_fact` | 规划或执行真正需要的事实 |
| `direct_sources` | 可直接支持的画面或文本 |
| `indirect_sources` | 组合或时序证据 |
| `counter_evidence` | 可以反驳的现象 |
| `required_context` | 窗口、角色、版本等条件 |
| `raw_input_types` | 帧、输入、窗口、时间等 |
| `extractor_candidates` | 颜色、OCR、模板、模型等 |
| `experiment_refs` | 用于验证的实验 |
| `current_status` | 支持、未知、不可观测等 |
| `known_failure_modes` | 已知误判来源 |

矩阵不是最终规则表，而是“构想需要什么数据”的总索引。

## 10. 从矩阵收束实现方向

```text
有稳定直接证据
-> 优先建立确定性检测器

有多个稳定间接证据
-> 建立组合EvidencePredicate

必须主动操作才能确认
-> 建立受控ExperimentPlan

当前无法观测
-> DEFERRED、请求用户或增加新输入源

只在少数上下文有效
-> 保留狭窄scope，不提前泛化
```

## 11. 实验一次只回答一个问题

实验不应验证“整个自动化系统能否运行”。一个实验只回答一个可以明确判定的问题，例如：

```text
PrintWindow和桌面截图的像素格式是否一致
静止界面连续帧有多少自然噪声
按下B后哪类区域稳定变化
R通道是否足以区分某个红色状态标记
OCR能否在十次采集中稳定读取一位小数
```

问题越小，失败后越容易知道缺少什么。

## 12. `ExperimentSpec`

```text
ExperimentSpec
├── experiment_id
├── question
├── hypothesis
├── scope
├── required_inputs
├── controlled_conditions
├── intervention
├── raw_outputs
├── derived_outputs
├── expected_observations
├── success_criteria
├── failure_modes
├── risk_class
├── max_attempts
├── timeout
├── stop_conditions
└── cleanup_or_rollback
```

实验定义必须在运行前冻结版本，避免结果出来后再修改成功标准。

## 13. `ExperimentRun`

```text
ExperimentRun
├── experiment_run_id
├── experiment_spec_id与version
├── environment_snapshot
├── input_refs
├── intervention_attempt_refs
├── raw_artifact_refs
├── derived_artifact_refs
├── observations
├── anomalies
├── outcome
├── conclusion_candidate
└── started_at与ended_at
```

`outcome`可以是：

```text
SUPPORTED
NOT_SUPPORTED
INCONCLUSIVE
INVALID_RUN
CANCELLED
```

实验失败、无结论和环境无效必须分开。

## 14. 原始数据和派生数据分离

```text
RawArtifact
-> 截图、原始帧、输入事件、窗口事件和原始OCR区域

DerivedArtifact
-> 通道图、差异图、掩码、特征、OCR结果和模型输出
```

原始数据尽量不可变。派生数据必须记录：

```text
producer_id
producer_version
input_artifact_refs
parameters
created_at
```

算法升级后可以重新生成派生数据，而不需要重新操作游戏。

## 15. 帧原始数据契约

```text
FramePacket
├── frame_id
├── captured_at_monotonic
├── wall_clock_at_capture
├── window_instance_id
├── focus_epoch
├── capture_backend
├── width与height
├── stride
├── bit_depth
├── pixel_format
├── channel_order
├── color_space
├── alpha_mode
├── dpi_and_scale
├── freshness
├── capture_health
└── image_buffer_or_artifact_ref
```

没有这些元数据，后续RGBA、颜色阈值和多后端比较容易建立在错误假设上。

## 16. RGBA不一定真是RGBA

Windows截图接口常见输出包括：

```text
BGRA
BGRX
RGBA
RGB
```

必须通过实验确认：

- 红蓝通道是否交换；
- 每行是否存在额外`stride`字节；
- Alpha是否始终为255；
- Alpha是直通、预乘还是没有语义的填充；
- 返回图像是否经过颜色空间转换；
- PrintWindow、桌面截图和其他后端是否一致。

不能因为数组有四个通道，就默认第四通道包含可用透明度。

## 17. Alpha模式

```text
AlphaMode
├── STRAIGHT
├── PREMULTIPLIED
├── OPAQUE_CONSTANT
├── UNUSED_PADDING
└── UNKNOWN
```

如果Alpha全部为255，它对游戏界面识别通常没有额外信息，但仍应记录实验结论。若为预乘Alpha，在分析RGB之前需要按正确规则处理。

## 18. 通道分解实验

对同一帧输出：

```text
原始画面
R通道灰度图
G通道灰度图
B通道灰度图
A通道灰度图
亮度图
可选HSV或其他颜色空间
各通道直方图
每通道最小值、最大值、均值和标准差
Alpha唯一值数量
```

实验回答：

- 通道顺序是否正确；
- 哪个通道最能区分目标状态；
- Alpha是否有意义；
- UI颜色是否受整体光照影响；
- 是否需要转换到HSV、Lab或亮度空间。

通道图不是新的事实源，它们是同一原始帧的可复现派生产物。

## 19. 静止画面噪声实验

游戏即使没有用户操作，也可能存在：

- 粒子和光效；
- 角色待机动画；
- 云、树、水面和背景运动；
- UI闪烁和冷却动画；
- 视频压缩或截图后端噪声；
- 动态分辨率和抗锯齿变化。

输出：

```text
相邻帧绝对差
每像素变化频率
稳定区域掩码
动态区域掩码
通道级噪声分布
不同时间间隔的差异统计
```

这决定后续“区域变化”阈值是否可用，不能只在一张静态截图上设定。

## 20. 输入前后时间窗实验

```text
PreActionWindow
-> action_id
-> PostActionWindow
```

需要测量：

- 输入事件时间戳与真正送达时间的差异；
- 游戏开始响应的延迟；
- 动画持续时间；
- 目标状态稳定时间；
- 截图缓存或旧帧造成的偏移；
- 不同帧率下能够取得多少有效样本。

结果用于确定`PrePostActionWindow`，而不是手写统一等待时间。

## 21. 图标状态实验

选择一个可重复切换的图标状态：

```text
NORMAL
-> 用户操作
-> SELECTED或DISABLED
-> 恢复
```

保存：

- 原始前后帧；
- 图标候选区域；
- 各通道差异；
- 模板和感知哈希；
- 稳定持续时间；
- 周围布局变化；
- 误触发和无变化样本。

先证明视觉身份和变体可以稳定区分，再讨论图标语义。

## 22. OCR数值实验

选择一个稳定整数或一位小数：

```text
同一画面重复采集
-> OCR原文
-> 字符候选
-> 多帧稳定
-> 单位和范围检查
```

输出：

- 每帧OCR结果；
- 小数点和单位识别频率；
- 错误字符分布；
- 最佳颜色通道或二值化方案；
- 多帧投票后的结果；
- 无法收束的样本。

## 23. 界面切换实验

选择一个安全且可逆的菜单：

```text
基础界面
-> 一个输入
-> 目标菜单
-> 同一输入或返回操作
-> 基础界面
```

实验用于验证：

- 变化区域是否可自动发现；
- 哪些特征属于稳定页面证据；
- 哪些变化只属于动画；
- 前后状态是否能在离线回放中重复判断；
- 输入失败时证据表现如何。

## 24. 实验优先级

建议按照以下原则排序：

```text
低风险优先
可重复优先
可离线重放优先
能够验证基础数据契约优先
被多个后续模块依赖优先
能快速否定错误假设优先
```

第一批不应选择不可逆消耗、复杂战斗或高风险悬崖场景。

## 25. 失败实验的价值

失败结果必须记录：

```text
为什么无法判断
哪些输入不够
哪些特征不稳定
是否存在不可消除混淆
需要增加什么传感器或上下文
是否应永久停止该方向
```

失败可以把问题从“继续调阈值”收束为：

```text
需要连续帧而不是单帧
需要窗口焦点证据
需要用户提供一个标签
需要主动实验
当前纯视觉不可观测
```

## 26. 反例和负样本

每个检测实验都应包含：

- 正常成功样本；
- 相似但不属于目标状态的样本；
- 操作没有送达的样本；
- 遮挡、动画或加载样本；
- 分辨率、UI缩放或游戏版本变化；
- 预期图标或文本缺失样本。

只有正样本会让很多错误特征看起来有效。

## 27. 实验结论的适用范围

```text
ExperimentConclusion
├── supported_claim
├── scope
├── required_conditions
├── unsupported_conditions
├── confidence_components
├── evidence_refs
├── counterexamples
├── extractor_versions
└── expiration_or_retest_conditions
```

例如“G通道能区分按钮状态”只能在指定游戏、UI版本、分辨率和区域内成立，不能直接推广到所有界面。

## 28. 从实验到基础算子

实验稳定支持的能力可以形成基础算子候选：

```text
region_changed
token_variant_is
ocr_integer
numeric_value_stable
capture_is_fresh
layout_matches
relative_depth_order
```

基础算子需要独立测试和明确输入输出。复杂状态和关系再由规则合成系统组合这些算子。

## 29. 从实验到数据契约

如果多个场景都需要同一种原始事实，应优先把它收束进公共数据契约，例如：

```text
所有视觉实验都需要frame_id和pixel_format
所有操作实验都需要action_id和输入前后窗
所有窗口实验都需要window_instance_id和focus_epoch
所有OCR实验都需要raw_text和roi_ref
所有模型输出都需要producer_version
```

公共契约应来自多个实验的共同需求，而不是凭空预建大量字段。

## 30. 从实验到规则

```text
ExperimentRun
-> FactRecord
-> RuleHypothesis
-> 离线回放
-> SHADOW
-> ACTIVE RuleSpec
```

单次实验结论不能直接写成活动规则。规则需要跨样本验证、反例和适用范围。

## 31. 文档如何收束

现有构想文档可以保持开放分析，但每篇逐步补充：

```text
需要判断的事实
可观测证据
不可观测部分
依赖的原始数据
最小实验
实验输出
当前结论状态
```

如果多篇文档依赖相同实验，不应重复实现，而是在实验目录和能力矩阵中引用同一个实验。

## 32. 建议的四个阶段产物

### 32.1 `ObservationCapabilityMatrix`

汇总所有构想与所需证据。

### 32.2 `RawDataContract`

确定帧、输入、窗口和时间最小字段。

### 32.3 `ExperimentCatalog`

保存实验问题、优先级、依赖、风险和当前状态。

### 32.4 `EvidenceBundle`

保存一次实验的原始数据、派生数据、环境和结论候选。

## 33. 当前下一阶段

当前讨论已经覆盖关系网、图标、物品、数值、资源规划、3D导航、故障和动态规则。下一阶段可以暂时停止扩展大架构，进行第一次完整可观测性审计：

1. 从现有文档提取所有需要判断的状态、数值和关系。
2. 标记直接、间接、实验和不可观测证据。
3. 统计共同依赖的原始数据字段。
4. 形成第一版`ObservationCapabilityMatrix`。
5. 排出最低成本的实验清单。
6. 先实现截图、输入、窗口和时间线实验工具。
7. 用实验结果反向修改规则和模块构想。

## 34. 第一批实验

```text
EXP-001 截图像素格式与RGBA/BGRA确认
EXP-002 静止画面自然噪声和稳定区域
EXP-003 输入事件与前后帧时间对齐
EXP-004 一个图标的视觉状态变化
EXP-005 一个OCR整数或一位小数
EXP-006 一个安全菜单的往返切换
```

这六项优先验证所有上层能力共同依赖的测量地基。

## 35. 当前不做的事情

第一批实验阶段不需要：

- 训练完整YOLO模型；
- 接入LLM实时判断；
- 建立通用3D地图；
- 让系统自主执行材料消耗；
- 自动生成大规模关系网；
- 一次性实现全部截图后端；
- 预先决定所有最终数据库结构。

## 36. 验收标准

- 每个进入实现的构想都有可观测性映射；
- 直接、间接、负向和不可观测证据不会混淆；
- 每个实验只回答一个明确问题；
- 原始数据和派生数据分别保存；
- 帧数据明确记录像素格式、通道顺序和Alpha模式；
- RGBA/BGRA结论来自实验而不是接口名称猜测；
- 输入实验保存前后时间窗和窗口归属；
- 失败和无结论实验同样可追溯；
- 新想法不改变数据契约或安全边界时不会继续膨胀架构；
- 当前不可观测的问题会明确标记并停止空转；
- 实验结果能够反向形成基础算子、数据契约或规则候选；
- 同一段原始数据可以使用新算法重新分析。

## 37. 当前结论

界迹当前最重要的收束不是继续猜测完整系统最终形态，而是建立一套能够测量游戏、保存原始事实、重复实验和判断信息边界的研究工具。

```text
天马行空的构想
-> 帮助发现问题空间和隐藏边界

可观测性审计
-> 判断画面和输入能否支撑这些想法

最小实验
-> 展示真实输出和失败方式

数据与规则收束
-> 决定下一步应该实现什么
```

`Trace Core`正是这套研究方法的第一层基础设施。先把测量系统做可靠，再让关系网、规则和AI建立在可复现证据上。
