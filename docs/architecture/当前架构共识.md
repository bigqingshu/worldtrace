# 当前架构共识

本文记录截至当前讨论已经收束的架构边界，供新对话和后续实现优先读取。详细推导仍以各专题文档为准。

## 项目定位

项目名称为“界迹（WorldTrace）”，目标是从用户游玩产生的连续画面、键鼠输入和窗口事件中提取可验证的小步骤，逐步形成能够规划和执行的游戏关系网。

第一版不追求通用3D智能体，也不一次实现完整关系网。开发从可验证的最小闭环开始，每个基础模块单独测试，再逐步组合。

## 构想收束与实验方法

开放构想用于发现隐藏状态、故障边界和新的数据需求，但构想不能直接成为实现任务。统一收束过程为：

```text
构想
-> 可证伪假设
-> 可观测性审计
-> 最小实验
-> 原始和派生数据分析
-> 基础算子、数据契约或规则候选
```

每个进入实现的能力都需要说明直接、间接、负向、上下文和实验性证据。现有输入无法区分的问题标记为`UNOBSERVABLE`并停止空转；新想法不改变数据契约、实验或安全边界时，只追加为案例。详细方法见[构想收束、可观测性审计与实验方法](构想收束、可观测性审计与实验方法.md)。

## 图模型

定义层采用以下关系：

```text
StateDefinition节点
-> TransitionDefinition边
-> 边引用CapabilitySpec
```

能力可以是原子能力、复合能力或 `ContinuousController`。能力模块依赖可以形成DAG；游戏空间拓扑和模块内部状态转换允许受控循环。地点图、状态图、能力调用图和运行记录不得混在同一张图中。

## 规则生成与执行边界

`StateDefinition`和`TransitionDefinition`不是必须由人手写并固化到Python中的最终结构。系统可以根据连续观测、用户操作、离线回放和受控实验生成新的状态规则、转换规则、计算公式和适用范围。

```text
事实
-> 关系或计算假设
-> 离线与影子验证
-> 版本化RuleSpec
-> 确定性编译和执行
```

固定的是截图、输入、基础检测、白名单运算、证据、版本和安全边界；动态生成的是基础算子的组合、阈值、公式、关系条件和上下文守卫。运行时禁止任意`eval`或动态脚本注入。

`ACTIVE`规则不可原地修改。新证据只能产生新的候选版本，经过`CANDIDATE`和`SHADOW`验证后再切换；已经生成的`ExecutablePlan`固定使用具体规则、检测器、能力和校准版本。详细设计见[证据驱动的规则生成、实验验证与运行编译构想](../concepts/rule_synthesis/证据驱动的规则生成、实验验证与运行编译构想.md)。

## 运行记录

运行层采用以下层级：

```text
PlanRun
-> CapabilityRun
-> StepAttempt
-> 可选GraphCallRun
-> 可选RecoveryRun
```

恢复过程不能覆盖原始失败尝试。公共结果由以下部分组成：

```text
ExecutionOutcome
+ reason_code
+ FailureAttribution
+ SampleDisposition
```

其中 `ExecutionOutcome` 只允许：

```text
SUCCEEDED / FAILED / UNKNOWN / CANCELLED / BLOCKED
```

## 发布与版本

能力和识别器使用独立发布生命周期：

```text
DRAFT
-> CANDIDATE
-> SHADOW
-> ACTIVE
-> DEGRADED
-> RETIRED
```

语义是否确认、验证记录是否充分、当前是否发布是三条独立状态轴，不能用一个“置信度”字段代替。

## LLM边界

LLM负责命名、解释、提出疑问、理解用户目标、提出抽象计划候选和解释结构化结果。LLM不直接决定当前界面状态、输入是否成功、动态控件绑定或故障归因。

计划候选经过结构校验和必要的用户确认后才能成为`AbstractPlan`。确定性编译器负责把`AbstractPlan`展开为`ExecutablePlan`，固定能力、子图、游戏适配器、检测器和校准版本。

普通数值默认由系统完成OCR复核、单位解析、Decimal或整数运算、取整和属性专用容差比较。只有多次有效观测仍与预期明显不符，或用户主动请求分析复杂属性时，才调用LLM。LLM分析保持为候选，用户确认后创建新规则或公式版本，不能覆盖原始证据。具体设计见[数值单位、误差容限与按需AI分析构想](../concepts/resource_planning/数值单位、误差容限与按需AI分析构想.md)。

## 程序事实与AI记忆

程序管理`EvidenceStore`、`FactStore`、`HypothesisStore`、`RuleRegistry`、`InventoryLedger`和`RunStore`等逻辑数据边界。AI工作记忆和长期记忆均为非权威上下文，不能代替这些程序记录。

```text
程序事实和候选
-> 带revision的只读ReadModel
-> AI提出Proposal / Question / Explanation
-> 程序保存候选并完成校验或用户确认
-> 正式Command创建新版本或追加事件
```

AI没有事实库、库存、活动规则、公式或运行计划的直接写权限，也不能删除原始证据。上述存储是长期逻辑所有权边界，不表示第一阶段需要一次实现；`Trace Core`仍只从可靠记录和回放开始。完整设计见[程序事实记忆、AI智能体记忆与写入治理](程序事实记忆、AI智能体记忆与写入治理.md)。

## 输入与视觉

视觉基础输入是连续 `FrameStream`，单帧只是从连续流中选择出的观察样本：

```text
CaptureService
-> FrameStream
-> FrameRingBuffer
-> FrameSelector
   -> StableFrame
   -> TemporalWindow
   -> PrePostActionWindow
   -> KeyFrameSequence
```

所有识别模块消费统一的 `frame_id` 或 `window_id`，不能各自临时截图。物理输入必须绑定窗口实例、焦点代次和控制配置代次。

## 视觉模型职责

- 图像变化、颜色和模板匹配承担高频低成本筛选。
- OCR和YOLO按具体任务调用。
- CLIP用于候选召回和语义消歧。
- SAM用于按需分割、跟踪辅助和离线素材制作。
- LLM只解释结构化结果，不进入实时控制闭环。

模型名称不等于业务能力。OCR、YOLO、CLIP和SAM应作为视觉模块中的可替换实现，而不是各自控制业务流程。

## 图标视觉标记

图标作为无需预先理解语义的视觉标记记录。系统为图标建立稳定机器身份、视觉变体、单次观测和时间变化事件，再将它们作为状态证据或操作后置条件。

```text
VisualTokenDefinition
-> VisualTokenObservation
-> VisualTokenEvent
-> VisualEvidencePredicate
```

图标不等于状态，也不天然等于可点击按钮。正常、高亮、变灰和冷却应优先作为同一图标的视觉变体；单次帧观测只进入运行证据，不创建永久关系节点。LLM只在用户询问时提供可选语义建议，具体设计见[图标视觉标记与状态证据构想](../concepts/interface_discovery/图标视觉标记与状态证据构想.md)。

## 3D导航

3D相关方案分为三层：

```text
视觉移动
-> 局部风险和短距离控制

立体地图
-> MapSpace、Portal和空间拓扑

无小地图副本
-> DungeonExplorer和ProgressFacts
```

第一版不直接建立米制3D地图，优先使用自我中心风险格：方向扇区、近中远距离、地面连续概率、障碍概率、落差风险和 `UNKNOWN`。

## 第一实现目标

首期只实现 `Trace Core`：

1. `CaptureService`
2. `InputRecorder`
3. `WindowRegistry`
4. 统一 `Timeline`
5. `FrameRingBuffer`
6. `EvidenceStore`
7. `ReplayTool`

完成标准是帧、输入和窗口事件可以可靠对齐，异常现场可以保存，同一记录可以离线重放。第一阶段不接入OCR、YOLO、CLIP、SAM或LLM。

具体阶段顺序、开源截图候选、实验输出和阶段门禁见[第一阶段开源采集验证与实现路线](第一阶段开源采集验证与实现路线.md)。当前成功率、全职与业余周期、主要风险和一年成功标准见[项目可行性、周期、风险与阶段成功标准](项目可行性、周期、风险与阶段成功标准.md)。
