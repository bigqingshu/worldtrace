# 目录与模块边界规则

本文用于约束以自然语言向AI提出需求时的代码归属，避免功能不断堆入单个脚本并引发早期反复重构。

## 总体方式

项目初期采用“模块化单体 + 实验区”。所有正式代码位于同一个Python包中，但模块之间通过明确契约协作。暂不按进程或微服务提前拆分。

```text
想法
-> docs/concepts
-> experiments中单独验证
-> 明确输入、输出和验收条件
-> 记录重要设计决定
-> 迁入src/worldtrace正式模块
-> 添加对应测试和模块说明
```

## 什么时候建立新模块

代码行数不是建立模块的唯一理由。满足以下条件中的至少两至三项时，才考虑形成独立模块：

- 有清晰且稳定的输入、输出。
- 可以独立测试和离线回放。
- 拥有自己的状态、资源或生命周期。
- 未来可能替换为另一种实现。
- 与现有代码具有不同的修改原因。
- 会被两个以上模块复用。

暂时无法确定归属的功能先进入 `experiments`，不能直接塞进当前最方便的正式脚本。

## 依赖边界

- `contracts`只保存跨模块数据结构和接口，不放调度或业务算法。
- `runtime`负责组装、调度、停止和资源协调，不实现识别算法。
- `main.py`只负责启动、读取配置和依赖注入。
- 模块不能直接读取另一个模块的内部缓存、数据库表或私有对象。
- 跨模块调用必须使用公共接口、事件或公共数据结构。
- 外部库和平台实现作为适配器存在，不能反向控制领域流程。
- 禁止循环导入；确实存在双向业务关系时，通过事件或上层调度器协调。

## 文件拆分信号

文件达到约300至500行时需要检查职责，但不机械按行数拆分。出现下列情况时应优先拆分：

- 同一个文件同时处理采集、识别和持久化。
- 修改一种功能时经常碰到无关代码。
- 测试必须启动大量无关依赖才能运行。
- 存在多个独立生命周期或错误处理策略。
- 文件名已经无法准确概括内容。

不应采用“每个类一个文件”或“每个想法一个目录”的机械规则。

## AI实现前置说明

每次要求AI实现功能前，至少提供或让AI先补全以下内容：

```text
目标：本次具体要解决什么
归属模块：代码应该进入哪个模块
输入：消费哪些数据和状态
输出：产生哪些数据、事件或副作用
允许修改：本次可以改动的目录或文件
禁止依赖：不能直接调用哪些实现
验收条件：怎样证明功能完成
代码性质：实验代码还是正式代码
```

AI开始修改前，应先报告“归属模块、是否需要新目录、公共契约变化和预计修改文件”。如果无法说明边界，应先做小实验或补架构分析。

## 中英文协作规则

- 所有目录、Python包、模块、类型和配置键使用英文。
- 中文文档、中文标题和中文解释可以正常使用。
- AI第一次提到英文标识符时，应附带中文含义。
- 每个正式模块落地时添加 `README.zh-CN.md`，说明职责、输入、输出、依赖和不负责范围。
- 新增或改名英文概念时同步更新[术语表](../术语表.md)。
