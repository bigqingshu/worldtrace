## 1. 当前结论

项目最开始实现的目标不是关系网、界面语义识别或3D导航，而是：

> `Capture Lab`（画面采集实验台）与`Trace Core v0`（轨迹事实核心初版）。

它们负责比较开源截图方案、统一流式帧数据、同步被动键鼠输入和窗口事件，并让开发者可以人工查看、保存和离线重放真实输出。

推荐总体顺序：

```text
开源项目与截图后端审计
-> 流式画面、被动输入、窗口与时间线
-> 人工检查像素和基础派生数据
-> 离线状态特征
-> 输入与变化组成关系候选
-> 受控键鼠执行
-> 一个完整UI往返闭环
-> 图标、OCR、物品和连续控件
-> 3D运动、深度和跳跃实验
```

## 2. 一个关键顺序调整

被动键鼠记录应与流式画面采集同时开始，而不是等待画面状态识别完成。

原因是用户输入提供天然时间锚点：

```text
输入前画面
-> 用户按键或鼠标操作
-> 输入后画面
```

如果早期只录画面，后续很难知道某次变化对应哪个操作，已有数据可能需要重新录制。

需要严格区分：

```text
PassiveInputRecording
-> 只记录用户对目标游戏的输入
-> 第一阶段开始

ActiveInputExecution
-> 系统主动向游戏发送输入
-> 关系候选验证后再开始
```

先使用非侵入式操作系统截图接口和测试账号，降低账号、稳定性和合规风险。

## 6. 统一截图后端接口

候选接口：

```text
CaptureBackend
├── open(target)
├── start_stream()
├── next_frame()
├── stop_stream()
├── get_capabilities()
└── get_health()
```

后端专用纹理、句柄和错误不能直接泄漏给上层。统一层也不能为了统一而立即把所有GPU帧强制复制到CPU。

第一版人工分析可以使用CPU数组；同时记录未来是否支持`GPU_TEXTURE`或零复制路径。

## 8. 截图后端需要测量的参数

### 8.1 正确性

- 像素格式是RGB、BGR、RGBA、BGRA还是BGRX；
- Alpha是否有效、恒定或只是填充；
- 窗口客户区是否包含边框和标题栏；
- DPI缩放后尺寸和坐标是否一致；
- HDR、色彩空间和Gamma是否发生转换；
- 尺寸变化后首帧是否有效。

### 8.2 时序

- 平均帧率；
- 帧间隔分布；
- 捕获延迟；
- 首帧延迟；
- 重复帧比例；
- 丢帧比例；
- 旧帧或缓存帧比例；
- 窗口切换后的恢复时间。

### 8.3 窗口行为

- 前台、后台和失去焦点；
- 被其他窗口部分或完全遮挡；
- 最小化；
- 窗口化、无边框和全屏；
- 多显示器；
- 多开相同游戏；
- 分辨率和窗口尺寸切换。

### 8.4 性能

- CPU占用；
- GPU占用；
- 内存带宽和复制次数；
- 缓冲队列长度；
- 单帧内存大小；
- 长时间运行内存增长；
- 对游戏帧率的影响。

## 10. 阶段1验收门槛

- 至少两个后端能够产生统一`FramePacket`；
- 可以明确验证通道顺序和Alpha模式；
- 可以区分新帧、重复帧、旧帧和失败；
- 窗口尺寸变化不会静默产生错位图像；
- 运行一段时间后能输出性能和健康报告；
- 所有结论附带后端、版本和实验环境。

未达到这些条件前，不进入正式状态识别。

## 11. 阶段2：Trace Core v0

`Trace Core v0`是可重放的事实层：

```text
CaptureService
+ InputRecorder
+ WindowRegistry
+ Timeline
-> FrameRingBuffer
-> EvidenceStore
-> ReplayTool
```

它不判断页面、图标、人物速度或操作成功。

## 12. `InputRecorder`

第一版只被动记录：

```text
InputEvent
├── input_event_id
├── monotonic_timestamp
├── source
├── device_type
├── event_type
├── key_or_button
├── position_or_delta
├── wheel_delta
├── target_window_candidate
├── focus_epoch
└── recording_session_id
```

需要记录按下与释放，避免只知道用户按过某键，却不知道持续时间和组合键。

### 12.1 输入隐私

全局输入记录只在用户明确开始录制时启用，并尽量限制为目标游戏窗口、指定时间段和需要的事件类型。

不保存其他应用中的文本内容，不把普通桌面输入混入游戏训练数据。

## 13. `WindowRegistry`

```text
WindowInstance
├── window_instance_id
├── process_id
├── process_start_time
├── native_window_handle
├── title_snapshot
├── executable_identity
├── client_rect
├── dpi_scale
├── generation
├── focus_epoch
└── health
```

仅保存窗口标题或句柄不足以区分游戏重启和多开实例。输入和帧必须绑定同一`window_instance_id`和代次。

## 14. 统一时间线

帧、输入和窗口事件使用同一单调时钟：

```text
Timeline
├── FrameEvent
├── InputEvent
├── WindowEvent
├── FocusEvent
└── CaptureHealthEvent
```

墙上时钟只用于人类查看和跨会话索引，事件顺序与时间差使用单调时钟。

## 15. 环形缓冲和证据包

```text
FrameRingBuffer
-> 保留最近若干秒帧和元数据

EvidenceBundle
├── trigger_event
├── pre_event_window
├── post_event_window
├── input_events
├── window_events
├── capture_health
├── environment_snapshot
└── artifact_refs
```

不需要永久保存所有高帧率原始画面。遇到输入、状态变化、异常或用户标记时保存关键时间窗，同时允许实验会话选择完整保存。

## 16. `ReplayTool`

离线回放需要：

- 按原时间顺序读取帧、输入和窗口事件；
- 支持逐帧、倍速、暂停和跳转；
- 显示输入事件标记；
- 切换原始与派生产物；
- 使用新算法重新分析旧证据；
- 固定或切换检测器和规则版本；
- 导出实验报告。

回放是后续关系发现、OCR、图标、运动和深度实验的共同入口。

## 17. 阶段2验收门槛

- 每帧拥有唯一`frame_id`；
- 每个输入拥有唯一`input_event_id`；
- 可以找到输入前后的帧窗口；
- 可以确认帧和输入属于同一游戏窗口；
- 可以区分截图失败和画面没有变化；
- 异常时可以保存最近数秒证据；
- 同一记录可以重复离线回放；
- 不需要OCR、YOLO、SAM、CLIP或LLM也能运行。

## 18. 阶段3：Frame Inspector

`Frame Inspector`用于人工观察真实输出，不是最终产品界面。

建议展示：

```text
原始帧
R/G/B/A通道
亮度图
可选HSV或Lab通道
颜色直方图
相邻帧差异热图
稳定与动态区域掩码
帧时间、后端和健康状态
输入事件时间标记
窗口和DPI元数据
```

## 19. 区分三类输出

```text
CaptureBackend原始输出
-> 像素、尺寸、格式、句柄和时间

系统派生输出
-> 通道、差异、稳定区域、颜色和候选框

上层解释
-> 页面状态、按钮、人物运动和操作结果
```

不能把派生特征误认为截图后端直接提供，也不能把视觉变化直接等同于业务语义。

## 20. 阶段3人工检查问题

- 实际是RGBA还是BGRA；
- Alpha是否有意义；
- 哪个通道更突出目标UI；
- 静止画面有多少自然噪声；
- 动画和光效主要集中在哪些区域；
- 输入后多久开始发生变化；
- 变化持续多久才稳定；
- PrintWindow和桌面截图是否显示同一时刻；
- 窗口遮挡或最小化时输出如何失败；
- 是否存在重复、撕裂或部分更新帧。

## 21. 阶段4：基础画面状态特征

选择一个简单、安全和可逆的UI往返：

```text
游戏基础界面
-> 用户按ESC
-> 基础菜单
-> 用户返回
-> 游戏基础界面
```

只实现：

- 稳定帧选择；
- 区域变化；
- 简单颜色与模板特征；
- 图标出现和消失候选；
- 页面布局指纹；
- 动画结束与稳定时间；
- `TRUE / FALSE / UNKNOWN`。

第一版状态只使用机器ID：

```text
state_candidate_001
state_candidate_002
```

不需要先由AI命名。

## 22. 阶段4验收门槛

- 同一状态重复进入时能够得到稳定候选；
- 相似但不同的页面不会被强制合并；
- 动画期间返回`UNKNOWN`或过渡状态；
- 截图异常不会被解释为状态变化；
- 离线回放多次得到相同结果；
- 每个判断列出使用的帧和特征。

## 23. 阶段5：初步关系候选

```text
StateCandidate
-> ActionObservation
-> VisualChangeEvent
-> StateCandidate
```

示例：

```text
state_001
+ KEY_PRESSED(ESC)
-> token_12出现
-> layout_03出现
-> state_002
```

这只是`TransitionHypothesis`，不是活动规则。

## 24. 关系候选验证

至少收集：

- 多次成功样本；
- 输入没有送达的样本；
- 相似状态中的同一按键；
- 动画、加载和弹窗样本；
- 前置条件不满足的样本；
- 游戏Bug或功能失效样本。

只有通过离线回放和反例检查，才能进入`CANDIDATE`或`SHADOW`。

第一张图只覆盖两三个状态和一个往返操作。

## 25. 阶段5验收门槛

- 能从输入时间锚点找到重复变化模式；
- 被动相关关系不会直接标为因果；
- 同一个按键的不同上下文可以保留多个候选；
- 关系拥有证据、版本和适用范围；
- 不使用LLM也能生成机器关系候选；
- 图规模保持在人工可检查范围。

## 26. 阶段6：受控键鼠执行

关系候选在离线和影子模式下稳定后，再实现主动输入：

```text
WindowRegistry
-> FocusLease
-> 输入前状态确认
-> 定位目标窗口
-> 执行一个安全按键或点击
-> 获取输入后的新鲜帧
-> 验证后置状态
-> 失败时释放全部按键并停止
```

## 27. 输入执行的固定安全边界

- 输入绑定`window_instance_id`；
- 执行前重新确认焦点和窗口代次；
- 同一时刻只有一个桌面物理输入所有者；
- 每个输入有最大持续时间；
- 停止时释放全部可能按住的键；
- 用户可以立即中止；
- 首批只使用无消耗、可逆操作；
- 结果必须由新鲜后置帧确认。

## 28. 鼠标定位

第一版可以记录桌面坐标作为原始事实，但正式规则逐步转换为：

```text
窗口客户区归一化坐标
+ 布局锚点
+ ControlSlot
+ 当前UI缩放
+ 操作后置证据
```

不能把一次绝对屏幕坐标直接当成跨分辨率按钮定义。

## 29. 阶段6验收门槛

- 输入只送到预期测试窗口；
- 切换焦点或窗口重启时拒绝执行；
- 一个按键和一个静态按钮可以安全执行；
- 每次尝试都产生`StepAttempt`和证据；
- 操作后无法确认时返回`UNKNOWN`；
- 停止、异常和超时都会释放输入资源。

## 30. 阶段7：第一个UI闭环

```text
识别状态A
-> 执行能力A到B
-> 验证状态B
-> 执行能力B到A
-> 验证重新到达状态A
```

建议选择ESC菜单或另一个无资源消耗的基础菜单。

这一步证明：

- 状态识别；
- 关系规则；
- 主动输入；
- 后置验证；
- 停止和恢复；
- 运行证据。

可以组合成一个真正闭环。

## 31. 阶段7验收门槛

- 连续重复多次往返而不依赖固定等待；
- 页面动画和延迟变化不会产生假成功；
- 输入错投、旧帧和弹窗能够被识别；
- 任一步失败不会继续盲目执行后续步骤；
- 可以离线解释每次成功和失败原因。

## 32. 阶段8：扩展二维和UI能力

完成首个闭环后，按单模块验证：

```text
图标视觉身份与变体
OCR整数、小数和单位
物品数量前后变化
滑块和滚轮微量校准
动态控件绑定
多页面关系
简单材料计划的只读验证
```

每项先在离线数据上验证，再进入受控执行。

## 34. 3D实验顺序

```text
镜头运动与人物运动分离
-> 静止、走路、跑步和疾跑阶段
-> 输入后实际推进和停止响应
-> 碰墙和无推进
-> 相对深度及地面连续性
-> 接近边缘和安全停止
-> 跳跃响应画像
```

跳跃、悬崖和移动平台不进入最初自动控制。

## 35. 3D阶段验收门槛

- 不把按键意图直接当成人物移动；
- 不把速度线或FOV单独当成真实速度；
- 可以区分镜头旋转和场景平移；
- 在安全平地输出稳定离散运动状态；
- 撞墙时识别无推进；
- 深度或运动证据不足时停止并返回`UNKNOWN`；
- 结果可以在相同录制数据上重复分析。

## 36. 阶段依赖关系

```text
Reference Audit
-> Capture Lab
-> Trace Core v0
-> Frame Inspector
-> State Features
```

后续阶段可以研究性并行，但不能跳过所依赖的数据和安全门槛。

## 39. 当前暂不实现

- 通用跨游戏状态语义；
- LLM实时画面判断；
- 自动大规模关系网；
- 任意脚本生成和执行；
- 复杂物品消耗；
- 正式账号高风险操作；
- 米制3D重建；
- 通用悬崖和跳跃控制；
- 一次性接入所有OCR和视觉模型。

## 40. 第一阶段完成定义

第一阶段完成不是“能够自动玩游戏”，而是：

```text
至少两种截图后端经过对比
帧、被动输入和窗口事件可靠对齐
原始数据可以人工检查
同一段数据可以离线回放
两个UI状态可以稳定区分
一条往返关系可以形成候选
一个安全输入可以在验证后执行
```

达到这些条件后，项目才证明已经拥有从游戏事实走向状态、关系和执行的最小技术链路。

## 41. 当前结论

第一阶段的核心不是选模型，而是建立测量和复现能力：

```text
开源采集方案
-> 统一事实数据
-> 人工理解真实输出
-> 离线提取状态特征
-> 形成小规模关系候选
-> 受控执行并验证结果
```

被动键鼠记录从最初就存在，主动键鼠执行在关系验证后开始；3D实验位于UI闭环之后，并首先使用离散运动状态和相对深度，而不是伪精确物理量。
