## 1. 当前想法

界迹内部需要同时存在两类容易被统称为“记忆”的内容：

- 程序通过截图、输入、实验和执行得到的事实、假设、规则、库存与运行记录；
- AI为了理解问题、解释结果和生成候选计划而维护的工作上下文与长期记忆。

这两类内容不能混在同一个聊天历史、向量库或自然语言文件中。AI可以查询程序提供的信息，但不能直接修改程序事实、活动规则、库存账本或正在执行的计划。

这里更准确的命名是：

```text
程序事实系统
+
AI智能体记忆
+
受控提案与写入治理
```

“程序分析的记忆”不应继续作为一个模糊的大存储，而应按事实、假设、规则、账本和运行记录拆分。

## 2. 核心结论

界迹采用以下单向权限原则：

```text
程序事实库
-> ReadModel或带revision的只读快照
-> AI

AI
-> Proposal / Question / Explanation
-> 受限提交接口与ProposalService
-> ProposalStore
-> 确定性校验或用户确认
-> 正式Command
-> 程序服务创建新版本或追加事件
```

AI拥有“读取、解释、询问和提出候选”的权限，不拥有“直接改事实、改库存、发布规则、改公式、批准计划和删除证据”的权限。

即使用户采纳AI建议，真正写入的也不是AI响应本身，而是程序根据固定Schema、权限、当前版本和确认记录生成的一条正式命令。

## 3. 为什么必须分开

### 3.1 AI记忆会压缩和改写

聊天历史会被截断，长期记忆通常由模型摘要生成。摘要可能遗漏条件、把假设写成事实，或者在模型升级后出现不同措辞。它不适合作为执行层的权威依据。

### 3.2 游戏事实需要可回放

“某按钮在某帧变灰”“库存从12变成10”“某次按键没有送达目标窗口”都需要回到原始帧、输入事件、窗口代次和时间戳复核。自然语言记忆无法提供这种证据链。

### 3.3 当前状态会过期

角色、界面、库存、任务阶段和游戏版本都可能变化。AI记住的旧状态不能直接参与当前判定，当前状态必须来自带时间和版本的程序查询。

### 3.4 写入错误的影响不对称

AI把一个名称说错通常只影响解释；AI若直接修改库存、活动规则或运行计划，则可能导致资源误用、错误输入或关系网被污染。因此需要在写入端建立比读取端更严格的边界。

## 4. 三个逻辑层

| 逻辑层 | 保存内容 | 是否权威 | 主要写入者 |
| --- | --- | --- | --- |
| 程序事实层 | 原始证据、结构事实、库存事件、运行结果 | 是，但仍保留版本和来源 | 对应领域服务 |
| 候选与分析层 | 假设、AI提案、分析报告、待确认解释 | 否 | 算法、AI或用户均可提出候选 |
| AI记忆层 | 当前任务上下文、用户偏好、问题索引、事实引用 | 否 | Agent记忆服务按策略维护 |

这不是简单的“两套数据库”。核心区别是数据的证据等级、权限和使用方式，而不是最终使用SQLite、PostgreSQL、对象文件还是其他存储引擎。

## 5. 程序事实系统

### 5.1 `EvidenceStore`

`EvidenceStore`保存最接近原始观测的证据，例如：

- 帧、帧窗口和关键截图；
- 键盘、鼠标和窗口事件；
- OCR、检测、模板匹配和深度模块的原始输出；
- 实验输入、环境信息和模型版本；
- 执行前后证据与异常现场。

证据原则上只追加，不允许AI覆盖或删除。空间清理由独立保留策略执行，并留下归档、校验或墓碑记录。

### 5.2 `FactStore`

`FactStore`保存从证据中得到的版本化结构事实，例如：

- 某个窗口实例在一段时间内处于前台；
- 某帧检测到某个视觉标记；
- 某次数值经过双帧OCR复核；
- 某次输入被送到指定窗口；
- 某个操作前后发生了可复核的状态变化。

每条事实至少需要引用来源证据、生成器版本、观察时间和适用对象。AI解释不能直接变成事实；它只能形成假设或提案，随后由程序验证。

### 5.3 `HypothesisStore`

`HypothesisStore`保存尚未验证的关系、语义和原因候选，例如：

- “这个图标可能表示体力不足”；
- “按下B可能打开背包”；
- “按钮缺失可能来自任务前置条件”；
- “这段视频中的地点可能对应当前地图锚点”。

候选必须带来源、生成方式、适用范围、反例、状态和可选TTL。AI提出的内容与程序模式发现器生成的内容都进入这里，不进入`FactStore`或`RuleRegistry`的活动版本。

### 5.4 `RuleRegistry`

`RuleRegistry`保存不可变的`RuleSpec`版本以及发布指针，包括状态规则、转换规则、计算公式、校准规则、恢复策略和对账规则。

AI可以提出`RuleProposal`，但不能：

- 原地修改`ACTIVE`规则；
- 自行把候选提升为`ACTIVE`；
- 绕过Schema和算子白名单；
- 用自然语言响应替代可执行规则；
- 让正在执行的计划悄悄切换规则版本。

### 5.5 `InventoryLedger`

`InventoryLedger`保存物品实例、堆叠、批次和库存变化事件。它是资源规划和消耗验证的权威来源，但不意味着每条视觉识别都必然正确。

库存纠错应通过新观测、对账和修正事件完成，不能让AI直接改成一个“看起来合理”的数量。AI可以解释差异或提出`InventoryCorrectionProposal`，程序仍需证据、确定性校验或用户确认后才能追加修正事件。

### 5.6 `RunStore`

`RunStore`保存计划和执行历史，例如：

```text
PlanRun
-> CapabilityRun
-> StepAttempt
-> RecoveryRun
-> ExecutionOutcome
```

原始失败尝试不能被AI总结覆盖。AI生成的复盘可以作为`AnalysisArtifact`关联到运行记录，但成功、失败、未知、取消和阻塞等结果由程序依据证据确定。

### 5.7 领域专用存储

以后的视频攻略、地点知识、物品说明和地图关系可以建立各自的领域存储，例如`GuideArtifactStore`、`GuidePlanStore`和`GuideExecutionStore`。其中`GuideExecutionStore`应作为攻略领域索引或投影视图引用通用`RunStore`中的运行ID，不能复制出第二份执行结果真相。它们仍服从相同治理规则：

- 原始来源和结构记录由程序管理；
- AI只读取查询结果；
- AI解析结果先作为候选；
- 正式更新由领域服务执行；
- 更换AI或清空聊天不影响已有数据。

## 6. AI智能体记忆

### 6.1 `AgentWorkingMemory`

`AgentWorkingMemory`是一次任务中的短期上下文，可以包含：

- 用户当前问题；
- 本轮读取的只读快照；
- 尚未提交的分析步骤；
- 工具调用结果摘要；
- 当前待回答的问题。

它可以在任务结束、上下文压缩或Agent重启后消失，不能承担任何必须长期保留的程序事实。

### 6.2 `AgentLongTermMemory`

`AgentLongTermMemory`只适合保存跨任务仍有帮助、且不会直接驱动危险执行的内容，例如：

- 用户已经确认的表达偏好；
- 用户长期关注的项目方向；
- 常用文档和问题索引；
- 对程序事实记录的稳定引用；
- 用户明确确认的术语解释。

它不应保存为权威内容的包括：

- 当前游戏界面和角色状态；
- 当前库存数量；
- 已验证规则的完整替代副本；
- 某次执行是否成功；
- 当前可执行计划；
- 未确认的AI推测；
- 密钥、令牌和不必要的敏感数据。

### 6.3 `AnalysisArtifact`

`AnalysisArtifact`是值得长期保存、但不属于程序事实的AI分析产物，例如：

- 数值差异解释；
- 攻略步骤解析；
- 规则候选说明；
- 失败复盘；
- 对复杂物品属性的按需分析。

它必须标明模型、提示或分析版本、输入事实引用、生成时间、结论状态和适用范围。新的分析创建新版本，不覆盖旧分析，也不能被执行器当成已验证事实直接使用。

## 7. AI长期记忆的最小记录

AI长期记忆至少应具有以下结构，而不是只有一段不断被重写的Markdown摘要：

```text
AgentMemoryEntry
- memory_id
- memory_type
- statement
- source_type
- source_refs
- created_at
- last_confirmed_at
- expires_at
- confirmation_status
- supersedes
- sensitivity
```

建议的`confirmation_status`包括：

```text
CANDIDATE / CONFIRMED / REJECTED / EXPIRED
```

由AI推测出的偏好只能先进入`CANDIDATE`。涉及执行、安全或资源消耗的内容即使被用户确认，也应转成程序中的正式配置或策略，而不是仅保存在AI记忆中。

## 8. 只读不是一句提示词

仅在系统提示词中写“不要修改数据库”不构成可靠边界。权限需要由程序和部署方式保证：

- AI工具只暴露查询接口和提案接口；
- 不向Agent提供数据库写入凭据；
- 查询返回不可变DTO或序列化快照；
- 文件系统工具不允许指向正式数据目录；
- 正式写服务不注册为AI可直接调用工具；
- 所有提案与命令都有独立审计记录；
- 高风险命令需要用户确认令牌。

即使AI受到提示注入、上下文污染或模型异常影响，也只能生成无效提案，不能越过写入边界。

## 9. `ReadModel`与版本快照

AI不应直接读取整个数据库，而应通过针对问题构造的`ReadModel`获得最小必要信息：

```text
ProgramStores
-> QueryService
-> ReadModel
-> AgentContext
```

一个只读快照至少可以带有：

```text
snapshot_id
revision
observed_at
valid_at
scope
source_refs
freshness
unknown_fields
```

这样AI可以知道“我看到的是哪个版本、何时的状态、缺了哪些字段”，而不是把一份无时间信息的摘要误当成当前事实。

不同问题使用不同视图。例如，材料规划只读取相关库存、目标、时间规则和预留；攻略对齐只读取相关地点候选、视觉锚点和可用能力。默认不把全部用户历史和全部游戏数据塞入上下文。

## 10. AI允许输出的三类结果

### 10.1 `Proposal`

结构化候选，例如规则候选、计划候选、记忆更新候选、库存纠错候选和解释标签候选。它必须声明依据、目标对象、基线版本、不确定项和期望动作。

### 10.2 `Question`

在证据不足、语义不明确或风险较高时向用户提问。问题可以帮助确认图标含义、步骤名称、计划目标或是否允许实验，但提问本身不改变程序状态。

### 10.3 `Explanation`

解释程序事实、差异和风险。解释可以保存为`AnalysisArtifact`，但不形成事实写入，也不代表用户已经授权执行。

三类结果统一进入`ProposalStore`或分析产物存储，不能通过自然语言中的“已经修正”“已确认”暗中改变系统状态。

## 11. 正式写入流程

推荐的完整路径为：

```text
AI读取revision=42的ReadModel
-> 生成Proposal(base_revision=42)
-> ProposalStore保存候选
-> SchemaValidator检查结构
-> PolicyEngine检查权限和风险
-> DeterministicValidator复算或复核
-> 必要时用户确认
-> CommandFactory生成正式Command
-> 领域服务检查当前revision
-> 追加事件或创建新版本
-> 返回CommitReceipt
-> AI重新查询新的ReadModel
```

正式`Command`至少应包含：

```text
command_id
command_type
target_id
base_revision
proposal_id
requested_by
approved_by
risk_level
evidence_refs
idempotency_key
created_at
```

如果当前版本已经变化，命令应拒绝并要求重新读取，而不是让旧提案覆盖新事实。

## 12. 写入权限矩阵

| 对象 | AI直接读取 | AI直接写入 | AI可否提案 | 正式写入方式 |
| --- | --- | --- | --- | --- |
| `EvidenceStore` | 经查询服务读取 | 否 | 可提议保留或标注 | 采集与证据服务追加 |
| `FactStore` | 是 | 否 | 可提出事实候选 | 事实服务依据证据创建版本 |
| `HypothesisStore` | 是 | 否 | 是 | 提案服务保存并标明来源 |
| `RuleRegistry` | 是 | 否 | 是 | 校验、影子验证和发布命令 |
| `InventoryLedger` | 是 | 否 | 可提出纠错或解释 | 库存服务追加事件 |
| `RunStore` | 是 | 否 | 可提交复盘产物 | 运行服务依据执行事实追加 |
| 活动公式 | 是 | 否 | 是 | 公式验证和版本发布命令 |
| 当前运行计划 | 是 | 否 | 可提出新计划 | 用户批准后重新编译 |
| `AgentWorkingMemory` | 是 | 可在任务内维护 | 不适用 | 会话生命周期管理 |
| `AgentLongTermMemory` | 是 | 不直接自由改写 | 是 | 记忆策略与确认服务创建版本 |
| `AnalysisArtifact` | 是 | 生成候选产物 | 是 | 分析产物服务保存并关联来源 |

## 13. 事实、假设与置信度不能混用

“程序保存”不等于“内容一定正确”。不同记录的地位必须明确：

```text
Evidence
-> Observation
-> FactCandidate
-> FactRecord
-> RuleHypothesis
-> ValidatedRuleVersion
```

AI建议通常停留在`FactCandidate`、`RuleHypothesis`或`AnalysisArtifact`。它的模型置信度不能直接替代OCR可靠性、因果支持度、上下文覆盖率和规则预测准确率。

候选推测还应带有：

- 来源和生成器版本；
- 适用游戏、版本和上下文；
- 支持证据和反例；
- 创建时间和TTL；
- 用户确认状态；
- 被新结论替代的关系。

过期内容可以继续作为历史，但不能参与当前执行决策。

## 14. 删除、修正与遗忘

三种操作需要分开：

- **修正事实**：追加新的事实版本或纠正事件，旧记录仍可追溯；
- **遗忘AI记忆**：按用户要求或保留策略删除非权威偏好与摘要；
- **清理原始数据**：由证据保留策略归档或删除大体积帧，并保存必要索引和审计记录。

AI不能自行删除证据、库存事件、规则版本或运行历史。涉及隐私删除时，由专门的数据治理命令按明确范围执行，不能借“记忆压缩”顺便覆盖或抹除程序记录。

## 15. 断线、换模型和记忆丢失时的行为

系统应满足：

- AI不可用时，已经编译的低风险确定性能力仍可按既有边界运行；
- 清空聊天后，程序事实、规则、库存和运行历史不变；
- 更换模型后，旧`AnalysisArtifact`仍能追溯其生成模型和输入；
- AI长期记忆损坏时，只损失便利性，不损失执行事实；
- 程序数据库恢复后，AI可以从新的`ReadModel`重新建立上下文；
- AI给出与当前revision冲突的提案时，写入服务拒绝执行。

这条隔离也是后续尝试多个模型、离线模型或不同用途Agent的前提。

## 16. 多Agent时的进一步边界

未来可能同时存在规划Agent、解释Agent、攻略解析Agent和失败复盘Agent。它们不能共享一个可任意覆盖的全局自然语言记忆。

推荐做法是：

- 每个任务有独立`AgentWorkingMemory`；
- 长期记忆按用户、项目、游戏Profile和用途划分作用域；
- 公共事实只通过程序查询服务共享；
- Agent之间传递事实引用和提案ID，不传递未经标记的“我记得”；
- 同一长期记忆条目的更新使用revision和冲突检测；
- 不同Agent不能相互授予程序写权限。

## 17. 与视频攻略方向的关系

以后从视频网站或本地攻略中提取路线时，字幕、关键帧、来源时间戳、步骤候选和对齐记录属于程序管理的数据，不应只留在某次AI对话中。

正确关系是：

```text
视频或文本攻略
-> 程序保存来源与结构化片段
-> AI只读分析
-> GuidePlanCandidate或AnalysisArtifact
-> 用户审核
-> 与已验证能力进行确定性编译
```

清空AI记忆后，既有攻略来源、候选计划和实际运行记录仍然存在；AI重新读取后可以继续分析。视频中的操作也不能因为AI“理解了”就直接变成活动规则或输入脚本。

## 18. 分阶段实现建议

### 阶段一：先完成程序事实底座

实现`Trace Core`中的帧、输入、窗口、时间线、证据和回放。此阶段不接入LLM，也不需要先建设完整AI记忆系统。

### 阶段二：建立结构事实与运行记录

增加最小`FactStore`和`RunStore`，让离线分析结果可以引用原始证据，验证事实版本和运行回放不会互相覆盖。

### 阶段三：建立假设与规则生命周期

实现`HypothesisStore`、`RuleRegistry`和手工规则解释器。先用程序算法生成候选，证明候选不能直接发布。

### 阶段四：实现只读查询层

为具体问题建立小型`ReadModel`，验证revision、时效、来源引用和未知字段能够完整传递，不直接把数据库暴露给调用者。

### 阶段五：接入AI只读分析

只允许AI读取固定证据包并输出`Explanation`或`Question`。先验证清空会话后程序数据完全不受影响。

### 阶段六：接入提案通道

实现`ProposalStore`、Schema校验、基线revision和审计记录。AI提出规则或计划候选，但暂不提供任何自动发布路径。

### 阶段七：接入受控命令

针对一个低风险案例实现“AI提案 -> 确定性复核 -> 用户确认 -> 新版本”的完整闭环，并注入旧revision、重复命令和错误提案测试。

### 阶段八：最后增加长期记忆

在程序事实和提案治理稳定后，再实现`AgentLongTermMemory`。它先只保存用户确认偏好和程序记录索引，不保存当前游戏事实。

## 19. 第一版验收标准

- AI没有正式数据库、账本和规则注册表的直接写权限；
- AI只能通过查询服务获取带revision和来源的最小视图；
- AI输出明确区分`Proposal`、`Question`和`Explanation`；
- AI提案不会直接成为事实或活动规则；
- 所有正式写入都经过程序Schema、权限和版本检查；
- 高风险或资源消耗相关变更需要用户明确确认；
- 当前状态不会从AI长期记忆中直接恢复；
- AI推测具有来源、TTL和确认状态；
- 清空会话、更换模型或关闭AI不会损坏程序事实；
- 旧分析和旧规则版本能够回溯到当时读取的证据与revision；
- AI不能删除原始证据、库存历史或失败运行记录；
- 无AI时仍能回放已有记录并执行已验证的确定性分析。

## 20. 当前结论

这部分不需要在项目最开始一次做完，但边界需要从第一天就确定：

```text
程序负责记住发生了什么
程序负责决定什么已经验证
AI负责帮助理解、提出候选和解释问题
用户与确定性规则负责授权正式改变
```

界迹的长期可靠性不应依赖AI“记得对不对”。AI可以随时替换，聊天可以随时清空，分析也可以被推翻；帧证据、结构事实、规则版本、库存账本和运行记录仍必须保持可追溯、可校验和可恢复。
